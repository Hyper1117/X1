第 1 题（Day 6）　你给线上服务加了一个健康探针，每 100 毫秒发一次请求并记录耗时。这个服务每 500 毫秒会卡顿一次，每次卡 200 毫秒。跑了一整天，探针报出来的 P99 只有 8 毫秒。探针没坏，请求也真的发出去了。为什么它测不到那 200 毫秒的卡顿？

看答案

因为探针的周期和故障的周期对上了拍子。探针每 100 毫秒发一次，故障每 500 毫秒来一次，500 是 100 的整数倍。于是探针的发送时刻和故障窗口之间的相对位置是固定的：要么每次都恰好错开，要么每次都恰好撞上。跑一整天也不会自己漂移过去。

这就是 Day 6 讲的锁相。两个周期只要成整数倍关系，采样点就永远落在被采样信号的同一个相位上，样本再多也补不上这个洞。

怎么破：把探针间隔改成一个跟服务周期不成整数倍的值（比如 97 毫秒），或者每次在间隔上加一点随机抖动。抖动不是为了好看，是为了让采样点在被测周期上慢慢扫过去。

今天会用到同一种警惕。当一个量的波动本身有结构时，采多少次不重要，采在哪里才重要。

第 2 题（Day 4）　一个 FastAPI 服务里有一段耗时 40 毫秒的同步函数堵住了事件循环。你把它改成 await loop.run_in_executor(None, f) 丢进线程池。什么情况下尾延迟会被修好，什么情况下几乎没变化？给出判断依据。

看答案

取决于那 40 毫秒里，这段代码有没有把 GIL 放开。

如果它是纯 Python 的计算（循环、字典操作、字符串拼接），它全程握着 GIL。丢进线程池之后，那个线程照样要拿 GIL 才能跑，事件循环所在的线程就还是抢不到 GIL。请求依然被堵住，只是堵在了另一个地方。尾延迟基本不变。

如果它是一次文件读写、一次网络调用，或者一次进入 C 扩展的计算（比如 numpy 的矩阵乘法、gzip 压缩、hashlib 求摘要），这些实现会在进入耗时段之前主动放开 GIL。这时线程池里那个线程干活的同时，事件循环拿得到 GIL，能继续接别的请求。尾延迟真的会好。

判断依据就一条：这段代码在干活的那段时间里，持有 GIL 吗？持有就搬不动，放开才搬得动。搬不动的那类只能换进程。

今天会看到一个结构相同、但发生在硬件层的现象：CPU 有时候不是在算，而是在等一个还没回来的东西。它在等的时候，利用率看上去照样是满的。

核心讲解

1. 你现在心里的内存模型，大概是错的

这一节回答：为什么"读一个变量"这件事，不能当成一个固定成本？

你写后端代码的时候，心里的内存模型大概是这样：变量在内存里，读它就是一次内存访问，很快，快到不用管。真正慢的是数据库、是网络、是磁盘。

这个模型让你在 Day 1 到 Day 6 一路都用得挺好。因为前六天看的都是毫秒级的事情：一次 HTTP 请求 40 毫秒，一次卡顿 200 毫秒。在毫秒的尺度上，内存访问确实可以当成免费的。

但从今天起你要处理的东西不在那个尺度上。一个 7B 模型的权重是 14 GB。生成一个 token，这 14 GB 要被完整读一遍。这时候"一次内存访问多快"就不是可以忽略的常数了，它直接决定了这台机器每秒能吐多少个字。

先建一个直觉。假设你在写一份材料：

  • 你手边摊开的那一页纸，伸手就够到。
  • 抽屉里的文件夹，要拉开抽屉找一下。
  • 楼下档案室的箱子，要下楼、登记、找柜号、搬上来。

三种"拿资料"在你的工作日志里都写作"查了一份资料"，但耗时差着好几个数量级。真实的机器就是这么组织的：CPU 旁边有几层容量越来越大、速度越来越慢的临时存放区，最外面才是内存条。

类比到此为止，接下来要把真实机制补上。而在讲机制之前，先把这个时间量出来。你自己量出来的数字，比任何一张网上抄来的"延迟数量级表"都有用。

2. 怎么把"一次访问要等多久"单独量出来

这一节回答：为什么不能写个循环读一遍数组然后除一下？

最自然的想法是：开一个大数组，循环读一遍，用总时间除以次数。这个数字是错的，而且会错得特别离谱。

原因是现代 CPU 不会老老实实一次读一个。它会同时把十几个读请求发出去，谁先回来先处理谁。所以你测到的不是"一次读要等多久"，而是"同时发出去一堆读、平均多久回来一个"。这两件事差十倍以上。

要测前者，必须让 CPU 没有别的活可干、只能干等着。办法是：让下一次读的地址，藏在上一次读回来的数据里。

把一块内存切成一个个格子，每个格子里写着下一个要去的格子编号。程序从 0 号格子开始，读出里面的数字，跳到那个格子，再读，再跳。CPU 不知道下一步去哪，只能等这一步的数据回来。于是每一步的耗时，就是一次访问的真实等待时间。

这个手法叫指针追逐（pointer chasing）。

下面这段 C 程序就是干这个的。为什么用 C 而不是 Python：这里要测的东西在 1 到 200 纳秒之间，而 Python 解释器执行一次 a[i] 本身就要 26 纳秒左右，会把前几级完全盖住。这一点在动手任务里会让你亲眼看到。

代码分三块：line_t 定义格子；build() 把格子串成一个环；main() 对一串工作集大小各跑一遍。

typedef struct { size_t next; char pad[56]; } line_t;   // 恰好 64 字节，正好占满一个 cache line

// mode 0 = 顺序：每步跳到下一个格子
// mode 1 = 随机：把所有格子打乱后串成一个环
static void build(line_t *a, size_t m, int mode){
    if(mode==0){ for(size_t i=0;i<m;i++) a[i].next=(i+1)%m; return; }
    size_t *p = malloc(m*sizeof(size_t));
    for(size_t i=0;i<m;i++) p[i]=i;
    for(size_t i=m-1;i>0;i--){ size_t j=xr()%(i+1); size_t t=p[i]; p[i]=p[j]; p[j]=t; }
    for(size_t i=0;i<m;i++) a[p[i]].next = p[(i+1)%m];   // 串成单一的环，保证每个格子都被走到
    free(p);
}

memset(a,0,bytes);                            // 先把每一页写一遍，把缺页开销挡在计时之外
for(size_t i=0;i<m;i++) idx=a[idx].next;      // 预热：该进缓存的先进去
double t0=now_s();
for(size_t i=0;i<iters;i++) idx=a[idx].next;  // 计时段：唯一的一次内存访问
double t1=now_s();

两个细节值得停一下。pad[56] 不是随手加的：它让每个格子恰好 64 字节，这样每跳一次就一定落到一块新的、之前没碰过的区域上，两种模式踩到的区域数量完全一样。memset 和预热循环放在计时之外，是因为这两步的开销属于别的问题（下一节就会讲它们），混进来会污染结果。

跑起来你应该看到一张两列的表：一列是顺序模式的耗时，一列是随机模式的。如果两列几乎一样，说明环没串对（多半退化成了几个小圈，实际工作集比你以为的小得多）；如果随机那一列的数字随工作集单调上升、顺序那一列基本不动，就对了。

随机那一列不是平滑上升的，是有台阶的：1.9 → 5.3 → 37 → 198。有两级跳得特别陡。从 1 MB 到 2 MB，从 6.99 涨到 37.25，翻了五倍多。从 128 MB 到 256 MB，从 98.86 涨到 198.25，翻了一倍。

$ for i in /sys/devices/system/cpu/cpu0/cache/index*; do
    echo "L$(cat $i/level) $(cat $i/type) $(cat $i/size) 行长=$(cat $i/coherency_line_size) 共享给=$(cat $i/shared_cpu_list)"
  done
L1 Data 48K        行长=64  共享给=0
L1 Instruction 32K 行长=64  共享给=0
L2 Unified 2048K   行长=64  共享给=0
L3 Unified 266240K 行长=64  共享给=0-1

这四行是这样读的：level 是第几级，数字越小离 CPU 越近；size 是容量；coherency_line_size 是最小搬运单位；shared_cpu_list 是哪几个逻辑核共用这一块。0 表示 0 号核自己独占，0-1 表示两个核共用。

对一下：

  • 48 KB：表里 16 KB 和 32 KB 是 1.9 纳秒，64 KB 就变成 5 纳秒了。台阶落在 32 KB 和 64 KB 之间。
  • 2048 KB：表里 1 MB 还是 6.99，2 MB 就变成 37.25。台阶正好落在 2048 KB 上。
  • 266240 KB（260 MB）：表里 128 MB 是 98.86，256 MB 变成 198.25，512 MB 到 216.22。这一级开始得比 260 MB 略早，然后在 512 MB 上稳住。

前两级对得非常准，第三级只对到"附近"。这不是巧合。机器自报的这三个容量，说的是它在 CPU 和内存条之间放了三层缓存（cache）：L1 最小最快、L2 中等、L3 最大最慢。你的数据落在哪一层，就是哪一层的速度。工作集一旦超过某一层的容量，那一层就装不下了，访问只能往下一层走，耗时立刻跳一级。

那个 coherency_line_size=64 也很重要。缓存不是按字节搬运的，最小单位是 64 字节，这个单位叫缓存行（cache line）。你只读了 1 个字节，硬件也会把包含它的那 64 字节整块搬进来。这就是为什么上面的格子要凑成 64 字节：只有这样才能保证每跳一次都真的换一行，而不是在同一行里原地打转。

关键结论

同一条读指令的耗时，在这台机器上跨越 100 倍：命中 L1 是 1.9 纳秒，跑到内存条是 198 纳秒。决定落在哪一档的，不是你读了多少数据，而是你正在反复访问的那块数据总共有多大。

4. 顺序那一列为什么一直是平的

这一节回答：同样是超出缓存 100 倍的工作集，为什么顺序跳完全不受影响？

回头看那张表的中间一列。工作集从 16 KB 涨到 512 MB，涨了三万倍，顺序跳的耗时从 1.89 纳秒只涨到 8.32 纳秒。在 512 MB 那一行，随机跳要 216 纳秒，顺序跳只要 8.32 纳秒——相差 26 倍。

两种模式踩到的缓存行数量一模一样，工作集一模一样，指令一模一样。唯一的差别是顺序。所以慢的原因不可能是"数据太多装不下"，只能是"下一次要读哪儿，事先猜不猜得到"。

硬件里有一个专门干这件事的部件。它盯着最近几次访问的地址，发现你在按固定间隔往前走，就自动把后面几块提前搬进缓存。等你的程序真的读到那里，数据已经在了，不用等。这个部件叫硬件预取器（hardware prefetcher）。

顺序跳的地址是 0、1、2、3……，规律明显，预取器每次都猜中，所以工作集再大也无所谓，数据总是提前到位。随机跳的地址毫无规律，预取器猜不中，每一步都得真的去等。

这里有一个竞争解释要排掉：顺序访问同时也更"省页"，会不会快是因为地址翻译更轻松，跟预取无关？第 7 节那组大页数据正好能回答。在 256 MB 的工作集上换成 2 MB 的大页之后，整块内存只占 128 个页，翻译的压力基本消失了。那一组里顺序跳仍然是 5.8 ~ 8.0 纳秒，随机跳仍然是 161 ~ 169 纳秒，差距还是二十多倍。把翻译的因素拿掉，顺序和随机的差距一点没变小。所以这个差距不是翻译造成的。

这条结论对你写服务的意义比看上去大得多：

  • 一个 Python 的 list 存了一百万个对象，遍历它的时候，list 本身是连续的，但那一百万个对象散落在堆的各个角落。你以为在做顺序扫描，硬件看到的是随机跳。
  • 同样一百万个数字，装在 numpy 数组里是一整块连续内存，遍历就是顺序访问。这是 numpy 比 list 快的原因之一，而且是很多人不会想到的那一条。
  • KV cache 用一个个固定大小的块存储、再用一张表把块串起来（这是 Day 10 的主题），换来的是内存不浪费，代价就是访问从顺序变成了跳跃。这个代价具体有多大，你今天已经有能力自己测了。

5. 接住 Day 3 留下的那个问题

这一节回答：为什么"CPU 利用率 100%"不等于"CPU 在干活"？

Day 3 讲 perf stat 的时候留了一句话没展开：IPC 低于 1 通常说明 CPU 在等内存。现在可以把它讲完了。

IPC 是 instructions per cycle，每个时钟周期平均完成几条指令。现代 x86 核心一个周期能同时推进四条左右，所以 IPC 越高越好。Brendan Gregg 给的判据很简单：IPC 大于 1，说明瓶颈在指令本身，该去优化代码；IPC 小于 1，说明系统卡在内存上，该去想办法减少内存访问、改善数据的局部性。他文章里举的例子是 0.78 的 IPC，在一个一周期能走四条的核心上，只用掉了 19.5% 的能力。

没干成的时候它在干什么？Gregg 那篇文章里的说法是：「stalled 的意思是处理器没有在推进指令，通常是因为它在等内存 I/O。」

把今天的两个数字放一起就知道等得有多久了。在这台机器上跑一条纯粹的整数加法依赖链，每一步都必须等上一步的结果。测出来是每秒 32.2 亿步，也就是 0.31 纳秒一步。而一次跑到内存条的随机读是 198 纳秒。

198 ÷ 0.31 ≈ 640。等一次内存的工夫，这个核本来可以往前推进 640 步串行计算。如果指令之间互相独立，还能更多。

而在这 198 纳秒里，操作系统眼中这个核是"忙"的。它没有让出 CPU，也没有去睡。Gregg 那篇文章的核心论点正是这个：「如今 CPU 已经比主存快得多，等内存这件事，主导了那个仍然被叫做 CPU 利用率的东西。」Day 4 你见过一次类似的错觉：事件循环被堵住的时候，CPU 也是满的。今天这个更深一层：这次连指令都没在执行，只是硬件在等。

6. 你申请到的内存，其实还不存在

这一节回答：进程说它要了 1 GB，机器上真的少了 1 GB 吗？

换一个角度。前面五节都在问"访问一块已经存在的内存要多久"。这一节问的是"这块内存是什么时候变出来的"。

操作系统不是按字节管理内存的，是按块。每一块的大小是固定的，x86 上默认 4096 字节，这个块叫内存页（page）。每个进程看到的是一套自己的虚拟地址，硬件靠一张页表把虚拟地址翻译成真正的物理地址。

关键在于：申请内存的时候，内核只是在页表上记了一笔"这段地址归你了"，并没有真的划出物理内存。物理内存要等到你第一次真正碰这块地址的时候才分配。

下面这段 Python 把这件事直接摆出来。它申请 1 GB，然后每隔 4096 字节写一个字节，也就是每一页碰一次。同时盯着两个数：进程占用的物理内存（VmRSS），和累计的缺页（page fault）次数。缺页就是"程序碰到了一个还没有物理内存撑着的页，硬件把控制权交给内核，内核现场分配一页再让程序继续"这个动作。

import mmap, time, resource

SIZE = 1 << 30   # 1 GB

def rss_kb():                                  # 进程当前真正占了多少物理内存
    with open("/proc/self/status") as f:
        for l in f:
            if l.startswith("VmRSS:"): return int(l.split()[1])

def minflt():                                  # 累计缺页次数（不需要读磁盘的那种）
    return resource.getrusage(resource.RUSAGE_SELF).ru_minflt

def sweep(m):
    t0 = time.perf_counter()
    for off in range(0, SIZE, 4096):
        m[off] = 1                             # 每一页碰一下，正好一次
    return time.perf_counter() - t0

m = mmap.mmap(-1, SIZE)                        # 申请 1 GB
print(f"刚 mmap 完: RSS={rss_kb()/1024:.0f} MB, 缺页={minflt()}")
for i in (1, 2, 3):
    print(f"第{i}遍: {sweep(m)*1e3:.1f} ms  RSS={rss_kb()/1024:.0f} MB  缺页={minflt()}")

Linux 提供了这个开关。mmap 的时候加上 MAP_POPULATE，内核会在 mmap 返回之前就把所有页都建好。

对照组把问题回答了：262 144 次缺页原封不动地搬到了 mmap 那一步，于是第一遍立刻从四百多毫秒掉到和第二遍同一个量级（36 ~ 65 毫秒对 34 ~ 41 毫秒）。慢的不是内存，是缺页。把它挪走，第一遍就不慢了。

关键结论

进程报出来的内存占用，是它碰过多少页，不是它申请了多少。一个刚起来的服务 RSS 很小，不代表它不会在第一批请求打进来的时候突然吃掉几个 G。那几个 G 是被第一次访问"变"出来的，而变的过程要花掉实打实的几百毫秒。

这条直接对上你四周后要做的事。一个推理服务启动时给 KV cache 预留了 40 GB，如果不预先碰一遍，这 40 GB 的缺页开销会分摊到最早那批请求头上。它们的首字延迟会莫名其妙地高，而你在代码里找不到任何一行慢的逻辑。Day 26 讲沙箱冷启动的时候，这件事会再出现一次。

7. 页多起来之后，翻译地址本身成了瓶颈

这一节回答：页表已经建好了，为什么访问还会慢？

页表解决了"虚拟地址怎么变成物理地址"。但每一次访问内存，都要先查一次页表。如果查页表本身也要跑一趟内存，那每次访问就变成两次，得不偿失。

所以 CPU 里有一小块专门缓存"最近翻译过的地址"的硬件，叫 TLB（translation lookaside buffer，地址翻译缓存）。一个 TLB 条目记住一页的翻译结果。

它的条目数是很有限的，而每个条目只管 4 KB。所以一个进程能被 TLB 完整覆盖的地址范围，就是"条目数 × 4 KB"这么大，远小于一个大模型权重的尺寸。超出这个范围之后，每次访问都要额外走一遍页表才能拿到物理地址。Linux 内核文档对此的说法是：「TLB 通常是相当稀缺的资源，工作集很大的应用会因为 TLB miss 而受到性能损失。」

对策是把页做大。x86 支持 2 MB 的页，同样一个 TLB 条目，覆盖范围一下子变成原来的 512 倍。内核文档给的理由是：「使用大页显著降低 TLB 压力，提高 TLB 命中率，从而提升整体系统性能。」这种页叫大页（huge page）。Linux 里这套机制叫 THP（transparent huge page，透明大页）："透明"的意思是你不用申请什么特殊内存，只要对一段普通内存打声招呼就行。

先看这台机器现在是什么状态：

$ cat /sys/kernel/mm/transparent_hugepage/enabled
always [madvise] never

方括号标的是当前值。三个选项的意思是：always 全局都用大页；never 全局都不用；madvise 是默认值，意思是只对主动开口要的那些内存区域用大页。怎么开口？调 madvise(地址, 长度, MADV_HUGEPAGE)。反过来 MADV_NOHUGEPAGE 是明确拒绝。

这两个开关正好构成一组干净的对照：同一段代码、同一块 256 MB、同一个随机环，只改页的大小。而且改没改成还能验证。/proc/self/smaps 里有一行 AnonHugePages，会告诉你这段区域里有多少字节真的被大页撑着。

四种组合各自单独起一个进程跑，互不干扰；每个进程内部重复 5 轮取最快的一轮，每种组合跑 3 个进程。下面每一格是这 3 个进程各自结果的范围：

先看第一行，它是这张表能不能信的前提：AnonHugePages 一个是 0，一个是 262144 kB，正好是全部 256 MB。说明开关真的生效了，不是白改。

然后重点看「顺序跳」和「随机跳」这两行的对比，因为这才是把原因钉死的地方。顺序那一行，两列的范围是重叠的（7.6~9.6 对 5.8~8.0），分不出快慢。随机那一行，两列的范围完全不沾边，大页稳定快 20 到 30 纳秒。把两种页大小的先后顺序对调再跑一遍，快慢关系不变。

为什么这个对比是关键：两行踩到的页数完全一样，都是 65 536 个 4 KB 页或 128 个 2 MB 页；换页大小的同时还换了物理内存的连续程度，而这个连续程度对两行也是一样的。如果大页的好处来自"页数变少"或者"物理上更连续"这类跟访问顺序无关的原因，顺序那一行也该跟着受益。它没有跟着受益。差别只出现在随机访问上，而随机访问是唯一让翻译失手的代价藏不住的模式。所以大页省下来的，是地址翻译的钱。

大页不是白给的。同样是写满 1 GB，两种页大小要处理的缺页次数是这样的：

写满 1 GB缺页次数每次缺页内核要干的事
4 KB 小页262 144找一页 4 KB 的空闲物理内存，清零，填页表
2 MB 大页512找连续的 2 MB 空闲物理内存，清零 2 MB，填页表

缺页次数正好差 512 倍（2 MB ÷ 4 KB = 512），这一点是确定的。但要清零的总字节数一模一样，都是 1 GB。而且大页要求物理上连续的 2 MB。内核文档提到，为了凑出大页，内核会进入直接回收（direct reclaim）；文档也直接点明了另一个代价：页错误里的清页和拷贝页变大，这是一个潜在的负面效应。

所以大页的正确用法不是全局打开，是对着那些又大又被随机访问的区域单独开。模型权重和 KV cache 正是这种区域。所以下次看到一条"建议开启 THP"的部署说明，你知道该问什么：这块内存有多大，访问它的模式是随机的还是顺序的。

8. 延迟之外的另一个数：一秒钟能搬多少字节

这一节回答：前面测的 198 纳秒，能不能直接换算成"这台机器读 14 GB 要多久"？

不能，而且差得很远。这是两个不同的量，必须分开。

延迟是"发出一次请求到数据回来要等多久"，前面七节测的都是它。带宽是"持续搬运时每秒能过多少字节"。它们不能互相换算，因为 CPU 可以同时让很多次访问在路上跑。这正是第 2 节里为了测延迟要费劲避开的东西。

用日常场景对一下：延迟是"一个包裹从下单到送到要三天"，带宽是"这条运输线一天能发一万个包裹"。三天是延迟，一万是带宽。它们没有换算关系，取决于路上能同时跑多少辆车。

Day 1 你已经见过一模一样的一对概念：一次请求的延迟，和整个服务每秒能处理多少请求。当时是在服务层面，现在是在硬件层面。同一件事换了个尺度。

测带宽的办法和测延迟正相反：要让访问尽可能互相独立、越多越好。做法就是顺序把一大块内存加起来，让编译器用多个累加器同时推进。

每个尺寸都反复扫到累计 2 GB 才停表，免得小尺寸那几行因为计时太短而不可信。

9. 现在轮到你猜了

先把场景说清楚。神经网络的一层，本质上是一个矩阵乘法：一个权重矩阵 W 乘上输入。如果一次只处理一个 token，输入就是一列；一次处理一批 32 个 token，输入就是 32 列。

关键的结构性事实是：不管这一批有几个 token，W 都只需要从头到尾读一遍。读进来的 W 可以给这一批里的每一列都用上。所以批量变大，读进来的字节数一个都没多，只有算术量变多了。

下面这个实验用一个 16384 × 16384 的 float32 权重矩阵，正好 1 GB。按上一节的表，这个尺寸装不进 L3，每次都得从内存条上捞。批量从 1 扫到 64，用 numpy 做矩阵乘法（底下调的是 OpenBLAS，限定单线程）。

# 跑之前先设 OPENBLAS_NUM_THREADS=1，把"用了几个核"这个变量固定住
import time, numpy as np

N = 16384
W = np.random.rand(N, N).astype(np.float32)          # 1 GB 的权重，装不进 L3
wb = W.nbytes
for B in (1, 2, 4, 8, 16, 32, 64):
    X = np.random.rand(N, B).astype(np.float32)      # 这一批 B 个 token 的输入
    W @ X                                            # 预热一次，别把第一次的开销算进去
    best = 1e9
    for _ in range(5):                               # 跑 5 次取最快的一次
        t0 = time.perf_counter(); W @ X; t1 = time.perf_counter()
        best = min(best, t1 - t0)
    print(f"{B}\t{best*1e3:8.2f} ms\t{best*1e3/B:8.2f} ms/列\t"
          f"{wb/best/1e9:6.2f} GB/s\t{2*N*N*B/best/1e9:6.2f} GFLOP/s")

取 5 次里最快的那一次，是为了把偶发的调度干扰挤出去；这里要问的是"最好情况下要多久"，不是"平均多久"。

那行 print 吐出五列：批量、总耗时、每列耗时（总耗时 ÷ 批量，也就是摊到每个 token 头上的时间）、读 W 的速率（按"W 只读一遍"算出来的）、以及算术速率。最后一列的单位 GFLOP/s 是"每秒十亿次浮点运算"，一次浮点加、一次浮点乘各算一次。这五列下一节会全部用上，到时候再逐个定义。

10.1 补上第二把尺子：这台机器每秒最多能做多少次运算

第 8 节量带宽的时候用了一个原则：要量哪条路，就设计一个只压这条路的程序。量带宽用的是顺序求和，因为它每秒能吃进的字节数最多、算得最少。现在要量另一条路，原则一样，方向相反：设计一个几乎不碰内存、只做运算的程序。

先把单位说清楚。浮点运算（FLOP，floating-point operation）就是一次浮点加法或一次浮点乘法，各算一次。GFLOP/s 是每秒十亿次浮点运算。上一节那段代码最后打印的那一列就是它，当时没解释，现在补上。

要把算术单元压满，程序得满足两个条件：

  • 数据必须一直待在寄存器里。只用几十个变量反复算（下面用 64 个，正好装得进 CPU 的向量寄存器），一个字节都不往内存跑。这样量到的就是纯粹的算术能力。
  • 算式之间不能互相等。这一点和第 2 节量延迟时的要求正好相反。那时候要"下一步必须等上一步"，才能量出等待时间；现在要"谁也不等谁"，才能把流水线填满。一条乘加指令从发出到出结果要等几个周期，如果所有算式串成一条链，CPU 大部分时间都在等自己。所以这里开 64 条互不相干的链。
/* peakflop.c —— 量这台机器每秒最多能做多少次浮点运算。
   不用矩阵乘法、不用 numpy、不碰任何库，只有一串谁也不等谁的乘加。*/
#include <stdio.h>
#include <time.h>

#define NACC 64            /* 64 条互不依赖的链，保证流水线不会因为等结果而空转 */
#define ITER 200000000L

static double now_s(void){
    struct timespec t; clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec + t.tv_nsec * 1e-9;
}

int main(void){
    float a[NACC], b = 1.0000001f, c = 0.0000001f;
    for (int k = 0; k < NACC; k++) a[k] = 1.0f + 0.001f * k;

    double t0 = now_s();
    for (long i = 0; i < ITER; i++)
        for (int k = 0; k < NACC; k++)
            a[k] = a[k] * b + c;      /* 一次乘 + 一次加 = 2 次浮点运算 */
    double t1 = now_s();

    float sink = 0;                   /* 把结果用掉，否则编译器会把整个循环删干净 */
    for (int k = 0; k < NACC; k++) sink += a[k];
    printf("%.1f GFLOP/s   (校验和 %.3f)\n",
           2.0 * NACC * ITER / (t1 - t0) / 1e9, sink);
    return 0;
}

那个 sink 不是装饰。-O3 会发现 a[] 的结果没人用，然后把整个循环删掉，你会量到一个好几万 GFLOP/s 的假数字。凡是量算力的微基准，第一件要检查的事就是循环还在不在。校验和打印出来是个合理的数，就说明它还在。

$ gcc -O3 -march=native -funroll-loops -o peakflop peakflop.c
$ ./peakflop
103.0 GFLOP/s   (校验和 66.049)

$ perf stat -e cycles ./peakflop        # 顺便数一下用了多少个时钟周期
103.0 GFLOP/s   (校验和 66.049)
       800,412,553      cycles

这个数字可以从两个方向验一遍，两边都对上才敢用。

第一验：每周期做了几次运算。总运算量是 2 × 64 × 2 亿 = 256 亿次，用掉 8.00 亿个周期，每周期 32.0 次。这个 32 是可以从指令集推出来的：这台机器支持 AVX2，一条 FMA（乘加）指令一次处理 8 个 float，每个 float 做一次乘一次加，就是 16 次运算；CPU 每个周期能发两条 FMA，8 × 2 × 2 = 32。实测 32.0，纸面 32，严丝合缝。

第二验：和第 5 节的时钟对一下。103.0 GFLOP/s ÷ 32 次每周期 = 3.22 GHz。第 5 节量整数依赖链时得到每秒 32.2 亿步，一步一个周期，也是 3.22 GHz。两个完全不同的程序量出同一个时钟。

所以这台机器的第二个能力数字是：单线程算力天花板 103.0 GFLOP/s。它和第 8 节那个 13.2 GB/s 一样，是独立量出来的，跟接下来要分析的矩阵乘法没有任何关系 —— 这一点很重要，否则后面就成了拿结论证明结论。

顺带记一条排查经验

如果你的机器支持 AVX-512，纸面上每周期能到 64 次，但很多型号跑 512 位指令时会降频，实测未必翻倍。纸面推算只用来验证实测的量级对不对，永远不要拿纸面数字代进后面的式子。要用就用你自己量出来的那个。

10.2 数一遍：这个矩阵乘法要搬多少字节、要做多少次运算

两把尺子有了。现在轮到负载：这个矩阵乘法往两条路上各压了多少东西？这一步不需要跑任何程序，数出来就行。

先把矩阵乘法写开。权重 W 是 N 行 N 列，输入 X 是 N 行 B 列（B 就是批量，一次处理几个 token），输出 Y 也是 N 行 B 列。输出的每一格是这么来的：

Yij = Wi1·X1j + Wi2·X2j + … + WiN·XNj

也就是"W 的第 i 行"和"X 的第 j 列"对应位置相乘再全部加起来。拿 N=3、B=2 看一眼：

现在把两件事分别数清楚。

要做多少次运算。输出一共 N×B 格。每一格是 N 次乘法加上 N−1 次加法，共 2N−1 次运算，惯例上直接记作 2N（差的那一次在 N 大的时候可以忽略，而且硬件上乘加是一条指令）。所以：

总运算次数 = 2N × N × B = 2N²B

3×3 那个例子代进去：2×9×2 = 36 次。手数一遍也是 36（6 格 × 每格 6 次）。

要搬多少字节。W 有 N² 个数。这里用的是 float32，每个数占 4 字节（float64 占 8 字节，推理里常用的 float16 占 2 字节，这个数后面还会再用到）。所以 W 一共 4N² 字节。而不管 B 是几，W 都只需要从头读一遍——这就是上一节那个结构性事实，在图上就是"每个格子被读 1 次、被用了 B 次"。X 和 Y 各只有 N×B 个数，B 很小的时候比 N² 小好几个数量级，忽略掉。所以：

总字节数 = 4N²（与 B 无关）

3×3 那个例子：4×9 = 36 字节。

四个数齐了。下一节把它们两两相除。

10.3 两次除法：负载的运算强度，机器的平衡点

10.1 和 10.2 分别给了机器的能力和负载的需求，现在把它们各自化成同一种单位，才能直接比较。这个共同单位就是"每一个字节配几次运算"。

第一次除法，负载这一侧。把 10.2 的两个结果相除：

2N²B ÷ 4N² = B / 2

N 消掉了。这个负载每搬进来一个字节能配上的运算次数，只由批量决定，跟矩阵多大完全无关。这个数叫运算强度（arithmetic intensity），是负载的属性。批量 1 时是 0.5，批量 64 时是 32。

第二次除法，机器这一侧。把 10.1 和第 8 节的两个结果相除：

103.0 GFLOP/s ÷ 13.2 GB/s ≈ 7.8 次运算每字节

单位是这么消掉的：每秒 1030 亿次运算 ÷ 每秒 132 亿字节 = 每字节 7.8 次运算。它的含义是：这台机器每从内存条上拉进来一个字节，你得能配上大约 7.8 次运算，两条路才刚好一样忙。配不满，算术单元干等着，多出来的算力白扔；配超了，内存条闲着，多出来的带宽白扔。这个数叫这台机器的机器平衡点（machine balance），是硬件的属性，跟你跑什么程序无关，量一次可以反复用。

两个数一比，拐点就出来了：

B / 2 = 7.8　→　B ≈ 16

批量小于 16，这个负载配不满这台机器的算力，时间由字节数说了算；批量大于 16，算力先用完，时间由运算次数说了算。

把这件事画出来，就是性能工程里用得最多的一张图。横轴是负载的运算强度，纵轴是它能达到的算术速率。斜的那段是带宽给的上限（每秒能拉进 13.2 GB，每个字节配 I 次运算，所以最多 13.2×I），平的那段是算力给的上限（103.0，再多的运算强度也没用）。两段相交处就是刚算出来的 B≈16。这张图叫屋顶线模型（roofline model）。

两根轴都是对数轴。斜段的斜率就是内存带宽，平段的高度就是算力天花板 —— 两个数都是独立量出来的，画这张图的时候还没跑过任何矩阵乘法。图上的圆点是 10.5 才会跑出来的实测，这里先放上去让你看清全貌；虚线那条屋顶是 10.6 的事。

10.4 把预测写下来

屋顶线不是一张示意图，它能出数。下面三条全部来自上一节那两个除法，一个实测值都没用到，所以它们是真正的预测，可以被实测推翻。

预测 · 跑实测之前先写下来

预测一：批量 1 时只用得上 6.4% 的算力。
运算强度 0.5，平衡点 7.8，两者之比 0.5 ÷ 7.8 = 6.4%。也就是说算术单元有 93.6% 的时间在干等字节到货。

预测二：每列耗时最多能改善 15.6 倍。
批量 1 时每列的时间是"把 W 读一遍"，即 4N² ÷ 带宽。批量大到吃满算力时，每列的时间是"做完这一列的运算"，即 2N² ÷ 算力。两者相除：
(4N² ÷ 带宽) ÷ (2N² ÷ 算力) = 2 × 算力 ÷ 带宽 N 又消掉了，只剩机器的两个数：2 × 103.0 ÷ 13.2 ≈ 15.6。注意这正好是平衡点的两倍，因为负载的运算强度是 B/2 而不是 B。

预测三：拐点在批量 16 附近。
之前每加一个 token 几乎不要钱，之后每加一个都要真金白银地多花时间。

10.6 那个 2 是什么：批量 ≥2 之后，W 被读了两遍

先看这个"2"能落在哪儿。屋顶线的四个输入里，带宽和算力是 10.1 和第 8 节独立量出来的，运算次数 2N²B 是 10.2 数出来的，都不太可能整体差一倍。剩下唯一可疑的是字节数 4N² —— 它假定 W 从内存条到算术单元只走一趟。

假设它实际走了两趟，会发生什么：运算强度减半（一个字节要被搬两次才顶一次用）→ 斜段的有效高度整体降一半（中间三行矮一半）→ 拐点右移一倍（16 变 31）。一个假设，两处异常同时消失。屋顶线图上那条虚线就是这么来的。

为什么会走两趟，是有具体机制的。这里要引入三个你上岗后天天会看到的缩写：BLAS（basic linear algebra subprograms，基础线性代数子程序库，numpy 底下调的 OpenBLAS 就是它的一个实现），GEMV（general matrix-vector multiply，矩阵乘向量），GEMM（general matrix-matrix multiply，矩阵乘矩阵）。批量为 1 时 X 只有一列，走的是 GEMV；批量 ≥2 时 X 是个矩阵，走的是 GEMM。这是两条完全不同的代码路径：

批量 16 往后开始往下掉（10.43、7.85、5.32），而且越掉越多。这也在意料之中：越靠近拐点，运算时间在总时间里占的比重越大，再拿"总时间"去除字节数，得到的当然不再是纯粹的带宽。屋顶线在拐点附近一向偏乐观，因为它假定搬运和运算完全重叠，真实硬件做不到。所以能干净还原带宽的只有批量 2、4、8 那三行 —— 恰好就是那三行。

再回头看拐点。加上这一遍之后，运算强度变成 B/4，拐点应该在 4 × 7.8 ≈ 31。如果不用硬件峰值 103.0 而用这个库在这个矩阵上实际跑到的 85.07，那就是 4 × 85.07 ÷ 13.2 ≈ 26。实测的过渡区在 20 到 30 之间，夹在这两个数中间。拐点本来就是一段而不是一个点，因为两条路不会完美重叠，而且实现达不到峰值。

把话说严谨："W 被读了两遍"目前是一个假设，不是已经证实的结论。它的分量在于它是先做出预测、预测再命中的 —— 一个"2"同时解释了拐点位置、中间三行的高度、和三个还原成带宽的数字，而这三件事我们并没有拿来拟合它。要真正钉死它，得直接去数内存流量，动手任务的加分题里给了三条互相独立的验法。

10.7 还剩一个竞争解释：会不会只是"库在大批量下效率高"

到这里所有证据都指向内存。但有一个解释同样说得通，而且跟内存毫无关系：也许批量大了之后，只是 BLAS 的内核写得更高效了。10.6 那张图里 GEMM 要打包，正好也支持这个说法 —— 打包这件事本身就是为了让内核跑得更快。

屋顶线对这件事有一个很硬的表态。预测二那条式子是：

每列耗时的改善倍数 = 2 × 算力 ÷ 批量 1 时的读取速率

里面只有机器的两个能力数，没有任何跟"库效率"有关的项。所以只要换一台"机器"，预测值就必须跟着变。而"换机器"不一定要换硬件：把权重换成装得进缓存的尺寸，那条路的带宽立刻从内存条的 12 变成缓存的 26（第 8 节量过：缓存里单线程约 25 GB/s，内存条上约 13 GB/s）。同一个库、同一段代码、同一串批量，唯一变的是 W 住在哪。

# 只换权重矩阵的尺寸，别的什么都不动
import time, numpy as np

def best_of(f, n=5):
    f()                                          # 预热
    return min((lambda t0=time.perf_counter(): (f(), time.perf_counter()-t0)[1])()
               for _ in range(n))

一，为什么两个小矩阵的改善"只有"7.5 倍？不是因为缓存里"没有可摊的东西"。缓存带宽同样有限，26 GB/s 对 103.0 GFLOP/s，平衡点是 4.0 次运算每字节，拐点提前到批量 8 附近（同样算上打包那一遍就是 16 附近）。屋顶线还在，只是屋顶抬高了、拐点左移了。规律一点没变，代进去的两个数变了。

二，10.5 里那个 0.83 是什么？看"批量 64 实际算力"这一列：小矩阵能跑到 99.8 和 99.1，是硬件峰值 103.0 的 97%；而 1 GB 那个只有 85.1，是 83%。少掉的那 17% 就是"即使批量 64，这个矩阵乘法仍然要从内存条上流 1 GB"的代价 —— 它始终没有真正变成纯计算。这也是为什么它的实测点在屋顶线图上永远差一点够不到平段。

10.8 反方向再验一次：运算量不变，只让字节数翻倍

到这里所有实验都是同一个方向：固定字节数、增加运算量，看到时间几乎不动。一个结论如果只在一个方向上被验证过，很容易是巧合。所以反过来做一次：固定运算量、增加字节数。

做法是把权重从 float32 换成 float64，矩阵形状和批量都不动。回到 10.2 数的那两个数：运算次数 2N²B 里没有"每个数占几字节"这一项，所以乘加次数一次都没多；而字节数 4N² 里的 4 要换成 8，字节数翻倍。

先出预测。float64 的运算强度变成 2N²B ÷ 8N² = B/4，批量 1 就是 0.25，比原来又低一半，更深地陷在斜段里。斜段上时间 = 字节数 ÷ 带宽，所以：耗时翻倍，读取速率不变。

# 形状不动、批量不动，只换数据类型
import time, numpy as np
N = 16384
for dt in (np.float32, np.float64):
    W = np.random.rand(N, N).astype(dt)
    X = np.random.rand(N, 1).astype(dt)
    W @ X
    best = min((lambda t0=time.perf_counter(): (W @ X, time.perf_counter()-t0)[1])()
               for _ in range(5))
    print(f"{np.dtype(dt).name:>8}   权重 {W.nbytes/2**30:.2f} GB   "
          f"乘加次数 {2*N*N} (不变)   耗时 {best*1e3:6.1f} ms   "
          f"读取速率 {W.nbytes/best/1e9:5.2f} GB/s")

这里也有一个竞争解释要排掉：float64 的算术吞吐通常只有 float32 的一半（AVX2 一条 FMA 只能装 4 个 double 而不是 8 个 float），会不会时间变长是因为算得慢了？式子可以直接回答，不用再做实验。算力天花板砍半，平衡点从 7.8 变成 3.9；而运算强度也同时砍半，从 0.5 变成 0.25。两边同步减半，这个点在屋顶线上的相对位置一动没动，还是在斜段上离拐点 15.6 倍远的地方。斜段上的时间只由字节数和带宽决定，天花板降到哪儿都不参与。所以砍掉一半算力，对耗时不会有任何影响。

两个方向合起来：加运算量，时间几乎不动；加字节数，时间跟着翻倍。这条路上收费的是字节，不是运算。

关键结论

原因是这台机器的两条路收费不对等：算力 103.0 GFLOP/s，带宽 13.2 GB/s，比值 7.8 —— 每拉进一个字节，得配上 7.8 次运算才算不浪费。而批量 B 的 float32 矩阵乘法只能配上 B/2 次。批量 1 时配的是 0.5，差了 15.6 倍，于是算术单元 94% 的时间在等字节到货，耗时完全由"把权重读一遍要多久"决定。

批量处理做的事，是把运算强度从 B/2 一路抬到平衡点。它一次乘法都没省，也一个字节都没少读；它让同一次昂贵的读，服务于更多的 token。抬到平衡点就到头了，再抬就是算力先用完 —— 那才是拐点的来历。

10.9 拿这台机器算一笔账

前面八小节都在一层矩阵上打转。现在把它推到整个模型上，回答标题里那个"为什么内存是大模型服务的第一约束"。

一个模型是几十层这样的矩阵串起来的，算一次前向要走完所有层，每层的权重都要读一遍。所以"生成一个 token"底下就是"把全部权重完整读一遍"。

把这件事代进 10.2 那套数法。设模型有 P 个参数，权重每个占 s 字节（float32 是 4，推理里常用的 float16 是 2，int8 是 1），批量为 B：

  • 一次前向要读的字节：s·P
  • 一次前向要做的运算：约 2·P·B（每个参数一次乘一次加，乘以批量 —— 和 10.2 完全一样的数法）

运算强度 = 2PB ÷ sP = 2B / s

P 消掉了。推理时的运算强度只由批量和权重精度决定，跟模型多大、多少层、什么结构统统无关。代进去看：float32 是 B/2（正好和 10.3 那个矩阵乘法一致），float16 是 B，int8 是 2B。

这条式子一次说清了两件本来看着不相干的事：

  • 批量该开多大？开到运算强度够着平衡点为止。float16 权重时运算强度就是 B，所以批量直接等于平衡点。这台机器上是 8。
  • 量化在省什么？把权重从 16 位压到 8 位，乘法一次都没少 —— s 从 2 变成 1，运算强度直接翻倍，相当于免费把你在横轴上的位置往右推一格。只要你还在斜段上，字节减半就是时间减半。

顺便也解释了为什么 CPU 和 GPU 上"合适的批量"差了两个数量级：

硬件算力带宽平衡点float16 权重时该开的批量

右边那一栏就是 Day 8 之后所有 batching 手段的根本动机：GPU 的算力涨得比带宽快得多，平衡点被推到了几百，所以单请求推理在 GPU 上会浪费掉 99% 以上的算力。这不是框架写得不好，是硬件的两条路本来就不对等。这张表只是量级示意 —— H100 那一行是标称值，真机上要按 10.1 和第 8 节那两套办法自己量。

最后回到时间。在斜段上（也就是批量还没到平衡点时），有一个只需要两个输入的式子：

每个 token 的时间下限 = 权重字节数 ÷ 内存带宽

代数之前先说清楚用哪个带宽。第 8 节量到两个：单线程约 13 GB/s，两线程约 27.6 GB/s。前面所有矩阵乘法实验为了把"用了几个核"这个变量固定住，全程锁了单线程，所以用的是 13。但真实的推理服务不会只用一个核，所以下面这笔账用两线程的 27.6。换带宽口径的时候必须说出来，这是自己做估算时最容易出错、也最容易被别人抓住的地方。

一个 30 亿参数的模型，float16 权重就是 6 GB。6 ÷ 27.6 ≈ 0.22 秒一个 token，每秒 4.6 个字。换成 70 亿参数是 14 GB，14 ÷ 27.6 ≈ 0.51 秒一个 token，每秒不到 2 个字。这台机器只有 8 GB 内存，装不下 14 GB 的权重，所以后一个数是把式子外推到一台带宽相同、内存更大的机器上。

注意式子里没有"框架"，也没有"代码写得好不好"。核数确实影响结果，但它只通过带宽这一项起作用：加核能压出更多带宽，那就把更大的带宽代进去。所以真正要量的一直是同一个东西 —— 你在自己那台机器上实际能压出多少带宽。

这两把尺子就是你四周后要天天用的：权重字节 ÷ 带宽给出单请求的时间下限，算力 ÷ 带宽给出批量该开到多大。两个都是几十行代码就能量出来的。任何一个跑不到这个量级的实现都有优化空间；任何一个声称远远超过它的说法，要么用了批量，要么用了缓存复用，要么在骗你。

而 Day 8 到 Day 14 要讲的东西，几乎全都是在跟这条屋顶线较劲：批量处理把运算强度从 B/2 抬到平衡点；KV cache 把已经算过的中间结果存下来别再算；prefix caching 让不同请求共用同一段已经算好的东西。它们的共同点是：都不是在让计算变快，都是在提高运算强度 —— 让每一个搬进来的字节，干更多的活。

任务 A（必做，约 60 分钟）：把你自己机器的阶梯量出来

这一节的目标：你手上多一张只属于你这台机器的延迟表，以后所有关于内存的判断都从它出发。

下面这段是纯标准库的 Python 版指针追逐，不需要装任何东西。它做的事和第 2 节那段 C 一样：把内存切成一个个 64 字节的格子，串成一个环，然后沿着环跳。

文件分三块：make_cycle() 造环，chase() 计时，最后的循环把工作集从 16 KB 扫到 256 MB。

"""用纯标准库量出内存延迟的阶梯。
每一步读出来的值就是下一步要读的下标，CPU 没法提前发起下一次读。"""
import array, random, time

STEP = 8          # 相邻两个下标隔 8 个元素 = 64 字节 = 一个 cache line
ELEM = 8          # array('q') 每个元素 8 字节

def make_cycle(n_lines, shuffled):
    order = list(range(n_lines))
    if shuffled:
        random.Random(42).shuffle(order)       # 固定种子，保证两次跑的是同一个环
    a = array.array('q', [0]) * (n_lines * STEP)
    for k in range(n_lines):
        a[order[k] * STEP] = order[(k + 1) % n_lines] * STEP
    return a

def chase(a, iters):
    i = 0
    t0 = time.perf_counter()
    for _ in range(iters):
        i = a[i]                               # 全程唯一的一次内存访问
    t1 = time.perf_counter()
    return (t1 - t0) / iters * 1e9, i

print("工作集KB\t顺序ns\t随机ns")
for kb in (16, 32, 64, 256, 1024, 2048, 8192, 32768, 131072, 262144):
    n_lines = kb * 1024 // (STEP * ELEM)
    row = []
    for shuffled in (False, True):
        a = make_cycle(n_lines, shuffled)
        chase(a, min(n_lines, 200000))         # 预热
        best = min(chase(a, 400000)[0] for _ in range(3))   # 三次取最快
        row.append(best)
    print(f"{kb}\t{row[0]:.1f}\t{row[1]:.1f}")

验收标准

  1. 顺序那一列从头到尾在同一个数量级内浮动，不随工作集增长。
  2. 随机那一列在某一行开始明显往上走，并且这一行的位置和你 /sys/devices/system/cpu/cpu0/cache/index2/size 里读到的 L2 容量对得上。上面这台机器 L2 是 2048 KB，表里正是 2048 那一行开始跳。
  3. 你能说出为什么前两级台阶（L1 和 L2 之间）在这张表里看不见。

常见坑

  • 两列数字几乎一样。多半是环没串成一个圈，退化成了若干小圈，实际工作集远小于标称值。把 chase() 改成走 n_lines 步并检查最后能不能回到 0，可以验证环的完整性。
  • 最后一行跑不动或者被系统杀掉。262144 KB 那一行要 256 MB 数组加上一个同样大小的中间 list，内存紧张的机器直接把最后一两行删掉即可。
  • 数字每次跑差很多。机器上有别的负载。关掉浏览器，或者把重复次数从 3 提到 5。

第 3 条验收标准就是这个任务真正的考点：C 版本量出来 L1 是 1.9 纳秒、L2 是 5.3 纳秒，而这张表里 16 KB 到 1024 KB 全是 26 纳秒左右。因为 Python 解释器执行一次 a[i] 本身就要 26 纳秒上下，这个固定开销比前两级台阶的高度还大，直接把它们盖住了。这不是 Python 的错，是任何测量工具都有的问题：当你的尺子的刻度比要量的东西还粗时，量出来的是尺子。

任务 B（约 45 分钟）：给你自己的服务做一次内存画像

这一节的目标：把今天的三个观察点接到你 Day 5、Day 6 一直在改的那个服务上。

下面这个脚本对一个正在运行的进程做三件事：读它真正占了多少物理内存、读它有多少内存是被大页撑着的、看它还在不在持续缺页。

"""给一个正在跑的进程做一次内存画像。用法: python3 memprofile.py <pid>"""
import sys, time

pid = sys.argv[1]

def read_kv(path, keys):
    out = {}
    with open(path) as f:
        for line in f:
            k = line.split(":")[0]
            if k in keys: out[k] = int(line.split()[1])
    return out

# smaps_rollup 是内核把这个进程所有内存区域汇总好的一份，比自己遍历 smaps 快得多
r = read_kv(f"/proc/{pid}/smaps_rollup", {"Rss", "Anonymous", "AnonHugePages"})
print(f"物理内存占用 RSS      : {r.get('Rss',0)/1024:9.1f} MB")
print(f"其中匿名内存(堆/栈)    : {r.get('Anonymous',0)/1024:9.1f} MB")
print(f"其中由大页撑着的部分   : {r.get('AnonHugePages',0)/1024:9.1f} MB"
      f"   ({100*r.get('AnonHugePages',0)/max(r.get('Anonymous',1),1):.1f}% 的匿名内存)")

def flt():
    with open(f"/proc/{pid}/stat") as f: p = f.read().split()
    return int(p[9]), int(p[11])          # 第 10 个字段是 minflt，第 12 个是 majflt

a = flt(); time.sleep(5); b = flt()       # 隔 5 秒采两次，看缺页还在不在长
print(f"5 秒内新增缺页(不读盘) : {b[0]-a[0]:9d} 次")
print(f"5 秒内新增缺页(要读盘) : {b[1]-a[1]:9d} 次")

跑起来应该看到四五行数字。如果报 FileNotFoundError，说明 pid 写错了或者进程已经退出；如果 smaps_rollup 不存在（较老的内核上没有这个文件），改成读 /proc/<pid>/status 里的 VmRSS。

拿它做三次测量，回答三个问题：

  1. 服务刚启动、还没打过流量时跑一次；压测跑满 30 秒之后再跑一次。RSS 涨了多少？涨的那部分是在什么时候被"变"出来的？
  2. 第二次测量时，「5 秒内新增缺页」还在不在明显增长？如果还在长，说明你的服务在稳态下仍然不断在碰新的页。这通常意味着它在反复分配和释放大块内存。
  3. 「由大页撑着的部分」是多少？绝大多数 Python 服务这一项是 0，因为没人替它调 madvise。记下这个数，Day 14 讲 KV cache 卸载的时候会用到。

验收标准：你能用一句话说清楚这个服务的内存是"启动时一次性吃进去的"还是"随请求慢慢长出来的"，并且有数字支撑。

加分题（做不完不影响明天）

  1. 量出这台机器的 TLB 覆盖范围。第 7 节只在 256 MB 一个尺寸上比了小页和大页。把工作集从 4 MB 扫到 512 MB，每个尺寸都跑一遍小页和大页的随机访问，画出"大页比小页快多少"这条曲线。这个差值从接近 0 变成明显大于 0 的那个拐点，就是这台机器的 TLB 用 4 KB 页覆盖不住的边界。
  2. 解释一个数字对不上的地方。C 版本在 256 MB 随机访问上量到 198 纳秒，Python 版本在同样尺寸上只量到 112 纳秒，而 Python 的解释器开销本身还有 26 纳秒。112 明显小于 26 + 198。这说明解释器那 26 纳秒的活，和那次还没回来的内存读，并不是排队做的。设计一个实验证实或推翻这个猜测。提示：往循环里加一点跟内存无关的计算，看总耗时涨不涨。
  3. 把批量拐点扫出来。第 10.5 节只给了 7 个批量点。把批量从 1 扫到 256，画出"每列耗时"和"总耗时"两条曲线。总耗时那条线的拐点在哪，和 10.6 给的 26~31 对得上吗？把权重换成 64 MB 再画一次：按 10.7 那条式子，拐点应该左移到 8 到 16 之间，实测移到哪了？
  4. 把"W 被读了两遍"这个假设钉死或者推翻。第 10.6 节给的解释是：批量 ≥2 时 BLAS 走 GEMM 路径，会先把 W 拷进打包缓冲区再乘，于是 1 GB 的 W 实际被过了两遍。它同时解释了三件事（拐点在 26~31 而不是 16、中间三行整齐地矮一半、三个读取速率乘 2 之后正好还原成带宽），但还没有被直接测过。三条互相独立的验法：(a) 直接数内存流量——用 perf stat -e LLC-load-misses 分别抓批量 1 和批量 2 那两次调用，缺失数乘以 64 字节就是从内存条上真正搬了多少，看是不是 1 GB 对 2 GB；(b) 把批量 2 的 W @ X 换成两次独立的单列 W @ x，如果两次单列反而更快，说明合起来算那一步确实付了额外的搬运钱；(c) 用 py-spy --native 或 ltrace 抓这两次调用，看它们是不是落在库里不同的函数上（sgemv 对 sgemm）。三条做完，你要么把它钉死，要么找到真正的原因。两种结果都值得写下来——这是你第一次自己审判一个性能假设。
  5. 量出你自己机器的算力天花板和平衡点。把 10.1 那段 peakflop.c 拿去跑，先确认校验和打印出来了（循环没被编译器删掉），再用 perf stat -e cycles 算出每周期多少次运算，看能不能和你机器的指令集（lscpu | grep -o 'avx[^ ]*' | sort -u）对上。然后除以你在任务 A 里量到的带宽，得到你自己那台机器的平衡点。把这个数写在笔记的第一页，后面三周会反复用到它。

上岗关联

场景一：有人报"服务变慢了"，但 CPU、内存、网络看上去都正常。

你在监控上看到 CPU 100%，内存没满，网络没满，磁盘没动。按 Day 3 的方法抓火焰图，最宽的平台是一个遍历大字典的函数。按老办法你会去优化那个函数的逻辑。今天你多了一个动作：先看这个字典有多大。如果它已经远超 L3，那么这个函数慢不是因为它的逻辑，是因为它每次访问都在等内存。改逻辑没用，要改的是数据布局，比如把散落的对象换成连续的数组，或者把热数据和冷数据分开存。

场景二：给一台新机器定容量，要回答"这台机器能扛多少路推理"。

不要从"它有多少核"开始，从两个数开始。用第 8 节那段顺序求和量出带宽，用 10.1 那段 peakflop.c 量出算力天花板。然后：权重字节数 ÷ 带宽给出批量 1 时每个 token 的时间下限；算力 ÷ 带宽给出这台机器的平衡点，也就是批量至少要开到多大才不浪费算力。两个数一起，就能算出这台机器在最划算的批量下平均吐一个 token 要多久。拿它和你要承诺的字间等待上限一比，就知道这台机器撑不撑得起你要的并发。这个指标明天会正式命名。整个估算不需要真的把模型部署上去，两段几十行的代码就能跑完，足够用来判断"这个方案根本不可能"还是"值得实际测一测"。扫批量曲线是用来验这个估算的，不是用来代替它的——你应该先知道拐点该在哪，再去扫。

场景三：一个服务重启后前几十秒明显慢，稳态之后就好了。

这是第 6 节那张表的现实版本。服务启动时申请了大块内存，但那些页要等第一批请求碰到它们才真的被分配。几十万次缺页的开销全压在最早那批请求上。排查手段是用任务 B 的脚本在启动后立刻采一次、稳态再采一次，看 RSS 和缺页计数的走向。解法是启动时主动把这块内存碰一遍（预热），或者在申请时就要求内核填好。注意这个解法只是把成本从"第一批请求"挪到了"启动过程"，总时间没变。但对用户来说差别很大。

同事和面试官常问的

  • 「你怎么判断一个服务是 CPU-bound 还是 memory-bound？」——期待你说出 IPC 这个指标，以及"两者在 top 里看起来一模一样"这件事。
  • 「为什么推理要做 batching？」——如果只答"提高吞吐"，那是复读文档。答"因为权重读一遍的成本是固定的，batch 让这次读服务更多 token"，就说明你知道底下发生了什么。追问"那 batch 是不是越大越好"，答拐点，并且说出拐点等于这台硬件的算力除以带宽——这是能算的，不是只能扫的。
  • 「THP 该不该开？」——期待你反问"哪块内存、什么访问模式"。全局 always 和对特定区域 madvise 是两个完全不同的决定。
  • 「进程 RSS 2 GB，是不是真的用了 2 GB？」——是，RSS 是碰过的页。但反过来不成立：申请了 10 GB 而 RSS 只有 2 GB 是完全正常的。

自检问题

1. 你的服务用一个一百万条目的 Python dict 做本地缓存，命中率 95%。同事说命中率这么高，缓存肯定没问题。从今天学的东西看，还有什么可能让这个缓存本身变成瓶颈？

命中率只说明"要找的东西在不在这个 dict 里"，不说明"找到它要多久"。

一百万条目的 dict，光是哈希表本身就有几十 MB，加上一百万个键对象和值对象散落在堆上，实际工作集轻松超过 L2。而哈希查找的访问模式天生是随机的。哈希的作用本来就是把键打散。这意味着预取器完全帮不上忙。

所以每一次"命中"，底下可能是两三次随机访问：一次读哈希桶，一次读键对象比较，一次读值对象。几十 MB 的工作集对应今天那张表里 8 MB 到 64 MB 那一档，每次约 60 纳秒，三次就是 180 纳秒。如果这个缓存长到几百 MB，同样三次就变成 600 纳秒。差别不在命中率上，在工作集掉进了哪一档。而这段时间 CPU 一直显示为满载。

怎么验证：把 dict 的条目数砍到十分之一（让工作集掉进 L3），命中率会下降，但如果整体延迟反而改善了，就说明瓶颈在访问成本而不在命中率。

2. 一个进程稳态 RSS 是 2 GB。你把它 kill 掉重启，第一批请求的 P99 比稳态高 10 倍。给出两个可能的原因，并说明怎么分别验证。

原因一：缺页。那 2 GB 在稳态下是碰过的页，重启后全没了，要重新一页一页地缺出来。2 GB 对应约 52 万次缺页。

原因二：缓存是空的。这里的"缓存"指的是进程自己的业务缓存（连接池、模板、编译好的正则、预热过的模型），不是硬件缓存。第一批请求要走完整的冷路径。

怎么分开：用任务 B 的脚本在重启后立刻采样，看「5 秒内新增缺页」这个数。如果它是几十万量级并且随着请求打进来持续增长，原因一成立。如果缺页很快归零、但延迟还是高，那就是原因二。

两个原因也可能同时存在。想彻底确认原因一的贡献有多大，就在服务启动时主动把那块内存整个碰一遍，再看第一批请求的 P99 掉了多少。这就是第 6 节那个 MAP_POPULATE 对照组的线上版本。

3. 运维建议把整台机器的 THP 设成 always 来提速。什么情况下这有效，什么情况下会帮倒忙？

有效的情况：机器上跑的是少数几个占用大块内存、并且对这块内存做随机访问的进程。推理服务的模型权重和 KV cache 正是这种。第 7 节的数据显示，256 MB 工作集上随机访问快了 20 到 30 纳秒，大约 13%。

帮倒忙的情况有两类。

第一类是凑大页本身的开销。内核文档写明，为了拿到大页，内核会进入直接回收；文档也点出页错误里的清页和拷贝页会变大，这是一个潜在的负面效应。always 模式意味着全机器所有内存都要付这份钱，而不只是那几块真正需要的。

第二类是内存浪费。内核文档直接提到，全局开启大页之后，应用可能占用更多内存资源；如果一大片地址被映射了却只被碰了一点点，这些内存就是白占的。

所以稳妥的做法是保持 madvise 模式，让真正需要的那几块内存自己开口要。内核文档里 madvise 也正是默认值。

4. 同一个 batch=1 的矩阵乘法，把权重从 float32 换成 float16（假设精度可接受）。乘法次数一次都没变。耗时会怎么变？

时间会大致跟着字节数走，也就是大约减半。前提是权重装不进缓存。

推理链是这样的：batch=1 时，耗时由"把权重读一遍要多久"决定。读一遍的时间 = 字节数 ÷ 带宽。float16 的字节数是 float32 的一半，带宽不变，所以时间减半。乘法次数完全不参与这个式子。

用屋顶线说是同一件事：运算强度 = 2B ÷ 每个权重占几字节。float32 时 batch=1 是 0.5，换成 float16 是 1，而这台机器的平衡点是 7.8。1 仍然远小于 7.8，所以这个点依旧稳稳落在斜段上，时间仍然只由字节数和带宽决定。判断“减半成不成立”的标准就是这个：换完之后运算强度有没有越过平衡点。没越过，减半就成立。

今天有一组数据正好是这条推理的反方向验证：同样的形状、同样的乘法次数，把 float32 换成 float64，字节数从 1 GB 变成 2 GB，耗时从 76 毫秒变成 170 毫秒，读取速率两边都在 13 GB/s 上下。字节翻倍，时间涨到 2 倍出头。往减半的方向走的是同一条式子。

什么情况下这条推理不成立：如果权重已经装得进缓存，那批量 1 就未必是带宽受限的，减半字节数的收益会小得多。另外如果这块硬件对 float16 的支持是"先转成 float32 再算"，那还会多出一步转换开销。所以这个判断的前提要说清楚：权重远大于缓存，且计算不是瓶颈。

今日五句话

合上这一页，用自己的话回答下面五个问题。每题写一到三句，写完对照后面的自查标准。

1. 为什么同一条读指令的耗时会差 100 倍？

2. 顺序访问和随机访问，慢的那个到底慢在哪一步？

3. 一个进程申请了 10 GB 内存，为什么 RSS 只有 200 MB？

4. 大页省下来的是什么？

5. 为什么批量处理能让推理服务快十几倍，而它一次乘法都没省？批量该开到多大，这个数怎么算出来？

逐句自查标准

  • 第 1 句如果写成"因为读的数据量不一样"，那就错了。数据量是一样的，每次都只读 8 个字节。差别在于你正在反复访问的那块区域总共多大，决定了它住在 L1、L2、L3 还是内存条上。
  • 第 2 句如果只写到"随机访问慢"，还差一层。要说出慢在"硬件猜不到下一个地址，所以没法提前把数据搬进来"。如果你写的是"随机访问的数据更分散所以缓存装不下"，那也不对。两种模式的工作集完全一样。
  • 第 3 句如果写成"操作系统超售了内存"，方向对但不准确。准确的说法是：申请只是在页表上记账，物理内存要等第一次访问那个页时才真的分配。RSS 统计的是碰过的页。
  • 第 4 句如果写成"减少了缺页次数"，只答对了表面。缺页次数确实从 26 万降到 512，但每次要清零的字节数变大了，总的清零工作量没变。真正省下来的是地址翻译的开销：同样多的 TLB 条目覆盖了 512 倍的地址范围。判断标准在今天的数据里：顺序访问下大页几乎没有收益，只有随机访问有。如果省的是缺页，顺序访问也该跟着受益。
  • 第 5 句如果写成"批量能更好地利用 CPU 的并行能力"，那是在复述一句正确但空洞的话。要说出：权重读一遍的成本是固定的，跟这一批有几个 token 无关；批量大了，这次读被摊到更多 token 头上。还应该补一句拐点。能把拐点算出来，才算真的答对。两步：先算机器平衡点 = 算力 ÷ 带宽，本页这台是 103.0 ÷ 13.2 ≈ 7.8；再看负载的运算强度怎么随批量长，它是 2B ÷ 每个权重占几字节。两者相等处就是拐点：float32 矩阵乘法（强度 B/2）拐点在 16，float16 权重的推理（强度 B）拐点就在 8。

明日预告

今天算出了这台机器的理论上限：权重读一遍要多久，就是一个 token 最快能多快；运算强度低于平衡点，时间就只由字节数说了算。但真实的推理服务里，有一个阶段完全不受这个上限约束。它读一遍权重能同时算出几百个 token，快得跟今天讲的规律好像不是一回事。
