命中率最高的那条规则，尾延迟是最差的

会话该回到哪一台机器：亲和要求「回原来那台」，均衡要求「哪台闲去哪台」。今天把这两边的价钱放在同一张表上，再看看工业界的路由器是用哪一个旋钮把它们调和掉的。

三道题，间隔一天、三天、七天。合上前面几页，先自己答一遍再展开。

第 1 题 · 来自 Day 24

昨天把一个连接池切成八个小池，那个平方级的扫描就便宜下来了；八个再往上切到三十二个，占核只从二成六走到二成二，会话耗时完全不动，收益已经耗尽。当时还顺手记了一句：会话按序号分池这条规则，以后可能会和别的分派规则打架。

今天那个「别的分派规则」来了：请求要按会话分到四台不同的推理服务上去。如果你顺手把连接池也改成「一台目标副本一个池」，昨天那条收益耗尽曲线还成立吗？

展开答案

不成立了，因为池数这个旋钮不再由你拧。

昨天池数是自由变量，你想切几份就切几份，所以能一直切到收益耗尽的那个点上。改成按目标副本分池之后，池数等于副本数——四台副本就是四个池，每个池装三十几条连接。昨天那张池数扫描表里，四个池那一行占核是三成二，八个池那一行是二成六，中间还差着六个百分点。也就是说你会被停在曲线还没走平的地方。

两条分法要同时满足，办法是让它们分层：按副本分组是外层，因为这一层是正确性要求（连接必须通到那台机器）；每个副本内部再切成几个小池是内层，这一层才是性能旋钮。层数变成两层之后，昨天那条曲线要在「每个副本内部」重新扫一遍。

接今天：今天整页都在动最外层那条分法——一条请求到底该去哪台副本。

第 2 题 · 来自 Day 22

那天量到：同一个三步任务，每次调用都起一个新沙箱要一秒一，整条会话共用一个沙箱只要零点三五秒，差三点二倍，而差额的八成八来自「把第一步重做了一遍」。当时还补了一句：会话级沙箱意味着这条会话被钉在了一台机器上。

现在把两样跨调用留在机器上的东西并排看：一台副本上的 KV cache，和这台机器上那个还活着的沙箱。假设某一轮请求被送到了别的机器上，这两样东西的后果差在哪？

展开答案

差在能不能自己长回来。

KV cache 那一份丢了，后果是要重新算一遍。慢，但结果一模一样——Day 16 验到过，复用一段前缀和把它重算一遍给出的是逐位相同的数值。所以走错机器在这一侧只是性能损失，而且是一次性的：算完之后新机器上就有了这一份，下一轮又能命中。

沙箱那一份丢了，后果是那个 rows 变量不存在了，而模型写的第二步代码里就是要用它。没有任何办法在新机器上「重算」出一个别处进程的内存。所以这一侧走错机器不是慢，是错。

一句话概括这两种约束的差别：一个是软的，走错了赔时间；一个是硬的，走错了赔正确性。今天大部分篇幅在算软的那一侧值多少钱，但真到了要写分派规则的时候，硬的那一侧没有商量余地，它决定了规则的骨架，软的那一侧只能在骨架里做优化。

第 3 题 · 来自 Day 18

立项那天给运行时的并发上限列了三条约束：一是下游模型服务的容量，那是别人的机器；二是每条在途会话在内存里的上下文，那随轮数涨；三是本进程每秒能处理多少次交接。当时的结论是三条里哪一条先撞上不能推，只能扫。

今天把下游从一台推理服务变成四台。这三条约束里，哪几条跟着变，哪一条一个字都不动？为什么？

展开答案

第一条变，而且变的方式不是简单地乘四。四台机器合起来的容量确实是四倍，但你能不能吃到这四倍，取决于请求分得匀不匀——今天整页量的就是这件事。分得不匀的时候，四台的实际容量会明显小于四倍，而且平均利用率还会显得很低。

第二条不动。在途会话的上下文躺在运行时自己的内存里，跟下游有几台机器毫无关系。

第三条也变，但方向容易看反。交接次数没变（还是一轮一次），变的是每次交接要往哪儿发——连接池现在要维护到四个不同下游的连接。Day 24 量到的那个平方级开销跟池里连接数有关，池怎么切，正好就是第 1 题的题目。

接今天：三条里第一条是今天的正题，它现在多了一个以前不存在的自变量——分派规则。

板块 2 · 核心讲解

第一部分 · 分派这一步在决定什么

1. 你手上那套粘性会话，搬过来要改三处

同一条会话的第二轮该发给哪台机器，这个问题你以前是怎么答的？

作为后端工程师，你八成已经在生产上配过一次粘性会话了。做法是在负载均衡器上按某个字段（cookie、用户 ID、URL 里的某一段）算一个值，同一个值永远落到同一台后端上，这样那台后端内存里的登录态、购物车、分片索引就都还在。

方向完全对，今天要做的就是这件事。但把它搬到推理服务前面，有三处不一样，而且每一处都会改变你该怎么配它。

第一处是「粘的是什么」。以前粘的是一份只有那台机器有的状态，别处没有，所以必须回去。现在粘的是一份缓存——回不去只是要重算，答案一个字都不会变。这一点 Day 16 验到了逐位相同。于是亲和从「必须」降级成了「划算」，而划算是可以被别的东西盖过去的。

第二处是「粘住之后能省多少」。以前省的是一次数据库查询，几毫秒。现在省的是一整段 prefill，Day 16 那张表给的量级是几百到几千毫秒。收益大了两三个数量级，所以值得为它多花力气。

第三处最容易被漏掉：这份状态会自己消失。购物车放在内存里不会因为别的用户来了就没了，KV cache 会——Day 21 量过，一条会话的两轮之间插进来别人的请求足够多的时候，属于它的那一段命中直接归零，只剩所有人共用的头部。所以「回到原来那台」这件事，只有在你回得够快的时候才值钱。

把这三处放在一起，今天要造的东西就有形状了：一个坐在运行时和推理服务之间的角色，它拿到一条请求，决定发给哪一台副本。这个动作叫 请求分派（request routing），做这件事的那个组件通常就叫路由器。它手上能有的信息只有两类——每台副本现在有多少请求没做完，以及每台副本的缓存里大概有些什么。今天整页在回答的问题是：这两类信息该怎么合起来用。

2. 一致性哈希：让「回到原来那台」在扩缩容之后还成立

先把最朴素的做法写出来，因为它能跑，而且很多地方就是这么开始的：把会话号哈希成一个整数，对副本数取模，得到几就发给第几台。

rep = sha256(session_id) % len(replicas)     # 能跑，但副本数一变就全乱

问题出在最后那个除数上。副本从四台加到五台，除数从 4 变成 5，几乎每一条会话算出来的余数都变了。这不是「有些会话要挪」，是「大部分会话都要挪」，而每挪一条就意味着新机器上没有它的任何一块，整条上下文要从头算一遍。

解决这件事的办法叫 一致性哈希（consistent hashing）。把哈希值的取值范围首尾相接看成一个圆环，这个环叫 哈希环（hash ring）。每台副本按自己名字的哈希值在环上占一个位置；一条会话也按会话号的哈希值落到环上某个点，然后顺时针走，遇到的第一台副本就是它的归宿。

这个结构的好处在拿掉一台副本的时候才看得出来：只有原本属于那台机器的那一段圆弧会改主人，交给顺时针方向的下一台；环上其他所有位置一动不动，落在那些位置上的会话完全不受影响。

环上每一段圆弧代表一个位置区间，标签是这段区间归哪台副本。左边四台都在，深色那三段属于 r2；右边 r2 摘掉，只有那三段顺时针交给了下一台，画成虚线。真实的环上一台副本占的不是三段而是上百段，画三段是为了看得清。

一台副本在环上只占一个位置的话，四台副本把整个环切成四段，而这四段的长度是它们名字的哈希值随手决定的，很可能一台占掉一大截、另一台只分到一点点。所以真实实现会给每台副本在环上放很多个位置，这些位置叫 虚拟节点（virtual node）——同一台机器在环上撒开成上百个小段，各段长度的抖动就被平均掉了。

SGLang 的那个路由网关就是这么做的，虚拟节点数写死在一个常量里：

// sgl-model-gateway/src/core/worker_registry.rs:29-31
/// Number of virtual nodes per physical worker for even distribution.
/// 150 is a common choice that provides good balance between memory and distribution.
const VIRTUAL_NODES_PER_WORKER: usize = 150;

环是在副本增减的时候建一次，不是每条请求建一次。建的时候把每台副本的地址和虚拟节点编号一起喂进哈希函数，得到的位置排好序；查的时候二分找到第一个不小于会话哈希值的位置，然后顺时针走，跳过所有不健康的副本：

// sgl-model-gateway/src/core/worker_registry.rs:63-75
for vnode in 0..VIRTUAL_NODES_PER_WORKER {
    let mut hasher = blake3::Hasher::new();
    hasher.update(url_bytes);            // 副本地址
    hasher.update(b"#");
    hasher.update(&(vnode as u64).to_le_bytes());   // 加上虚拟节点编号
    let pos = u64::from_le_bytes(hash.as_bytes()[..8].try_into().unwrap());
    entries.push((pos, Arc::clone(&url)));
}
entries.sort_unstable_by_key(|(pos, _)| *pos);       // 排好序，查的时候二分

「跳过不健康的副本」这一句顺手把故障转移也办了：一台机器挂掉，落在它那些段上的会话继续顺时针走一步，落到下一台活着的机器上；等它回来，这些会话又走回去。这条路径上没有任何需要人参与的重新分配。

到这里为止全是机制，一个数都还没有。取模到底有多糟、一百五十个虚拟节点到底够不够匀，得量。

第二部分 · 今天的台子

3. 实验装置

今天没有模型，也没有真的推理服务。被量的是分派规则本身，所以台子分成两半：一半是真跑的矩阵乘，它只负责回答「算 n 个 token 要多久」；另一半是一个确定性的模拟器，它按那个答案把时间摆出来。中间还有一个完全独立的小账台，只管哈希环。

实线框是主线：会话发生器把请求交给路由器，路由器挑一台副本。虚线框的两个账台各自独立跑，其中 P1 的三个输出被模拟器当成时间单价用，P2 和时间完全无关。底下那条虚线是 agent 循环的下一轮。首 token 延迟＝在队列里等的时间＋prefill，整轮耗时再加上 decode，两个数都在副本这一侧算出来。

3.1 一条请求里有什么

没有文字，没有分词器。一条请求就是会话号加一串整数，跟 Day 16 和 Day 20 那两个模拟器同一个形状：

("s007", 第 2 轮, prompt=[8134, 291, 30028, ... 共 1776 个],  gen=[4471, ... 共 142 个])
         ^^^^^^^^  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^  ^^^^^^^^^^^^^^^^^^^^^^^^
         路由器唯一   头部 1024 个 + 前面各轮攒下来的 + 这一轮   这一轮模型吐出来的，
         能看的标识   新送进去的那一截                          下一轮会被原样包在里面

路由器拿到这条请求之后，可以做两件事：数一数每台副本手上还有几条没做完，以及拿这串 token 去每台副本的缓存里试一次，看能对上几块。它做完决定，请求就进那台副本的队列。

3.2 哪些是真的，哪些是假的

左边写这个台子在哪儿偷了懒，右边写这个懒换来的一句今天不能说的话。

简化掉的地方后果
四台「副本」是模拟器里的四个对象，没有真进程，也没有网络往返今天所有毫秒数都是按 P1 那三个单价算出来的，不是端到端实测。它们之间的比例可信，绝对值只在这台两核机器这副骨架上成立
一台副本一次只跑一条请求，没有连续批处理今天不下任何关于批处理、混合批、token 预算的结论。真实引擎会把几条请求拼进同一步，那会让排队这一侧的形状完全不同——今天量到的排队代价是它的上界
路由器直接查每台副本的真实缓存，能对上几块一清二楚这是缓存感知路由的上限。真实路由器手上只有一棵近似的树，是按请求历史自己维护的，会比真相乐观也会比真相悲观。所以今天不下关于「近似到什么程度还够用」的结论
没有分词器，token 是随机整数，每一段的长度是随机数不下任何关于中英文、某个词表、某段真实文本的结论。所有长度单位都是 token 位

第三行是今天最大的一处简化，要单独记一笔。让路由器看见真相，等于假设那棵近似树永远是对的。真实系统里这棵树会漂移，而漂移的方向是有偏的——它记得自己发过什么，不知道对面淘汰了什么。所以今天缓存感知那几行的命中率，是它在现场能拿到的上限。

6. 揭晓（二）：命中率最高的那一行，尾延迟是倒数第二

  • 看每台手上还有几条没做完，发给最少的那台。这条规则叫 最少在途（least outstanding requests），也叫最短队列。

问题三的答案是：一台接了全部一千零九十条，另外三台一条都没有。

机制只有三步，而且每一步都很自然。

粗框是缓存里有东西的副本。第三步那三条虚线是后来的请求：它们各自去四台上试一遍，只有 r1 能对上，于是全都汇到 r1。

第一条请求进来的时候，四台副本的缓存都是空的，能对上的块数都是零，规则只能随手挑一台，这里挑中了 r1。跑完之后 r1 存下了这条请求的全部块，包括那 1024 个 token 的共用头部。

第二条请求进来，它和第一条共用头部。在 r1 上能对上 64 块，在另外三台上一块都对不上。规则说「给对得最多的那台」，于是又是 r1。之后每一条都一样：别的三台永远等不到自己的第一条请求，也就永远进不了这个循环。

这种把所有流量吸过去的副本叫 热点副本（hotspot）。它的成因不是负载不均衡没被处理，是规则里根本没有任何一项会随负载变化——它只读缓存状态，而缓存状态本身是被它自己的决定写出来的。这是一个正反馈：赢过一次就更容易赢下一次。

再看命中率那一列，32.1%，比轮询还低。这一点值得停一下：全部请求都落在同一台机器上，缓存应该最热才对。低的原因在 Day 16 那个词上——复用距离。一百二十条会话全挤在一台副本的 32768 个 token 位里，一条会话的两轮之间插进来的是另外一百多条会话的块，属于它自己的那一段早被 LRU 挤没了。所以私有那一半只剩 2.5%，命中的几乎全是头部。

关键结论

一条只看缓存的分派规则不是「偏向缓存」，它会退化成单机。工业界的路由器里没有这条规则的纯粹形式，全都配了一个逃生口——这不是稳健性上的锦上添花，是让这条规则能用的前提。第四部分那两个默认值就是这两个逃生口。

9. 真实路由器的两条判据

SGLang 的那个路由网关里，缓存感知这条策略的文件开头写着一段很长的注释，第一句就把它的立场说清楚了：这不是一条策略，是两条策略加一个开关。

// sgl-model-gateway/src/policies/cache_aware.rs:1-16
    Cache-Aware Load Balancing Router
    ...
    The router dynamically switches between these strategies based on load conditions:
    - Uses load balancing when the system is imbalanced
    - Uses cache-aware routing when the system is balanced

    A system is considered imbalanced if both conditions are met:
    1. (max - min) > abs_threshold
    2. max > rel_threshold * min

翻成大白话：先看四台副本手上没做完的请求数，最多的那台和最少的那台差得够远，就不管缓存了，直接发给最闲的那台；差得不远，才轮到缓存说话。这个判断是每条请求都做一次的。

缓存说话的时候还有第二道门。注释里那几行写着：

// sgl-model-gateway/src/policies/cache_aware.rs:26-31
    b. If match rate > cache_threshold:
       Route to the worker with highest match (likely has relevant data cached)
    c. If match rate ≤ cache_threshold:
       Route to the worker with smallest tree size (most available cache capacity)

这里的匹配率，就是 3.3 节那条轨迹里那一列：在能对上最多的那台副本上，命中的部分占这条请求的比例。匹配率门槛（cache_threshold）过不去，就不按缓存分，按别的分。这一道门正是第 7 节那个热点副本的解药——四台都是空的时候匹配率是零，零过不了门槛，于是第一批请求会被摊开，每台都拿到属于自己的第一条。

代码里那个分岔长这样，两条判据一前一后：

// sgl-model-gateway/src/policies/cache_aware.rs:410-419
let is_imbalanced = max_load.saturating_sub(min_load) > self.config.balance_abs_threshold
    && (max_load as f32) > (min_load as f32 * self.config.balance_rel_threshold);

if is_imbalanced {
    return self.select_worker_min_load(...);   // 失衡：谁闲给谁，平局随机
}
// 没失衡才往下走，去那棵近似树里查最长匹配

这三个旋钮的默认值写在配置里，一处能全看到：

// sgl-model-gateway/src/config/types.rs:809-814
cache_threshold: 0.8,
balance_abs_threshold: 10,
balance_rel_threshold: 1.5,
eviction_interval_secs: 300,

这种「优先回原来那台，但条件不合适就放弃」的做法，行业里叫 软亲和（soft affinity）；与之相对的是 硬亲和（hard affinity）——温故第 2 题里那个会话级沙箱就是硬的，走错了不是慢，是错。今天的模拟器里那条「混合」规则，就是把上面这两条判据照抄了一遍。

板块 3 · 动手任务

两个任务，约两小时。任务 A 是今天的交付物：一个能回答「换这条分派规则值多少」的模拟器。任务 B 把同一套读法用到你手上已经有的东西上。

任务 A（必做，约 75 分钟）· 让四台副本和一个路由器跑起来

第 1 步：一台副本 = 一份缓存 + 一个队列

缓存那一半 Day 16 和 Day 20 都写过，直接搬过来：切成十六个 token 一块，只对装满的块串 hash，查的时候从第 0 块起连续命中、遇到第一个不中就停。队列那一半是新的，而且只需要一个数：这台副本忙到什么时候。

class Replica:
    def __init__(self, cap_tokens):
        self.cache   = PrefixCache(cap_tokens)   # Day 16 那一套，一个字不改
        self.free_at = 0.0                       # 忙到什么时候（毫秒）
        self.out     = 0                         # 手上还有几条没做完 —— 路由器唯一看得见的负载

    def admit(self, now, prompt, gen, slope, inter, dec):
        nb   = self.cache.lookup(prompt, len(prompt) - 1)   # 留最后一个 token 不给命中
        comp = len(prompt) - nb * BLOCK
        self.cache.insert(prompt + gen)                     # 生成的那一截也进缓存
        svc   = inter + slope * comp + dec * len(gen)
        start = max(now, self.free_at)                      # 前面有人就得等
        self.free_at = start + svc
        return start - now, inter + slope * comp, svc       # 排队、prefill、整条服务时间

那个 len(prompt) - 1 不是笔误，是 Day 16 第 12 节那段源码注释里的规矩：哪怕一条请求全命中，也必须留最后一个 token 重算，因为采样下一个 token 需要最后那个位置的输出。

验收标准：同一条 prompt 连着 admit 两次，第二次的 comp 应该正好是 16（一整块），不是 0，也不是 1。常见坑：把 insert 写在 lookup 前面，于是每条请求都自己命中自己，命中率好得不像话。

第 2 步：一致性哈希环

照第 2 节那段源码写：每台副本 150 个虚拟节点，位置是「副本名 + 分隔符 + 虚拟节点编号」的哈希值，排好序；查的时候二分找第一个不小于会话哈希值的位置，找不到就绕回开头。

验收标准：造两万个会话号，四台副本各分到多少条，最多的一台除以平均应该落在 1.0 到 1.2 之间。然后加第五台，重新分一遍，换了机器的会话应该在两成到两成五之间——如果这个数接近八成，说明你写的还是取模。

常见坑：虚拟节点的位置只哈希了副本名，没把编号拼进去，于是一台副本的 150 个虚拟节点全落在同一个位置上，等于没有虚拟节点。症状是上面那个比值稳定在 1.7 附近下不来。

第 3 步：路由器和五条规则

五条规则写在同一个函数里，用一个字符串参数切换。轮询、最少在途、二选一各只有两三行；会话亲和是查一次环；混合那一条照第 9 节那两条判据写。

def route(policy, reps, sid, prompt, ring, abs_thr=10, rel_thr=1.5, cache_thr=0.8):
    loads = [r.out for r in reps]
    least = min(range(len(reps)), key=lambda i: loads[i])
    if policy == "least":     return least
    if policy == "affinity":  return ring.find(sid)
    if policy == "hybrid":
        mx, mn = max(loads), min(loads)
        if mx - mn > abs_thr and mx > mn * rel_thr:   # 判据一：排得太不均，放弃缓存
            return least
        mb   = [r.cache.lookup(prompt, len(prompt) - 1) for r in reps]
        best = max(range(len(reps)), key=lambda i: mb[i])
        rate = mb[best] * BLOCK / len(prompt)          # 判据二：匹配率够不够
        return best if rate > cache_thr else least
    ...

写完先跑一次「只看最长匹配」的版本，也就是把最后一行改成无条件 return best。你应该看到第 7 节那个形状：一台接了全部，另外三台是零。看到这个形状再往下写，因为它是后面所有对照的起点。

验收标准：把匹配率门槛设成大于 1 的数，混合那条规则跑出来的每一个数都必须和最少在途完全相同。不相同说明还有别的分支在偷偷用缓存。

第 4 步：泊松到达和事件循环

用一个小顶堆装事件，两种事件：一条请求到达、一条请求做完。到达时路由、算服务时间、把「做完」压回堆里；做完时把那台副本的在途数减一，并且在 240 毫秒之后把这条会话的下一轮压回堆里。同一时刻的两种事件，「做完」要排在「到达」前面，否则路由器看到的在途数会多算。

报四组数：命中率（拆成头部和会话私有两半）、每台副本处理了几条和累计忙了多久、首 token 延迟的 P50 和 P99、四台合计忙了多少秒。最后一组是第 8 节那个「等价机器数」的原料。

验收标准：头部那一半命中率在五条规则下应当基本相同（差在一个百分点以内）。它要是随规则变，说明你的头部没有被所有会话共用，后面所有的拆分都读不出东西。

常见坑：把「做完」事件和「下一轮到达」事件安排在同一个时刻，然后按压栈顺序处理。这会让同一条会话的下一轮在自己还没释放许可的时候就被路由，看起来像是负载凭空多了一条。

任务 B（约 40 分钟）· 用到你自己手上的东西

挑一个你写过的、前面挂着负载均衡的服务，不一定和模型有关。做四件事。

  • 找出它现在的分派规则是什么。如果是轮询或者随机，问一句：后端有没有任何一份「这一次和上一次相关」的状态？有的话，它现在正在被浪费掉。
  • 如果它已经配了粘性会话，找出粘的那个键是什么，以及后端数量变化的时候这个键是怎么映射的。是取模就按第 5 节那两个数估一估扩容的代价。
  • 给它加一个指标：每台后端处理的请求数（或者忙时），报最大值除以平均值。这个数是今天整页的核心读数，而多数面板上没有它——面板通常只有平均值。
  • 回答一个问题：如果某一台后端慢了三倍，你现在这条规则要多久才会发现？发现的判据是什么？

验收标准：你能指着一行配置说出「这里定的是分派规则」，并且说得出它在后端数量变化时会让多少比例的键换主人。

加分题

  • 第 3.2 节写着路由器直接查了副本的真实缓存，而真实路由器手上只有一棵按请求历史自己维护的近似树。给模拟器加上这一层：路由器只记得自己发过什么，不知道副本淘汰了什么。命中率会掉多少？在什么条件下这棵树会漂移得最厉害？
  • 第 12 节的结论是「条数认不出慢」。把路由器看到的负载从「在途条数」换成「这台副本手上还欠着多少个 token 没算完」，重跑那张慢副本的表。r1 分到的条数会掉到多少？换成 token 之后，前面那些不慢的表有没有变差？
  • 今天的副本一次只跑一条请求。加上连续批处理：一台副本每一步从队列里取若干条拼成一批，一批的耗时按 Day 9 那套算。批处理会让排队的形状完全不同，先猜一下亲和和均衡的差距是变大还是变小，再跑。
  • 第 13 节那张表里，四台以后加机器只买到并行度。把每台副本的缓存容量同时按副本数往下调（总缓存不变），再扫一遍副本数。这条曲线的形状会变成什么样？
  • 今天所有会话的头部完全相同。造两种租户，各有各的头部，混在一起跑。匹配率门槛 0.8 还是最优的吗？如果不是，往哪个方向动？

板块 4 · 工作现场

场景一 · 「开了粘性会话，命中率从七成上到九成，可 P99 更差了」

这句话在今天这一页上有完整的对应：第 6 节那张表里，亲和那一行的命中率是全表最高，首 token P99 是全表倒数第二。所以第一件事不是怀疑数据，是承认这两件事可以同时成立。

要定位，去要一个多数面板上没有的数：每台副本处理的请求数或者忙时，报最大值除以平均值。这个数明显大于 1，问题就是倾斜；接近 1，那问题在别处，得换个方向查。

倾斜的来源有两种，要分开。一种是会话本身长短不一，哈希环没法预知；另一种是环的位置本来就不匀，这一种可以直接看每台副本分到的会话条数——它和请求条数不是一回事。

止血最快的一步是把硬亲和改成软亲和：加一条匹配率门槛，让第一轮和匹配率不高的请求走最闲的那台。第 10 节那张扫描表给了这个门槛的形状——两端都糟，中间有一段宽平地，先取 0.8 再按自己的流量往两边试。

场景二 · 「扩容加了一倍机器，命中率反而掉了」

先问一句这个服务的分派规则是不是对后端数量取模，再问一句这次扩容是不是正好翻倍。这两问的组合决定了代价：翻倍的时候取模只让一半的会话换机器，和一致性哈希一样好；不是翻倍的时候，同一套配置能让八成的会话换机器。而换机器等于整条上下文重算。

这一类掉幅是一次性的，几分钟到几十分钟之后会自己恢复，但恢复期间的尾延迟会很难看，而且它会在下一次扩容时原样再来一遍。

如果它已经是一致性哈希，那要看的就不是命中率总数，而是把它拆成头部和会话私有两半。头部那一半掉，说明副本变多之后每台都要为共用头部各冷启动一次——这一笔今天量过，一千多条请求摊下来小到读不出来，如果你的现场里它很大，说明请求总数相对副本数太少了，那是扩得过头了。私有那一半掉，说明会话被打散了，去查分派那一层拿到会话号没有。

还有一种情况和分派规则无关：每台副本的缓存容量是固定的，机器变多、总缓存变大，本该更好；但如果扩容的同时并发也涨了，复用距离可能涨得比缓存快。第 13 节那张表的前两行就是这个形状，那里命中率掉到三成二，不是路由的问题，是容量真的不够。

场景三 · 「有一台机器一直在告警，别的几台闲着」

这个现象有两个成因，症状很像，修法完全相反。

第一种是那台机器变慢了——邻居在抢核、盘在等、刚重启缓存是冷的。判据是它每条请求的服务时间比别人长，而分到的请求数不一定多。这时候要做的是把它摘出去，或者让路由器的负载改成带单位的量。

第二种是它被规则吸过去了。判据是它每条请求的服务时间和别人一样，只是条数多。第 7 节那个热点副本是这种情形的极端形态，成因是规则里没有任何一项随负载变化。这时候摘机器没有用，摘掉之后下一台会变成新的热点。

分辨这两种只要一个除法：那台机器的忙时除以它处理的条数，和别的机器比。今天第 12 节那张表里特意把「条数倾斜」和「忙时倾斜」分成两列，就是为了这个除法。

同事和面试官常问的

「同一个用户的请求要不要固定发到同一台机器？」——先反问是什么状态钉在那台机器上。是缓存，那是软亲和，走错了赔时间，值多少钱可以量；是进程内存里的东西（比如一个跨调用活着的沙箱），那是硬亲和，走错了赔正确性，没得商量。这两个答案对应的方案完全不同，混在一起答就说明没分清。

「那软亲和该怎么做？」——不要做成「永远回原来那台」。给它一个逃生口：匹配率不够就走最闲的那台。可以给出实测的形状：只按最长匹配分派会让四台副本变成一台，加上一道 0.8 的匹配率门槛之后，命中率几乎不变而负载重新摊平。

「我们的平均利用率才六成，为什么还慢？」——因为平均利用率是几台机器平均出来的。要看的是最忙那台除以平均。实测里有一档平均利用率只有六成二，而首 token 的 P99 是二十三万毫秒，因为其中一台早就排满了。这和 Day 24 那句「CPU 才用了一半为什么不能再多放点」是同一类错误，只是从单机换到了多机。

「命中率是不是越高越好？」——不是。命中率省的是每条请求的计算量，用户等的时间里还有排队那一段。实测里命中率最高的那条规则，首 token 的尾延迟是全表倒数第二。正确的目标函数是延迟，命中率只是它的一个输入。

「加机器能解决吗？」——要看卡在哪一段。如果是缓存装不下（命中率的私有那一半很低），加机器有用，因为每台副本各带一份缓存。如果是倾斜（最忙除以平均明显大于 1），加机器会让倾斜更大，因为会话总数不变、每台上摊到的更少。这两种情况在同一张监控图上长得一样。

板块 5 · 自检问题

1. 有人提议：「把匹配率门槛从 0.8 调到 0.95，这样只有非常确定命中的时候才粘，更安全。」用今天的数评估。

「更安全」这个直觉的方向是对的——门槛越高，越少因为缓存而牺牲均衡，负载确实更平。第 10 节那张表里 0.95 那一行的忙时倾斜是 1.012，比 0.8 那一行的 1.048 还平一点点。

问题在它同时把缓存关掉了。0.95 那一行的命中率是 72.7%，和门槛大于 1（也就是完全不用缓存）那一行的 72.0% 几乎一样。要算的 token 从四十万涨到一百零三万，按第 8 节的折算，四台机器的忙时会从 3.37 台涨回 4.00 台。

原因在 3.3 节那条轨迹上：一条会话第二轮的匹配率是 0.856，第三轮 0.860。门槛设到 0.95，这些轮全都过不去，能过去的只剩最后几轮。所以这个旋钮不是「越高越保守」，是「越高越接近不用缓存」。

错在哪：把一个双端旋钮当成了单向的安全度。它的两端是两种不同的坏，最优点在中间，而中间那段的位置由你的流量形状定。

2. 你们的服务用一致性哈希做会话亲和，四台副本。监控显示命中率稳定在九成，但每周有一两次 P99 突然翻几倍，持续十几分钟然后自己好。命中率在这十几分钟里没掉。查什么？

命中率没掉是最强的线索：它排除了「会话被打散」和「缓存被挤掉」这两类原因——那两类都会让私有那一半的命中率跟着掉。

剩下的方向是有一台副本变慢了，而亲和认不出这件事。第 12 节量过这个形状：r1 的服务时间乘以三，亲和照样给它塞了 178 条请求，而最少在途只给了 107 条；与此同时亲和的命中率是 89.6%，一点没掉。

要查的是每台副本的「忙时除以处理条数」，也就是它每条请求平均要花多久。这个数在那十几分钟里如果有一台明显高出来，就定案了。至于它为什么慢，那是另一个问题——邻居、盘、刚重启缓存冷，都有可能。

修法有两条。短期是把那台摘出去，一致性哈希会顺时针把它的会话交给下一台，别的会话完全不受影响（第 5 节量过，被连累的比例是 0）。长期是把路由器看到的负载从条数换成带单位的量。

错在哪：看到 P99 涨先去查缓存。命中率这一列已经把缓存这条线排除掉了。

3. 一个同事说：「第 7 节那个热点副本是模拟器的毛病。真实系统里第一条请求之后，别的副本迟早也会拿到请求，就不会一直是那一台了。」他说的对吗？

不对，而且他的推理里少了一步。别的副本要拿到请求，得先有一条请求被判给它；而在「只看谁对得最多」这条规则下，判给谁完全由缓存内容决定，跟负载、跟时间、跟已经积压了多少都没有关系。

第一台副本存下共用头部之后，它在任何一条新请求上的匹配块数都至少是头部那 64 块，而别的副本是零。零永远不大于 64，所以别的副本永远等不到自己的第一条。这是一个自我封闭的循环，不会因为时间长就打破。

真实系统里确实不会出现这个形状，但原因不是他说的那个，是真实路由器里根本没有这条规则的纯粹形式——它们都配了逃生口。SGLang 那个网关的逃生口是匹配率门槛，而且门槛过不去的时候它不是发给最闲的，是发给「树最小的那台」，也就是缓存最空的那台，方向是主动去喂那些还没热起来的副本。

错在哪：默认「随机性迟早会打破对称」。这条规则里没有随机性，也没有任何随时间变化的量。

4. 你把副本从四台加到八台，命中率几乎没变（89.3% → 89.0%），P99 却好了一倍。有人说这说明缓存不重要，加机器才有用。怎么回应？

这两个数都是第 13 节那张表里的，而它们说的是两件事，不能拿一件去否定另一件。

命中率没变，说明四台的时候缓存已经够用了——它在这条曲线上已经走平。走平的地方再加容量当然看不出效果，这不等于缓存不重要。同一张表往回看两行：只有一台副本的时候命中率是 32.1%，两台是 49.4%，到四台才跳到 89.3%。前面那两行的缓存严重不够，加机器买到的正是缓存。

P99 好了一倍，来自另一个自变量：同样的负载摊到更多台上，每台的利用率降下来，排队就短了。这一笔和命中率无关，它在关掉缓存的时候一样成立。

还有一件反方向的事要一起报：同一张表里忙时倾斜从 1.048 涨到 1.242。会话总数没变，机器越多每台上摊到的会话越少，哈希环那点抖动就越显眼。所以这次扩容买到了并行度，同时买回来一点倾斜。

错在哪：拿一条已经走平的曲线上的一个点，去证明这条曲线不重要。要证明这件事，得把容量往下调，看它掉不掉。

1 · 为什么「命中率最高」和「用户等得最少」可以不是同一条规则？各自的自变量是什么？

2 · 一条只看「谁缓存得最多」的分派规则会退化成什么？说清是哪一步开始出不去的。

3 · 匹配率门槛这个旋钮的两端分别是什么？为什么它的最优值不是一个通用常数？

4 · 副本从四台变成三台，取模和一致性哈希各有多少会话换了机器？被连累的那一部分差在哪儿？

5 · 一台副本慢了三倍，「最少在途」这条规则能发现吗？为什么发现得晚？

逐句自查

第 1 句　如果只写「命中率高不代表快」，是复述不是回答。要说出两个自变量：命中率决定每条请求自己要算多少，倾斜决定它要排多久。实测里亲和的命中率是全表最高而首 token P99 是倒数第二，这两个数出自同一次运行。

第 2 句　答「负载不均」不够。要说到自我封闭那一步：第一台副本存下共用头部之后，它在任何新请求上的匹配块数都至少是头部那些块，别的副本是零，所以别的副本永远等不到自己的第一条请求。实测是一台接了 1090 条，另外三台是 0。

第 3 句　两端是「热点副本」和「完全不用缓存」。最优值不通用，是因为它由「共用头部有多长」和「每轮新增多少」的比值定——今天这批流量里第一轮的匹配率是 0.749、第二轮起是 0.856 以上，门槛要卡在这两个数之间。换一种流量，这两个数就变了。

第 4 句　取模是七成半，一致性哈希是两成半。差别的关键不在这两个数本身，在被连累的那一部分：一致性哈希下，原本不在那台机器上的会话被影响的比例是 0；取模下，剩下那七成五里有一半跟着改了归宿，而它们和这次故障毫无关系。

第 5 句　能发现，但发现得晚，而且是间接发现的。它数的是在途条数，而一台机器慢下来之后，要等到请求在它手上堆起来，条数才会涨。也就是说，判据本身滞后于原因。实测里最少在途最终只给了那台慢机器 107 条（均分是 272 条），说明它确实躲开了；但躲开之前已经有一批请求排在里面了。如果答成「发现不了」，看那一列的条数。
