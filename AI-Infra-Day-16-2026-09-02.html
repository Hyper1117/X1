第 1 题 · 来自 Day 15

Day 15 算出来的结论是：在那台机器上，把一条被踢掉的序列搬到别处存着，比让它回来重算快约 196 倍。可 vLLM V1 的默认抢占模式偏偏是重算。这两件事矛盾吗？如果不矛盾，是式子里的哪一项翻了方向？

看答案

不矛盾。那个比值是「每 token 的 KV 字节数 × 算力」比上「参数量 × 搬运速率」，四项里有两项是机器的属性。

算力和搬运速率在 CPU 和 GPU 上不是按同一个比例变的。GPU 的算力比那台两核机器高三四个数量级，而它对外搬东西走的不是内存条，是一条带宽低得多的外部总线。分子涨了几千倍，分母只涨了几倍，比值就从「搬远比重算便宜」翻到了另一边。

还有一项不在式子里但真实存在：重算可以和别人的批次拼进同一次前向，搬运的那些字节没人能替它分摊。

接今天：今天要把这个式子从「两条路」扩成「一整级阶梯」——显存装不下往内存放，内存装不下往盘上放，每一级都要拿同一个式子问一遍"从这儿取回来，还是干脆重算"。

第 2 题 · 来自 Day 13

containerd 不直接拉起 runc，中间隔着一个常驻的 shim 进程。看起来是多了一层。如果把它去掉，让 containerd 自己 fork-exec runc，具体会坏在哪两件事上？

看答案

坏在 containerd 自己重启这件事上。runc 创建完容器就退出了，容器的 1 号进程会被过继给上面某个进程。如果那个进程是 containerd 本人，那 containerd 一升级、一重启，所有正在跑的容器的标准输入输出就断了，退出码也没人接。

有了常驻的 shim，容器的父进程是 shim 不是 containerd。containerd 可以随时重启，容器照常跑，重启完再通过套接字连回每个 shim。

第二件事是收尸。shim 启动时把自己设成 subreaper，于是容器里所有没人认领的孤儿进程都归它管，它负责等待并回收，否则僵尸进程会一直堆着。

接今天：今天讲的东西也是一层"看起来多余"的间接——两条请求之间凭什么知道对方算过同样的东西，靠的就是中间这一层簿记。

第 3 题 · 来自 Day 9

你把 max_num_batched_tokens 从 8192 调到 512。现在来了一条 prompt 长 8000 个 token 的请求，而且这台机器上此刻没有别的请求。这条请求的首 token 延迟会变好还是变坏？为什么？

看答案

明显变坏。这个参数是调度器每一步手上的 token 预算，一条 8000 token 的 prompt 在预算 512 之下会被自动切成 16 步才算完——分块预填充不是一个额外开关，它就是预算的自然结果。

切成 16 步之后，那 512 MiB 权重要被完整读 16 遍，而按 Day 8 的结论，一次前向的成本主要就是读这一遍权重。所以总的算完时间会涨好几倍，而首 token 要等到最后一块算完才出得来。

Day 9 的原话是：分块预填充单独用会让总账变差，它必须和「把 prompt 和 decode 挤进同一步」配套才是净收益。此刻机器上没有别人，配套的那一半不存在，剩下的就只有代价。

接今天：今天要动的是同一个位置的另一个旋钮——不是把这 8000 个 token 切开分几步算，而是让其中一大截根本不用算。

1. 两条请求的开头一模一样，中间的东西也会一模一样吗

先看一天里最常见的两种流量。

一种是同一个系统提示词。你的服务给每条请求都在最前面拼上同一段话——角色设定、输出格式要求、几十个工具的说明书。一千个用户问一千个不同的问题，但这一千条请求的开头几百个 token 完全一致。

另一种是 agent 的多轮。第一轮你把任务描述发过去，模型回一段话并要求调用某个工具；你把工具的返回拼在后面，连同前面所有内容一起再发过去，这是第二轮；第三轮又在第二轮的全部内容后面接一截。每一轮的输入，都是上一轮输入的一个扩展。

Day 15 整天都在算"一条序列的 KV 要占多少字节"，而算法从头到尾假设这份 KV 是它自己的。上面这两种流量把这个假设摊在了桌面上：如果一千条请求的前五百个 token 一样，服务器现在存的是一千份内容相同的东西，而且每一条进来时都把这五百个 token 重新过了一遍网络。

加一层缓存是最顺手的一步，你在别的系统里这么干过很多次：把整条 prompt 当 key，把算好的东西当 value，进来先查一下。方向是对的，可按整条 prompt 做 key 几乎永远查不中——一千个用户的问题各不相同，整条 prompt 一千个样。要有用，缓存的粒度必须比"整条请求"细。

细到什么程度、凭什么可以细、细了之后怎么查——这三个问题是今天的全部内容。但在拆它们之前，得先确认一件更基本的事：开头一样，算出来的中间结果真的一样吗。这件事听起来显然，可"显然"在性能工程里不值钱，它必须被验到字节。

3. 把"开头一样"验到字节

要验它，先得说清楚一个 token 的 K 和 V 是从哪儿来的。Day 15 说过它们是"把 token 过一遍网络算出来的"，今天要把这句话里的一个限定条件挖出来。

模型算第 i 个位置的时候，允许它看的只有第 0 到第 i 个位置，后面的一律看不见。这不是实现上的偷懒，是任务定义决定的：模型的活儿是根据前文预测下一个词，训练的时候要是让它偷看到后面，它就学不到东西。这个"只许往前看"的限制，就叫 因果注意力（causal attention），实现上是给注意力打分的矩阵盖一层上三角的掩码。

顺着这个限制推一层。第 i 个位置在第一层的 K 和 V，只由第 i 个 token 本身决定。它在第二层的 K 和 V，由第一层第 0 到第 i 个位置的输出决定。往上每加一层，依赖范围最多扩到"第 0 到第 i 个位置"，永远扩不到第 i 个之后。所以：

第 i 个位置在任何一层里的 K 和 V，只取决于第 0 到第 i 这一段 token，跟它后面有什么、总共有多长，一点关系都没有。

推理到此结束，接下来是验证。P1 搭了一个两层的因果注意力骨架，构造两条序列：它们共享开头 64 个 token，之后一条自己接 40 个、另一条自己接 90 个。然后逐层逐位置比这两条序列的 K 和 V。

后缀相同、前缀不同，尾巴上的 K 差了 4.373——那不是数值误差，那是完全无关的两个数。原因就在上面那条推理里：第 i 个位置的 K 依赖它前面的全部 token，前面换了，它就跟着换。

第二行和第三行给的是同一件事的更精确形状：动一个 token，它之前的位置一个不受影响，它自己和它之后的全部改变。所以两条序列能共用的，恰好就是"从第 0 个 token 开始、一路相同、直到第一个不同为止"的那一段。

把算过的这一段存下来、后面来的请求直接拿去用，这个做法就叫 前缀缓存（prefix caching）。vLLM 里它的开关名字更长一点，叫自动前缀缓存（enable_prefix_caching，在当前版本里默认是开的，vllm/config/cache.py 第 139 行），"自动"是说你不用告诉它哪一段是公共前缀，它自己发现。

关键结论

因果注意力这个限制，在训练那一侧是为了不让模型偷看未来；在服务这一侧，它顺手把 KV 变成了一件可以跨请求复用的东西。能复用的范围也被它精确地框死了：只能是前缀，一个 token 都不能错位。

4. 逐个 token 比一遍行不行

知道了要匹配的是最长公共前缀，最直接的实现是：新请求进来，拿它的 token 列表和缓存里每一条已有的序列从头比，看谁的公共前缀最长。

这个做法能出正确答案，代价是它和缓存里的序列条数成正比。缓存里躺着一万条序列，来一条新请求就要比一万次，每次还要逐个 token 走。而这件事发生在请求路径上——Day 14 讲过，请求路径上的每一微秒都会原样加到用户等待的时间里。

两个主流引擎给了两种不同的答案。它们的差别不是实现细节，是两种结构在"匹配粒度"和"淘汰谁"上的取舍，两边都该看一遍。

5. vLLM 的做法：把前缀压进一个 hash

先说一个铺垫。hash 函数（这里是 sha256）做的事是把任意长的一段字节压成一个固定长度的指纹，内容一样指纹一定一样，内容不一样指纹几乎一定不一样。

vLLM 的想法是：既然 KV 本来就是按块存的（Day 15 的块，默认 16 个 token 一块），那就给每一块算一个指纹，指纹里不光装本块的 token，还要装它前面所有块的信息。做法是把上一块的指纹和本块的 token 一起喂进 hash 函数：

# vllm/v1/core/kv_cache_utils.py:642-648
if not parent_block_hash:
    parent_block_hash = NONE_HASH          # 第一块没有父块，用一个固定的种子
curr_block_token_ids_tuple = tuple(curr_block_token_ids)
return BlockHash(
    hash_function((parent_block_hash, curr_block_token_ids_tuple, extra_keys))
)

这样串起来的一列指纹，叫 块 hash 链（chained block hash）。它有一个直接的好处：第 k 块的指纹已经把第 0 到第 k 块的全部内容装进去了，所以"这一块的指纹在缓存里"这一个条件，等价于"从头到这一块为止的整段前缀都对得上"。于是匹配退化成一次哈希表查找，跟缓存里有多少条序列没关系。

vLLM 里循环算这条链的地方，明确写着只对装满的块算：

最后一行说明这条链是"一荣俱荣一损俱损"的：动第 7 个 token，它落在第 0 块里，于是第 0 块的指纹变了，第 1 块的父变了所以也变了，之后全部变。这正是"一块没中，后面不用再看"这个优化成立的前提。

6. SGLang 的做法：把公共前缀显式画成一棵树

hash 链把"共享"这件事藏了起来——哈希表是平的，一万个块躺在一个字典里，谁和谁共享前缀，从数据结构上看不出来。SGLang 走的是另一条路：把共享的形状直接建成一棵树。

树的根是空串。从根出发的每一条边带着一小段 token，从根走到某个节点，把沿途各段接起来，就是一段被缓存的前缀。两条请求只要开头一样，走的就是同一段路径，到分岔的地方才各走各的。这种"边上带着一串字符、公共部分只存一份"的树，叫 基数树（radix tree，也译前缀树）；SGLang 把它和注意力接在一起的这套东西叫 RadixAttention。

匹配就是从根往下走，每一步拿剩下的 token 和某条边比。走到某条边中间就比不下去了怎么办？SGLang 的做法是把那条边切成两截，在切点上插一个新节点。这个动作叫 节点分裂（node split），源码里是 _split_node（python/sglang/srt/mem_cache/radix_cache.py 第 705 行），被 _match_prefix_helper 在匹配停在边中间时调用：

# python/sglang/srt/mem_cache/radix_cache.py:689-698
prefix_len = child.key.match(key, page_size=self.page_size)
if prefix_len < len(child.key):
    new_node = self._split_node(child.key, child, prefix_len)   # 从中间切开
    value.append(new_node.value)
    node = new_node
    break
else:
    value.append(child.value)      # 整条边都对上了，继续往下走
    node = child
    key = key[prefix_len:]

分裂不复制 KV，它只是把一条边的记账拆成两段，让"公共到这里为止"这件事在结构上有个位置可以站。代价是匹配这个动作会顺手改动树，所以它不是一个纯粹的读操作。

7. 两条路差在哪：能对到多细，以及先淘汰谁

两种结构的第一个差别是匹配粒度。hash 链只能对上整块，块里剩的零头一律作废；树可以停在边的任意位置，粒度细到单个 token（当引擎按页管理显存时，会被向下取整到页边界）。

第二个差别更有意思，在淘汰这一侧。缓存总会满，满了要扔掉一些块，扔哪些？两边用的都是 最近最少使用（LRU, least recently used）——最久没被碰过的先扔——但落地方式完全不同。

vLLM 没有单独的缓存池。它的前缀缓存就住在空闲块队列里：一条请求跑完，它的块引用计数归零，被放回队列；带指纹的块放到队尾，不带指纹的放到队首。而分配新块永远从队首取。

# vllm/v1/core/block_pool.py:737-747
if block.block_hash is None or not self.enable_caching:
    # LIFO reuse of non-cached blocks for better GPU locality.
    blocks_to_evict_first.append(block)
else:
    # FIFO reuse of cached blocks for LRU eviction behavior.
    blocks_to_evict_last.append(block)
self.free_block_queue.prepend_n(blocks_to_evict_first)
self.free_block_queue.append_n(blocks_to_evict_last)

代码注释里那两个词说的就是这件事：带指纹的块进队尾、从队首出，是先进先出（FIFO），最久没被碰过的自然最先被取走，等于 LRU；不带指纹的块进队首、也从队首出，是后进先出（LIFO），刚放回来的马上被再用，对硬件缓存更友好。取到一个还带着指纹的块时，引擎顺手把这个指纹从缓存表里摘掉（_maybe_evict_cached_block，同文件第 679 行）。所以在 vLLM 里，缓存不占任何额外内存——它用的全是"还没被别人拿走的空闲块"。这一条直接回答了一个常见问题：开前缀缓存要不要给它单独留一块显存？不要，它花的是本来就闲着的容量。

SGLang 那一侧，淘汰是从树的叶子往上收：把所有可淘汰的叶子按优先级（默认是最后访问时间）放进一个堆，弹一个删一个，删完之后如果父节点变成了叶子且没人锁着，就把父节点也放进堆里。

# python/sglang/srt/mem_cache/radix_cache.py:606-616
while num_evicted < num_tokens and len(eviction_heap):
    _priority, x = heapq.heappop(eviction_heap)
    self.token_to_kv_pool_allocator.free_segment(x.value, start_pos=0)
    num_evicted += len(x.value)
    self._delete_leaf(x)
    if len(x.parent.children) == 0 and x.parent.lock_ref == 0:
        new_priority = self.eviction_strategy.get_priority(x.parent)
        heapq.heappush(eviction_heap, (new_priority, x.parent))

"只从叶子开始扔"这条规则有个免费的副作用：被越多请求共享的前缀，在树上离根越近，越不可能是叶子，于是越晚被扔掉。那段所有人都用的系统提示词会自然沉到最后才被淘汰，不需要谁去给它标一个"重要"的标记。vLLM 那边达到类似效果靠的是另一条路——所有人都在用的块，它的最后访问时间一直被刷新，在 LRU 队列里永远排不到前面去。

要追平得开到 131072——十六倍。这个数不是随便撞上的：四十个任务各自跑完最后一轮时的上下文加起来是 126856 个 token，131072 是扫描点里第一个大于它的。也就是说，交错顺序下，缓存必须同时装得下所有在途会话的全部上下文，少一点都不行。

机制并不复杂，但只有把它说到具体的量上才有用。成组顺序下，任务 t0 的第二轮紧跟在第一轮后面，中间没有别人，第一轮留下的块一个都没被挤掉。交错顺序下，t0 的第一轮和第二轮之间隔着另外 39 个任务的请求，这些请求要往缓存里塞进将近十万个 token 的块。LRU 是按"最久没碰"扔的，t0 的块在这十万个 token 涌进来的过程中一路往队首挪，等 t0 回来时早被扔光了。

这里有个词专门指这件事：一份数据被用过之后，到它下一次被用之前，中间来过多少别的数据，叫它的 复用距离（reuse distance）。缓存要能兜住一次复用，容量就得大于这次复用的距离。决定缓存够不够的，从来不是数据总量，是复用距离。

关键结论

"我们的缓存命中率只有三成"这句话，单独看什么信息都没有。它可能是流量本来就不共享（第 9 节第一行），可能是缓存开小了，也可能是缓存不小、但请求的到达顺序把每一次复用的距离拉得比缓存还长。三种情况该动的旋钮完全不同，其中第三种根本不在这台机器上。

第三种情况怎么办，是 Day 25 的整天题目——它牵扯到多机之间怎么分派请求，以及这么做会和负载均衡打架。今天只把它的价钱量出来：在这批负载上，它值五十二个百分点的命中率，或者十六倍的缓存容量。

但左边那一列告诉你这个结论有条件。共享系统提示词那一栏在 32 到 128 之间掉得很陡，从 67.6% 一路掉到 56.9%。手算一下就知道为什么：系统提示词 613 个 token，块 32 时能对上 19 块 608 个，块 64 时 9 块 576 个，块 128 时只有 4 块 512 个。共享的那一段总共才 613，丢掉 101 个就是丢掉六分之一。

所以这一笔账的大小，取决于"公共前缀有多长"和"块有多大"的比值，不取决于块本身。公共前缀是几千个 token 的 agent 场景，块开大了无所谓；公共前缀只有几百个 token 的场景，块开到 128 就开始伤筋动骨。

# vllm/v1/core/kv_cache_manager.py:252-258
# NOTE: When all tokens hit the cache, we must recompute the last token
# to obtain logits. Thus, set max_cache_hit_length to prompt_length - 1.
# This can trigger recomputation of an entire block, rather than just
# the single last token, because allocate_slots() requires
# num_computed_tokens to be block-size aligned.
max_cache_hit_length = request.num_tokens - 1

连带后果是：因为分配要按块对齐，少算一个 token 会导致最后一整块都得重来。所以表里的最后一行按重算 16 个 token 计，正好是一块。

第四部分 · 装不下的时候，往下一级放

13. 把 Day 15 那个二选一，扩成一级一级的阶梯

前面三部分默认缓存里的东西都在同一个地方。真实的服务不是：显存是最贵最小的一级，它装不下的东西，可以往 CPU 内存放，再装不下往 SSD 放。把 KV 从显存挪到下一级存着，这个动作叫 卸载（offloading）；这一整套按速度和容量排开的结构，叫 分级缓存（tiering），直接连着 GPU 的那一级叫 主层（primary tier），再往下的叫 次层（secondary tier）；把一段 KV 从下层搬回上层，叫 提升（promotion）。

每往下加一级，都要回答同一个问题，而 Day 15 已经把这个问题的形状给出来了：从这一级取回来，和干脆重算一遍，哪个便宜？当时是在"搬出去存着"和"扔掉重算"之间二选一，现在只是把"这一级"换成阶梯上的任意一层，式子一模一样。

P7 在同一个进程里量了两边。重算那一侧，用 P5 那副骨架喂 2048 列，除以 2048 得到每 token 2367 微秒。取回那一侧，量三种搬运：

第二列的单位是每秒多少个十亿字节，分子是搬动的字节数，分母是墙上时钟走过的秒数。第三列是把它换算到一个 token 上：Day 15 算过这套设定下一个 token 的 KV 是 65536 字节，除以速率就得到微秒数。

这台机器上两级都远比重算便宜，连读一次云硬盘都快 26 倍。反过来问更有用：搬运速率要慢到什么程度，取回才不如重算？把 65536 字节除以 2367 微秒，得到 27.7 MB/s。低于这个速率的存储，才轮得到"不如重算"。这台两核机器上的这个门槛低得离谱，任何一块盘、甚至一根网线都跨得过去。

但这个门槛完全是被"重算太慢"抬上去的。GPU 上重算一个 token 的成本要低三四个数量级，那个 27.7 MB/s 会跟着涨到几十 GB/s——于是同一道除法在那边给出的答案完全不同，这也正是温故第 1 题的落点。

14. 工业实现里，这条阶梯长什么样

vLLM 自带的卸载连接器把上面那条约束写在文档第一段：

# docs/features/kv_offloading_usage.md
Only the CPU primary tier has direct GPU access. Secondary tiers cannot
read from or write to GPU memory; all GPU<->secondary transfers are
staged through the CPU primary tier.

显存和 CPU 内存之间那条通道，在多数机器上是 PCIe（外设互连总线）——显卡插在主板上的那条槽，也是所有数据进出显卡的必经之路。它的带宽比显存自己的内存带宽低一到两个数量级，所以"往 CPU 内存卸载"这件事，贵的不是 CPU 内存慢，是这条路窄。

同一份文档的配置表里有两个默认值，比任何解释都能说明这条路有多窄。一个是 offload_prompt_only，默认为真，意思是只把 prompt 阶段产生的块往下卸载，生成阶段产生的一概不管。另一个是 store_threshold，意思是一个块要被查询到多少次，才值得花力气往下写。

两个默认值指向同一个判断：往下写是要花带宽的，而写下去的东西不一定有人来取。prompt 那部分块是公共前缀最可能出现的地方，值得写；一个用户这一轮生成出来的一百多个 token，多半再没有第二个人会用到，写下去就是白占那条窄路。

把这套东西做到极致的是 Mooncake，Moonshot AI 给 Kimi 用的服务平台。它的论文摘要里有一句话正好是这一节的总结：它"利用 GPU 集群里没被用起来的 CPU、内存和 SSD 资源，实现一个分离式的 KVCache 缓存"。论文报告在长上下文场景下吞吐相对基线最高提升 525%，真实负载上多接住了 75% 的请求。

这里要留意一件事：那 525% 不是"开了前缀缓存"带来的，Mooncake 同时还把 prefill 和 decode 拆到了两组机器上跑。两件事互相咬合，从这个数字里拆不出前缀缓存单独贡献了多少。页尾的专项深挖给了一段可以直接用的题目。

板块 3 · 动手任务

任务 A（必做，约 70 分钟）· 写一个能回答"我们该开多大缓存"的模拟器

目标是把第 10 节那个结论变成一个你自己跑过、改过的工具。分四步。

第一步：块 hash 链

先写出链本身。它是后面一切的基础，也是最容易写错的地方——错了不会报错，只会让命中率悄悄偏低。

import hashlib, pickle
NONE_HASH = hashlib.sha256(b"none").digest()

def chain(tokens, B):
    out, parent = [], NONE_HASH
    for i in range(0, len(tokens) - B + 1, B):     # 只对装满的块算，不足一块的尾巴不算
        parent = hashlib.sha256(
            pickle.dumps((parent, tuple(tokens[i:i+B])))   # 父 hash 和本块 token 一起喂
        ).digest()
        out.append(parent)
    return out

写完先验两件事：同一段前缀接两条不同尾巴，两条链从头连续相同的块数应该等于"前缀长度整除块大小"；改动前缀里任意一个 token，从它所在的那一块起，后面的 hash 应该全部变。跑出来不是这样，说明父 hash 没接上，往下的所有实验都不用做了。

第二步：加上缓存和 LRU

用 OrderedDict 就够了：查中一块就 move_to_end，插满了就 popitem(last=False)。查找必须是"从第 0 块起连续命中，遇到第一个不中立刻停"，不能跳过去接着找——链式 hash 保证了后面必然也不中，跳过去找是在浪费时间，而且如果你写成了"统计总共中了几块"，得到的数会比真实命中率高，还高得不明显，很难发现。

第三步：造三种负载

照 2.4 节那张参数表造，或者用你自己觉得更像的数。三种必须都有，因为第一种（完全不共享）是你的对照组：如果它跑出来的命中率不是 0，说明你的实现有 bug。

agent 那种要特别注意一点：一条请求要同时记住 prompt 和这一轮生成出来的 token，插缓存时插的是两者拼起来的序列，而下一轮的 prompt 必须包含上一轮生成的那一截原文。这一点写错了，命中会在每一轮的边界上断掉，你会得到一个偏低但看起来很合理的命中率。

第四步：扫两个变量

扫缓存容量，画出命中率曲线；然后把请求顺序从"按会话成组"改成"轮次交错"，再扫一遍。两条曲线之间的水平距离，就是你这批负载的复用距离。

验收标准

  • 独立请求那一组，任何容量下命中率都是 0.0%。
  • 共享系统提示词那一组，命中 token 总数应该等于 (请求数 − 1) × (系统提示词长度 // 块大小) × 块大小，能对上整数。对不上就是链或者查找写错了。
  • 交错顺序追平成组顺序的那个容量点，应该接近"所有会话最终上下文长度之和"。

常见坑

  • 把 token 存成 numpy 的整数标量。功能没错，但 pickle 会慢十几倍，扫一遍参数要等很久。存成 Python 的 int。
  • 缓存容量用"多少个 token"记，而块表用"多少块"记，两者换算时忘了除以块大小。表现是扫块大小的时候曲线形状很怪。
  • 命中率的分母写成了"prompt 加生成"。生成那部分不该进分母，进了之后所有命中率会被系统性压低。

任务 B（约 40 分钟）· 给你自己那个玩具引擎装上前缀缓存

Day 15 的任务 B 里你给引擎加了块池和抢占。现在给它加一层前缀缓存：

  • 请求放行之前先查一次最长命中前缀，命中的那些块直接挂到这条请求的块表上，引用计数加一，不重新分配。
  • 这条请求实际要算的 token 数从 prompt 长度减去命中长度。注意留最后一块要重算（第 12 节那段源码注释）。
  • 请求跑完之后，它的块引用计数减一，但不要立刻还回空闲池——带 hash 的块放到空闲队列尾部，不带的放队首，分配时从队首取。这就是 vLLM 那套 LRU。
  • 打三个数：前缀命中率、平均每步在跑几条、以及被前缀缓存救下来的 token 总数。

验收标准

  • 把同一批请求跑两遍（第二遍缓存是热的），第二遍的总步数应该明显少于第一遍。
  • 开缓存之后可用块数会比不开时"看起来"更少，因为跑完的块不再立刻回到队首——但抢占次数不应该因此上升。如果上升了，说明带 hash 的块在被真正需要时没被正确回收。

  • 第 13 节那个 27.7 MB/s 的门槛，换成你手上那张卡再算一遍：重算一个 token 的成本用它的标称算力和模型参数量估（一次前向大约 2 × 参数量 次浮点运算），搬运速率用实测的主机到显存拷贝速率。算出来的门槛是多少？你机器上的 SSD 跨得过去吗？
  • 把任务 A 的模拟器改成基数树，匹配粒度改到单个 token，淘汰改成"只从叶子扔"。用同一批负载跑，看命中率差多少。差得比你预期的小的话，想一想第 11 节那张表的最后一列在说什么。
  • 给任务 A 的负载加一种新流量：一批请求共享同一段很长的文档（比如 8000 个 token），每条问一个不同的问题。它的命中率天花板是多少？把它和"共享系统提示词"那一组比，两者的曲线在容量扫描上的形状有什么不同？

板块 4 · 工作现场

场景一：命中率从 80% 掉到 30%，代码一行没改

周一早上监控告警，前缀缓存命中率跌了一半多，首 token 延迟的 P99 跟着涨。查发布记录，服务端一周没上线了。

先分三种可能，这三种是互斥的，一个一个排除。

第一种，流量的共享结构变了。比如某个调用方给每条请求的开头拼了一个时间戳或者请求 ID——那一个 token 就能让整条 hash 链从第 0 块起全部作废。查法是抽样几条请求的 prompt，把它们的前 200 个 token 逐字对一遍。这类事故最常见，也最容易修。

第二种，缓存容量变小了。有人调低了给 KV 的显存比例，或者换了更大的模型使权重占得更多。查法是看引擎报的总块数有没有变。

第三种，容量和流量都没变，是并发涨了。这就是第 10 节那件事：同时在途的会话变多，每一次复用的距离被拉长，超过了缓存能兜住的范围。它的特征很好认——命中率和并发数的曲线反着走，而且是连续的、不是台阶状的。

场景二：产品问"我们把上下文从 8K 提到 32K，缓存还够用吗"

这个问题不能直接答够或不够，要先把它翻译成一个可以算的式子。

缓存要装的东西约等于"同时在途的会话数 × 每个会话的平均上下文长度"。上下文上限翻四倍，通常意味着平均上下文也跟着涨（虽然不会是四倍），于是分子涨。而 KV 那部分显存不变，能装的 token 数不变。两边一除，命中率会掉，掉多少取决于涨了多少。

要回答得靠谱，你需要向他们要一个数：会话的上下文长度分布，尤其是高百分位。平均值在这里会骗人——一条 32K 的会话，占的位置抵得上十六条 2K 的。

能给的缓解办法有三条：把长上下文的请求单独路由到一组机器（Day 25 的题目）；把 KV 往 CPU 内存卸载一层，用带宽换容量（第 13 节）；以及最直接的，把给 KV 的显存比例调上去，前提是激活值那边还有余量。

场景三：安全同事问"两个客户的数据会不会通过缓存串"

这个问题问得对，而且答案不是"不会"。前缀缓存是按内容匹配的，两个租户只要 prompt 的开头一样，就会命中同一批块。数据本身不会泄露——命中只是省了计算，返回的内容还是各算各的。但时间会泄露：攻击者可以构造一段 prompt，通过首 token 延迟明显变短，推断出"这段内容之前有人发过"。

vLLM 给的解法是每条请求可以带一个 缓存盐（cache salt），它被混进第一块的 hash 里，于是只有带同一个盐的请求才可能互相命中。文档里的原话是：

# docs/design/prefix_caching.md
By including a `cache_salt` in the request, this value is injected into
the hash of the first block, ensuring that only requests with the same
salt can reuse cached KV blocks. This prevents timing-based attacks where
an adversary could infer cached content by observing latency differences.

代价你现在能自己算：按租户下盐，等于把一个大缓存切成 N 个互不相通的小缓存。共享的系统提示词从"全体共用一份"变成"每个租户一份"，第 9 节那 67.6% 会按租户数被稀释。安全和命中率在这里是直接对冲的，怎么切要看你的租户模型——同一个公司内部的用户之间通常可以共享，跨公司通常不行。

同事和面试官常问的

「前缀缓存为什么只能匹配前缀，不能匹配中间任意一段相同的内容？」
从因果注意力答起：一个位置的 K 和 V 依赖它前面的全部 token，前面换了它就换了。所以两段内容相同但前文不同的 token，算出来的 KV 是两组完全无关的数——第 3 节那个 4.373 就是这个。补一句：正因为这个依赖是严格的，复用才是无损的，输出一个字都不会变。

「vLLM 和 SGLang 的前缀缓存有什么区别？」
别只答"一个用 hash 一个用树"。说清两个真实差别：匹配粒度上，hash 链只能对到整块，树能停在边中间；淘汰上，树只从叶子往上扔，于是被共享得越多的前缀越靠近根、越晚被扔，这是结构自带的，不需要额外策略。再补一句量级：在公共前缀足够长的场景，粒度这个差别不到一个百分点。

「开了前缀缓存要给它单独留多少显存？」
不用留。vLLM 的缓存就住在空闲块队列里——跑完的块不立刻擦掉，等到真的需要分配时才顺手作废。所以它是拿空闲容量白捡的，唯一的额外开销是每块一次 hash，一条 2048 token 的 prompt 是零点二毫秒量级。

「命中率 90% 了，为什么延迟没怎么降？」
先反问一句输出多长。前缀缓存只动 prefill，decode 一步都省不掉。输入几千输出一百的 agent 请求，省下来的能占端到端时间的大半；输入几百输出两千的写作请求，省下来的会被生成阶段完全淹没。这不是调优问题，是这个优化的作用域。

「怎么把命中率提上去？」
按顺序问三件事。第一，公共的东西是不是真的在最前面——把随请求变化的内容（时间戳、用户 ID、检索到的片段）挪到 prompt 后半段，能让前面那一大段变成稳定前缀。第二，缓存容量够不够装下所有在途会话的上下文。第三，同一个会话的请求是不是每次都落在同一台机器上。这三件事的杠杆一件比一件大，代价也一件比一件高。

板块 5 · 自检问题

1. 有人为了省内存，把系统提示词从 613 个 token 精简到 600 个，其他都没动，块大小是 128。命中率会怎么变？

会变好，而且好得不成比例——但方向和"精简"这个动作本身没关系。

613 除以 128 等于 4 余 101，能对上 4 块 512 个 token，剩下 101 个每条请求都要重算。600 除以 128 等于 4 余 88，还是 4 块 512 个，剩 88 个。所以这一改其实几乎没改善命中的绝对量，只是分母小了一点点。

真正有效的改法是把它精简到 512，或者反过来补到 640。640 除以 128 正好是 5 块，一个 token 都不浪费——加长反而比缩短更划算。这件事的一般形状是：公共前缀的长度对块大小的余数才是那笔损失，前缀本身多长不重要。

错在哪：把"内存省了"和"命中率高了"当成同一件事。这两件事在块边界这个问题上是脱钩的。

2. 你的服务命中率长期稳定在 62%。有人提议把给 KV 的显存比例从 0.85 调到 0.92，说缓存大了命中率就上去了。这个提议在什么情况下有效，什么情况下一点用都没有？

要先看命中率是被什么卡住的。第 10 节那两张表给出了两种完全不同的形状。

如果曲线已经压平了——也就是当前容量已经在天花板上——那再加容量一点用都没有。这时候 62% 是流量本身的上限，唯一能动的是流量的形状：把公共的内容挪到前面去，或者让同一个会话总落在同一台机器上。

如果曲线还在爬坡段，加容量就直接换来命中率。判断的办法很简单，不用改代码：把并发压到平时的一半再看命中率。如果明显上去了，说明你在爬坡段，是容量或者复用距离的问题；如果没动，说明你在天花板上。

错在哪：把容量当成命中率的唯一自变量。它只是三个自变量里的一个，而且往往不是最紧的那个。

3. 一条请求和十分钟前的某条一字不差地重复。它的首 token 延迟能降到接近零吗？

不能，有三个各自独立的原因，任何一个单独成立都足以让它降不到零。

第一，引擎故意留了最后一个 token 不给命中，因为采样下一个 token 需要最后那个位置的输出，而缓存里只存了 K 和 V。又因为分配要按块对齐，实际会重算最后一整块——块大小 16 时就是 16 个 token。

第二，十分钟是很长的时间。这条请求的块还在不在缓存里，取决于这十分钟里有多少别的请求挤进来过，也就是它的复用距离。多半已经被 LRU 扔掉了。

第三，就算全命中，请求还要排队、要等调度器把它放进某一个引擎步、要走网络。这些 Day 2 和 Day 9 都量过，它们不因为命中而消失。

错在哪：把"命中率 100%"读成"prefill 时间为零"。它只是"prefill 的 token 数降到一块"。

4. 两个团队共用一个推理服务。A 团队的请求平均输入 3000、输出 80；B 团队平均输入 300、输出 1500。缓存容量紧张，只能优先保住一边。保谁？

保 A，而且差距不小。

先看能省的绝对量：A 每条能省下来的是几千个 token 的 prefill，B 只有几百个，A 的分子本来就大一个数量级。

再看省下来的能不能变成用户感受到的时间。按第 12 节那张表的形状：A 是输入长输出短，省掉的 prefill 占端到端时间的大头；B 是输入短输出长，它的时间几乎全花在 decode 上，而 decode 一个 token 都省不掉——就算把 B 的命中率做到 100%，它的总时间也几乎不动。

还有第三层，容量这一侧也站在 A 这边吗？不一定。B 的输出长，意味着它每条请求占住的块更多、占的时间更久。所以"保住 A 的缓存"和"给 B 让出足够的运行内存"未必冲突，但需要分开看：缓存这件事优先 A，运行时的块预算是另一笔账。

错在哪：只比输入长度就下结论。要比的是"能省的量"乘以"省了之后占端到端时间的比例"，这是两个因子。

5. 你把服务从 vLLM 换到 SGLang，别的都没改，命中率从 84% 涨到 84.4%，但 P99 首 token 延迟变差了。可能是什么？

命中率那 0.4 个百分点符合预期：第 11 节那张表里，块大小 1（相当于逐 token 匹配）和块大小 16 之间，agent 场景就差这么多。粒度更细带来的收益，在公共前缀有几千个 token 的时候本来就微不足道。

延迟变差要另找原因，而且不该先怀疑缓存本身。一个值得先看的地方是：基数树的匹配不是只读的——匹配停在一条边中间时会触发节点分裂，改动树的结构。这意味着匹配这个动作要拿锁，而它发生在请求路径上。前缀分布很碎的流量会让分裂频繁发生。

但这只是一个假设，不是结论。换引擎同时换掉了调度器、批处理策略、采样实现和一堆默认参数，任何一个都可能是原因。正确的做法是先把两边的批处理参数对齐，再用 Day 3 那套采样剖析器看时间实际花在哪，而不是从"我换了缓存实现"倒推。

错在哪：拿一个只值 0.4 个百分点的改动，去解释一个明显的延迟回退。量级对不上的因果，通常是错的因果。

板块 10 · 今日五句话

合上这一页，用自己的话回答

1. 为什么两条请求能共用的一定是前缀，而不能是中间任意相同的一段？

2. 块 hash 链里，每一块的指纹为什么要把上一块的指纹装进去？如果不装，查找会变成什么样？

3. 同一批请求、同样的缓存容量，命中率能差五十多个百分点。差在哪个量上？

4. 一条请求的命中率做到 90% 之后，用户感受到的时间省了多少？这个问题还缺哪个输入才能回答？

5. 判断"从下一级取回来"还是"干脆重算"，要拿哪几个量做除法？为什么这个判断在 CPU 上和 GPU 上会翻方向？

逐句自查标准

第 1 句　如果写成"因为缓存是按前缀存的"，那是拿结论当理由。要答到因果注意力：一个位置的 K 和 V 依赖它前面的全部 token。可以补一个具体证据——前缀改一个 token，从那一位起后面全变，之前的一位不变。

第 2 句　如果只写"为了区分不同的块"，漏了最关键的一半。装进父指纹之后，"这一块在缓存里"这一个条件就等价于"从头到这一块的整段前缀都对得上"，于是查找从"逐个 token 比对每一条已有序列"变成一次哈希表查找，跟缓存里有多少条序列无关。不装的话，你得另外存一份"这一块的前文是什么"，才能确认匹配的是同一条路径。

第 3 句　答"到达顺序"只答了表象。要落到复用距离上：同一个会话的两次请求之间隔了多少别人的 token。成组顺序下这个距离接近零，交错顺序下它是另外 39 个会话的全部增量。缓存容量必须大于这个距离，命中才兑现得了。

第 4 句　缺的输入是输出长度。同样 90% 的命中率，生成 16 个 token 时端到端省七成多，生成 512 个时只省一成半。原因是前缀缓存只作用在 prefill 上。如果你答的是"缺机器配置"，方向不对——机器换了，两边同时变，比例大致不动。

第 5 句　四个量：每 token 的 KV 字节数、搬运速率、模型参数量、算力。前两个决定取回要多久，后两个决定重算要多久。翻方向的原因是算力和搬运速率在两种硬件上不成比例地变——GPU 的算力高三四个数量级，而它对外的通道是一条带宽有限的总线。只答"GPU 更快"不够，要说清楚是分子分母各自变了多少。
