Q1 · 1 天前（Day 9 · 调度与批处理）

输出长度全都一样的那一组里，连续批处理输给了静态批处理。它输在哪一笔账上？为什么这笔账的大小几乎不随输出长度变化，而赢的那一笔会变？

展开答案

输在 prefill 那一笔。定长那组里，static 做了 22 次 prefill、共 5.0 秒；continuous 做了 87 次、共 11.3 秒。

机制是这样：static 一次放行八条，八条的 prompt 挤进同一次矩阵乘法，512 MiB 的权重只被读一遍。continuous 是空一个补一个，每补一条就单独做一次 prefill，每次都要把权重再完整读一遍。所以它的额外开销正比于「放行了多少次」，而放行次数约等于请求条数——跟每条请求吐多少个字没关系。定长那组多花 6.3 秒，变长那组多花 8.9 秒，两个数差不多。

赢的那一笔是 decode。它省下来的是「空槽位」，而空槽位的多少完全取决于同一批里最长和最短差多少。定长时只省下 3.6 秒，变长时省下 26.9 秒，差了七倍多。

今天要用到这个思路的地方是：一个机制的代价和它的收益，往往由两个完全不同的量决定。今天量隔离开销的时候，同一件事会再出现一次。

Q2 · 3 天前（Day 7 · 内存层级）

指针追逐那个程序，工作集 512 MB 时顺序跳每次 8.32 纳秒、随机跳每次 216.22 纳秒。现在把页从 4 KB 换成 2 MB 的大页，其余一律不动。随机那一列会往哪个方向变、变多少？这个对照是用来排掉哪一个竞争解释的？

展开答案

基本不变。Day 7 在 256 MB 工作集上跑的那组大页数据是：顺序跳 5.8 ~ 8.0 纳秒，随机跳 161 ~ 169 纳秒，二十多倍的差距一点没缩小。

要排掉的竞争解释是：「顺序访问之所以快，是因为它连着走，地址翻译更省事，跟预取器无关。」换成 2 MB 的页之后，256 MB 的工作集只占 128 个页，TLB 完全装得下，翻译这条路上的压力基本消失了。差距还在，就说明差距不是翻译造成的，只能是预取器猜不猜得中造成的。

这里的方法比结论更值钱：想证明「A 导致了 B」，就找一个只关掉竞争解释、不动 A 的对照。今天量 seccomp 开销时会用同一招。

Q3 · 7 天前（Day 3 · 剖析器与火焰图）

一张 on-CPU 火焰图上，某个函数占了 99%。同一段时间 perf stat 报的 task-clock 是 4 秒，而程序总共跑了 20 秒。把这两个数放在一起，能推出什么？这个 99% 换算成真实时间是多少？下一步该做什么？

展开答案

task-clock 除以墙上时钟：4 ÷ 20 = 0.2。也就是这 20 秒里只有 4 秒真的在 CPU 上，剩下 16 秒线程是 S 状态，在等某件事。

on-CPU 火焰图只统计线程状态为 R 的那些样本，所以图上那个 100% 覆盖的只是这 4 秒。99% × 4 秒 ≈ 3.96 秒，占 20 秒的真实时间不到两成。

下一步不是去优化那个函数——最多只能省下两成。要转 off-CPU：py-spy record --idle 把等待也算进来，或者用 strace 看它到底卡在哪个系统调用上。

今天会把 strace 再拿出来用一次，但换一个用途：不是看它在等谁，是数它一共发了多少个系统调用。这个数字直接决定了今天第三把锁贵不贵。

1. 你现在会怎么隔离一段模型生成的代码

先把场景摆出来。你的 agent 让模型写了一段 Python，要在你的服务器上跑一下看结果。这段代码你没读过，也来不及读。

你是后端工程师，第一反应大概是这样几条：起一个子进程去跑，别在主进程里跑；给它一个超时，到点就 kill；用一个低权限的用户跑，别用 root；再把工作目录限制在某个临时目录里。

这几条都对，但它们全都建立在同一个假设上：这段代码会规规矩矩待在你划的范围里。而这个假设是错的，因为进程默认能看见的东西比你想的多得多。它能 ls / 看到你整台机器的目录结构，能读 /proc 里其他进程的命令行（里面常常带着数据库密码），能 connect 到内网的任何一台机器，能开一万个进程把机器压垮，能申请到内存耗尽为止。超时和低权限用户，一条都拦不住这些。

Linux 提供了三样专门的东西来管这三类问题。这三样彼此完全独立，各管一件事，谁也替不了谁：

要解决的问题Linux 提供的东西一句话
它能看见什么命名空间（namespace）给它一套自己的编号，别的编号它查不到
它能用多少控制组（cgroup，control group）给它一个额度，超了就限速或者杀掉
它能对内核说什么seccomp给内核入口挂一张名单，名单上的请求直接打回

这张表是今天全篇的骨架，后面三个部分依次是它的三行。把这三样东西装在一起、再配上一套自己的根目录，得到的东西就叫一个沙箱（sandbox）——一个让不受信任的代码跑起来、但跑不出去的执行环境。

先说清楚一件事，免得后面每一节都要提：这三样东西没有一样能挡住「内核自己有 bug」。这个缺口是第四部分的全部内容。

3. 第一把锁：把编号换掉

先讲现象，最后再给名字。

你的进程能看见别的进程，靠的是进程号。能看见别的网卡，靠的是内核里那张网络设备表。能看见 /etc，靠的是当前这套挂载点。这些「表」在内核里都是一份，全机器共用。

Linux 做的事很朴素：把这些表复制成多份，每份挂一个编号，然后规定每个进程只查其中一份。你的进程查的是 7 号表，别人的进程查的是 3 号表，两边的内容互不相干。查不到，就等于看不见。

这个「一份被复制出来的表加它的编号」就叫一个命名空间（namespace）。每个进程的每一类表各属于哪个编号，可以直接看出来：

# /proc/<pid>/ns/ 下面每个文件是一个软链接，指向 类型:[编号]
$ ls -l /proc/self/ns/
cgroup -> cgroup:[4026531835]
ipc    -> ipc:[4026531839]
mnt    -> mnt:[4026531832]
net    -> net:[4026531833]
pid    -> pid:[4026531836]
time   -> time:[4026531834]
user   -> user:[4026531837]
uts    -> uts:[4026531838]

八种类型，八个编号。man 手册 namespaces(7) 列的就是这八种，各自隔离的东西是：

mntCLONE_NEWNS挂载点
pidCLONE_NEWPID进程号
netCLONE_NEWNET网络设备、协议栈、端口
ipcCLONE_NEWIPCSystem V IPC 和 POSIX 消息队列（进程之间互相传消息的几种老机制）

八行里今天真正会动的是前五种。user 那一行值得单记一笔，因为它的权限规则和别的不一样：手册说「用 clone(2) 和 unshare(2) 创建新命名空间在大多数情况下需要 CAP_SYS_ADMIN 能力」，紧接着补了一句「用户命名空间是例外：从 Linux 3.8 起，创建用户命名空间不需要任何特权」。这句话在第三部分会变成一个具体的攻击动作。

能力（capabilities）是这里出现的新词：Linux 把过去 root 的那一大坨权力拆成了四十来个独立的开关，CAP_SYS_ADMIN 是其中管「系统管理类操作」的那一个。今天你会反复看到它，因为它几乎是所有隔离操作的入场券。

要让它看不到宿主的文件，得再做一步：把根换掉。这一步叫换根（chroot 是老办法，pivot_root 是容器实际用的那个），明天 Day 11 整段讲。今天你要带走的只是这个因果：开挂载命名空间不等于换根，它只是让你有资格改自己这份挂载表而不影响别人。

# 只换网络命名空间，不动挂载
$ unshare --net -- ls /sys/class/net

# 同时换挂载命名空间，并且重新挂一次 sysfs
$ unshare --net --mount -- bash -c 'mount -t sysfs sysfs /sys && ls /sys/class/net'

网络命名空间确实换了，网络也确实不通了。但 /sys 是一个挂载点，挂上去的那份内容还是进新命名空间之前的那一份，它显示的是旧网络命名空间的设备。换句话说，一个命名空间隔离出来的东西，可以通过另一个命名空间里的旧挂载漏回来。本节开头那张表的 B 列之所以对得上，是因为跑之前重新挂了一次 sysfs。

第二类：机器有多大，它还是照实说

/proc/cpuinfo 报 2 个 CPU，/proc/meminfo 报 8023 MB。这两个数是整台机器的，不是给你这个沙箱的。第二部分给它配上 CPU 配额之后，这两个数一个字都不会变——这一点先记着，第 14 节会拿实测数据把它钉死。

第三类：系统调用一个没少

最后一行是关键。探针在新的命名空间里再次调用 unshare(CLONE_NEWUSER)，成功了。也就是说，被关起来的这个进程，有能力自己再开一层命名空间。

再想一步：如果它能开用户命名空间，它就能在那层里拿到 root，然后用 root 去碰一些平时碰不到的内核代码路径。这条路是历史上多起逃逸（container escape）的起点——逃逸的意思是：本该被关住的代码，最终在宿主上执行了自己的指令。

而这条路命名空间和配额都堵不住，因为它既不是「看见了什么」，也不是「用了多少」，而是「向内核提了一个请求」。这需要第三把锁。

关键结论

命名空间管的是「查哪张表」。它把进程号、主机名、网络挡得干干净净，但它不换根、不改变机器自报的规格、也不减少一个可以发出的系统调用。把它当成一整套沙箱来用，是最常见的第一个错误。

5. 配额是怎么写下来的

「给这个沙箱半个 CPU」这句话，翻译成内核听得懂的形式，是什么样子？

你可能想到过两个办法。一个是 nice：调低优先级。但优先级只在抢不过来的时候起作用，机器空着的时候它照样能吃满，限不住。另一个是 taskset（Day 6 用过，把进程钉在某几个核上）。它能限，但粒度是整颗核，给不出「半个」。

真正的办法是 cgroup。它的接口是文件系统：建一个目录就是建一个组，往目录里的文件写数字就是设限，往 tasks 里写一个进程号就是把那个进程放进这个组。

# 建组
mkdir -p /sys/fs/cgroup/cpu/lab
# 设限：每 100000 微秒的窗口里，最多用掉 50000 微秒的 CPU 时间
echo 100000 > /sys/fs/cgroup/cpu/lab/cpu.cfs_period_us
echo  50000 > /sys/fs/cgroup/cpu/lab/cpu.cfs_quota_us
# 入组：把当前这个 shell 放进去，之后它 exec 出来的一切都跟着进来
echo $BASHPID > /sys/fs/cgroup/cpu/lab/tasks

把这两个数的单位拆开说清楚，因为这是今天最容易糊过去的地方。cfs_period_us 的单位是微秒，量的是墙上时钟走过多久，它划出一个个首尾相接的窗口。cfs_quota_us 的单位也是微秒，但量的是CPU 时间——这个组里所有线程占用 CPU 的时间加起来。

所以 50000 / 100000 的意思是：墙上时钟每走过 100 毫秒，这个组总共只能用掉 50 毫秒的 CPU 时间。用完了，这个窗口剩下的时间里它一步都不能走。这个「用完额度被停下」的动作叫节流（throttling）。

额度用完到窗口结束的这段时间，进程既没有在等 IO，也没有在等锁，它是被内核冻住的。这一点值得停一下：Day 3 那张 on-CPU / off-CPU 的表里，这种状态两边都不太好归类——它不在 CPU 上，但它等的不是任何一个具体的东西，等的是一个时钟。

v1 和 v2 的文件名对照

cgroup 有两代，文件名不一样。内核文档写得很直白：「和 v1 不同，cgroup v2 只有单一层级。」v1 是每个控制器一棵树（/sys/fs/cgroup/cpu、/sys/fs/cgroup/memory……各挂各的），v2 把它们合成一棵。今天这台机器上 cpu / memory / pids 都挂在 v1 上，所以实测数字全部来自左边那一列。

那 17.61 毫秒本身又是怎么来的？它比一个 10 毫秒的窗口还长，所以那一块活儿必然横跨了至少两个窗口、连着挨了两次冻结。窗口越密，一块活儿被切开的次数越多，但每一刀都很浅。

关键结论

CPU 配额里的两个数管的是两件不同的事。配额除以周期决定平均速度，周期本身决定卡顿的粒度。默认周期 100 毫秒，意味着任何被限了 CPU 的服务，天生就带着一个最长可达数十毫秒的规律性停顿——而这个停顿在中位数上完全看不见。

把这条接到你四周后的活上：一个 agent 的沙箱如果按默认周期限成半个 CPU，它执行的每段代码都会周期性地停几十毫秒。单看一次不要紧，但 agent 一轮要跑十几次工具调用，这些停顿会一次次叠进端到端延迟里。Day 2 算过一次同类的账：串行调用越多，尾部被放大得越厉害。

怎么禁掉一个系统调用，以及为什么这套机制永远读不懂「不许打开某个文件」

9. 在内核门口挂一张名单

一个进程想干任何一件超出自己内存范围的事，都得先问内核。那道门能不能装个人守着？

先把「问内核」这件事说具体。打开文件、发网络包、创建进程、映射内存——这些进程自己做不到，只能通过一个约定好的入口请内核来做。请求的形式是把一个号码放进寄存器，然后触发一条特殊指令。这个号码就是系统调用号（syscall number），每个功能一个固定的号，全系统统一。

这台机器上的头文件 asm/unistd_64.h 里定义了 373 个号，最大的一个是 461。数量级记住就行：三百多个入口，每一个都是内核里的一段代码。

既然请求都要经过这道门，那就在门口挂一张名单：来一个请求，看一眼号码，在名单上就打回，不在就放行。Linux 里这个机制叫 seccomp（secure computing mode）。名单本身用内核里那套通用的小程序格式写，叫 BPF，所以完整的说法是 seccomp-BPF 过滤器。

「打回」有好几种打法，内核文档列了这几种返回值：

返回值文档原文的意思什么时候用
SECCOMP_RET_ALLOW「系统调用被执行」名单之外的默认动作
SECCOMP_RET_ERRNO「返回值的低 16 位作为 errno 传给用户态，系统调用不执行」最常用。程序会以为自己权限不够，通常还能继续跑
SECCOMP_RET_KILL_PROCESS「整个进程立刻退出，系统调用不执行」确定不该出现的调用，直接了断
SECCOMP_RET_TRAP「内核向触发的线程发一个 SIGSYS 信号，系统调用不执行」把控制权交回用户态自己处理。第四部分会看到有人拿它做了很大的事
SECCOMP_RET_USER_NOTIF「往用户态的通知文件描述符上发一条消息」让另一个进程来裁决这次调用

今天用的是第二行，返回 EPERM。下面这段 C 程序把一张名单装上去，然后 exec 目标程序。exec 这个动作是「把当前进程正在运行的程序整个换成另一个，进程号不变」，而过滤器是挂在进程上的，所以它会跟着活到新程序里去——这正是它能用来包别人的原因。程序分三块：拼出 BPF 指令、装上过滤器、exec。

/* 第一块：拼指令。先核对架构，再逐个比对号码，命中就跳到最后那条 EPERM */
prog[i++] = BPF_STMT(BPF_LD|BPF_W|BPF_ABS, offsetof(struct seccomp_data, arch));
prog[i++] = BPF_JUMP(BPF_JMP|BPF_JEQ|BPF_K, AUDIT_ARCH_X86_64, 1, 0);
prog[i++] = BPF_STMT(BPF_RET|BPF_K, SECCOMP_RET_KILL_PROCESS);  /* 架构不对，直接杀 */
prog[i++] = BPF_STMT(BPF_LD|BPF_W|BPF_ABS, offsetof(struct seccomp_data, nr));
for (int k = 0; k < n; k++)
    /* 命中就往前跳 (n-k) 条，正好落在最后那条 EPERM 上 */
    prog[i++] = BPF_JUMP(BPF_JMP|BPF_JEQ|BPF_K, nrs[k], n - k, 0);
prog[i++] = BPF_STMT(BPF_RET|BPF_K, SECCOMP_RET_ALLOW);
prog[i++] = BPF_STMT(BPF_RET|BPF_K, SECCOMP_RET_ERRNO | (EPERM & SECCOMP_RET_DATA));

/* 第二块：装上。不加 NO_NEW_PRIVS 这一句，非特权进程根本装不了 */
prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0);
syscall(SYS_seccomp, SECCOMP_SET_MODE_FILTER, 0, &fprog);

/* 第三块：换成目标程序，过滤器跟着走 */
execvp(argv[2], &argv[2]);

有两行不是可选的，漏了会出事。

一行是 PR_SET_NO_NEW_PRIVS。文档写着：「使用之前，任务必须调用 prctl(PR_SET_NO_NEW_PRIVS, 1)，或者以其命名空间内的 CAP_SYS_ADMIN 特权运行。」它的字面意思是「我以后不再获得任何新权限」，作用是保证 exec 一个 setuid 程序（那种一执行就自动切换成文件属主身份的程序，sudo 就是）也不能借机提权——否则被关的进程只要找一个 setuid 的二进制就能绕出去。

另一行是最开头对架构的核对。文档专门点名了这个坑：「使用中最大的陷阱是只按系统调用号过滤而不检查架构值……永远检查 arch 值！」原因是同一个号码在不同架构下是不同的功能，32 位那套编号和 64 位这套完全对不上，不核对就等于名单形同虚设。

装上去跑一遍。272 是 unshare 的号，正是第一部分末尾那个堵不住的动作。返回值里的 errno=1 就是 EPERM，系统调用失败时的那个错误码，含义是「不允许这么干」：

$ ./seccomp_run 272 python3 -c "调用 unshare(CLONE_NEWUSER)"
unshare 返回 -1 errno= 1 Operation not permitted

$ ./seccomp_run 272 python3 -c "print(open('/hostmark.txt').read())"
宿主机的暗号-a7f3          ← 别的一切照常

第一把和第二把锁堵不住的东西，第三把锁一行名单就堵住了。回头看第 3 节引的那句手册：创建用户命名空间不需要任何特权，所以这个动作连能力那道关都不用绕——能拦住它的，只有名单。三把锁各管一件事，到这里凑齐了。

10. 它认号码，不认意思

接下来这个实验解释了为什么写 seccomp 名单是件专业活，而不是「把危险的调用列一列」那么简单。

打开一个文件在 Linux 上有两个入口：老的 open 是 2 号，新的 openat 是 257 号。功能上后者能干前者的一切。写一个程序，同一个文件走两个号各打开一次：

# 什么都不禁
open(2 号)        成功，读到: 宿主机的暗号-a7f3
openat(257 号)    成功，读到: 宿主机的暗号-a7f3

# 只禁 2 号
open(2 号)        失败 errno=1 Operation not permitted
openat(257 号)    成功，读到: 宿主机的暗号-a7f3        ← 同一个文件，照样打开了

名单挡住的是号码，不是「打开文件」这件事。你以为封了一扇门，其实旁边还有一扇。

那把 257 也一起禁掉呢？

$ ./seccomp_run 2,257 python3 two_doors.py
python3: error while loading shared libraries: libm.so.6:
         cannot open shared object file: Operation not permitted

连动态链接器都没走到 main 就死了。动态链接器是程序启动时负责把 libc 这类共享库找出来装进内存的那一步，而装共享库就得打开文件。这是写名单最真实的难处：禁得太少不管用，禁得太多程序起不来，中间那条线要靠对目标程序的实际了解来划。

更根本的一条限制在内核文档里：「BPF 程序不能解引用指针，这使得所有过滤器只能直接对系统调用的参数求值。」

把这句话翻译成后果。openat 的参数里，路径不是字符串本身，而是一个指向字符串的地址。过滤器拿得到那个地址的数值，但不能顺着它去看内容。所以下面这条规则，seccomp 永远写不出来：

# 想写的：
如果 系统调用 == openat 且 路径 == "/etc/shadow"  →  拒绝
# 能写的：
如果 系统调用 == openat  →  拒绝（不管打开的是什么）

这个限制不是偷懒，是有意的。文档给了理由：「BPF 使得 seccomp 的使用者不可能落入检查时刻与使用时刻（TOCTOU）攻击的陷阱，而这类攻击在系统调用拦截框架里很常见。」如果过滤器去读那个地址上的字符串，程序完全可以在过滤器读完之后、内核真正用它之前，从另一个线程把内容改掉——检查过的和用上的不是同一个东西。干脆不让读，这个漏洞就不存在。

所以要限制「能打开哪些文件」，得换一把锁：那是第一把锁配上换根要做的事，明天 Day 11 会做。三把锁不能互相替代，这是又一个具体例证。

11. 工业界的名单长什么样

你可能以为容器的默认名单是「只放行必要的几十个」。实际是反过来的。Docker 的文档说，默认配置文件「在 300 多个系统调用里禁掉了大约 44 个」，默认动作是 SCMP_ACT_ERRNO，也就是「造成一个 Permission Denied 错误」。

第二处，好几条理由都写着「本来也已由某个 CAP 把关」。这说明能力和 seccomp 是两道叠在一起的关卡，不是二选一：能力管「你有没有资格做这类事」，seccomp 管「这个号码准不准发出来」。工业实践是两道都上，任何一道漏了另一道还在。

13. 三把锁全上，启动贵了多少

沙箱和普通服务有个结构性差别：普通服务起一次跑一整天，沙箱是每来一段代码就起一个、跑完就扔。所以启动开销不是一次性成本，它乘在每一次调用上。

被杀那一行值得补一句机制。内存超限时进程不是收到 MemoryError，而是直接被 SIGKILL 打死（SIGKILL 是那个程序拦不住、也来不及善后的终止信号，kill -9 发的就是它）——这就是内核文档说的「在这个 cgroup 里触发 OOM killer」，也叫 OOM 杀手（OOM killer）。事后可以从计数器里读到确凿证据：memory.max_usage_in_bytes 停在 268435456，正好是上限；memory.failcnt 记了 181 次分配失败；memory.oom_control 里的 oom_kill 计到了 2。进程数那边同样有账：pids.peak 是 64，pids.events 里的 max 记了 2 次撞顶。

这里对你写 Python 服务有个直接后果：被 cgroup 限住的进程，捕获不到自己的死。try / except MemoryError 拦不住 SIGKILL。沙箱里跑的代码如果吃爆内存，你在容器内部写任何清理逻辑都不会执行，善后只能在外面做。

那三个一模一样的数字

最后三行——cpuinfo 报 2 个 CPU、os.cpu_count() 返回 2、meminfo 报 8023 MB——从 A 到 D 一个字没变，尽管 C 和 D 明明只有半个 CPU 和 256 MiB。

原因是这三个数都在回答「机器有多大」——前两个来自 /proc 里的硬件信息，第三个是 Python 转手问的同一件事——而 cgroup 限的是「你能用多少」。它从来没打算修改机器有多大这个事实。

要知道自己实际有多少，只能去读 cgroup 自己的文件：

# 在一个 50 毫秒 / 100 毫秒 的 cgroup 里问四个问题
os.cpu_count()         = 2          ← 机器有几个核
len(sched_getaffinity) = 2          ← 允许我跑在几个核上
nproc 会说：             2          ← 同上
配额 / 周期            = 50000 / 100000 = 0.5 个核    ← 这个才是真的

这是一个每年都要坑一批人的坑，因为几乎所有语言的运行时都默认读第一个数。线程池按 os.cpu_count() 开 2 个工作线程，而配额只够 0.5 个核，结果就是两个线程互相抢那半个核的额度，双双被节流，尾延迟直接翻番。今天的动手任务 A 会让你亲手做一遍这个换算。

15. 三把锁之上，还剩什么

名单禁掉 44 个、还开着 260 多个，这个「还开着」到底意味着多大的风险？

把前面几节的事实串起来看：沙箱里的进程查不到宿主的进程号、用不了超过额度的 CPU、发不出名单上的系统调用。但它剩下能发的那两百多个系统调用，走的是和宿主上所有别的程序完全相同的那一份内核代码。整台机器只有一个内核，沙箱里外共用。

所以只要那两百多个入口里有任何一个存在可以被利用的缺陷，被关起来的代码就有机会在内核里执行到不该执行的地方，进而拿到宿主的权限。这就是第 4 节提过的逃逸。三把锁都是在内核外面加约束，没有一把能修内核里面的 bug。

「一个系统能被外部输入触碰到的入口的总和」，这个概念叫攻击面（attack surface）。标准容器的攻击面，就是那两百多个系统调用背后的全部内核代码。这个面很大，而且它的大小不取决于你的沙箱写得多好。

缩小它只有两条路，业界两条都走了。

16. 两条更贵的路

第一条：换一个内核来接应用的系统调用

思路是在应用和宿主内核之间插一层：应用发的系统调用不再直达宿主内核，而是被一个跑在用户态的程序接住，由它自己实现这些系统调用的语义。这个程序就叫应用内核（application kernel）。Google 的 gVisor 是这条路上最有名的实现，它那个用户态内核叫 Sentry，官方文档描述它是「一个运行这些容器、并拦截和响应应用发出的系统调用的内核」。

安全模型是两层。gVisor 的文档写得很清楚：「第一，应用与宿主 System API 的直接交互被 Sentry 拦截，由 Sentry 自己实现这套 API。第二，Sentry 自身可访问的 System API 被最小化到一个更安全的受限集合。」也就是说应用碰不到宿主内核，而 Sentry 自己能碰到的部分被刻意削到很小——文档说它「只发出一个最小的宿主系统调用集合」，并且这个集合默认「不包括创建新 socket 或者打开文件」。

它靠什么拦截？这里有一个今天刚学过的东西的另一种用法。gVisor 现在默认的平台叫 Systrap，文档说它「依赖 seccomp 的 SECCOMP_RET_TRAP 特性来拦截系统调用。这会让内核向触发的线程发送 SIGSYS，从而把控制权交给 gVisor 来处理这个系统调用」。同一个机制，你用它返回 EPERM 来拒绝，gVisor 用它把请求转交给自己的内核。文档还提到 Systrap「在 2023 年中取代 ptrace 成为 gVisor 的默认平台」，而更早那个基于 ptrace 的平台「上下文切换开销很高，所以系统调用密集的应用要付出性能代价」。

代价写在文档里：「gVisor 对系统调用密集的负载可能提供较差的性能。」这和你在第 12 节量到的东西是同一类账，只是量级完全不同——你测到的是每次多花二十几纳秒，而这里是每次都要绕一趟用户态。

第二条：给它一个自己的内核

更彻底的做法是不共享内核：起一台真的虚拟机，里面跑一个独立的客机内核，应用的系统调用由那个内核处理，宿主内核只面对虚拟机这一个客户。

传统虚拟机太重，起一台要几十秒。所以出现了microVM：把虚拟硬件砍到只剩必需的几样，换来极快的启动和极小的内存开销。AWS 的 Firecracker 是这条路的代表，它的 README 说自己「排除了不必要的设备和面向客机的功能，以减小内存占用和攻击面」。规格文件里给了两个可以直接引用的数：「从收到 Firecracker 的 InstanceStart API 调用，到 Linux 客机用户态 /sbin/init 进程开始，耗时 ≤ 125 毫秒。」以及「Firecracker 的虚拟机管理器线程内存开销 ≤ 5 MiB。」跑虚拟机的那个程序叫虚拟机监视器（hypervisor / VMM）。

值得注意的是，Firecracker 自己也用今天这三把锁：README 里写着它有「高级的、按线程区分的 seccomp 过滤器」，还有一个叫 Jailer 的东西，「在生产场景下启动 Firecracker 时使用，它先施加一层 cgroup / 命名空间隔离屏障，然后放弃特权」。所以这不是「三把锁 vs 虚拟机」的二选一，而是虚拟机之外还套着三把锁。

Kata Containers 走的是把 microVM 接进容器生态的路。它的架构文档说，虚拟机里跑着一个用 Rust 写的常驻进程 kata-agent，并且它的架构「允许一台虚拟机里跑多个容器，以支持那些需要在一个 pod 里跑多个容器的容器引擎」——pod 是 Kubernetes 里一组总是被一起调度、共享网络的容器。它对自己的定位写得很直接：用硬件虚拟化技术提供「更强的工作负载隔离，作为第二道防线」。

关键结论

三把锁全部上齐，被隔离的代码仍然和宿主共用同一个内核。它们缩小的是「能做什么」，缩小不了「做的时候碰到的是谁的代码」。真正换掉那份代码，只有换一个用户态内核或者换一个客机内核这两条路，代价分别落在每次系统调用上和每次启动上。

第 1 步：确认你的机器上 cgroup 挂在哪一代

这一步必须先做，因为文件名不一样，做错了后面所有命令都会报「没有这个文件」。

# 有 cgroup.controllers 这个文件、且里面列着 cpu，就是 v2
cat /sys/fs/cgroup/cgroup.controllers 2>/dev/null
# 有 /sys/fs/cgroup/cpu/ 这个目录，就是 v1（今天这台机器是这种）
ls -d /sys/fs/cgroup/cpu 2>/dev/null

看到哪一种，后面就用哪一套文件名，第 5 节那张对照表可以直接查。

第 2 步：复现节流的形状

写一个循环，每做完一小块固定的活儿就记一次时间，把相邻两次的时间差收集起来。块要小到一个周期能装下十几块——4 到 5 毫秒是合适的量级，怎么标定见装置那节的参数表。

然后在三种设置下各跑一次：不限、半个 CPU 配默认周期、半个 CPU 配十分之一的周期。每次跑之前把 cgroup 目录删了重建，让计数器归零。

验收标准：三次的「占 CPU 时间」应该基本相同；后两次的总时长应该都是第一次的两倍左右；第二次的间隔中位数应该和第一次几乎一样，而 P99 高出一个数量级；第三次的 P99 应该明显低于第二次。最后用 cpu.stat 验一遍加法：总时长 ≈ 占 CPU 时间 + throttled_time。

第 3 步：写出「我到底有几个核」这个函数

这是今天最该带走的一段代码，因为它是你上岗后会真的写进项目里的东西。三个来源都读，取最小值：

import os

def quota_from_cgroup():
    """返回配额折算出来的核数；没有配额就返回 None。v2 和 v1 的文件名不一样，都试一遍。"""
    try:                                    # cgroup v2：一行两个数 "MAX PERIOD"
        raw = open("/sys/fs/cgroup/cpu.max").read().split()
        if raw[0] != "max":
            return int(raw[0]) / int(raw[1])
        return None
    except FileNotFoundError:
        pass
    # cgroup v1：两个文件分开放，而且当前进程在哪个组里要从 /proc/self/cgroup 里查
    line = [l for l in open("/proc/self/cgroup") if ":cpu," in l or l.split(":")[1] == "cpu"]
    if not line:
        return None
    path = "/sys/fs/cgroup/cpu" + line[0].rstrip().split(":", 2)[2]
    try:
        q = int(open(path + "/cpu.cfs_quota_us").read())
        p = int(open(path + "/cpu.cfs_period_us").read())
    except FileNotFoundError:
        return None
    return None if q < 0 else q / p         # -1 表示不限

def usable_cpus():
    candidates = [os.cpu_count(), len(os.sched_getaffinity(0))]
    q = quota_from_cgroup()
    if q is not None:
        candidates.append(q)
    return min(candidates)

第 4 步：命名空间和名单

用 unshare --pid --fork --mount --mount-proc --uts --ipc --net 起一个 shell，在里面数 /proc 下的数字目录、看主机名、试着连一个外网地址。然后确认你还是能读到宿主上的某个文件——这一条是今天最反直觉的事实，一定要自己看到。

seccomp 那部分把第 9 节那段 C 编译出来跑，禁 272 号，再确认别的功能没受影响。

常见坑

  • echo ... > cpu.cfs_quota_us 报 Invalid argument：v1 要求先写周期再写配额，而且配额不能小于 1000 微秒。顺序反了就会失败。
  • rmdir 那个 cgroup 目录报 Device or resource busy：里面还有进程。cat tasks 看看是谁，把它移回根组或者等它退出。
  • 没有 --fork，进程号那张表看着没生效：unshare 自己不会换到新的进程号命名空间里去，要下一个进程才行。
  • 加了 --pid 却没加 --mount-proc，/proc 里还是宿主那一堆：因为 /proc 是一个挂载点，进程号换了，挂载点没换。这和第 4 节那个「网卡从 /sys 里看还是宿主的」是同一件事。
  • usable_cpus() 返回 0.5，直接拿去开线程池会崩：实际用的时候外面要包一层，比如 max(1, round(usable_cpus()))。函数本身返回小数是对的，因为你有时需要知道「不足一个核」这个事实。
  • 编译 seccomp 那段报 offsetof 未声明：少了 #include <stddef.h>。

任务 B · 把配额扣到你自己的服务上（约 1 小时）

把 Day 1 那个最小服务重新起来（没留着的话，任何一个 FastAPI 服务都行），用你 Day 1 写的压测器打它，记下 P50 和 P99。这是基线。

然后做三件事：

  1. 把服务进程放进一个半个 CPU、默认周期的 cgroup，同样的压测再打一遍。
  2. 只把周期从 100000 微秒改成 10000 微秒，配额跟着按比例改成 5000，份额不变，再打一遍。
  3. 跑完之后读 cpu.stat，记下 nr_throttled 除以 nr_periods 的比例。

验收标准：三次的吞吐应该是第一次明显高、后两次接近；P99 应该是第二次最差、第三次介于中间。你要能用一句话说清楚第二次和第三次差在哪，而且这句话里不能出现「更快」「更慢」，只能出现「停顿的长度」和「停顿的次数」。

如果你的服务是 IO 密集的（大部分时间在等，Day 3 那套判断法），可能三次的 P99 差别都不大。这本身就是一个值得写下来的结论：配额限的是 CPU 时间，一个在等的进程不消耗配额。把这个现象记下来，Day 12 讲磁盘和网络配额时会接上。

加分题

  • 今天全程是单线程。开两个线程做同样的活儿，放进同一个半个 CPU 的组里，总吞吐会怎么变？间隔分布会怎么变？（提示：配额是整组共享的，两个线程会一起把额度烧完）
  • 如果你的机器是 cgroup v2，用 cpu.max 把第 7 节那张表重跑一遍，看 throttled_usec 和这里的 throttled_time 差多少个零。
  • 用 SECCOMP_RET_USER_NOTIF 代替 SECCOMP_RET_ERRNO 写一个过滤器：不直接拒绝，而是把请求转给另一个进程裁决。这是第 16 节那两条路的雏形。

上岗关联

场景一 · 沙箱里的代码「莫名其妙很慢」

用户反馈说同一段脚本，本地跑 2 秒，放进你们的代码执行沙箱要 8 秒。你上去测，平均每步的耗时和本地几乎一样，看不出问题。

今天这一页给了你下一步：读 cpu.stat，看 nr_throttled 占 nr_periods 的比例。如果接近 1，问题就是节流，而不是任何一行代码。要缓解，第一选择是减小周期而不是加大配额——加大配额要多花钱，减小周期是免费的。

场景二 · 线程池开得比配额还多

推理服务或者 agent runtime 部署到 K8s 上，配了 cpu: 500m（就是 0.5 个核）。服务里某个库按 os.cpu_count() 开了线程池，机器有 64 个核，于是它开了 64 个线程去抢半个核的额度。表现是 CPU 用量看着没超，延迟却高得离谱。

排查动作是第 14 节那三行：进程里同时打印 os.cpu_count()、len(os.sched_getaffinity(0)) 和配额除以周期，三个数不一致就是这个病。常见的元凶是 OpenBLAS、numpy、tokenizers 这类会自己开线程的库——Day 9 那套装置全程锁死 OPENBLAS_NUM_THREADS=1 就是为了避开这件事。

场景三 · 要不要为一个新客户上 microVM

产品要开放「用户上传代码并执行」。安全同事问你现在的容器方案够不够。

你的回答需要包含三层：第一，容器里那两百多个还开着的系统调用共用宿主内核，内核有洞就能逃；第二，可以选的两条路各自的代价——应用内核每次系统调用变贵，microVM 每次启动变贵（Firecracker 规格是 125 毫秒以内）；第三，这个选择取决于代码来自谁，自己团队的代码和用户上传的代码，要防的根本不是同一件事。

同事和面试官常问的

  • 「namespace 和 cgroup 的区别是什么？」——一个管看得见什么，一个管用得了多少。能补一句「它们完全独立，可以只开一个」会显得你真用过。
  • 「容器算不算虚拟机？」——不算，容器共用宿主内核，虚拟机有自己的客机内核。差别落在攻击面上。
  • 「seccomp 能不能限制某个进程只读某个目录？」——不能，过滤器不能解引用指针，看不到路径字符串。这件事要靠换根和挂载选项。
  • 「CPU limit 设成 0.5，服务会变成什么样？」——平均速度减半，但不是每步都慢一半，而是全速跑完配额再冻住，冻的长度上限是周期减配额。
  • 「容器里 free 和 nproc 为什么是宿主的数？」——它们读的是 /proc，报的是机器规格，跟 cgroup 无关。要看配额得读 cgroup 的文件。

自检问题

Q1 · 一个服务被限成 cpu.max = "20000 100000"。它每 30 毫秒要往外吐一个心跳包，超过 100 毫秒没吐就会被判定为掉线。这个服务会不会掉线？为什么？

会，而且是必然会，不是偶发。

配额 20000 微秒、周期 100000 微秒，也就是每 100 毫秒里最多用 20 毫秒的 CPU 时间。用完之后剩下的 80 毫秒被冻住，一步都走不了。

心跳是 30 毫秒一次，也就是说在被冻住的那 80 毫秒里，至少会错过两次心跳。第 8 节那个走查里量到的就是这个形状：50 毫秒配额配 100 毫秒周期时，一次冻结的平均长度实测 49.9 毫秒，正好是周期减配额。这里份额更小，一次冻结按同样的算法是 80 毫秒。

错在哪：如果你答「不会，因为它只需要 20% 的 CPU，够用」，那是把平均速度当成了瞬时速度。配额保证的是长期平均，不保证任何一个 100 毫秒窗口内的响应性。

怎么救：把周期改小，比如 "2000 10000"，份额一模一样还是 0.2，但一次最多只冻 8 毫秒，心跳就不会被卡住。

Q2 · 有人给沙箱写了一条 seccomp 规则：禁掉 openat，理由是「不让它读文件」。这条规则会造成什么后果？如果目的确实是限制它读哪些文件，正确的做法是什么？

后果是程序根本起不来。第 10 节实测过：把 2 号和 257 号一起禁掉之后，Python 连动态链接器那一步都过不去，报的是加载 libm.so.6 失败。因为加载共享库本身就要打开文件。

更根本的问题是这条规则的目的和手段错配了。seccomp 的粒度是系统调用号，它要么全禁要么全放，做不到「只禁某些路径」。内核文档说得很直接：BPF 程序不能解引用指针，所以过滤器拿得到路径参数的地址，却看不到地址上的字符串。

正确做法是换一把锁：用挂载命名空间加换根，让沙箱的根目录里根本不存在那些文件。看不见的东西不需要禁。这也是为什么三把锁必须配套使用——每一把都有它够不着的地方。

Q3 · 你把一个沙箱配成：五种命名空间 + 半个 CPU + 256 MiB 内存 + 64 个进程上限 + Docker 默认的 seccomp 名单。现在让它跑一段你完全不信任的代码。列出三件它仍然可能做到的事。

第一，读到宿主文件系统上的文件。命名空间不换根，第 4 节和第 14 节的探针在四种配置下都读到了宿主的标记文件。要挡住这一条必须再做换根。

第二，知道这台机器的真实规格。/proc/cpuinfo 和 /proc/meminfo 报的一直是整机的数，配额一个字都没改它们。这本身不算严重，但它意味着代码能推断出自己在什么样的机器上，也意味着任何按机器规格自动调参的库都会算错。

第三，对宿主内核发出两百多种系统调用。Docker 的默认名单只禁掉 300 多个里的 44 个左右。剩下的每一个都直达宿主内核，内核有洞就是逃逸的入口。

如果你只答出「还能耗尽磁盘」「还能打内网」，那也对，但那是配额没配全的问题，补上就行；上面三条是这套机制的结构性边界，补配置补不掉。

Q4 · 第 12 节量到装 seccomp 之后每次系统调用多花约 23 纳秒，而规则从 1 条加到 64 条看不出差别。为什么规则数不影响？这个「看不出差别」的结论，你怎么确认它不是因为测量精度不够？

规则数不影响，是因为多出来的开销主要是「进出过滤器这条路」的固定成本：内核在系统调用入口多了一次判断和一次 BPF 程序的调用。而 BPF 程序本身是几十条极简单的比较指令，跑在 CPU 上快到可以忽略——64 次整数比较连一纳秒都不到。

确认精度够不够，看的是同一档内部的波动和档与档之间的差距哪个大。无过滤器那一档五遍落在 253.6 到 258.3 之间，波动约 5 纳秒；有过滤器和无过滤器之间差了二十几纳秒，是波动的四五倍，所以「装了过滤器变慢」这个结论站得住。而 1 条、50 条、64 条这三档的范围互相重叠，差距小于各自的波动，所以只能说「测不出差别」，不能说「一定完全相同」。

这两种说法的区别很重要。前一句是结论，后一句是结论加上了测量精度的限制。写报告时把它们混为一谈，是很多性能结论后来被推翻的原因。

合上页面，用自己的话写五句

1 · 命名空间做到了「看不见」，它靠的是什么机制？为什么开了挂载命名空间之后还能读到宿主的文件？

2 · cpu.cfs_quota_us=50000、cpu.cfs_period_us=100000 这两个数，各自的单位分子和分母是什么？合起来是什么意思？

3 · 一个被限成半个 CPU 的程序，为什么间隔的中位数几乎不变而 P99 涨了十倍？想改善 P99 该动哪个数，动了之后总时长会变吗？

4 · seccomp 为什么写不出「不许打开 /etc/shadow」这条规则？内核给的理由是什么？

5 · 三把锁全上之后还剩什么没挡住？业界的两条应对路各自把代价付在了哪里？

逐句自查

第 1 句　机制要说到「内核里那张表被复制成多份，每份一个编号，进程只查自己那份」。第二问如果写成「因为没生效」就错了：它生效了，只是复制出来的那份挂载表内容和原来一模一样。要看不到宿主文件，得再做换根这一步。

第 2 句　两个都是微秒，但量的东西不同：周期量的是墙上时钟走过的时间，配额量的是这一组消耗的 CPU 时间。只写「50% 的 CPU」不算答对，因为那句话丢掉了周期，而周期正是第 3 句的答案所在。

第 3 句　要说出形状：全速跑满配额，然后被冻住到窗口翻页，所以一半以上的块跑得和不限时一样快，慢的全挤在被冻住的那几块上。改善 P99 要动周期而不是配额；周期变小之后总时长基本不变（实测 20.288 对 20.479），因为份额没变。如果你答「加大配额」，那是花钱解决问题，而且没回答为什么中位数不变。

第 4 句　因为过滤器不能解引用指针，路径是一个地址，它只看得到地址本身。内核给的理由是防 TOCTOU：如果允许过滤器去读那块内存，程序可以在检查之后、内核使用之前把内容换掉。只答「因为 seccomp 只认号码」对了一半，漏了「参数里的指针也读不了」这一层。

第 5 句　剩下的是共享同一个宿主内核，那两百多个还开着的系统调用背后是同一份内核代码。两条路：应用内核把代价付在每次系统调用上（gVisor 文档承认对系统调用密集的负载性能较差），microVM 把代价付在每次启动上（Firecracker 规格是 125 毫秒以内）。如果你写成「microVM 更安全所以更好」，那是漏掉了代价那一半。
