Q1 · 1 天前（Day 3 · 采样剖析器与 on-CPU 盲区）

你用 py-spy record 默认参数给一个服务录了 30 秒火焰图，图上最宽的是 epoll_wait，别的什么都看不出来。同事说"那说明服务挺健康的"。他这句话错在哪？你手上还有哪一条 30 秒内就能拿到的数据，可以立刻验证他是不是说反了？

展开答案

他把"on-CPU 火焰图上看不出东西"当成了"没有问题"。这两件事完全不同。

py-spy 默认只统计线程状态是 R（在 CPU 上跑）的那些样本，状态是 S（在等）的样本直接跳过不采。所以这张图回答的问题是"CPU 忙的时候在忙什么"，不是"时间花在哪"。如果一个服务九成时间在等，这张图会把那九成完全抹掉，剩下一成里最宽的那个函数被放大成主角。

图上最宽的是 epoll_wait，这本身就是信号：连"在 CPU 上"的那点时间都主要花在等事件上，说明真正在算的活儿少得可怜。

立刻能验证的数据：perf stat 输出里的 task-clock，除以墙上时钟走过的时间。这个比值就是"进程真正占用 CPU 的时间占比"。如果它只有 0.2，说明八成时间根本没在用 CPU，那就得走 off-CPU 方向。也可以直接加 --idle 重录一张，把等待中的栈也画进来。

今天要讲的，正是这条 off-CPU 路线上最常见的一种灾难，而且它是 Python 独有的。

Q2 · 3 天前（Day 1 · 全景与基线）

你在周报里写「服务平均延迟 30 毫秒」，leader 说这个数没意义，要看 P99。P99 = 200ms 逐字翻译成中文是什么？为什么平均值会掩盖问题？如果一个 agent 任务要串行调用这个服务 15 次，情况会更好还是更坏？

展开答案

P99 的逐字翻译：把这段时间内所有请求的延迟从小到大排成一队，站在 99% 那个位置上的请求，它的延迟是 200 毫秒。也就是每 100 个请求里有 1 个比 200 毫秒还慢。

平均值为什么掩盖问题，举个具体的数：99 个请求各花 10ms，1 个花了 2000ms。平均 = (99×10 + 2000) ÷ 100 = 29.9ms。周报上写"平均 30ms"，看起来非常健康，但确实有一个用户干等了 2 秒。平均值把这个人平摊没了。

第三问结论是更坏。单次不踩到慢请求的概率是 99%，串行 15 次一次都不踩到的概率是 0.9915 ≈ 86%，反过来至少踩到一次的概率 ≈ 14%。每 7 个 agent 任务就有 1 个会明显变慢。调用链越长，尾部延迟被放大得越厉害。

今天你会看到这条规律的一个极端版本：一个故障，它对中位数完全没有影响，只把尾巴掀翻——如果你的监控只有平均值和 P50，它在你面板上根本不存在。

核心讲解

1. 今天这一节要回答的问题

CPU 利用率只有 35%，机器看起来有的是余力，为什么有一部分用户要等好几秒？

昨天你学会了"看见"：用采样剖析器把时间的去向摊开。昨天最后留了个尾巴——CPU 没跑满但服务就是慢，这类问题在 on-CPU 火焰图上根本不会出现，得走 off-CPU 方向。

今天要拆的，就是这条路线上最常见、也最有 Python 特色的一种。它的现场长这样：

  • 监控面板上 CPU 35%，内存充裕，磁盘和网络都很闲。
  • P50 延迟看起来完全正常，跟平时一样。
  • 但每十个请求里就有一个要等一百毫秒以上，健康检查偶尔超时，告警在响。
  • 你把机器扩容一倍，情况只好了一点点。

这四条同时出现，几乎可以断定是同一件事。而它的根源，藏在 asyncio 的一个基本设定里。

2. 一个人的餐厅：事件循环是怎么回事

这一节回答：asyncio 凭什么能用一个线程同时招呼几百个请求？

先把机制说清楚，不然后面的实验读不懂。

Python 的异步框架（FastAPI、aiohttp，以及 vLLM 的 API 层）底下都是同一个东西：事件循环（event loop）。它只有一条性质需要你记住——它是单线程的。整个服务，同一时刻只有一个执行流在往前推进。

这听起来像个严重的限制，但它靠一个技巧绕开了。换成日常场景你就明白了。

想象一家餐厅只雇了一个服务员。他要招呼十几桌客人，怎么忙得过来？

关键在于他从不干等。走到 A 桌接下点单，把单子递进厨房——然后立刻转身去 B 桌，不在厨房门口等菜。接完 B 桌去 C 桌。等厨房喊"A 桌的菜好了"，他再回去端。

只要"等待"这件事可以交给别人（厨房），一个服务员就能同时服务十几桌。事件循环干的就是这个：网络包在路上飞的时候、数据库在磁盘上找数据的时候，这些等待都不需要 CPU，事件循环就趁这段时间去处理别的请求。

代码里，那个"立刻转身"的动作就是 await：

# await 做两件事，缺一不可：
#   一、发起这次网络请求
#   二、把控制权交还给事件循环
# 第二件才是关键。交还之后，事件循环才能去处理别人。
data = await http_client.get(url)

所以"异步"的本质不是"更快"，而是把等待的时间让出来给别人用。它对"在等"的活有效，对"在算"的活完全无效——因为算的时候没有等待可以让。

这里正好补一对贯穿今天的词。一段代码耗时，时间只有两种去处：

  • 在算。CPU 一刻不停执行指令，比如把大字典转成 JSON、算哈希、做矩阵乘。这叫 CPU 密集（CPU-bound）。给它更多核，它能同时干更多份。
  • 在等。CPU 什么都没干，在等外面回话，比如等数据库、等下游接口、等磁盘。这叫 IO 密集（IO-bound）。给它更多核完全没用，它本来也不用 CPU。

3. 服务员自己炒菜：一行没有 await 的代码

这一节回答：在 async def 里写一段普通的同步计算，会发生什么？

回到餐厅。假设有一道菜不用进厨房，服务员得在前台自己现做，做一次要 47 毫秒。

这 47 毫秒里，他招呼不了任何人。B 桌举手他看不见，C 桌想结账他没空，门口新来的客人在等位。整个餐厅停摆 47 毫秒。

代码里对应的就是这个：

async def handler(request):
    # 注意：这一行没有 await，它是普通的同步调用。
    # json.dumps 会一路算完才返回，中途一次控制权都不交还。
    body = json.dumps(big_object)      # ← 47ms，全程占着事件循环
    return body

这里有个特别容易踩的坑：函数签名写了 async def，很多人就默认它"是异步的"。async def 不会把同步代码变成异步的，它只是让这个函数有资格使用 await。函数体里那一行是同步的，就是同步的。

这个行为有个专门的名字，叫 阻塞事件循环（blocking the event loop）。

现在问题来了：这件事到底有多严重？严重到什么程度、伤害落在谁身上，这两点几乎所有人第一次都会猜错。所以先猜一下再往下看。

一个你八成会猜错的实验

实验很简单，上面用到的概念都讲过了。一个服务跑在 2 核机器上，有三个接口：

  • /await：里面写 await asyncio.sleep(0.048)。它在等，48 毫秒。
  • /block：里面写同步的 json.dumps(大对象)，实测算一次 47 毫秒。它在算。
  • /health：什么都不干，直接返回。它是"无辜路人"，正常情况下 1 毫秒以内就该回来。

压测方式：平均每秒 10 个请求打到 /await 或 /block，到达时刻随机。同时另开一个独立的进程，不定时地去探 /health，记录它的延迟。

先跟着算一笔账：一次请求占 47 毫秒，每秒来 10 个，也就是每秒有 470 毫秒被占用。一秒有 1000 毫秒。所以事件循环大约一半时间在忙，一半时间空着——听起来相当宽松。

4. 揭晓：中位数纹丝不动，尾巴被掀翻了

下面这张表对比 /await 和 /block。两边的请求速率一样、单次耗时一样，唯一的区别是那 47 毫秒在等还是在算。这样切是为了把"负载高低"这个变量彻底排除掉。

被压的接口/health P50/health P90/health P99
/await（在等）0.7 ms0.9 ms1.1 ms
/block（在算）0.8 ms76.3 ms199.3 ms

这张表要把 P50 和 P90 两列并排着看，单看任何一列都会得出错误结论。

P50 那一列：0.7 对 0.8。中位数完全没有反应，两种情况一模一样。

P90 那一列：0.9 对 76.3。差了 85 倍。

为什么中位数一点没动

回到刚才算的那笔账：事件循环大约一半时间被占着。

一个健康检查请求到达的时刻是随机的。它有大约一半的概率落在空闲窗口里，那它 1 毫秒就回来了，跟没有故障时一模一样。既然过半的请求都是这样，中位数当然就是"没事"的那个值。

这里可以精确一点：只要占用率低于 50%，P50 就基本不受影响。这个门槛非常具体，也解释了后面 22 rps 时会发生什么。

为什么尾巴会这么难看

另外那一半请求，撞上了正在执行的 json.dumps。它们必须等这一整次算完——没有任何办法插队，因为事件循环压根没在轮转。

撞进去的位置是随机的，所以还要等的时间大致均匀分布在 0 到 47 毫秒之间。粗算一下 P90：需要找到那个 v，使"等待超过 v"的概率等于 10%。

0.50 × (47 − v) ÷ 47 = 0.10　→　v ≈ 38 毫秒

模型给出 38 毫秒，实测 76.3 毫秒。量级对了，但偏低了一半。差在哪？模型假设"撞上时只需等当前这一次"。实际到达是随机的，会出现短时间内挤进来好几个请求的情况，健康检查前面排的不止一个。这部分排队正是 Day 2 讲的内容。

能算出量级、并说清模型少算了什么，比背下 76.3 这个数有用得多。

关键结论

只要负载还没超过容量，事件循环被阻塞伤害的是尾巴，不是中位数。
这直接决定你的监控怎么配。如果面板上只有"平均延迟"和"P50"，这类故障会完全隐形——面板一片绿，而每十个用户里有一个在等一百毫秒以上，健康检查在偶尔超时。这正好接上昨天 Q2 那道题：平均值把出事的那个人平摊没了。

5. 那把它扔到别的线程去？

这一节回答：问题定位到了——一段同步代码占着单线程的事件循环。最自然的解法管不管用？

既然罪魁是"它占着那唯一的线程"，最自然的想法就是：把它挪到另一个线程去跑，别占着主线程。

asyncio 确实提供了这个能力，叫 线程池外派（run_in_executor）：

from concurrent.futures import ThreadPoolExecutor
POOL = ThreadPoolExecutor(max_workers=4)

async def handler(request):
    loop = asyncio.get_running_loop()
    # 把 cpu_work 丢给线程池里的某个线程去执行。
    # 当前协程在这里 await —— 也就是交还了控制权，
    # 事件循环因此可以继续处理别人。看起来问题就解决了。
    n = await loop.run_in_executor(POOL, cpu_work)
    return n

看起来无懈可击。但这个办法有时候完全管用，有时候几乎没用，而且差别不在"活有多重"上。

要看清这一点，需要再加一组对照。下面把四种做法放在一起，两个维度交叉：

  • 维度一：怎么执行——同步执行在事件循环上，还是扔进线程池。
  • 维度二：干哪种活——两种都是纯计算，都用 C 扩展实现，都不碰网络和磁盘，而且单次耗时被调到几乎一样（json.dumps 实测 47.3 毫秒，hashlib.sha256 实测 50.5 毫秒）。

为什么必须这样交叉：如果只测"同步"和"线程池"两个格子，那不管出什么数字，都能编出一套解释。加上第二个维度之后，两组横向对比各自回答一个独立的问题。

做法/health P90/health P99
/await（基准：不做任何计算）0.9 ms1.1 ms
json.dumps，同步执行76.3 ms199.3 ms
sha256，同步执行81.7 ms217.0 ms
json.dumps，扔进线程池45.5 ms161.7 ms

这张表要横着比两次。

第一次，比第 2 行和第 3 行（都是同步执行）：76.3 对 81.7，基本一样。结论是——只要同步执行在事件循环上，干的是什么活完全无所谓，阻塞就是阻塞。

第二次，比第 4 行和第 5 行（都扔进了线程池）：1.1 对 45.5，差了 40 倍。sha256 那一行掉回到了 1.1 毫秒——和什么都不干的基准行（0.9）一模一样，问题被彻底解决了。而 json.dumps 只从 76.3 降到 45.5，问题基本还在。

两种活耗时几乎相同，外派机制完全相同，线程池配置完全相同。那差别只能来自这两种计算本身的某个性质。是什么性质？

6. GIL：差别就在这里

这一节回答：那个性质是什么，以及它为什么能决定线程池管不管用。

差别是 GIL（Global Interpreter Lock，全局解释器锁）。

CPython 解释器内部有一把全局的锁。规则只有一条：任何线程想执行 Python 字节码，必须先拿到这把锁。而一个进程里只有一把。所以哪怕你开一百个线程，同一时刻真正在跑 Python 代码的永远只有一个。

为什么要有这么个东西？因为 CPython 的每个对象内部都带一个引用计数，多个线程同时改同一个对象的计数会出错。用一把大锁把整个解释器保护起来，是最简单可靠的做法，代价就是牺牲了多线程并行。

关键在下面这一步。C 扩展在做那种不碰任何 Python 对象、纯粹啃一块连续内存的活时，它可以主动把 GIL 放开，算完再拿回来。这个动作叫 放开 GIL（release the GIL）。

现在回头看那两行数据，就全通了：

  • hashlib.sha256 对大块数据正是这么做的。它一放手，事件循环所在的线程立刻能拿到 GIL 继续干活。所以 /health 完全恢复。
  • json.dumps 全程都在读写 Python 的 dict、list、str 对象，它不能放开 GIL，只能一路握着算完。事件循环所在的线程虽然没有被自己的代码占住，但它拿不到 GIL，照样动不了。它只是从"被自己卡住"变成了"被别的线程卡住"，对外表现差不多。

所以线程池救不救得了，判据只有一条：

今天最实用的一条判据

把一段 CPU 密集的代码扔进线程池有没有用，只取决于它执行期间会不会放开 GIL。

  • 会放开：真正的 IO（读写文件、socket 收发）、time.sleep、以及一部分 C 扩展的重计算——hashlib、numpy 的大数组运算、压缩解压、图像编解码。扔进去有用。
  • 不放开：任何以 Python 对象为主要操作对象的代码——纯 Python 循环、json.dumps / json.loads、Pydantic 的校验与序列化、大量字符串拼接、正则匹配。扔进去基本没用。

这条判据对你四周后的岗位特别要命。推理服务和 agent 平台的响应里充满了大 JSON：工具调用的参数、整轮对话历史、流式返回的 token 批次。这些序列化每一次都是不放 GIL 的 C 调用。它们看起来不像"计算"，但对事件循环来说和一段死循环没有区别——而且扔进线程池也救不了。

/await 完成了 23.6 个/秒，跟得上目标。/block 只完成 21.3，跟不上 22。差的那部分不会消失，它堆在队列里。每秒差 0.7 个，压 20 秒队列就堆到十几个，最后到达的请求得等前面所有人算完——P99 就冲到了 4.1 秒。

但今天真正要看的变化是 /health 的 P50 从 0.8 变成了 192.3 毫秒。

为什么这次中位数守不住了？回到第 4 节那个门槛：10 rps 时占用率约 50%，所以有一半的空闲窗口可以接住健康检查。现在占用率超过 100%，空闲窗口消失了。任何时刻到达的请求都得排队，中位数自然也就崩了。

欠载时只有尾巴受伤，一旦过载，全体受伤。两者之间没有平滑过渡，只隔着"容量"这一条线。这正是 Day 2 讲的"利用率与 P99 的非线性关系"在 Python 单线程事件循环上的具体形态。

8. 怎么在线上把它测出来

这一节回答：线上你不知道哪一行代码有问题，用什么数字判断事件循环健不健康？

上面的实验里我们知道是哪个接口在捣鬼，因为服务是自己写的。线上没有这个信息，你需要一个不依赖任何业务知识的健康指标。

方法出奇地简单，而且和昨天的采样器是同一个思路：派一个哨兵进去，看它能不能按时回来。

具体做法：开一个后台协程，让它睡一小会，醒来后看实际过了多久。一切正常时它应该基本准时。如果它打算睡 50 毫秒、结果过了 98 毫秒才醒，那多出来的 48 毫秒就是它排队等事件循环的时长。

这个"实际睡了多久 减去 打算睡多久"的差值，叫 事件循环延迟（event loop lag）。

LAG = []

async def lag_monitor():
    rnd = random.Random(12345)
    while True:
        # 间隔必须随机。这个坑昨天见过一次：
        # 如果哨兵用固定周期，而负载也有周期性，两者会"对齐"——
        # 要么每次都恰好撞进阻塞窗口，要么每次都恰好躲开。
        # 那样测出来的是两个周期的相位，不是系统的性质。
        #（昨天 py-spy 用 99 Hz 而不是 100 Hz，是同一个道理。）
        iv = rnd.uniform(0.02, 0.08)
        t0 = time.perf_counter()          # 用 perf_counter：单调时钟，不会被系统改时间影响
        await asyncio.sleep(iv)
        LAG.append((time.perf_counter() - t0 - iv) * 1000)

装上之后，第一件要学的事是：这个指标的中位数是瞎的，别看它。

场景样本数均值P50P90P99
/await 10 rps（健康）· 25 秒6300.80 ms0.74 ms1.32 ms2.16 ms
/block 10 rps（欠载但阻塞）· 25 秒52011.32 ms1.02 ms41.15 ms89.91 ms
/block 22 rps（严重过载）· 20 秒162116.54 ms0.96 ms445.5 ms1957 ms

这张表先看 P50 那一列：0.74、1.02、0.96。三种情况几乎一模一样——哪怕第三行的服务已经烂到健康检查要等 192 毫秒。P50 在这个指标上完全没有诊断价值。

原因和第 4 节是同一个：探针大部分时候落在健康的时刻，中位数被那些健康样本占据了。所以要看均值、P90、P99——那才是有信号的地方。

9. 但这个指标还有一个更深的盲区

这一节回答：既然 P50 没用，那数一数"有多少个样本是坏的"，总该行了吧？

这是一个非常自然的下一步：既然中位数被健康样本淹了，那就统计超过某个阈值的样本占多大比例，比如超过 10 毫秒的占几成。这个指标看起来又直观又适合做告警。

结果它有一个很坏的性质：服务越糟，它给出的数字反而越小。

场景① 超 10ms 的样本占比② 累计滞后 ÷ 墙上时间
/await 10 rps（健康）0.0%2.0%
/block 10 rps（欠载但阻塞）27.5%23.5%
/block 22 rps（严重过载）21.6%94.4%

②的算法：把所有 lag 值加起来，除以实验时长。每一次 L 毫秒的滞后，意味着事件循环有 L 毫秒不可用，所以这个比值是"循环不可用时间占比"的下界。

看①这一列：10 rps 时是 27.5%，到了 22 rps 反而降到 21.6%。服务从"欠载但有点卡"恶化成"完全过载、健康检查要等 192 毫秒"，这个指标却往下走了。如果你的告警阈值配在 20%～25% 之间，它会在真正的灾难时刻停止告警。

再看②这一列：2.0% → 23.5% → 94.4%，单调上升，跨了两个数量级。而且 94.4% 这个数是对的——用第 7 节的数据验算一下：实际完成 21.3 个/秒 × 47.3 毫秒 = 1.008，正好是满载。

为什么①会低估

线索在上一节那张表的样本数那一列：健康时 25 秒采到 630 个样本，过载时 20 秒只采到 162 个。

原因是：事件循环卡住的时候，哨兵自己也跑不起来。它也是个协程，它也要排队等事件循环。一次持续两秒的卡顿，只会产生一个样本；而同样两秒的健康时段，会产生几十个样本。

于是探针系统性地漏采了它本该测量的那段时间。①是按样本加权的，所以被这个偏差扭曲；②是按时间加权的——一次两秒的卡顿贡献两秒，不管它只产生了一个样本。

这个毛病叫 采样偏差（sampling bias）。

你昨天已经见过它一次了。昨天那个 on-CPU 盲区，机制一模一样：采样器看到线程状态是 S 就跳过不采，于是"在等待"这件事在火焰图上一个样本都不剩。今天是同一个毛病换了张脸：探针在循环卡住时跑不动，于是"卡住"这件事在统计里被稀释。

共同的形状是：当你的观测手段和被观测对象共享同一个受损的资源时，它会在你最需要它的时候失灵。这条规律你会在这份材料里反复遇到，值得现在就记下来。

落到生产上怎么配

把事件循环延迟接进监控时，上报这两个，它们都是按时间加权的：

  1. 累计滞后总量（把 lag 值加起来）。等价做法是把均值和样本数一起上报，因为 均值 × 样本数 ÷ 时长 就是累计占比。
  2. 哨兵的实际执行次数。630 → 520 → 162。这个数掉下来，本身就是"循环忙到连哨兵都排不上队"的直接证据。指标停止上报，就是最强的告警信号。

10. 把今天的两件事分开记

这一节回答：今天讲的两个机制，各自负责解释什么？

今天最容易被搅混的地方，是把"阻塞事件循环"和"GIL"当成一件事。第 5 节那张 2×2 的表正好把它们分开了。

机制 A：阻塞事件循环机制 B：GIL
它决定什么同步代码会不会卡住整个服务把代码扔进线程池能不能救
根源asyncio 是协作式调度，单线程，靠协程主动交还控制权CPython 同一时刻只允许一个线程执行 Python 字节码
跟另一个有关吗无关。会放 GIL 的 sha256 同步跑，一样糟（81.7 对 76.3）无关。它跟 asyncio 没关系，写普通多线程程序一样撞上
如果 CPython 去掉 GIL还在，一点不变消失

这张表最该记住的是最后一行。假如哪天 CPython 真的去掉了 GIL（PEP 703 正在做这件事），机制 B 的问题会消失，机制 A 一点都不会变。Node.js 从来没有 GIL，社区里一样天天在说 don't block the event loop。

那到底该怎么修

今天的重点是"看见"，修的部分下周展开。但先把地图给你：

  1. 先量，再动。装上事件循环延迟哨兵，看累计滞后和执行次数。数字正常就说明问题不在这儿，别浪费时间。
  2. 看那段同步代码能不能变成真正的异步。如果它其实是 IO（用了 requests 而不是异步 HTTP 客户端、用了同步数据库驱动），换成异步版本就解决了，这是收益最高的一类。
  3. 如果它确实是计算，先想办法让它变快或变少。一次 47 毫秒变成一次 5 毫秒，尾延迟的伤害也跟着缩到十分之一。
  4. 判断能不能靠线程池：这段代码放不放 GIL。
  5. 把活挪出这个 Python 进程。这是绕开 GIL 的根本办法，因为 GIL 是每个进程一把的。代价是进程间传数据要序列化，而序列化本身又是不放 GIL 的活——所以它不是免费的。

动手任务

两个任务，一共约 2 小时。任务 A 是必做，纯标准库，不用装任何包。任务 B 把今天的哨兵装到你自己的服务上。

任务 A · 亲手复现"中位数是瞎的"（约 1 小时）

第 1 步：服务端

这个文件分四块：第一块准备两种计算原料；第二块是随机间隔的哨兵；第三块按路径分发到五种行为；第四块启动时先量一遍两种计算的耗时再开始服务。

用裸 asyncio 而不是 FastAPI，是为了让你直接看见事件循环，中间没有框架挡着。FastAPI 跑在完全相同的事件循环上，结论一样。

# d4_server.py
import asyncio, json, time, random, hashlib
from concurrent.futures import ThreadPoolExecutor

# ---- 第一块：两种计算原料 ----
random.seed(0)                       # 固定种子，保证你我的数据量一致
PAYLOAD = [{"id": i, "name": f"item-{i}",
            "vec": [random.random() for _ in range(16)],
            "meta": {"tags": ["a","b","c"], "ok": True}} for i in range(5000)]
BUF = random.randbytes(19_500_000)   # 大小要调到让 w_release() 的耗时贴近 w_hold()
hashlib.sha256(BUF)                  # 预热：把这块内存真实触碰一遍，避开首次缺页的开销

POOL = ThreadPoolExecutor(max_workers=4)
def w_hold():    return len(json.dumps(PAYLOAD))            # C 调用，全程持有 GIL
def w_release(): return len(hashlib.sha256(BUF).digest())   # C 调用，会放开 GIL

# ---- 第二块：事件循环延迟哨兵（间隔随机）----
LAG = []
async def lag_monitor():
    rnd = random.Random(12345)
    while True:
        iv = rnd.uniform(0.02, 0.08)
        t0 = time.perf_counter()
        await asyncio.sleep(iv)
        LAG.append((time.perf_counter() - t0 - iv) * 1000)

# ---- 第三块：处理请求 ----
async def handle(reader, writer):
    try:
        line = await reader.readline()
        if not line: writer.close(); return
        while True:                       # 把 HTTP 头读干净，否则下次读会串
            h = await reader.readline()
            if h in (b"\r\n", b"\n", b""): break
        path = line.split()[1].decode()

        if   path == "/block":      n = w_hold()
        elif path == "/block_rel":  n = w_release()
        elif path == "/thread":
            n = await asyncio.get_running_loop().run_in_executor(POOL, w_hold)
        elif path == "/thread_rel":
            n = await asyncio.get_running_loop().run_in_executor(POOL, w_release)
        elif path == "/await":
            await asyncio.sleep(0.048); n = 0   # 48ms，对齐 w_hold 的实测耗时
        elif path == "/lag":
            s = sorted(LAG)
            def q(p): return round(s[min(len(s)-1, int(len(s)*p))], 2)
            body = json.dumps({"n": len(s), "mean": round(sum(s)/max(1,len(s)),2),
                               "sum_s": round(sum(s)/1000, 2),   # 累计滞后，单位秒
                               "p50": q(.5), "p90": q(.9), "p99": q(.99)}).encode()
            writer.write(b"HTTP/1.1 200 OK\r\nContent-Length: %d\r\nConnection: close\r\n\r\n"%len(body)+body)
            await writer.drain(); writer.close(); return
        else:
            n = 0                                     # /health 走这里，什么都不做

        body = b'{"ok":true,"n":%d}' % n
        writer.write(b"HTTP/1.1 200 OK\r\nContent-Length: %d\r\nConnection: close\r\n\r\n"%len(body)+body)
        await writer.drain()
    except Exception:
        pass
    finally:
        try: writer.close()
        except: pass

# ---- 第四块：启动 ----
async def main():
    # 对照的前提是两种活耗时相当。而 sha256 的速度取决于当天这台机器的
    # 内存带宽，同一台机器不同时段可能差好几倍。所以每次启动都现场量一遍。
    for f, name in ((w_hold, "w_hold  (json.dumps, 不放 GIL)"),
                    (w_release, "w_release(sha256,     放 GIL)")):
        for _ in range(3): f()
        xs = []
        for _ in range(5):
            t = time.perf_counter(); f(); xs.append((time.perf_counter()-t)*1000)
        xs.sort()
        print(f"  {name}: {xs[len(xs)//2]:.1f} ms  (范围 {xs[0]:.1f}~{xs[-1]:.1f})", flush=True)

    _t = asyncio.create_task(lag_monitor())   # 用变量接住，否则任务可能被 GC 掉
    srv = await asyncio.start_server(handle, "127.0.0.1", 8848, backlog=512)
    print("listening 8848", flush=True)
    async with srv:
        await srv.serve_forever()

asyncio.run(main())

跑起来该看到什么：先打印两行实测耗时，然后 listening 8848，然后卡住等连接。先检查那两行数字是不是接近——差超过 20% 就调 BUF 的字节数把它们拉平，否则第 5 节那个对照根本不成立。

第 2 步：压测端

这是一个开环压测器：按预定时间表发请求，不管上一个有没有回来。两个细节写在注释里，都是很容易搞错的地方。

# d4_load.py
import asyncio, time, sys, random

async def one(path, t_intended, results):
    now = time.perf_counter()
    if t_intended > now:
        await asyncio.sleep(t_intended - now)
    start = t_intended     # ← 从"计划发出的时刻"起算，不是从"实际连上"起算。
                           #   服务卡住时连接本身就建不上，那段干等也必须算进延迟
    try:
        r, w = await asyncio.open_connection("127.0.0.1", 8848)
        w.write(f"GET {path} HTTP/1.1\r\nHost: x\r\nConnection: close\r\n\r\n".encode())
        await w.drain(); await r.read(); w.close()
        results.append((time.perf_counter() - start) * 1000)
    except Exception:
        results.append(float("nan"))

async def run(path, rps, secs):
    rnd = random.Random(99); results = []; t0 = time.perf_counter()
    ts, t = [], 0.0
    for _ in range(int(rps * secs)):
        t += rnd.expovariate(rps)   # 指数间隔 = 随机到达。
                                    # 如果用均匀节拍，每个请求都来得刚刚好，几乎测不出排队
        ts.append(t0 + t)
    await asyncio.gather(*[asyncio.create_task(one(path, x, results)) for x in ts])
    ok = sorted(x for x in results if x == x)   # x == x 用来滤掉 nan
    def p(q): return ok[min(len(ok)-1, int(len(ok)*q))]
    wall = time.perf_counter() - t0
    print(f"  {path:12s} P50={p(.5):8.1f} P90={p(.9):8.1f} "
          f"P99={p(.99):9.1f} 实际速率={len(ok)/wall:5.1f}/s")

if __name__ == "__main__":
    asyncio.run(run(sys.argv[1], float(sys.argv[2]), float(sys.argv[3])))

第 3 步：探针（必须是单独一个进程）

这一条不是可选的。如果把探 /health 的代码和压测代码放进同一个进程，探针会被压测任务自己拖慢，测出来的延迟里有一大截是客户端自己的排队，跟服务端一点关系都没有。

# d4_probe.py —— 单独一个进程跑，不要和 d4_load.py 合并
import asyncio, time, sys, random, json
async def main(dur):
    rnd = random.Random(7); out = []; end = time.perf_counter() + dur
    while time.perf_counter() < end:
        t = time.perf_counter()
        try:
            r, w = await asyncio.open_connection("127.0.0.1", 8848)
            w.write(b"GET /health HTTP/1.1\r\nHost: x\r\nConnection: close\r\n\r\n")
            await w.drain(); await r.read(); w.close()
            out.append((time.perf_counter() - t) * 1000)
        except Exception: pass
        await asyncio.sleep(rnd.uniform(0.02, 0.08))   # 抖动，避免和负载对齐
    s = sorted(out)
    def q(p): return round(s[min(len(s)-1,int(len(s)*p))], 1)
    print(json.dumps({"n": len(s), "p50": q(.5), "p90": q(.9), "p99": q(.99)}))
asyncio.run(main(float(sys.argv[1])))

第 4 步：跑

# 终端 1：起服务。每换一个端点都要重启，否则 LAG 会累加，污染分位数
python3 d4_server.py

# 终端 2：先起探针，再起压测
python3 d4_probe.py 25 &
python3 d4_load.py /block 10 25

# 压完看事件循环延迟
curl -s localhost:8848/lag

# 重启服务，把 /block 依次换成：/await  /block_rel  /thread  /thread_rel
# 最后跑一次过载：python3 d4_load.py /block 22 20

验收标准：

  • 服务启动打印的两个耗时相差 20% 以内。差太多先调 BUF。
  • 五种情况下 /health 的 P50 全部在 1 毫秒左右。亲眼确认一遍中位数是瞎的。
  • /block 和 /block_rel 的 /health P90 接近（几十毫秒量级）。
  • /thread_rel 的 /health P90 回到个位数毫秒，/thread 明显回不去。
  • 过载那一次，/health 的 P50 也崩了，同时 /lag 返回的 n 大幅下降、sum_s 接近实验总时长。

常见坑：

  • 换端点忘了重启服务：LAG 一直累加，上一轮的数据会污染这一轮。
  • 探针和压测器合并了：会测出一个漂亮但完全错误的 P50。
  • 用了 time.time() 测延迟：它会被 NTP 校准往回拨，你可能量出负数。一律用 time.perf_counter()。
  • BUF 大小写死后就不管了：sha256 的速度取决于内存带宽，同一台机器不同时段可能差几倍。每次跑之前看一眼启动打印的那两行。
  • 核数太少：压测器和服务会互相抢 CPU，绝对数值会偏大。先 nproc 看看。结论方向不受影响。

任务 B · 装到真实服务上，并抓一次现场（约 1 小时）

把 Day 1 那个最小服务（或任何一个 FastAPI 服务）跑起来，做三件事。

① 把哨兵装进去。把上面 lag_monitor 那二十行抄进你的服务，在启动事件里挂上。压测 30 秒，看 sum_s ÷ 30 是多少。健康的服务这个比值应该在 5% 以下。

② 打开 asyncio 的调试模式，让它自己告状。asyncio 内置了一个检查：某个回调执行超过 100 毫秒就打警告。

# -W default 让警告都打出来，不被默认过滤规则吃掉
PYTHONASYNCIODEBUG=1 python3 -W default your_server.py

你会看到类似 Executing <Task ...> took 0.152 seconds 的警告，后面跟着协程名字和文件行号——直接把嫌疑人指出来了。如果什么都没出现，说明单次阻塞没到默认阈值 100 毫秒，在启动代码里加一行把阈值调低：asyncio.get_running_loop().slow_callback_duration = 0.02。

③ 用昨天的 py-spy 抓现场，看 GIL 长什么样。这一步能把今天的第 6 节变成你亲眼看到的东西。

py-spy dump --pid <PID> --nonblocking          # 打印所有线程当前的 Python 调用栈

拿任务 A 那个服务做对照，连打几次 dump：

  • 压 /block 时，栈顶反复落在 json.dumps 附近，而且是在 MainThread 上。
  • 压 /thread 时，栈顶转移到了 ThreadPoolExecutor-0_x 这样的工作线程上，主线程看起来很闲，但服务依然慢。这一幕就是 GIL 的可视化。
  • 再压 /thread_rel，栈顶同样在工作线程上，但这次服务是好的。说明"栈顶在哪个线程"本身判断不了好坏，还得看那段代码放不放 GIL。

如果 py-spy 报 permission denied，回到 Day 3 第 1 步的 ptrace 权限那一节。

上岗关联

推理服务的网关层。vLLM、SGLang 前面都有一层 Python 写的 HTTP 服务，负责收请求、校验参数、拼 prompt、按 SSE 流式吐回结果。模型计算在别处，但这一层一卡，所有请求都被拖累，而你在 GPU 监控上完全看不出问题。流式返回尤其危险：每吐一批 token 就要序列化一次，高并发下每秒几千次，每一次都是不放 GIL 的 C 调用。

Agent 运行时（阶段三你要自己造一个）。Agent 的上下文越滚越大，每一轮都要把整个上下文序列化一次发给模型。上下文从 4K token 涨到 100K token，一次可能要几百毫秒，这期间同进程的其他会话全部停摆。而且这类负载天然是"少数请求特别大"，正好命中今天讲的尾延迟形态。

Sandbox 服务（阶段四）。沙箱执行完代码要把 stdout 收回来。如果某个用户的程序打印了 50 MB 输出，你在异步处理函数里对它做一次字符串处理或 JSON 编码，整个调度服务卡住好几秒。一个用户就能拖垮所有用户，这既是性能问题也是可用性问题。

面试和同事常问的四道题，今天的内容正好覆盖：

  • "服务 CPU 才 40%，P99 却两秒，你怎么查？"——先量事件循环延迟判断是不是被阻塞，正常的话再走 Day 3 的 on-CPU / off-CPU 分流。
  • "Python 有 GIL，还能做高性能服务吗？"——想听你能区分 IO 密集和 CPU 密集，并且知道 GIL 只锁 Python 字节码、不锁放开了 GIL 的 C 扩展。
  • "这段代码我扔线程池了，为什么还是慢？"——想听"放不放 GIL"这个判据，最好能举 json.dumps 和 hashlib 的对比。
  • "你们的延迟监控看哪几个指标？"——如果你能说出"事件循环延迟不能看 P50，也不能只看超阈值比例，因为探针在卡住时采不到样"，这个回答会非常扎实。

自检问题

1. 同样是"一次 47 毫秒的活"，为什么 /await 完全没事，/block 却把 P90 抬到 76 毫秒？两者对事件循环做的事，差别在哪一个动作上？

差别只在一个动作：有没有把控制权交还给事件循环。

await asyncio.sleep(0.048) 做的是：登记一个 48 毫秒后的闹钟，然后立刻把控制权还给事件循环。这 48 毫秒里事件循环是自由的，可以去处理健康检查、可以接新连接、可以推进别的请求。所以哪怕同时有 100 个请求在"等"，它们也只是 100 个闹钟，互相不挡道。

json.dumps(big_object) 做的是：一路算完才返回。这 47 毫秒里没有任何一个时刻控制权回到事件循环手上。事件循环不是"忙"，是压根没在运行——它被困在这个函数调用的栈里出不来。

所以关键不是"耗时多久"，而是"这段时间里事件循环能不能转"。这也解释了为什么 async def 这个签名毫无保护作用：它只是让函数有资格写 await，至于你写不写，它管不着。

2. 函数 def embed(texts) 里用 numpy 做大矩阵运算，单次 200 毫秒。同事说"扔 run_in_executor 就行"。你同意吗？如果换成 def render(data)，里面是纯 Python 的字符串模板拼接，同样 200 毫秒，答案还一样吗？

答案不同，但判据是同一条：这段代码执行期间放不放 GIL。

embed：倾向同意，但必须验证。numpy 做大数组运算时，底层是 C / BLAS 在啃一块连续内存，不碰 Python 对象，通常会放开 GIL。那它就属于今天表里 sha256 那一行。

为什么必须验证？numpy 不是所有操作都放。小数组运算里函数调用和对象开销占大头；用了 Python 层循环或 np.vectorize 包装的也会退化成不放。验证方法就是今天这个对照的缩小版：把它当作 w_release 塞进任务 A 那个服务，看 /health 的 P90 会不会回到基准线。回去了，就是放了。

还有一个坑：BLAS 自己通常也开多线程。外面开 4 个线程、里面每个再开 8 个，会开出几十个线程互相抢核，反而更慢。用 OMP_NUM_THREADS 之类的环境变量把里层线程数固定住。

render：不同意。纯 Python 字符串拼接每一步都在执行 Python 字节码、创建销毁 str 对象，全程需要 GIL。它属于 json.dumps 那一行——今天实测 /health P90 只从 76.3 降到 45.5，问题基本还在。

所以 render 的正确方向是：让它变快（换模板引擎、少拼一点），或者挪到别的进程去。

3. 某团队把事件循环延迟接进了监控，告警配的是"超过 10 毫秒的样本占比大于 20% 就报警"。这比只看 P50 强多了。但它仍然有一个致命问题，是什么？

致命问题是：这个指标在服务最糟的时候反而会下降，于是告警会在灾难时刻自己关掉。

看今天的实测：10 rps（欠载但阻塞）时"超 10ms 占比"是 27.5%；22 rps（严重过载、循环 94% 不可用）时反而降到 21.6%。服务烂了四倍，指标却往下走。阈值配在 20%～25% 之间的话，它会正好在最需要报警的时候低于阈值。

原因是这个指标按样本加权，而样本本身被采样偏差扭曲了：循环卡住时哨兵跑不起来，一次两秒的卡顿只产生一个样本，同样两秒的健康时段产生几十个。样本集被健康时刻主导。今天实测样本数从 630 掉到 162，就是这个效应的直接证据。

改法是换成按时间加权的指标：

  • 累计滞后 ÷ 时长：2.0% → 23.5% → 94.4%，单调，跨两个数量级，而且 94.4% 和理论满载值 1.008 吻合。
  • 哨兵执行次数相对基线的降幅：630 → 520 → 162。指标本身停止上报，就是最强的告警信号。

更一般的教训：当你的观测手段和被观测对象共享同一个受损资源时，它会在你最需要它的时候失灵。昨天 on-CPU 火焰图看不见等待，是同一个毛病的另一张脸。

4. 假如 CPython 明天就去掉了 GIL，今天第 5 节那张表里的四行，各自会怎么变？

逐行问一个问题就行：这一行的毛病属于机制 A 还是机制 B？

json.dumps 同步执行：完全不变，还是那么糟。它的问题是机制 A。同步代码占着单线程的事件循环不交还控制权，这跟别的线程能不能同时跑 Python 代码毫无关系。哪怕一个进程里一百个线程都能并行，这一个事件循环该卡还是卡。

sha256 同步执行：完全不变。它本来就是会放 GIL 的活，却依然糟（81.7）——这正是它在表里存在的意义：证明机制 A 和 GIL 无关。

json.dumps 扔线程池：会大幅改善，接近 sha256 那一行。它的问题是机制 B。GIL 一去掉，工作线程和事件循环所在的线程就能真的同时跑。

sha256 扔线程池：基本不变，它本来就已经好了（P90 = 1.1，等于基准线）。

一句话总结：去掉 GIL 消灭的是"线程池救不了你"，消灭不了"不要阻塞事件循环"。Node.js 从来没有 GIL，社区里一样天天在说 don't block the event loop。

合上这一页，不看笔记

想象你要把今天这块讲给一个刚入职的同事听。他 Python 写得很熟，但从来没做过性能相关的工作。用五句话讲给他听，每句都要是完整的中文句子，不能只写关键词。

第 1 句——事件循环是单线程的，它凭什么还能同时招呼很多请求？

第 2 句——一行没有 await 的同步代码，会对整个服务做什么？

第 3 句——这种故障为什么在 P50 上完全看不出来，只有尾巴受伤？

第 4 句——同样是纯计算，为什么有的扔进线程池就好了，有的扔了没用？

第 5 句——事件循环延迟这个指标，为什么"坏样本占比"是个陷阱？

自查标准

  • 第 1 句如果没提到"把等待的时间让出来给别人用"，回去重读第 2 节那个餐厅的例子。
  • 第 2 句如果写成"会让服务变慢"，太软了。准确的说法是：这段时间里事件循环压根没在运行，所有其他请求一步都推进不了。
  • 第 3 句如果写成"所有请求都会变慢"，那就错了。欠载时中位数根本不动（今天五组数据里 P50 全是 0.7～0.9 毫秒）。这是最反直觉、也最影响监控配置的一条。
  • 第 4 句如果写成"CPU 密集的扔线程池没用"，那是记住了结论没记住判据。判据是"放不放 GIL"——hashlib.sha256 也是 CPU 密集的，但它扔进线程池完全有用（P90 从 81.7 回到 1.1）。
  • 第 5 句如果只写"要看 P99 不要看 P50"，你只学到了一半。更深的一层是：哨兵在服务最糟的时候会失灵，所以按样本加权的指标会反向变化。这和昨天火焰图的盲区是同一个毛病。
