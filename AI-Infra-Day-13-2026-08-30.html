Q1 · 1 天前（Day 12 · 只读根、配额、出网、逃逸自查）

Day 12 最后一步用 setpriv 清空能力边界集、把用户号换成 65534，并且强调这一步必须排在换根、重挂 /proc、装 seccomp 名单之后。如果有人把它提到 pivot_root 之前，第一个失败的会是哪个动作，报什么错？为什么后面几步也一样过不去？

展开答案

第一个失败的是 mount --bind "$ROOT" "$ROOT"，也就是 pivot_root 之前那一步绑定挂载，报 EPERM（Operation not permitted）。

推理是这样的：挂载、换根、重挂 /proc、往 /proc/sys 上盖东西，这几个动作都要求进程持有 CAP_SYS_ADMIN。setpriv --bounding-set=-all 把边界集清空，等于把这个进程以后能拿到的能力上限设成零；--reuid=65534 这个动作本身又会把当前有效能力一起清掉。两件事叠起来，之后所有需要特权的系统调用都会返回 EPERM。

装 seccomp 名单也一样过不去，除非先设了 NO_NEW_PRIVS——不设的话，装过滤器这个动作本身要 CAP_SYS_ADMIN。

接今天：这个顺序不是 Day 12 拍脑袋定的，runc 的源码里就是这么排的。今天第 8 节会把那几行找出来，顺便解释为什么 seccomp 在 runc 里有两个可能的位置。

Q2 · 3 天前（Day 10 · 隔离谱系与安全边界）

沙箱里跑 nproc，看到的是宿主的核数，哪怕 cgroup 只给了半个 CPU。namespace、cgroup、seccomp 三把锁里，为什么没有一把管得了这件事？要让它看到"半个"，得换成什么手段？

展开答案

三把锁各管一件事，而这件事三样都不沾边：

  • namespace 管的是"哪些编号你看得见"——进程号、挂载表、主机名、网络设备。内核里没有"CPU 命名空间"这一类，所以 /proc/cpuinfo 里那几行不归它管。
  • cgroup 管的是"你能用多少"，它改的是调度器给这个组多少时间片，不改任何一个文件的内容。
  • seccomp 管的是"这个系统调用号许不许发"。读 /proc/cpuinfo 用的是 openat 和 read，这两个调用你不可能禁掉，禁了什么都跑不了。

要让它看对，三条路：应用自己去读 cgroup 的配额文件算出可用核数（Java 和 Go 的新版本都这么做）；或者在容器里用一个用户态文件系统把 /proc/cpuinfo 顶掉；或者干脆上 microVM，让它有一个自己的内核，那个内核确实只有半个 CPU。

接今天：runc 也不做这件事。今天会把 runc 默认那份配置从头读一遍，你会看到里面没有任何一项能改 /proc/cpuinfo——它管的是边界，不是幻觉。

Q3 · 7 天前（Day 6 · 测量本身也会说谎）

Day 6 有一条硬规矩：探针不能住在被测对象的进程里。今天量启动耗时的脚本是一个 Python 程序，它用 subprocess 把被测命令 fork 出去，在前后各读一次时钟。这算不算把探针塞进了被测对象？有没有别的东西混进了每一档的数字里？

展开答案

不算。Day 6 那条规矩防的是探针和被测对象抢同一份资源——同一个 GIL、同一个事件循环、同一个线程池。这里被测对象是一个独立的进程，计时进程在它 fork 之前和 wait 之后各读一次时钟，两者不共享任何运行时结构。

但确实有东西混进来了：Python 起一个子进程本身要 fork、要 exec、要 wait，这层开销被算进了每一档。所以表 A 第一行"直接跑 /bin/true，不隔离"那 2.7 毫秒不是零，它是这套测量方法的地板。比较各档时应该看它们相对这个地板的增量。

板块 2 · 第一部分你那一百行，在规范里叫什么名字

1. 从 Day 12 结尾那个问题说起

昨天收工的时候，你手上是一个不到一百行的 shell 脚本。它能起一个进程，这个进程有自己的进程号表、自己的挂载表、自己的主机名、自己的网络栈；它的根是只读的，写进去的东西落在一个一次性的上层；它的 CPU、内存、进程数、磁盘都有上限；它出不了网，除了你放行的那一个地址；跑代码的那个用户不是 root，也没有任何能力。

这套东西在 2013 年之后的容器生态里已经被人写过很多遍了。写得最多的那一份叫 runc，它是一个 Go 程序，代码量大概是你那一百行的两千倍。今天要做的事很简单：把两份放在一起，逐条对。

对之前先说清楚一件事：runc 不是"更好的 minibox"，它和 minibox 是同一个角色。这个角色在生态里有个位置，先把这个位置认出来，后面的分层才立得住。

2. bundle：一个目录、一份 JSON、一个 rootfs

你昨天的脚本，输入是两样东西：一个 rootfs 目录的路径，加上一串写死在脚本里的参数（配额多少、挂哪些东西、丢哪些能力）。这两样东西一个在文件系统里，一个在代码里。

规范做的第一件事，就是把第二样也搬到文件系统里，和第一样放进同一个目录。这个目录叫文件系统包（filesystem bundle），它只需要满足两条：

东西规定
运行时配置文件（config.json）必须存在，必须叫这个名字，必须在包目录的根下
容器的根文件系统是 config.json 里 root.path 指到的那个目录

出处：OCI runtime-spec，bundle.md 第 13–17 行。规范用的是 MUST，不是 SHOULD。

就这么两条。没有规定目录叫什么名字、放在哪、rootfs 是怎么铺出来的——铺 rootfs 是别人的活，今天第 15 节会说是谁的。把配置从代码里搬到一个 JSON 文件里，这个动作看着平淡，但它是整个生态能分层的原因：从此"谁来算出这份配置"和"谁来照着这份配置干活"可以是两个程序。

4. 三份规范，各管一段

OCI 这三个字母是 开放容器倡议（Open Container Initiative），一个 2015 年成立的标准组织。它出了三份规范，名字很像，管的东西完全不同。分清楚它们，你就知道一个问题该去哪一份里找答案。

规范管什么今天用到的部分
运行时规范（runtime-spec）拿到一个已经铺好的目录之后，怎么把它变成一个跑着的进程config.json 的全部字段、生命周期的四个状态、六个钩子
镜像规范（image-spec）一个镜像由哪些层组成、每层怎么打包、怎么寻址今天完全不碰，明天 Day 14 的主线
分发规范（distribution-spec）镜像仓库的 HTTP 接口长什么样今天不碰

今天全程只在第一份里。config.json 是整个体系里唯一的接口：上面那一层的活是算出这份 JSON，下面那一层的活是照着它干。你昨天那个脚本之所以不是 runc 的替代品而是它的同类，正是因为它也在做"照着一份配置干活"这件事——只是那份配置写在脚本正文里，没人能从外面替换。

第三列是 mountinfo 里最能说明问题的一列，它写的是"来源文件系统里的哪个子树被挂过来了"。19–23 那五条的来源就是它们自己（/proc/sys 的来源是 procfs 里的 /sys），这是把一棵已有的树绑到自己身上、再重挂成只读——Day 12 那两行 mount --bind 加 mount -o remount,bind,ro 干的就是这件事。

25、26 两条的来源写着 /null，暴露得更彻底：那是 /dev/null 被绑到了这两个路径上。/dev 是个 tmpfs，所以这两条的类型也就跟着显示成 tmpfs。这正是 Day 12 那个 mount --bind /dev/null /proc/xxx。

24、27 两条不一样，来源是 /、类型是只读 tmpfs——因为 /proc/acpi 和 /sys/firmware 是目录不是文件，往目录上绑 /dev/null 会失败，得盖一个空的只读 tmpfs。同一个"遮住"的意图，目标是文件还是目录，手法不同。

7. 每一条差别都能在源码里指到行

上面那些不是猜的。runc 这个命令行工具本身很薄，真正干活的代码在一个叫 libcontainer 的 Go 库里，命名空间、rootfs、cgroup、能力全在那里面。跟 rootfs 有关的三个函数放在 libcontainer/rootfs_linux.go，正好对应你写过的三段 shell。

先看换根。你昨天写的是 pivot_root . oldroot，而且必须先在 rootfs 里建一个 oldroot 目录，否则报 No such file or directory。runc 不建这个目录：

oldroot, _ := unix.Open("/", unix.O_DIRECTORY|unix.O_RDONLY, 0)   // 1152：先把旧根打开，攥住这个编号
newroot, _ := unix.Open(rootfs, unix.O_DIRECTORY|unix.O_RDONLY, 0) // 1158
unix.Fchdir(newroot)                                              // 1165：切到新根
unix.PivotRoot(".", ".")                                          // 1169：两个参数都是点
unix.Fchdir(oldroot)                                              // 1178：靠 fd 走回旧根
mount("", ".", "", unix.MS_SLAVE|unix.MS_REC, "")                 // 1187：把旧根改成 rslave
unmount(".", unix.MNT_DETACH)                                     // 1191：惰性卸载，和你昨天写的 umount -l 同一个标志
unix.Chdir("/")                                                   // 1196

这段是 Go，但每一行都对得上你写过的 shell。差别只有两处，而且两处都有理由。第一处是 pivot_root(".", ".")：两个参数都是当前目录，旧根被叠在新根的同一个挂载点上，然后靠一开始打开旧根拿到的那个编号（文件描述符 file descriptor）走回去把它卸掉——进程打开一个目录会拿到一个编号，之后哪怕路径已经不通了，拿这个编号还能回到那个目录。这样 rootfs 里就不需要预留任何目录——上面第 3 节那个 bundle 的 rootfs 里确实没有 oldroot，而 minibox 那份里有一个。

第二处在 1187 行：旧根被改成 rslave 而不是你写的 rprivate。1182–1186 行的注释解释了原因——用 rprivate 时遇到过竞态，容器这边还攥着某个挂载的引用，宿主那边的程序以为它已经没有挂载了，然后出事。rslave 保留了"宿主的变化传进来"这个方向，只切断"容器的变化传出去"。Day 11 讲挂载传播时留的那个"四种类型各有什么真实用途"，这就是其中一个。

读到这里可以停一下：你昨天遇到的每一个坑——绑定挂载要先 make-rprivate、卸旧根要用惰性卸载、/proc 要重挂——在这份代码里都能找到对应的一行，而且旁边通常有一段注释写着当年是怎么踩到的。

这个倒转不难解释。minibox 是一个 bash 脚本，它要起两个 bash 解释器，还要 fork-exec 出十来个独立的小程序：三次 rmdir、三次 mkdir、一次 unshare、一次 hostname、四次 mount、一次 pivot_root、一次 umount。每一个都要被内核装载进内存、初始化、跑几微秒的活、再退出。这些开销全部记在用户态账上，而且和"隔离"这件事本身没有半点关系。

runc 是一个静态编译的 Go 二进制，配置解析完之后直接发系统调用。它内核态花得多，是因为它真的在内核里干活——27 次 mount、一串 prctl、写 cgroup 文件、pivot_root。花在内核态的每一毫秒都买到了一项具体的约束。

关键结论

"做的事多"和"启动慢"之间没有必然联系。决定启动开销的是你用什么东西去发那些系统调用，不是你发了多少个。一个 shell 脚本哪怕只做三件事，光是把那些小程序拉起来就已经比一个二进制做二十七件事更贵了。

这条在挑沙箱实现时很实用：看到某个方案"功能少所以应该更快"，先去看它是不是用脚本串起来的。

12. 为什么起一个容器要两条命令

如果 runc run 就能一步起来，为什么规范里还要单独定义 create 和 start？

规范给容器定了四个容器状态（container state），写在 runtime-spec 的 runtime.md 第 19–22 行：

状态含义（规范原文的意思）
creating正在创建
created创建操作已完成，但用户指定的那个程序既没退出、也还没被执行
running用户指定的程序已经开始执行，还没退出
stopped容器进程已经退出

created 这个状态是整个设计的关键：环境全部搭好了，但用户的程序一行都还没跑。同一份文档第 57–79 行把生命周期拆成 13 步，第 2 步造环境、第 6 步才调 start、第 8 步才真正 execve 用户程序，中间第 3、4、5 步和第 7 步留给了四类生命周期钩子（lifecycle hooks）——规范一共定义了六个这样的插入点，允许你在容器起来的特定时刻插进一段自己的程序，网络插件和设备注入都靠它。

规范只说"必须有这个状态"，没说怎么实现。runc 的实现在上面走一遍那段日志里已经全露出来了：create 返回之后，runc state 报 created，pid 是 17554，而宿主上那个 pid 的命令行是 runc init——不是 sleep 300。状态目录里有两个文件，其中一个是 exec.fifo。

这个 执行栅栏（exec fifo）是一个命名管道。runc init 把该做的都做完之后，停在这里等：

// libcontainer/standard_init_linux.go:254 起
// 等 fifo 的另一端被打开，再 exec 用户进程。
fifoFile, err := pathrs.Reopen(l.fifoFile, unix.O_WRONLY|unix.O_CLOEXEC)  // 258
fifoFile.Write([]byte("0"))   // 263：写这一个字节会阻塞，直到有人来读
...
system.Exec(name, l.config.Args, l.config.Env)   // 297：这才 execve 用户的程序

命名管道有一条内核规定：写端打开时如果还没有读端，写操作就一直卡着。所以 runc init 卡在 263 行。runc start 干的事只有一件——把这个 fifo 打开读一下。写端一通，263 行返回，297 行 execve，进程的映像被换成用户的程序，pid 不变。日志里那个 17554 前后一致，命令行从 runc init 变成 /bin/sh -c sleep 300，就是这一下。

这个设计值多少钱，表 D 说了算：

起一个容器要付的是前两条：28.7 + 7.5 = 36.2 毫秒，其中 create 占了 79%。start 那 7.5 毫秒里还有 5.4 毫秒是把 runc 这个二进制拉起来的钱——回表 A 第三行。真正属于 start 自己的活，只有两毫秒出头。

关键结论

create 做完了几乎所有的活，start 只是去捅一下那根管子。这意味着一个沙箱池可以把容器预先造到 created 停住，请求真来的时候只付 start 那一笔。在这台机器上，这是把 36 毫秒挪成 7.5 毫秒。

代价是每个预热的容器都占着一个 runc init 进程、一套命名空间和一整套挂载点。池子开多大，是这笔内存和那笔延迟之间的权衡。

13. runc init 是同一个二进制，但它到得比 Go 还早

上面那个停在半路的进程叫 初始化进程（runc init）。它不是另一个程序，就是 runc 自己，多带了一个参数：

// libcontainer/container_linux.go:508 起
safeExe, err = exeseal.CloneSelfExe(c.stateDir)   // 508：先把自己这个二进制复制一份
exePath = "/proc/self/fd/" + strconv.Itoa(int(safeExe.Fd()))  // 512
cmd := exec.Command(exePath, "init")              // 517：拿这份副本，带一个 init 参数起自己

489–493 行的注释说明了为什么要复制：万一容器里的程序设法覆盖了这个二进制文件，也只能糟蹋掉这一份副本，动不了系统上别的容器。这个先复制再执行的做法叫 二进制自克隆（binary cloning），是 2019 年那个著名漏洞（容器内进程通过 /proc/self/exe 改写宿主上的 runc 二进制）之后加的防线。

配置不走命令行参数，走一根管子：536–546 行把三个文件描述符号塞进环境变量 _LIBCONTAINER_INITPIPE、_LIBCONTAINER_SYNCPIPE、_LIBCONTAINER_LOGPIPE。子进程从那些管子里读配置、往回报进度。

还有一层更隐蔽的东西。创建命名空间这件事必须在 Go 运行时起来之前做完——Go 程序一启动就有一堆线程，而 unshare 某些命名空间只对单线程进程有效。runc 的办法是塞一段 C 进去，用 构造函数钩子（constructor）让它在 main 之前跑：

// libcontainer/nsenter/nsenter.go 全文，一共 12 行
/*
#cgo CFLAGS: -Wall
extern void nsexec();
void __attribute__((constructor)) init(void) {
	nsexec();
}
*/
import "C"

__attribute__((constructor)) 是 GCC 的一个标注，被它标上的函数会在 main 之前由动态链接器调用。nsexec() 的第一件事（nsexec.c 第 716–719 行）是查环境变量 _LIBCONTAINER_INITPIPE：查不到就直接返回，让 Go 正常启动——这说明同一个二进制既是 runc run 也是 runc init，靠环境变量分岔。

查得到的话，它就进入一套三段式创建（stage 0 / 1 / 2），nsexec.c 第 820 行的 switch (setjmp(env)) 是分岔点：

阶段行号它的活
stage 0（父）828造出 stage 1，替它写 uid_map / gid_map，再把最终的 pid 报给上面
stage 1（子）986先 setns 加入指定的命名空间，再 unshare 出要新建的那些，然后造出 stage 2
stage 2（孙）1153它才是新进程号表里的 1 号进程，做完扫尾就把控制权交回 Go

为什么非要三段？795–806 行的注释给了理由：进程号命名空间只对之后创建的子进程生效，调 unshare(CLONE_NEWPID) 的那个进程自己还在旧表里。所以必须再 fork 一次，新表里的 1 号进程才存在——这正是你昨天 unshare 命令行上那个 --fork 参数在做的事，Day 11 的脚本注释里写着"进程号那张表要在下一个进程身上才生效"。runc 多出来的第三段，是为了让父进程还能拿到孙子的 pid 报上去。

14. runc 之上：containerd 和它派出去的那个 shim

runc 是个一次性的命令行工具：起一个容器，返回，退出。它不常驻，不监听端口，不知道机器上有多少容器在跑。干这种活的程序有个统称，叫低层运行时（low-level runtime），也叫运行时引擎。

常驻的那些事——管镜像、把 rootfs 铺出来、算出 config.json、记住机器上有哪些容器、对外提供接口——归高层运行时（high-level runtime）。containerd 是这一层里最常见的一个，Kubernetes 的 kubelet 通过一套叫 容器运行时接口（CRI）的接口跟它说话。

containerd 的官方文档（core/runtime/v2/README.md）开门见山写着一句：这个守护进程不直接拉起容器。它拉起的是一个叫垫片（shim）的中间进程，由 shim 去 fork-exec 真正的 runc。containerd 和 shim 之间说话走的是 Unix 套接字上的一个轻量远程调用协议，叫 ttRPC——名字里那个 tt 是 “tiny” 的意思，它是 gRPC 的一个精简版，为的是让每台机器上成百上千个 shim 进程不至于各自扛一份沉重的运行时。

containerd 不自己拉容器，它拉的是 shim，这一层看起来多余，其实解决的是一个很具体的问题：runc 跑完就退出，那容器进程的父进程是谁？如果是 containerd 自己，那 containerd 一升级重启，所有容器的 stdio 就断了、退出码也没人收。有了 shim，containerd 可以随时重启，容器照常跑着，重启完再通过套接字连回去。

文档里还提到一件事：一个 shim 可以带多个容器。containerd 那个 runc shim 是按标签分组的，Kubernetes 同一个 pod 里的容器带着同一个 sandbox-id 标签，于是归同一个 shim 管。这就是"pod 里的容器共享命名空间"在进程层面的落地方式。

15. 那个接信号、转信号、收尸的角色，叫 subreaper

Day 11 场景二留过一个问题：容器里的 1 号进程只处理它自己装了处理函数的信号，用户提交的代码通常什么都没装，所以 SIGTERM 对它是空的。当时说正确做法是让 1 号进程是你自己写的一个小程序，负责接信号、转信号、顺便回收派生出来的子进程，并且说这个角色有个专门的名字。

名字是 子收割者（subreaper），它其实是内核的一个进程属性：

// containerd pkg/sys/reaper/reaper_utils_linux.go:26
func SetSubreaper(i int) error {
	return unix.Prctl(unix.PR_SET_CHILD_SUBREAPER, uintptr(i), 0, 0, 0)
}

平时一个进程死了，它的孤儿子进程会被过继给 1 号进程，由 1 号进程收尸。设了 PR_SET_CHILD_SUBREAPER 之后，这条链上的孤儿会被过继给最近的那个 subreaper，而不是一路飘到 1 号。没人收尸的进程会一直停在僵尸（zombie）状态占着进程号表的一个位置，攒多了就把 pids.max 撑满——Day 10 设的那个 64。

containerd 的 shim 启动时第一批动作里就有这一下（pkg/shim/shim.go 第 243–247 行调 subreaper()，Linux 上的实现在 pkg/shim/shim_linux.go 第 29–31 行，就是上面那个 Prctl）。runc 自己也有同一套逻辑：signals.go 第 21–27 行按需把自己设成 subreaper，第 86–121 行那个循环就是完整的角色定义——收到 SIGCHLD 就调 reap()（127 行，wait4 加 WNOHANG 循环到收干净为止），收到 SIGWINCH 就调整终端大小，收到别的一律 kill(pid1, 信号) 转给容器的 1 号进程。

最后一件事：谁决定 config.json 里的什么。同一个字段在不同层有不同的默认值，这张表值得记住：

字段OCI 默认（runc spec 生成的）containerd 的默认

seccomp没有这个键，也就是不装一份默认动作为"报错误码"、放行 414 个系统调用名的白名单（contrib/seccomp/seccomp_default.go，487 行是默认动作）

第 1 步：拿到 runc

看到 Package libseccomp was not found，是缺开发头文件，装 libseccomp-dev 再编。

用你 Day 11 造的那个 rootfs 就行，不用重造。这一步做完你会有一份 169 行的 config.json，先整份读一遍，边读边在旁边标注"这一条我 Day 11/12 写在哪一行"。

第 3 步：用探针把差别量出来

第 4 步：把 create 和 start 分开跑一遍

runc create c1               # 注意：容器的 stdout 会被继承，别用管道接它
runc state c1 | grep status  # 应该是 created
ps -p $(runc state c1 | python3 -c "import json,sys; print(json.load(sys.stdin)['pid'])") -o args=
ls /run/runc/c1              # 应该看到 exec.fifo 和 state.json
runc start c1                # 再看一遍上面两条，pid 不变，命令行变了，fifo 没了

看到 runc create 一直不返回，多半是你把它的 stdout 接到了管道或者 $(...) 里——容器进程继承了那个管子并且不关，读的一方就一直等。

验收标准

  • 你的对照表里，每一项差别都能指到 config.json 的一个具体字段，或者写明"这一项不是配置管的"。
  • 你能说出 created 状态下那个进程的命令行是什么，以及它在等谁。
  • 用你自己机器上的数字回答：create 和 start 各占整个启动的几成。

常见坑

  • runc 必须以 root 跑，或者配好用户命名空间。非 root 直接跑会在造 cgroup 那步失败。
  • 容器 ID 不能重名。上一次没 delete 干净，下一次 create 会报 already exists。runc list 看有哪些残留。
  • runc delete 要求状态是 stopped。kill 之后立刻 delete 会失败，等几十毫秒。
  • 默认 config.json 的根是只读的。想写东西得自己加一个 tmpfs 挂载点，或者把 root.readonly 改成 false。

板块 5自检问题

1 · 有人把 config.json 里的 process.args 改了，但容器已经 create 过、还没 start。start 之后跑的是新的还是旧的？

旧的。runtime-spec 第 61 行有一句明确规定：create 这一步之后对 config.json 的任何修改都不得影响这个容器。

runc 的实现让这条规定成为必然：create 的时候配置已经通过管子传给了 runc init，并且序列化进了 state.json。runc init 停在 exec.fifo 上时，它要执行的 args 早就在自己的内存里了，start 只是捅一下管子，根本不会再去读那个 JSON 文件。

错在哪：容易以为 start 是"这时候才去读配置执行"。不是——start 什么都不读。

2 · 你在 config.json 里既设了 noNewPrivileges: true，又给了一份 seccomp 名单，名单里忘了放行 execve。容器起得来吗？

起不来，而且失败的位置很特别：装名单会成功，execve 那一下会被自己的名单挡住。

推理：设了 NO_NEW_PRIVS，runc 走 standard_init_linux.go 第 226 行那条路，也就是把 seccomp 拖到尽可能晚才装。那个位置在第 297 行 execve 之前一点点。装完之后紧接着就是 execve，而它不在白名单里，内核直接拒绝。

如果没设 NO_NEW_PRIVS，走的是 178 行那条路，装得更早，同样会死在 execve——只是中间还隔着降权那一堆动作，报错的调用栈不一样。

错在哪：以为"名单是给用户代码用的，运行时自己的动作不受限"。恰恰相反，名单一旦装上，装它的那个进程自己第一个受约束，而它接下来必然要发 execve。

3 · 表 A 里 minibox 和 runc 的 P50 差不到四毫秒，但表 C 显示两者的用户态 CPU 差了将近一倍。为什么墙上时钟没体现出这个差别？

因为这台机器有 2 个核，而这两个装置在启动过程里都不是单线程串行的。minibox 那些 fork 出来的小程序、runc 的 Go 运行时和它的子进程，都能在两个核上重叠跑。CPU 时间是把所有核上的时间加起来，墙上时钟只算最长的那条路径。

换个说法：CPU 时间量的是"一共烧了多少"，墙上时钟量的是"等了多久"。有并行的时候前者可以大于后者。这也是为什么这两个指标都要报——只看墙上时钟，你会以为 minibox 和 runc 一样省；只看 CPU 时间，你会以为 runc 更贵。

顺带一个推论：如果把机器压满（比如同时起 50 个沙箱），CPU 时间才是决定吞吐的那个量，那时 minibox 那种把钱烧在 fork-exec 上的做法会明显吃亏。

4 · 你的沙箱池预先 create 了 20 个容器停在 created。这时候有人在宿主上 kill -9 掉了其中一个的 runc init 进程。runc state 会报什么？runc start 会怎样？

runc state 会报 stopped。判断"还活着没有"靠的是 state.json 里记的 init_process_pid 加上 init_process_start（进程的启动时刻），进程没了就查不到，状态落到 stopped。

runc start 会失败。runtime-spec 第 127 行规定得很直白：对一个不处于 created 状态的容器执行 start，必须不产生任何效果并且报错。

对池子的含义：created 不是一个可以放着不管的状态。池子必须自己定期核对每个坑位的状态，发现掉了的就补一个新的——这跟连接池探活是同一类问题。

板块 10今日五句话

合上页面，用自己的话写五句

1 · OCI bundle 是什么？它只规定了哪两样东西？

2 · created 这个状态里，那个进程正在干什么？它在等谁？

3 · runc 做的事比 minibox 多十倍，为什么启动没有慢十倍？钱花的地方有什么不同？

4 · 为什么 runc 要把创建命名空间的代码写成 C 的构造函数，而不是写在 Go 的 main 里？

5 · 一个容器里攒了一堆僵尸进程，往上要查哪两件事？

逐句自查

  • 第 1 句如果写成"bundle 就是镜像"就错了。镜像是分层的、要解开才能用，bundle 是已经解开摊平的一个目录加一份 JSON；从镜像变成 bundle 是上一层的活。规范对 bundle 只有两条要求：config.json 必须在根下且必须叫这个名字，rootfs 是 root.path 指到的目录。
  • 第 2 句如果只写"容器已经创建好了"就没答到点上。要具体到进程：那是 runc init，命名空间、挂载、能力、cgroup 全部就位，它卡在往 exec.fifo 写一个字节的那次系统调用上，等一个读端出现。用户的程序一行都还没跑。
  • 第 3 句如果写成"因为 runc 用 Go 写的比 shell 快"，只对了一半，而且丢了最重要的部分。关键是钱花在哪：minibox 的开销四分之三在用户态，来自反复 fork-exec 十几个小程序；runc 的开销六成在内核态，来自真正的 mount、prctl、写 cgroup。前者的钱和隔离无关，后者的钱每一分都买到了约束。
  • 第 4 句如果只写"为了早点执行"就不够。要说出机制：Go 运行时一启动就是多线程的，而建命名空间这个动作对多线程进程有限制；构造函数在 main 之前、Go 运行时起线程之前执行，那时进程还是单线程的。
  • 第 5 句如果只写"1 号进程没收尸"就漏了一半。两件事：一是容器里的 1 号进程是谁——如果是用户代码本身，它多半不会 wait；二是外面那层有没有设 subreaper 兜住。两条都不成立，僵尸就会一直堆到 pids.max。
