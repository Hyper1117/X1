第 1 题（Day 18 · 交接的计价方式）

昨天量到：账按交接次数收，一条六轮的会话非流式是六次交接，改成流式变成七百七十四次，同样六十四条并发，运行时占核从两成一涨到七成四。

今天你要在一轮里调三个工具，而且是串行调。一条六轮会话的交接次数从六变成多少？运行时那堵墙往哪个方向挪？为什么方向可以直接推出来，具体挪到哪儿却必须重新扫一遍？

展开答案

次数从六变成二十四：每一轮一次模型调用加三次工具调用，六轮就是二十四次。

方向可以推，是因为昨天第 7 节那张表已经把「每次交接净耗 CPU」这一列量出来了，而它在低并发段大致是个常数。同样的并发条数下，每条会话的交接次数翻了四倍，运行时要干的活就翻四倍，墙只会往前挪。

具体挪到哪儿不能推，理由也在同一张表：那一列本身是并发数的函数，从一点一毫秒一路走到二十三点八毫秒。昨天那道「按单条开销外推得到四百零五条、实测墙在九十六到一百二十八之间」的账，就是这个错误的完整演示——用曲线最平那一段的斜率去外推，方向对，倍数一定是错的。

接今天：今天这三个工具会改成并发发出去。并发之后交接次数一次都没少，变的是它们挤在同一段时间里——而这件事会把另一个东西暴露出来，和 CPU 无关。

第 2 题（Day 16 · 前缀缓存的命中率）

Day 16 量过：四十个 agent 任务、每个六轮，按「一个任务做到底再开下一个」的顺序重放，token 级前缀命中率是 84.5%；一条请求都不改，只把顺序换成四十个任务轮流各推进一轮，掉到 31.9%。

现在换一件事：顺序不动，但你在第 3 轮往上下文末尾追加了一段一千字节的东西。第 4、5、6 轮的前缀命中率会因此变差吗？说出理由，再说出这一千字节真正要在哪两个地方付钱。

展开答案

不会变差。前缀缓存能复用的范围被因果注意力框死了：只能是前缀，一个 token 都不能错位。而「往末尾追加」这个动作恰恰不破坏前缀——第 4 轮的上下文仍然完整地包含第 3 轮的上下文作为开头，第 3 轮算过的那些块照样对得上。Day 16 那句「agent 场景天然是一条不断加长的公共前缀」，说的就是这个性质。

钱付在另外两个地方。第一是传：Day 18 第 10 节量过，追加进上下文的东西会在后面每一轮被完整地重新序列化、写进 socket、跨过网络。前缀缓存省掉的是「算」，一个字节的传输都省不掉。第二是容量：这一千字节变成缓存里的若干个块，一直占着不放。Day 16 那张容量扫描表说过，容量不够的时候命中率会被复用距离拖下去——多占的每一块都在把别人的复用距离往外推。

今天接在哪儿：第 11 节算的就是这笔账，只不过追加进去的那段东西是一段错误信息。

第 3 题（Day 12 · 出网白名单的兜底规则）

Day 12 那张表：白名单最后一条兜底规则用 DROP 时，被拦下的调用五次全都停在 10005 毫秒上下；换成 REJECT，五次全是 0.0 毫秒。

那个 10005 毫秒是从哪儿来的？它不是网络的属性，那它是谁的属性？这件事对「给一次工具调用设多长超时」意味着什么？

展开答案

它是调用方自己设的超时。包被丢掉之后没有任何回音，调用方只能一直等到自己放弃，所以量出来的时长精确地等于那个超时值——改一下超时，这一列的数字就跟着改。

换句话说，在 DROP 这条路上，「一次失败要多久」这个数完全不由被调用的那一侧决定，由你设的超时决定。REJECT 则把决定权交还给内核：连接被拒绝当场返回，代码走进自己的异常分支。

对超时的意义有两层。第一层是数值上的：超时不是安全带，它是失败路径的时长，你设成多少，最坏情况就有多长。第二层更要紧：只要一次调用可能以「等满超时」的方式失败，那么一轮里调用的次数越多，这种失败被撞上的概率就越高，而串行调用会把每一次的时长直接相加。

和今天的关系：第 9 节会看到，超时到点之后运行时这一侧确实停下来了，而被调的那一侧根本不知道有过这回事。

板块 2 · 第一部分一个工具，在协议里长什么样

从你现在会写的那段分派代码起步。它缺的东西一条条列出来，合起来正好就是一份现成的规范。

1. 你现在会怎么分派

模型凭什么知道你有一个叫「读文件」的东西？

昨天那个循环里，模型返回 {"tool": "search", "arg": "step-1"}，你解析出 tool 这个字段，然后照着它去做。做的那一步写出来大概是这样：

if d["tool"] == "search":
    result = do_search(d["arg"])
elif d["tool"] == "read_file":
    result = read_file(d["arg"])
else:
    result = "unknown tool"

这段代码是对的，而且能跑。问题不在它执行得对不对，在它对模型完全不可见。

模型那一侧只看得见你发过去的那段上下文。你的 if 分支写了什么、参数叫什么名字、少传一个会怎样，它一个字都不知道。它只能靠猜——而猜出来的东西你这段代码接不住，于是掉进 else。

所以真正缺的不是执行的代码，是一份说明书，一份必须放进上下文里、由模型读的说明书。

2. 说明书上要有三样东西

把「让模型能正确发起一次调用」需要的信息一条条列出来，只有三样。

要告诉模型的为什么少不了写成什么
这个工具叫什么模型要在输出里指名道姓，名字对不上就分派不了一个字符串，比如 read_file
它是干什么用的模型要在若干个工具之间挑一个，挑的依据只有这段话一段自然语言
参数长什么样模型要生成一个参数对象。哪些必填、每个是什么类型、有没有默认值，它得先知道一份机器可读的类型描述

头两样是字符串，第三样需要一点结构。用什么写？这里不需要发明新东西：描述「一个 JSON 对象应该长什么样」这件事早就有一套标准写法，叫 JSON Schema——用 type 说类型、properties 说有哪些字段、required 说哪些必填。

把这三样打包成一条记录、放进一张表里、让模型每次都能看到，这个动作就叫 工具注册（tool registration），那份参数描述叫这个工具的 参数模式（input schema）。

说明书这个类比可以再推一步：说明书要随货一起发出去，光放在仓库里没用。这句话决定了后面第 4 节那笔账。

3. 这套东西有一份现成的规范

三样东西怎么摆、调用请求怎么发、结果怎么回，每家都能自己定一套。模型上下文协议（MCP / Model Context Protocol） 是其中被采用得最广的那一份，也是这门课里你最可能真的要接的那一份。

它的底子不是新东西：消息格式用的是 JSON-RPC 2.0——一种很老的远程调用约定，每条请求带一个方法名、一包参数、一个 请求编号（request id），回来的响应带同一个编号，靠编号把请求和响应配对。下面这些行号都出自本机装的 mcp 这个包的 1.27.0 版，路径写在页尾。

结果那一行里的 content 是一个数组，元素叫 内容块（content block），可以是文本、图片、音频或者一段资源引用（types.py:1206）。工具还可以额外声明一份 outputSchema，这时候结果里要多带一份 结构化输出（structuredContent），服务端会拿它跟 schema 校验一遍再发出去。

把一个普通的 Python 函数变成上面那份说明书，这一步 SDK 是自动做的，而它取材的地方很直白：server/fastmcp/tools/base.py:66 那一行是 func_doc = description or fn.__doc__ or ""——函数的文档字符串原样变成给模型看的 description；下面第 77 行把函数签名转成一个 pydantic 模型（Python 里根据类型标注做校验的那个库）再从它导出 JSON Schema，变成 inputSchema。

也就是说，你随手写的那句中文注释，会被完整地发给模型，而且是每一轮都发。这句话不是修辞，下一节把它换算成字节。

所以「工具越多越好用」这句话在基础设施这一侧是有价钱的，而且这个价钱按轮数收。真实系统里的做法是不把全部工具都挂上去，而是先按任务筛一遍再注册——这一步值多少钱，你现在有了一把尺子可以自己算。

5.2 一次调用长什么样

运行时发给工具服务的是这一行。cid 是这一次调用的编号，dur 是这个工具要花多久，fail 决定它成功还是失败：

问题一的答案是两行，而且它们出现在运行时已经收工六百毫秒之后。

发生了什么，一步一步说清楚。asyncio.gather 的行为是：把若干个协程一起交给事件循环，等它们全部完成；但只要其中一个抛了异常，它立刻把这个异常向上抛出，不再等别的。它做的是「不再等」，而不是「叫停」——另外两条协程仍然是活的，仍然挂在那个事件循环上，仍然在等自己那条 HTTP 响应。

更要紧的是，就算它真把那两条协程杀了也没用。请求已经发出去了。工具服务那一侧收到的是一个完整的 HTTP 请求，它开工、sleep、写账本，这一串动作在另一个进程里，运行时这一侧做什么都影响不到它。

类比一下：你同时给三家店打电话下单，第二家说不做了，你挂断所有电话——但第一家和第三家已经在做了，而且做完会送到你门口。挂电话解决的是你要不要听，不解决他们做不做。
关键结论

并发发出去的那一刻，副作用会不会发生这件事就已经不由你决定了。运行时能决定的只有两件：要不要等，以及等到的结果算不算数。

这句话直接接上昨天第 12 节那个矩阵。那天的窗口是「副作用生效了、检查点还没写」，今天这个窗口更宽：副作用生效的时刻，比运行时以为这一轮已经结束的时刻还要晚半秒多。所以那一步的幂等键在今天这个场合不是可选项——它是唯一能把账对上的东西。

  • 默认的 gather 拿到零个：异常一抛，那两个已经完成或即将完成的结果全都被丢掉了。
  • 加上 return_exceptions 之后拿到三个：它不再把异常往上抛，而是把异常本身当成一个结果放进列表里，等所有协程都有了结局才返回。这三个结果里有两个是成功的数据，一个是那个异常——都能拿去用。这种「一部分成功、一部分失败，都收下」的收法叫 部分结果（partial results）。

问题二问的是超时。一个八百毫秒的工具，运行时给它三百毫秒预算，到点由 asyncio.timeout 取消。跑五遍：

两行的运行时返回时刻几乎一样，差的那四毫秒是多发的那一条通知本身。五遍里两列的取值都没有出现过分歧。

第一行是问题二的答案：运行时三百毫秒就报了超时，五百毫秒之后，那行 done 照样写进了账本。取消这个动作发生在你的进程里——它让一条协程停止等待、抛出 CancelledError、把栈解开。这些事情对面一个字都不知道。

第二行是修法，而修法的形状很朴素：多发一条消息，明确告诉对面「刚才那一次不要了」；对面在真正产生副作用之前查一下这个标记，是就跳过。工具服务在账本里留下的那行 skip，就是它查过并且跳过的证据。

要注意这个修法成立的前提：被调的那一侧必须自己愿意查。你没有任何办法从外面强行终止另一个进程里的一段逻辑，能做的只是把「不要了」这个意思送到，剩下的由它自己决定。这种取消叫 协作式取消（cooperative cancellation），而那条专门用来送这个意思的消息叫 取消通知（cancellation notification）。

回到 MCP。这条通道在协议里是有的：types.py:1740-1764 定义了 notifications/cancelled 这个通知，参数是要取消的 requestId 加一句可选的原因。服务端也照着做了——shared/session.py:403-406 收到这个通知时，会去在飞的请求表里找对应的那一条，找到就取消它。

有意思的是发送这一侧。客户端的超时逻辑在 shared/session.py:289-302：等响应超时之后它抛一个 McpError，然后在 finally 里（:309-313）把本地的几个登记项清掉，仅此而已。在整个 1.27.0 版的包里，CancelledNotification 这个类只在 types.py 里被定义过，没有任何一处构造它并发出去。

关键结论

协议里有一条取消通道，服务端会听，而客户端超时的时候默认不说。也就是说，用现成的 SDK 写一个带超时的工具调用，你拿到的行为正是上面那张表的第一行：本地干净了，对面照跑。

所以「超时」这件事要拆成两个动作分别写：一个是本地停止等待，这个 asyncio.timeout 就够了；另一个是把取消送到对面，这个要你自己发。少了后半截，超时保护的只是你的延迟，不是你的正确性。

这也给昨天那份设计文档补上一条：超时的时长要往下传。一轮总共只剩三百毫秒的时候，没有理由给这一轮里的某个工具四秒的预算。把「还剩多久」当成参数一层层传下去，这个做法叫 截止时间传递（deadline propagation）；Day 12 那道温故题给它补了一句注解——在 DROP 那条路上，你传下去的这个数就是失败路径的实际时长。

板块 2 · 第四部分错误往哪儿去

工具失败是常态，不是异常路径。这一部分讲失败之后那段文字走哪条路、写成什么形状、以及这个选择在一条会话里值多少字节。

10. 一次失败，有两条完全不同的路

「工具调用失败了」这句话其实盖住了两件很不一样的事。

第一件：这条消息本身就不对。方法名拼错了、参数不是合法 JSON、编号对不上。这类问题跟工具没关系，是你的客户端写坏了，走的是 JSON-RPC 的错误响应——一个 code、一句 message、一包可选的 data（types.py:193-211）。这类错误传上去是给你看的。

第二件：消息完全正确，工具也确实被调用了，但它干活的时候出了问题——文件不存在、外部接口挂了、除零了。这类问题模型有可能自己绕过去：换个文件名、换个做法、或者告诉用户这条路走不通。所以它不该走错误响应那条路，它得走到模型面前。

MCP 是这么区分的：第二类失败回的是一个成功的 JSON-RPC 响应，里面装着一个 CallToolResult，只是这个结果的 isError 字段是 true（types.py:1363-1369）。把这两类分开的英文叫法是 协议错误（protocol error） 和 工具错误（tool error），后者的那个标志位就叫 错误标志（isError）。

SDK 里这一步只有两行。工具函数抛出任何异常，服务端接住，转成一个带错误标志的正常结果（server/lowlevel/server.py:583-584）：

# mcp/server/lowlevel/server.py:583-584
except Exception as e:
    return self._make_error_result(str(e))

这两行里藏着今天最实用的一个决定：它用的是 str(e)，不是 traceback.format_exc()。异常的那一句话被留下，栈被扔掉。

协议在另一处把同样的意思写成了规矩。ErrorData 的 message 字段旁边跟着一句注释（types.py:199-203）：这个 message 应该限制成一句简短的话。

两处都在说同一件事，而且这件事跟「哪种写法更优雅」无关。下一节把它换成字节。

把堆栈原样喂回给模型，到底贵在哪儿？

关键结论

一段追加进上下文的东西，它的真实价钱不是它自己的长度，是长度乘以「它之后还有几轮」。同一段堆栈出现在第 2 轮和出现在第 5 轮，账完全不同。

这就是 Day 18 第 10 节那个平方式子的另一副面孔：那天算的是每轮固定增长的那一截，今天算的是某一轮突然多出来的一大块。两者的机制是同一个——上下文只往后长，从来不改前面，所以任何进去的东西都会被后面每一轮重新搬一遍。

说清楚账之后，做法就不需要靠品味来定了：回给模型的那一段应该是能让它改变下一步动作的最短文字。堆栈里唯一具备这个作用的就是最后那一行，前面七层调用帧是给你排查用的——它们该进你的日志，不该进上下文。

这个「不加区分地把大段文字塞进上下文、让它在后面每一轮里被重复搬运」的毛病有个通用叫法：上下文污染（context pollution）。怎么把已经进去的东西清出来是 Day 20 的题目；今天做的是不让它进去。

12. 参数写错的时候，回给模型的是哪句话

模型生成的参数不合 schema，是最常见的一种工具错误。MCP 在真正执行之前先拿工具的 inputSchema 校一遍，不过就转成一句带错误标志的话回给模型（server/lowlevel/server.py:528-532），让它自己改了重来。

这句话说得清不清楚，直接决定模型能不能改对。拿一份三个参数的 schema，喂三种典型的错法：

模型写错的方式回给它的字节回给它的那句话
少了必填参数53Input validation error: 'path' is a required property
类型写错了57Input validation error: '很多' is not of type 'integer'
参数名拼错了53Input validation error: 'path' is a required property

前两行很好：五十来个字节，说清了是哪个字段、错在哪里，模型下一轮改得对。

第三行和第一行一模一样，而它们其实是两回事。模型把 path 写成了 pathh，它得到的提示是「缺少 path」——于是它很可能再加一个 path，同时把那个拼错的键留在原地，然后重复同样的错法。

原因在 JSON Schema 的默认行为：没写 additionalProperties 的时候，多出来的字段是被允许的，校验器只看见「必填的那个不在」。而 SDK 从函数签名自动生成的 schema 里，恰好没有这一项。

补上 "additionalProperties": false 之后再试一遍，得到的是这个：

补上之后的错法字节那句话
只拼错，必填的那个还是缺53还是 'path' is a required property
拼错了，但必填的那个也带上了86Additional properties are not allowed ('pathh' was unexpected)

只修好了一半：必填项缺失这条规则先触发，多余字段那条规则轮不上。所以这一项该加，但加了它不等于拼错的场景都能说清楚——真要说清楚，得在校验失败之后自己比对一次键名，把「你是不是想写 path」这句话拼进去。这一步值多少字节、值不值，你现在有第 11 节那把尺子可以自己算。

两个任务，约两小时。任务 A 是在昨天那个骨架上长出工具这一层；任务 B 把今天这套读法用到你手上已有的东西上。

任务 A（必做，约 80 分钟）· 把工具做成真的

第 1 步：先有一个会写账本的工具服务

今天所有关于「副作用发生了没有」的判断，都要从一个运行时说了不算的地方读。所以工具必须住在另一个进程里，而且要在自己开工和收工的时候各留一行记录。

@app.post("/call")
async def call(req: Request):
    r = await req.json()
    name, cid = r["name"], r.get("cid", "-")
    dur = float(r.get("dur", 0.8))
    fail = bool(r.get("fail", False))
    mark("start", name, cid)
    if fail:                      # 失败的那个工具：早早地抛，不写 done
        await asyncio.sleep(dur)
        return JSONResponse({"error": "boom"}, status_code=500)
    await asyncio.sleep(dur)
    if cid in CANCELLED:          # 产生副作用之前查一次：这一次还算不算数
        mark("skip", name, cid)
        return JSONResponse({"result": "cancelled"}, status_code=499)
    mark("done", name, cid)       # 副作用在这一行生效
    return JSONResponse({"result": f"{name}:ok"})

每一行记录里除了相对毫秒，还要记一个 time.time()。两个进程的 monotonic 零点不一样，只有这口挂钟是共用的，跨进程排先后要靠它。

中间那个查取消标记的分支现在还用不上，它是第 4 步的东西，先照原样写进去。

验收标准：curl 打一次，账本里出现两行，两行的时间差约等于你传的 dur。

常见坑：把账本写在运行时进程里。这样你量的是「运行时以为发生了什么」，而今天整页要问的恰恰是它以为错了的地方。

第 2 步：写出工具注册表，量它的字节

挑三个你真会用的工具（读文件、执行一段代码、查一次外部接口），把名字、说明、参数 schema 三样写全。装了 mcp 这个包的话可以让它替你从函数签名生成；不装就手写 JSON Schema，形状是一样的。

然后把这份注册表序列化，数字节，再乘以你打算跑多少轮。

验收标准：你能说出「加一个工具，一条十轮会话要多花多少字节」，并且这个数是你自己算的，不是抄本页的六百七十。

常见坑：只数了 schema，忘了它每一轮都要重发一次。这一步的答案里必须有轮数这个乘数。

第 3 步：一轮三个工具，四种写法各跑一遍

照本页第 8 节的场景：两个慢的会写账本，中间一个快的必然失败。四种写法各跑五遍，每遍在运行时返回的那一刻和一秒半之后各读一次账本。

if strategy == "serial":
    try:
        for p in plan:
            out.append(await call_tool(**p))          # 一个一个来，前一个失败就到此为止
    except Exception as e:
        err = str(e)
elif strategy == "gather":
    tasks = [asyncio.ensure_future(call_tool(**p)) for p in plan]
    try:
        out = await asyncio.gather(*tasks)            # 一个失败就抛，已完成的结果全丢
    except Exception as e:
        err = str(e)
elif strategy == "gather_re":
    tasks = [asyncio.ensure_future(call_tool(**p)) for p in plan]
    res = await asyncio.gather(*tasks, return_exceptions=True)   # 全等完，异常当结果收
    out = [r if not isinstance(r, Exception) else {"error": str(r)} for r in res]
    err = next((str(r) for r in res if isinstance(r, Exception)), None)
elif strategy == "taskgroup":
    try:
        async with asyncio.TaskGroup() as tg:         # 一个失败，取消同组的兄弟
            tasks = [tg.create_task(call_tool(**p)) for p in plan]
        out = [t.result() for t in tasks]
    except* Exception as eg:                          # 异常组要用 except* 接
        err = str(eg.exceptions[0])

验收标准：你的表里，三种并发写法「一秒半之后账本几行 done」这一列必须相等。不相等说明有一个工具没真被发出去，最常见的原因是把协程建好了却没交给事件循环。

常见坑：用 time.sleep 而不是 asyncio.sleep 写工具服务的等待。症状是三个工具排成一队，你会得到一个「并发根本没省时间」的假结论——Day 4 那条规矩在这里照样管用。

第 4 步：加超时，然后加取消通道

给单个工具调用套一层 asyncio.timeout，预算取一个夹在快慢两个工具中间的值。跑一遍，读账本。然后加上第二段：超时之后往工具服务发一条「这一次不要了」，工具服务在写 done 之前先查一下这个标记。

t0 = time.monotonic(); state = "ok"
try:
    async with asyncio.timeout(budget):
        await call_tool("alpha", cid, dur)
except asyncio.TimeoutError:
    state = "timeout"
    if notify:                       # 取消要走一条真的通道，对面才知道
        await cli.post("http://127.0.0.1:8002/cancel", json={"cid": cid})
return {"state": state, "ms": round((time.monotonic() - t0) * 1000, 2)}

验收标准：两次跑出来的账本必须不同——没有通知的那次有 done，有通知的那次没有。如果两次一样，检查工具服务是不是在 sleep 之前就查了标记（那时候通知还没到）。

常见坑：以为把 HTTP 客户端的连接关掉就等于取消。关连接改变的是你这一侧的状态，对面的处理函数是不是跟着停，取决于对面那个框架的行为，不取决于你。要停就要发一条它认得的消息。

第 5 步：量错误的三种形状

让一个工具在几层调用之后真的抛一个异常，把 traceback.format_exc()、str(e)、和一个结构化对象三种写法各跑一条六轮会话，记录累计发出的字节。

验收标准：三个数之间的差，应该正好等于「这一段的字节差」乘以「出错那一轮之后还剩几轮」。对不上就说明你的错误被追加进上下文的位置和你以为的不一样。

常见坑：忘了 JSON 转义。堆栈里的换行和引号进 JSON 时各要多占一个字节，几十个加起来是实打实的差额。

板块 4工作现场

场景一 · 「有个用户被重复执行了一次操作，可我们的代码明明报了错」

这句话里的「明明报了错」正是线索。第 7 节那张轨迹说得很清楚：运行时报错退出的时刻，和副作用真正落地的时刻，中间隔着最慢那个工具的剩余时长。日志里那条错误记录的时间戳，比事情真正发生的时间早了半秒多。

排查顺序：先看这一轮是不是并发发出了多个工具调用。是的话，把「发出的调用数」和「日志里记下的成功数」分别数出来——前者才是副作用可能发生的次数，后者只是你收到了几个回执。这两个数不一致是正常的，不一致的量就是你的风险敞口。

止血的做法和昨天一样：给会写数据的每一步配一个键，执行前先查。长期的做法是在注册表里就把工具分成两类，会写数据的那一类一轮里最多发一个。

场景二 · 「上下文涨得太快，我们才聊了几轮就顶到窗口上限了」

先分开两笔账再动手，因为它们的形状完全不同。

一笔是每轮固定的那一截：工具注册表。它是轮数的一次方，但常数很大——第 4 节量到挂三十二个工具时它占发出总量的九成半。这一笔的修法是筛工具，不是压缩对话。

另一笔是某几轮突然多出来的大块：报错时塞进去的堆栈、一次返回了整个文件的工具、一次没截断的查询结果。这一笔按「它之后还剩几轮」计价，所以越早进去的越贵。这一笔的修法是在写进上下文之前就把它裁短。

判断是哪一笔很快：把每一轮发出的字节打出来，看它是一条平缓的直线，还是某一轮之后整体抬高了一截。抬高的那一截就是第二笔。

场景三 · 「模型总是把某个工具的参数写错」

先别急着改提示词。第 12 节那两张表说明，模型改不对的一个常见原因是它收到的报错本身指错了地方——键名拼错时，校验器说的是「缺少必填参数」。

要看的第一样东西是那条失败调用的完整参数对象，和你回给模型的那句原话。如果模型每次都补一个字段而不是改一个字段，基本就是这个毛病。

第二样是工具的 description。它取自函数的文档字符串，而文档字符串通常是写给同事看的——里面可能全是实现细节，一个字都没说清楚参数该传什么。这两样都改完还不对，再去想提示词。

同事和面试官常问的

「一轮里要调好几个工具，你怎么发？」——先反问这几个工具会不会写数据。都是只读的，就并发发，用任务组，返回得早、收得干净；有写操作的，一轮最多发一个，或者每个带键。然后再补一句关键的：无论哪种写法，请求发出去之后副作用就不由运行时决定了，实测三种并发写法的最终账本完全一样。能说到这一句，说明你不是在背 API。

「超时到了，你怎么把下游停掉？」——本地取消和通知对面是两个动作，只做前一个的话下游照跑。MCP 里有 notifications/cancelled 这条通道，服务端会听，但 Python 的 SDK 客户端在超时路径上默认不发。追问「那怎么办」，答：自己发，并且下游要在产生副作用之前查一次。

「工具报错了，你回给模型什么？」——异常那一句话加工具名，堆栈进日志。理由要给数：一段堆栈上千字节，在一条六轮会话里被重发四次；同一个异常写成一行只有四十来个字节。再补一句：MCP 自己也是这么做的，SDK 里那一行用的是 str(e)。

「你们挂了多少个工具？」——这个问题问的其实是上下文成本。一个工具的说明书六七百字节，每一轮重发一次，挂三十二个的时候它能占到发出总量的九成半。所以工具不是越多越好，注册表要按任务筛。

「工具执行失败和调用失败，你们怎么区分？」——两条路。消息本身不对是协议错误，走 JSON-RPC 的错误响应，那是给你看的；工具被正确调用但干活出了问题，回的是一个成功的响应，里面的结果带一个 isError 标志，那是给模型看的。分不开的话，模型会收到一堆它无能为力的东西，而你会漏掉真正该报警的那些。

板块 5自检问题

1. 有人说：「我们改用 TaskGroup 了，所以一个工具失败的时候，另外两个会被取消，副作用不会发生。」这句话对不对？

前半句对，后半句错，而且两句之间少了一步推理。

任务组确实会取消兄弟任务，第 8 节那张轨迹里两条取消发生在两百零六毫秒。但取消这个动作的作用范围是你这个进程里的协程：它让协程停止等待、抛出取消异常、把栈解开。工具服务在另一个进程里，它收到的是一个完整的 HTTP 请求，早就开工了。实测两条 done 照样在八百毫秒落进账本。

更直接的证据是三种并发写法的最终账本完全一样，都是两行。如果取消真能挡住副作用，任务组那一行应该比默认 gather 那一行少。

错在哪：把「我不再等它了」当成了「它不会发生了」。这两件事之间隔着一个进程边界，而边界那一侧不听你的。

2. 团队想给每个工具都加上重试：失败了就再调一次，最多三次。用今天的数评估这个提议。

这个提议有两笔账要分开算，而且它们指向不同的修法。

第一笔是副作用。重试的前提是这一步可以安全地重来，而昨天第 12 节已经把这件事讲透了：崩溃恢复免费给你的只有至少一次，想要恰好一次得每一步自己带键。重试把这个问题从「偶尔崩一次」放大成「每次失败都必然重来」，所以没有幂等键的工具不能加重试，加了就是把偶发的重复变成常态。

第二笔是上下文。失败的那次要不要写进上下文？如果每次失败都追加一段错误，重试三次就是三段，而按第 11 节的账，这三段都要在后面每一轮里重发。写成一行摘要的话代价可以接受；写成堆栈的话，三段堆栈就是三千多字节，乘以剩下的轮数。

合理的做法是分层：能安全重来的工具在运行时内部悄悄重试，模型完全不知道有过这件事，上下文里一个字都不多；不能安全重来的工具不重试，直接把那一句话回给模型，由它决定下一步。

错在哪：把重试当成一个纯粹的可靠性设置。它同时是一个副作用问题和一个上下文预算问题，而这两者的修法都不在重试次数这个旋钮上。

3. 一条会话在第 2 轮工具报错，回给模型的是完整堆栈。有人说：「反正有前缀缓存，这段堆栈不会重新计算，成本可以忽略。」哪儿错了？

这句话把「算」和「传」当成了一件事。

前缀缓存能做到的事情是：模型那一侧不必重新计算前面已经算过的 token。这一点在 agent 场景确实成立得很好——Day 16 量到顺序重放时命中率能到 84.5%，靠的正是上下文只往后长、不改前面这个性质，而追加一段堆栈同样不破坏这个性质。

但字节还是要传。第 11 节量到，那段堆栈在第 2 轮末尾进上下文之后，第 3 到第 6 轮各要把它完整地重新序列化、写进 socket、跨过网络一次，四次合计四千四百八十字节，让整条会话的发出总量涨了七成二。这一段路上前缀缓存一个字节都省不掉。

还有第二处代价：这段堆栈会变成缓存里的若干个块，一直占着不放，把别人的复用距离往外推。Day 16 那张容量扫描表说明，命中率掉下来的一种典型原因就是这个。

错在哪：把前缀缓存当成了「上下文变长不要钱」的许可证。它省的是模型那一侧的计算，运行时这一侧的传输和缓存容量都照付。

4. 有人提议：把工具的 description 写得越详细越好，「反正只是几句话」。用第 4 节的数评估。

「只是几句话」这个判断的问题在于它数错了单位。

一个工具的完整说明书量出来是六百七十字节，其中说明文字占相当一部分。而这份说明书的位置在上下文最前面，属于每一轮都要原样重发的那一段——所以它的真实价钱是字节数乘以轮数，再乘以工具数。

把数代进去看：挂三十二个工具，每一轮要发两万一千多字节的注册表，六轮累计十二万九千多，占整条会话发出总量的九成半；而真正的对话从头到尾只有六千二百字节。这时候多写几句话不是多几句话，是多几句话乘以一百九十二。

但这不等于说明要写得越短越好。说明是模型挑工具的唯一依据，写得不清楚会直接变成第 12 节那种反复出错的循环，而每一次出错的代价同样按轮数收。真正该做的是把两件事分开：说明只写模型需要的（这个工具在什么情况下该用、参数是什么意思），实现细节写成代码注释——后者不会被发给模型。

错在哪：只看了这段文字自己有多长，没看它会被复制多少份。

板块 10今日五句话

把这一页扣过去，用自己的话答下面五个问题，每题一两句。

1 · 模型凭什么知道你有哪些工具？这份「凭什么」在一条 K 轮会话里要花多少字节，按什么方式增长？

2 · 一轮里并发发出三个工具调用，其中一个失败了。四种收法在「什么时候返回」「拿到几个结果」「副作用发生几次」这三件事上分别是什么答案？哪一件是四种都改不了的？

3 · 超时之后 asyncio.timeout 取消了那条协程。此刻工具服务那一侧在干什么？要让它真的停下来，还缺哪一步？

4 · 一段一千零八十八字节的堆栈在第 2 轮进上下文，一条六轮会话为它多付多少字节？这个数是怎么算出来的？

5 · 「工具调用失败」这句话盖住了哪两件不同的事？它们各自回给谁，为什么不能混成一条路？

逐句自查

第 1 句如果只写「靠工具注册表」，缺了后半问。要给出增长的形状：注册表在上下文最前面，每一轮原样重发一次，所以是 K × 每个工具的字节 × 工具数，对轮数是一次方。再补一个量级：一个工具约六百七十字节，挂三十二个跑六轮，它占发给模型的总量的九成半。

第 2 句如果只答了前两件事就漏掉了今天最要紧的一件。第三件的答案是：三种并发写法完全一样，都是两行——发出去几个调用就发生几次副作用，这一件不在收法的选择范围里。串行那一行只有一行，唯一的原因是第三个工具从来没被发出去。

第 3 句如果写成「工具服务已经被取消了」就答反了。它什么都不知道，照常 sleep 完、照常写下那行 done——实测运行时三百毫秒出头就返回了，副作用八百毫秒才落地。缺的那一步是把取消送到对面，而且对面要在产生副作用之前查一次。

第 4 句如果只写「一千零八十八乘以四」就差了一点。每一次重发多付的是一千一百二十，多出来的四十字节是二十二个换行和十八个引号在 JSON 里各被转义成两个字符；四次合计四千四百八十。乘数是四，因为错误在第 2 轮末尾进上下文，之后还剩四轮。

第 5 句如果答成「一种是网络错误一种是业务错误」就抓错了分界。分界不在错误的成因，在这段信息回给谁：消息本身不对是协议错误，走 JSON-RPC 的错误响应，给你看；工具被正确调用但干活失败，回的是一个成功的响应加一个 isError 标志，给模型看。混成一条路的后果是模型收到一堆它无能为力的东西，而你漏掉真正该报警的那些。
