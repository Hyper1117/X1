第 1 题 · Day 22 · 杀干净与读得到

昨天那张四种杀法的表里，「只杀直接子进程」剩 2 个后台进程，「杀整个进程组」剩 1 个，而后两种做法都剩 0 个。前两行报出来的 duration_ms 是 4019 和 4022，后两行是 1018 和 1083，超时预算都是 1000 毫秒。

一段模型生成的代码用 start_new_session=True 起了一个后台进程，它躲开了按进程组发的信号。为什么它躲不开后两种做法？另外，前两行多出来的那三秒是在等什么，为什么这一等会让已经打印出来的那行日志一起消失？

展开答案

setsid 改的是这个进程属于哪个进程组和哪个进程会话，它改不了两件事：这个进程在哪个进程号命名空间里，以及它被记在哪个 cgroup 的名单上。第三种做法杀的是命名空间里的 1 号进程，内核会把这个命名空间里剩下的全部收走；第四种做法读的是 cgroup 的名单，而新建的子孙自动继承父进程的 cgroup，退不出去。两条路都不经过「分组」这个可以被被杀方自己改掉的东西。

那三秒是读回 stdout 的二次超时被用满了。子进程的标准输出是一根管道，读端在执行服务手里。管道读到结尾的条件不是「写的那个进程死了」，而是「所有持有写端的进程都关掉了它」。fork 会把父进程打开的每个文件描述符原样复制给孩子，所以两个还活着的后台进程手里各握着一份写端。对照实验把后台进程的 stdout 指到 /dev/null，同样的杀法，杀完之后的读只花了 19.3 毫秒。

那行 started 消失，是因为读的那一侧等满三秒之后整个放弃了，已经躺在管道缓冲区里的字节跟着一起被丢掉——不是被截断，是一个字都没有。

接今天：昨天问的是这三秒怎么来的，今天问的是它记在谁的账上。第 8 节会看到，同样一批调用，这三秒放在哪一段里，会让你的指标板指向两个完全不同的地方。

第 2 题 · Day 20 · 窗口开大之后

一条 30 轮会话，头部 1024 个 token，用「每一轮都丢掉最早的那一轮」这种滑动窗口裁法。窗口从 4096 换成 8192，别的一个字不动。

这条策略真正要算的 token 会变多还是变少？给出两档的数字。再解释：为什么「满了就丢掉一半」在同样的改动下走势完全不同？

展开答案

变多，从 56806 涨到 89187，涨了将近六成。窗口 2048 那一档是 22455，所以这条线是单调往上的。

机制是一句话：每一次断点之后要重算的量等于「窗口减头部」。滑动窗口每一轮都在上下文最前面动刀，每一轮都制造一个断点；断点之后能对上的只有头部那 1024 个 token，这个数跟窗口多大没有关系。而每轮的 prompt 长度因为始终贴着上限，约等于窗口。窗口翻倍，单次断点的代价跟着翻，断点次数又不下降，总量就往上走。

「满了就丢掉一半」那三档是 10667 / 12567 / 15750，也在涨，但从一万涨到一万六，很温和。它的断点次数随窗口下降——窗口越大越晚顶破、顶破得越少，单次变贵和次数变少两个方向抵消掉大部分。

接今天：那天把 token 折成了时间，用的是一条前向耗时曲线的斜率。今天折的是另一样东西——钱。同一批 token 数，换一张单价表，结论会不会跟着变，第 12 节有答案。

第 3 题 · Day 16 · 顺序换了一下

40 个任务各 6 轮，共 240 条请求。缓存开到 8192 个 token 位、块大小 16，按「一个任务从头做到尾」的顺序重放，token 级前缀命中率是 84.5%。一个 token 都不改，只把顺序换成「40 个任务轮流各推进一轮」，命中率变成 31.9%。

这 52.6 个百分点丢在什么机制上？要追平 84.5%，缓存得开到 131072 个 token 位——这个数不是试出来的，它是怎么算出来的？

展开答案

丢在复用距离上：一份数据被用过之后，到它下一次被用之前，中间来过多少别的数据。成组顺序下，一个任务的第 2 轮紧跟着第 1 轮，中间没有别人，所以缓存只要装得下一条会话的上下文就够了；交错顺序下，两轮之间隔着另外 39 个任务将近十万个 token 的块，LRU 把先前那些块全挤掉了。

131072 的来历：40 个任务各自跑完最后一轮时的上下文加起来是 126856 个 token，131072 是扫描点里第一个大于它的值。也就是说交错顺序下，缓存必须同时装得下所有在途会话的全部上下文。中间几档正好演示了「差一点」的后果——32768 只到 35.7%，65536 也才 51.0%。

接今天：那天量的是命中率，一个比例。今天要把这个比例挂到账单上——命中的那部分 token 不是不要钱，是换了一档单价。第 11 节会看到这一档在一条 agent 会话里占多大。

板块 2 · 第一部分从一行日志到一棵树

先把你现在的查法摆出来，再逐条说明它在哪儿不够，最后给不够的那几处各配一样东西。

1. 你现在会怎么查一条慢会话

线上有人说「我那个任务转了快一分钟」。你手上有这个运行时的日志，你会怎么办？

作为后端工程师，第一反应大概是这样：在循环的每一步前后各打一行日志，带上时间戳，出了事去日志里 grep 一下，把相邻两行的时间戳一减，就知道哪一段慢。这个办法在你过去写的接口上一直很好用，因为那些接口一次请求做一件事，日志是一条一条挨着的。

放到 agent 运行时上，它会在四个地方断掉。

#断在哪儿为什么
1日志行不再挨着几十条会话同时在跑，每条都在往同一个文件里写。你 grep 出来的相邻两行，很可能属于两条不同的会话。
2一条会话不止一个进程Day 17 那天推理服务自己就拆成了前端和引擎两个进程；再往外还有工具执行那一侧。日志分散在几台机器几个文件里，时间戳还未必对得齐。
3轮数事先不知道你没法预先写死「第几行减第几行」。一条会话可能转 3 轮，也可能转 30 轮。
4有些段是套在一起的「执行工具」这一段里面还套着「起沙箱」「跑代码」「读回输出」。两个时间戳一减只给你最外面那一层。

第 1 条最好办，也最能说明补法的形状。

2. 给每条记录配一个号，再配一个「谁生的」

要让同一条会话的日志行能被挑出来，最省事的做法是给每条会话生成一个随机的号，这条会话产生的每一行都带上它。查的时候不再 grep 关键字，而是按这个号筛。这个号在业内叫 关联 ID（correlation id）。

光有它还解不了第 4 条：同一条会话里，「执行工具」和「跑代码」都带着同一个号，你还是不知道后者是套在前者里面的。所以再给每条记录配第二样东西：它自己的一个号，以及生它的那条记录的号。

有了这两样，一条会话的所有记录就不再是一串，而是一棵树。这种「一段有始有终、带着自己的号和父亲的号」的记录，就叫一个 span（跨度）；同一条会话的全部 span 合起来叫一条 trace（追踪）；那个原来叫关联 ID 的东西，在这套说法里叫 trace_id，每个 span 自己那个号叫 span_id，父亲那个叫 parent_span_id。

一个 span 上除了这三个号和起止时刻，还挂三类东西：

挂什么叫什么放什么进去
键值对属性（attributes）整段期间都成立的事实：模型名、工具名、这一轮是第几轮、用了多少 token
带时刻的一行字事件（events）段里某个瞬间发生的事：第一个 token 到了、重试了一次、抛了个异常
成/败状态（status）这一段是正常结束还是出错结束

这三样的分工可以这么记：属性回答「这一段是什么」，事件回答「这一段里什么时候发生了什么」，状态回答「这一段成了没有」。属性挂错成事件，你就失去了按它筛选的能力；事件挂错成属性，你就失去了它发生的时刻。

把这套记录装到一个系统上，让你能事后从它吐出来的数据里，问出没有预先设想过的问题——这个能力叫 可观测性（observability）。它和监控的分界就在「没有预先设想过」这几个字上：监控回答你事先想好要问的那几个问题，可观测性要求你在数据被产生的那一刻，就把足够多的东西记下来。

给已有的代码加上这些记录的动作，叫 埋点 / 插桩（instrumentation）。这个词 Day 3 出现过一次——那天区分采样式剖析器和插桩式剖析器，插桩指的是「在每个函数出入口塞代码」。是同一个词同一个意思，只是这次塞的位置由你自己挑，不是工具替你塞满全部函数。

3. 号怎么跨进程传过去

第 2 条断点还没补：一条会话横跨好几个进程。运行时调模型是一次 HTTP 请求，执行工具可能是另一次。对面那个进程要想把自己的 span 挂到你这棵树上，它得先知道你的 trace_id 和当前那个 span 的 span_id。

做法是把这两个号写进请求头，跟着请求一起过去。这个动作叫 上下文传播（context propagation），头的格式由 W3C 定死了一份，叫 W3C Trace Context，头名 traceparent。

下面这一行是今天这台机器上真的注入出来的一个头，跟着它逐段拆开：

traceparent: 00-349c643473fb49eb7b36015af3d6ae84-916a4272db2f5ef5-03
             ^^ ^------------------------------^ ^--------------^ ^^
             |  |                                |                |
             |  trace_id：32 个十六进制字符        span_id：16 个    采样标志
             版本号，目前恒为 00                   （父给的）        01 = 采，00 = 不采

格式在 SDK 里就是一条正则，写在 opentelemetry/trace/propagation/tracecontext.py:18-21：版本 2 位、trace_id 32 位、span_id 16 位、标志 2 位，用短横线隔开。收到请求的那一侧解析这一行，把里面的 span_id 当成自己那个 span 的父亲，一棵树就跨过进程边界接上了。

最后那两位是采样标志。上面那个例子是 03 而不是 01，因为最低位是「采样与否」、次低位是另一个标志位；只有最低位跟采样有关。这一位在整条链路上是跟着传的，所以采不采这个决定是在链路的最前面做完的，后面每一跳照办——这叫 头部采样（head sampling），第 10 节还会回到它。

4. 字段名不能自己发明

树建起来了，属性该叫什么名字？你可以叫 model，也可以叫 llm_model，也可以叫 gen_ai.request.model。三种都能跑。

但只有第三种能让别人写的仪表板认得出来。这类「大家约好某类东西叫什么名字」的清单叫 语义约定（semantic conventions），OpenTelemetry 为大模型这一类专门出了一组，前缀是 gen_ai.。这些名字在装好的包里就是一堆常量，可以直接打开看：

GEN_AI_USAGE_CACHE_READ_INPUT_TOKENS  = "gen_ai.usage.cache_read.input_tokens"    # 第 286 行

最后那两行值得单独看一眼。约定里 token 的用量不是一个数，是四个数：整价的输入、命中缓存的输入、写进缓存的输入、输出。这四个数一开始就是分开的，因为它们的单价本来就不一样——这一点第 11 节整节在讲。

同一个文件里，gen_ai.usage.prompt_tokens（第 308 行）和 gen_ai.usage.completion_tokens（第 293 行）都标着 Deprecated，各自指向 input_tokens 和 output_tokens。这类改名在这套约定里很常见，抄的时候要看一眼包里的注释，别照着两年前的博客写。

所以属性名不是内部实现细节，它是接口。自己发明一套名字，意味着所有现成的仪表板、告警规则、成本分析工具对你的 trace 一句话都看不懂，全都要重写；而抄约定的成本，不过是打开这个文件查一次。

所以正确的算法不是减「时长之和」，是减「这些孩子在时间轴上盖住的那些区间的并集」。做法很直接：把所有孩子的 [开始, 结束] 按开始时刻排序，从左往右扫，重叠的合并成一段，最后把每段的长度加起来。这个量叫 区间并集（interval union），父 span 时长减去它，才是这个节点自身耗时（self time）的正确口径。自身耗时这个词 Day 3 讲火焰图时引过，那天所有的调用都是排着的、不重叠的，所以那天减和减并集是一回事。

关键结论

一旦一个节点的孩子里出现并发，「父减子之和」这个式子就失效，而且失效的方式很好认：它会给出负数。看到负的自身耗时不要去查代码有没有打错点，那通常是对的——它在告诉你这一层有并发。真正要换的是算法。

再往上看一层。整条会话的 session span 是 5652.46 毫秒，而 27 个后代的时长加起来是 12458.08 毫秒，是它的 2.2 倍。这个 2.2 倍没有任何物理含义，它只是「重叠被数了几遍」的一个副产物。任何把一棵 trace 里所有 span 时长加起来当「总耗时」的仪表板，都在报这个数。

换个说法：span 树是一份空间上的包含关系，不是一份时间上的划分。父亲包着孩子，说的是「孩子这段活儿是在父亲这段期间发生的」，不是「父亲的时间被孩子们分掉了」。加法要成立，得先保证被加的那些段两两不重叠——表 B 那条路成立，正是因为它沿着同一层从左到右走，不跨层。

一条会话真正的「时间去哪了」，要顺着另一条路读：从根出发，每一层挑那个决定了父亲何时结束的孩子，一路走到叶子。这条路叫 关键路径（critical path）。第 1 轮的关键路径是 chat（739.91）接上最长的那个工具（241.31）；三个工具里另外两个再快也不会让这一轮变短，只有 240 毫秒那个会。所以「该优化哪个工具」这个问题，答案不在三个工具的平均耗时里，在关键路径上出现的次数里。

还有一条路根本不采样，只是把粒度调粗：129 个流式事件不各成一个 span，而是变成这个 chat span 上的两个属性——首 token 的时刻、事件总数。Day 18 那天关心的每一轮首 token 延迟，两个属性就够了，用不着 774 个 span。

关键结论

账上最容易漏的不是算错，是漏记。正常结束的会话账都对得上，出错和被取消的那些会话最容易一分钱都不上账——恰恰它们花的钱一分不少。判断一套成本核算做没做对，看的不是总额，是「失败的会话在不在账上」。

    # 命中缓存那一档：和上一轮的公共前缀，向下取整到 16 个 token 的整块
    hit_tok = (approx_tokens(prompt[:common_prefix_chars(prompt, last)]) // BLOCK) * BLOCK
    _last_prompt[sid] = prompt

    await asyncio.sleep(TTFT_MS / 1000.0)                    # 首 token 之前
    if n_out > 1:
        await asyncio.sleep(ITL_MS * (n_out - 1) / 1000.0)   # 之后每个 token

    head = body["reply_head"]
    text = head + "词" * max(0, n_out * 4 - len(head))       # 正好折成 n_out 个 token
    inp = approx_tokens(prompt)
    return {"text": text, "usage": {
        "input_tokens": inp,
        "cache_read_input_tokens": min(hit_tok, inp),
        "output_tokens": approx_tokens(text)}}

跑起来之后 curl 一下，应该看到 output_tokens 正好等于你传的 n_out。如果不等，多半是 reply_head 比 n_out × 4 还长，说明这两个参数配得不对。

第 3 步：算自身耗时，看到那个负数

def union_ms(ivs):                    # ivs 是 [(开始纳秒, 结束纳秒), ...]
    ivs = sorted(ivs); tot = 0; cs, ce = None, None
    for a, b in ivs:
        if cs is None:      cs, ce = a, b
        elif a <= ce:       ce = max(ce, b)      # 和当前这段重叠，合并
        else:               tot += ce - cs; cs, ce = a, b
    if cs is not None: tot += ce - cs
    return tot / 1e6

对每个 turn 打两个数：父时长减孩子时长之和，父时长减孩子区间并集。前者应该是一个稳定的负数，后者应该是零点几毫秒。

验收标准：两个数的差，等于「三个工具时长之和减去它们的区间并集」。这个等式对得上，说明你的并集算对了。

第 4 步：把 CPU 那把秤按到 span 上，看它怎么崩

并发跑 1 条、8 条、32 条，每档在叶子 span 两端读 time.process_time_ns()，把差值全加起来，和整批会话真实消耗的 CPU 比。

验收标准：并发 1 那一档倍数应该接近 1，并发 32 那一档应该是几十倍。常见坑：如果并发 1 那一档也偏得很多，检查一下是不是把父 span 也算进去了——嵌套本身就会重复计一遍。

第 5 步：把账拆到「哪一轮引入的内容」

用第 2 步收下来的逐轮 usage，做两件事：按单价折成钱；再把每一轮的钱按「这段内容是哪一轮进的上下文」摊回去。然后把工具返回的字符数从 200 改成 2000，重跑，比较两条会话。

验收标准：execute_tool 那些 span 上的 token 数是 0，而两条会话的账单差了两倍以上。差额要能逐项对上——整价那一档的增量乘整价，加上缓存那一档的增量乘缓存价，等于总差额。对不上说明你把某一档记重了。

任务 B（约 40 分钟）· 用到你自己手上的东西

挑一个你自己写过的、内部有并发的服务或脚本——批量抓取、并发调几个下游、多线程处理一批文件都行。给它打三层 span：一次请求／一个批次／每个并发单元。然后只算一件事：每一层的自身耗时，用区间并集那个口径。

验收标准：你能指着某一层说出「这一层自己花了多少、剩下的都在等孩子」，并且指得出关键路径上是哪几个孩子。如果关键路径上反复出现同一个下游，那就是你该优化的那个；如果每次都不一样，说明瓶颈是并发度而不是某个具体下游。

板块 4工作现场

场景一 · 「工具调用的 P99 是 4 秒，可每个工具单独拿出来测都在 200 毫秒以内」

有人拿着指标板来找你：工具执行这条曲线的尾巴很长，可挨个工具压测都很快。

先问一句：这条曲线是从哪个 span 上读出来的？如果 execute_tool 这个 span 从「派出去」一直包到「结果拿回来、进程清理完」，那它里面至少混着三样东西——工具自己算的时间、超时预算被用满的时间、以及杀完之后等资源放手的时间。第 8 节那张表就是这个形状：同一批调用，整段记在一起是 4000.7 毫秒，拆开之后工具那一段是 1000.2，剩下 3000.4 在等管道。

动作是把 span 切开，切法照「坏掉的原因是不是同一类」这条判据。切完之后大概率会看到：工具那一段的 P99 正好等于你设的超时预算——那说明它不是慢，是被超时打断的；真正的尾巴在清理那一段上，而清理慢的原因昨天讲过，是某个后台进程还握着管道的写端。

场景二 · 「这个月的账单涨了三倍，请求数一条没多」

会话数没变，账单翻了三倍。三个方向，按能证伪的顺序查。

第一个方向是轮数。表 O 那条关系是：累计 input 大约是最终上下文的「轮数除以二」倍，所以平均轮数从 6 涨到 12，账就翻一倍——而轮数是模型每一轮的输出决定的，换个提示词、换个模型版本都可能让它变。这个数应该直接从 session span 的属性里读出来，不用猜。

第二个方向是工具往上下文里塞了多少。表 L 那两行：只把工具返回从 200 字符改到 2000，账单 2.43 倍。查法是把 execute_tool 上那个「返回了多少字符」的属性按工具名分组看分布——通常是某一个工具在某类输入下开始返回巨大的结果，比如一次搜索命中了一大堆。

第三个方向是命中缓存那一档的比例掉了。表 K 里它占 65.8%，如果掉到接近零，同样的 token 数账单会按整价和缓存价的比值往上跳。掉下去的原因 Day 16 和 Day 20 各讲了一半：可能是路由把同一条会话打散了，也可能是有人在上下文前面动了刀。分辨方法是看 gen_ai.usage.cache_read.input_tokens 是「所有会话一起掉」还是「只有某些会话掉」——前者指向路由和容量，后者指向那些会话触发了截断。

场景三 · 「出问题那条会话的 trace，中间少了一层」

一条超时的会话，trace 上 session 和几个 execute_tool 都在，中间的 turn 没了，几个孩子挂不上父亲。

先排除「那段代码没执行」——如果没执行，孩子也不会有。孩子在、父亲不在，说明这些 span 被产生出来了，只是没能送出去。第 10 节那张丢弃表给出了形状：丢的不是随机几条，是一整段连续的时间窗口，因为定长队列满了之后从最老的那头挤。而队列满，最容易发生在流量突增的时候。

能确认的办法是找 Queue full, dropping 那行警告，它就在丢弃发生的那一刻打出来。确认之后有三条路：把粒度调粗（第 10 节那个「129 个事件换成两个属性」）、把队列上限调大（代价是内存和一次丢得更多）、或者上尾部采样（代价是所有 span 得先攒齐）。三条路里最先该试的是第一条，因为它同时降的是 CPU、字节和丢弃概率。

同事和面试官常问的

  • 「你们的 trace 采样率是多少？」——这个问题真正在问的是你知不知道采样决定在哪里做。默认是头部采样，根 span 上决定完了往下传，靠 traceparent 最后两位。它的问题是出错的会话最想留却留不住，所以答案通常是两段：普通流量按比例头部采样，出错和超长的会话另走一条尾部采样的路。只答一个百分比等于没答。
  • 「一条会话的成本你怎么算？」——把这条 trace 上所有 chat span 的四档 usage 各自求和再乘单价。要点是「四档」不是「一个总 token 数」，以及「所有 chat」不是「最后一轮」。拿最后一轮的 input 估，24 轮的会话会估成实际的十二分之一。
  • 「trace 打细一点有什么坏处？」——三笔账一起涨：CPU（每个 span 二十几微秒，802 个 span 让运行时的 CPU 涨到 2.55 倍）、字节（同一条会话从 10 KB 涨到 272 KB）、以及丢弃概率（队列是定长的）。而且丢起来是丢一整段时间窗口，正好在你最需要的时候。
  • 「自身耗时怎么算？」——父 span 时长减去孩子们区间的并集。如果对方说「减去孩子时长之和」，一个反例就够了：三个并发的工具，那个式子会给出负数。
  • 「为什么不把每个 span 的 CPU 也记上？」——因为进程 CPU 时钟是全进程的，异步单线程下一个 span 的两次读数之间跑的可能全是别人的回调。32 条并发时按 span 摊出来的 CPU 之和是真实值的 42 倍。CPU 归因交给进程级指标加剖析器。
  • 「属性名为什么要用那么长的 gen_ai. 前缀？」——因为它是接口不是实现。用约定的名字，现成的仪表板和成本分析工具直接认；自己发明，这些全要自己写一遍，而且换一个工具再写一遍。

板块 5自检问题

1. 某个 turn 的自身耗时，用区间并集那个口径算出来是 180 毫秒。这一轮只有一次 chat 和两个并发工具，运行时的代码里没有任何重活。这 180 毫秒可能是什么？

两种可能，而且分辨方法不一样。

第一种：运行时真的在这一轮里干了 180 毫秒的活。最可能的地方是把上下文序列化成 JSON——表 O 那条关系告诉你，第 24 轮的 prompt 有六千多个 token，折成字符是两万多，序列化和拼接都不是零成本。这一种的特征是它随轮数增长。

第二种：有一段时间没有被任何子 span 盖住。并集口径算的是「孩子们盖住了多少」，没盖住的全部落进父亲的自身耗时里。典型的漏点是等许可（Day 14 那个并发上限）、等连接池（把建好的 TCP 连接留着复用的那个池子）给一条连接、以及队列里排队——这些都是真的在等，但没人给它开一个 span。这一种的特征是它随并发数增长，跟轮数无关。

分辨办法有两个。便宜的那个：把这个数按轮数和按并发数各画一条曲线，看它跟着哪个变。彻底的那个：给怀疑的那一段补一个 span，补完之后父亲的自身耗时应该塌回零点几毫秒——塌不回去说明还有别的洞。

错在哪：最常见的错是看到自身耗时不为零就去优化运行时的代码。第二种情况下运行时一行代码都没多跑，它只是在排队。

2. 为了降账单，有人把上下文改成「每轮丢掉最早的一轮」。trace 上 input_tokens 明显下降了，账单却涨了。为什么？

因为账单不是按 input_tokens 收的，是按拆开的四档分别收的，而这个改动把其中两档整个搬了家。

Day 20 量过这件事的 token 那一面：滑动窗口让发出量降到不裁剪的四成三，可要算的 token 变成 5.3 倍。今天的账单是同一件事的钱那一面。在上下文最前面动刀，从断点往后所有的块都对不上了（Day 16 那条块 hash 链），于是原本躺在 cache_read_input_tokens 那一档、只按十分之一单价付的 token，全部搬到整价那一档去了。

拿今天的比例估一下量级：表 K 里命中缓存那一档占 65.8%，单价是整价的十分之一。假设裁剪之后它塌到接近零，同样一份 token 的钱大约要乘上 1 / (0.342 + 0.658 × 0.1)，也就是两倍半左右。而 input_tokens 这个总数只降了不到一半。两个方向一叠，账单往上走。

错在哪：把 input_tokens 当成账单的代理指标。它不是。真正该盯的是「整价那一档」这一列，它才是钱。

3. 表 H 说 28 个 span 只让运行时的 CPU 涨 17%。有人据此说「埋点开销可以忽略，粒度想打多细打多细」。哪儿错了？

错在把一个百分比当成了结论，而它其实是一个乘法的结果。

那 17% 的构成是：28 个 span 乘每个二十几微秒，约 0.6 毫秒，落在一条会话 13.22 毫秒的 CPU 上。同一条乘法用在 802 个 span 上就是 18 毫秒，占比变成 155%。表 H 第三行量到的 2.55 倍，正是这条乘法算出来的。所以能忽略的不是「埋点」，是「28 个 span 这个量级的埋点」。

而且 CPU 只是三笔账里的一笔。字节那一笔从 10 KB 涨到 272 KB，是 26 倍；丢弃那一笔更不线性——队列上限是 2048 条，粒度乘 28 倍意味着能撑住的并发会话数除以 28，超过之后丢的是一整段连续的时间窗口。

错在哪：判据不该是「埋点占了百分之几」，该是「这条链路一秒钟产生多少个 span」。前者随你现在的流量变，后者是设计的性质。

4. 一条会话超时失败了，成本报表里没有它。有人说这挺合理——失败不该收钱。哪儿错了？

钱和成功与否没关系。这条会话在失败之前已经调了几轮模型，每一轮的 token 模型那一侧都算过了，账照收。报表上没有它，只说明你的代码把 usage 记在了「正常返回」那条路径上，异常路径直接跳过了。

这个漏法有两个后果。一是总额系统性偏低，而且偏多少取决于失败率——失败率一涨，报表反而显得更省钱。二是它漏掉的恰恰是最贵的那一类：失败的会话通常伴随重试，而重试意味着同一段上下文再送一遍，Day 18 那六种崩溃组合已经量过这件事的形状。

修法在第 13 节那张表的第一行：结束原因是 session 这一层的属性，成本汇总按 trace 走而不是按返回值走。判断一套核算做没做对，看的不是总额，是失败的会话在不在账上。

5. 决定「这两段该不该合成一个 span」的判据是什么？举一个今天见过的例子。

逐句自查

  • 第 1 句如果写成「因为孩子的时间没算全」就错了，方向反了——是算重了，同一段时间被几个并发的孩子各数了一遍，所以减出来是负数。正确算法要点是「区间并集」，不是「取最大的那个孩子」；取最大的那个只在「孩子们全部同时开始」时才碰巧对。
  • 第 2 句如果只写「因为有并发」就不够。要点是为什么并发会坏事：这个时钟返回的是整个进程的 CPU，而 asyncio 是单线程的，一个 span 挂在 await 上的时候事件循环正在跑别人的回调，那些 CPU 全落进了这两次读数之间。补一句量级会更好：32 条并发下加起来是真实值的 42 倍。
  • 第 3 句如果只答「它引入了多少 token」就少了一半。另一半是「它之后还剩几轮」——同样一段内容，第 1 轮引入和第 5 轮引入，尾巴长度差四轮。不出现在自己那个 span 上，是因为工具本身不调模型，那笔钱在后面每一个 chat span 上。
  • 第 4 句如果写成「丢掉最新的」就错了，正好反过来：队列是定长的、新的从左边进，挤掉的是最右边最老的那条。落到眼前的样子是一整段连续时间窗口的 span 集体消失，剩下的孩子成了孤儿——不是随机零星地缺几条。
  • 第 5 句如果答「按代码里的函数边界切」就错了。判据是「这两段坏掉的原因是不是同一类」。今天的例子是 execute_tool 和 release_output：一个坏了要去查工具，一个坏了要去查有谁还握着管道的写端，修法完全不同，所以必须分开。
