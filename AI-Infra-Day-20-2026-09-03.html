第 1 题（Day 19 · 一段文字的价钱由它进去的时刻决定）

昨天量到：一段一千零八十八字节的堆栈在第 2 轮末尾追加进上下文，一条六轮会话为它多发四千四百八十字节。

现在把同一段堆栈挪一挪：它改成在第 5 轮末尾才进去，别的一个字不动。这条六轮会话为它多发多少字节？把算法写出来，再用一句话说清楚这条规律的形状。

展开答案

多发一千一百二十字节。

算法和昨天完全一样，只有乘数变了。每一次重发要付的不是一千零八十八，是一千一百二十——多出来的四十字节是那些换行和引号进 JSON 时被转义多占的。乘数等于「这段东西之后还剩几轮」：第 2 轮末尾进去，第 3 到第 6 轮各重发一次，乘数是四；第 5 轮末尾进去，只剩第 6 轮一轮，乘数是一。

形状是这样的：上下文只往后长、从来不改前面，所以任何进去的东西都会被它后面的每一轮原样搬一遍。一段文字的价钱等于它自己的长度乘以它之后还剩几轮——同一段东西，进去得越早越贵。

接今天：既然进去得早的最贵，那把进去得早的那些清出来，是不是就该最省？今天整页在算这笔账，而它有一个非常不直观的答案。

第 2 题（Day 17 · 停止串为什么判在前端）

vLLM 的引擎进程里没有分词器，它手上只有整数。一条请求设了停止串，这件事的判定发生在前端进程，而且判出来之后还要再往引擎发一条消息。

为什么这件事引擎自己判不了？为什么判出来之后还要多一个来回？

展开答案

引擎判不了，是因为停止串是一串字，而引擎手上是一串整数。这两者之间不是一一对应的：一个停止串可能横跨两个 token，也可能只占某个 token 的后半截。要认出它，必须先把整数拼回文字，而拼回文字这件事需要分词器，分词器住在前端。

多的那个来回是这么来的：引擎按自己知道的条件（到达 EOS、到达长度上限）判断这条请求还没结束，于是继续往下算；前端拿到新吐出来的字，拼进已有的文字里，这才发现停止串出现了。此刻引擎那一侧还在跑，所以前端要再发一条中止消息回去。

这不是设计缺陷，是「引擎不碰文字」这个决定的必然代价。要让引擎自己判，就得把分词器搬进引擎进程，那套进程隔离也就没了。

接今天：今天要做的事也全部发生在运行时这一侧。上下文怎么拼、裁掉哪一段，引擎一个字都不知道——它收到的只是一串 token，然后拿这串 token 去和自己缓存里的块对。所以你在这一侧动的每一刀，对面都只能靠「对不对得上」来感知。

第 3 题（Day 13 · 为什么起一个容器要两条命令）

runtime-spec 给容器定了四个状态，其中 created 是「创建操作已完成，但用户指定的那个程序既没退出、也还没被执行」。

如果规范只留 run 一条命令、不单独定义 create 和 start，会失去什么？举一类具体的东西说明。

展开答案

失去的是「环境全搭好了，但用户的程序一行都还没跑」这个可以被外人插手的时刻。

规范把生命周期拆成十三步，其中有四类生命周期钩子的插入点落在造完环境之后、真正 execve 用户程序之前。网络插件要在这个时刻把网卡塞进去，设备注入要在这个时刻把设备节点建好——这些动作必须发生在命名空间已经建好之后，又必须发生在用户程序看到这个环境之前。只有一条 run 的话，这个窗口不存在，插不进去。

接今天：今天第四部分要给会话造一个形状完全一样的时刻。一条被打断的会话重新跑起来，不能一上来就往下走——得先有一个「状态从库里装回来了，但下一轮还没发出去」的时刻，因为装回来的东西对不对，决定了下一轮的代价。

先把「上下文太长了」这句抱怨拆成可以数的东西：里面装了什么、哪一块在长、第几轮会满。然后看现成的库满了之后是怎么做的。

1. 手边那一行截断代码

上下文顶到上限的那一刻，你会先删哪一段？

你手边多半已经有这么一行，或者迟早会写出来：

if len(ctx) > LIMIT:
    ctx = ctx[-LIMIT:]      # 只留最后这么多，前面的不要了

这一行是对的，能跑，而且它抓住了正确的直觉：新的比旧的重要。它有两个问题，一个今天下一节就能看见，另一个要到第三部分才露面。

先说名字。模型能接受的输入长度有个上限，Day 15 那个 max_model_len 就是它——那天是从显存那一侧看它，因为每一个 token 位都要真的占住一块 KV cache。今天从运行时这一侧看同一个数：它是你能花的总额。

你要花的东西不止一样：系统提示词要占、工具注册表要占、历史轮次要占、这一轮模型要吐出来的东西也得留出位置。给这几样分别定下能占多少，这件事叫做上下文预算（context budget）。

这个词要和 Day 9 那个「token 预算」分开。那一个是调度器在一个引擎步里手上有多少 token 可以派，管的是这台机器这一瞬间的吞吐；今天这一个是一条会话在窗口上限之内怎么分配，管的是这条会话能记住多少。两个数没有任何换算关系，只是碰巧都叫预算。

3. 满了之后的四种做法，现成的库是怎么写的

先把四种做法用大白话摆出来，再一个一个给名字。

  • 每次刚好超一点，就丢掉最早的那一轮，让长度始终贴着上限——这叫滑动窗口（sliding window）。
  • 超了就一口气丢到半满，丢完能撑好几轮再说——它和上一种同属截断（truncation）：丢掉的内容不再出现，是真的没了。
  • 丢之前先把那几轮总结成一小段，用这一小段顶替原来那一大段——这叫上下文压缩（context compaction）。这个英文词 Day 15 出现过一次，那天说的是把 KV cache 里的碎片挪到一起，和今天不是一件事，只是同名。
  • 什么都不丢，换一个窗口更大的模型。这一条不需要新词，但它有代价，第 8 节会把这个代价量出来。

这几件事不用你从头写。langchain-core 这个包里有一个专门做裁剪的函数，签名里那几个参数就是上面这些选择：

# langchain_core/messages/utils.py:1133 起
def trim_messages(
    messages, *, max_tokens,
    token_counter,                     # 怎么数长度，见下
    strategy = "last",                 # :1141 保留末端还是首端
    include_system = False,            # :1145 第 0 条系统消息要不要单独留下
    start_on = None,                   # 裁完之后第一条必须是哪种消息
    ...
)

strategy 这一项就是末端保留 / 首端保留（trim strategy "last" / "first"）；include_system 是保住系统消息（include_system），它把第 0 条系统消息拎出来不参与裁剪，剩下的预算再给后面的消息（:2086 起那个函数里，先减掉系统消息的长度再往下算）。

还有一个参数值得单独看：token_counter。这个函数需要知道每条消息有多长，而真去跑一遍分词器是要花钱的。库里给了一个不跑分词器的默认实现（:2244）：

# langchain_core/messages/utils.py:2244-2248
def count_tokens_approximately(
    messages, *,
    chars_per_token = 4.0,             # 按每 4 个字符算一个 token
    extra_tokens_per_message = 3.0,    # 每条消息再加 3 个，算那些特殊标记
    ...
)

字符数除以四，每条再加三个——这种做法叫近似计数（approximate token counting），函数自己的文档里写着这个四是「常见英文文本」的经验值。裁剪的预算是拿它算的，所以你的预算天然带着一个误差；换一种语言、换一个模型的词表，这个四就不再准。

把这个函数真的跑一遍，看它裁出来什么。造一段十六条的对话：一条系统消息，然后五轮，每轮三条——用户问一句、模型发一次工具调用、工具回一个结果。预算给一百二十个 token。

第一行是最常见的写法，也是最该盯一眼的那一行。裁完之后紧跟在系统消息后面的是一条工具结果——而产生这个结果的那次工具调用，已经被裁掉了。模型会看到一段自己没发出过的工具返回。这种东西叫悬空的工具结果（dangling tool result），很多模型的接口会直接判成格式非法。

第三行就是修法：加上「裁完之后第一条必须是用户消息」这个约束，那条悬空的结果被一起丢掉。代价写在第三列——同样的预算，留下的东西少了十六个 token。库把这个约束做成参数而不是默认行为，是因为消息该怎么配对由你用的模型接口定，库不替你决定。

第四行是首端保留，它留下了最早的几条，最后停在一条没人回答的用户消息上。对一段还要往下走的对话来说这几乎从来不是你想要的；这个选项存在，是为了另一类场景——比如你要的是这段对话的开头而不是结尾。

压缩那一条也有现成的写法。openai-agents 这个包里有一个会自动做压缩的会话装饰器，它的默认触发条件写得很直白：

# agents/memory/openai_responses_compaction_session.py:28
DEFAULT_COMPACTION_THRESHOLD = 10

# :58-60
def default_should_trigger_compaction(context):
    """攒够十条候选就压一次"""
    return len(context["compaction_candidate_items"]) >= DEFAULT_COMPACTION_THRESHOLD

攒够十条才动一次，这个数叫压缩阈值（compaction threshold）。同一个文件里（:34-54）还规定了哪些条目算「候选」：用户发的消息不算，已经是压缩产物的条目也不算——也就是说，被压掉的是模型的输出和工具的结果，用户原话留着。

「攒够十条才动一次」这个设计，和上面滑动窗口那种「每次超一点就削一点」是两种完全相反的节奏。哪一种更贵，第三部分整章在回答。

4.2 一条会话在底座里是什么

没有文字，没有分词器。一条会话就是一串整数加一个结构：

会话 t0 = {
  "head":  [8134, 291, 30028, ...],          # 1024 个整数：系统提示词 + 工具注册表
  "turns": [([...331 个...], [...106 个...]), # 第 1 轮：送进去的那一截 / 模型吐出来的那一截

6. 裁掉最早那一轮的那一刻，能对上的只剩头部

你把上下文前面动了一刀，缓存里那些块还认得出这条会话吗？

先回忆缓存那一侧是怎么认块的。Day 16 讲过：把上下文切成十六个 token 一块，从第 0 块开始逐块串 hash——每一块的 hash 用「父 hash 加上本块的 token」一起算出来。查的时候从第 0 块往后走，走到第一个对不上的就停。

这个算法有一个直接的后果：能被复用的只可能是前缀，而且是从头开始一个 token 都不错位的前缀。往末尾追加东西不破坏它——第 5 轮的上下文完整地包含第 4 轮的上下文作为开头，前面那些块照样对得上。这就是 Day 16 说的「agent 的上下文天然是一条不断加长的公共前缀」。

裁剪做的事情正好相反。它动的是前面。

第 3 到第 7 轮那一段的内容一个字都没变，可它对不上了。原因不在内容，在位置：它前面少了两轮的九百七十个 token，于是它的第一块从原来的第 91 块变成了第 64 块，块的切分边界跟着整体平移，每一块装的 token 组合都变了，串出来的 hash 自然全不一样。

所以第 8 行的命中块是 64——缓存里能对上的到头部为止，头部之后的一切都要重新算一遍。这件事有个名字，叫前缀失效（prefix invalidation），发生失效的那个位置叫断点。

关键结论

断点越靠前，重算得越多；而所有裁剪策略天然都从最前面动手，因为最前面的东西最旧、最该丢。「该丢的那一段」和「最贵的那个位置」是同一段，这就是上下文压缩这件事的根本代价。

顺带解释了 Day 19 那道温故题的另一半。那天的结论是「一段东西进去得越早越贵」，因为它之后每一轮都要重发一次。今天补上的是：把它清出去也不免费，而且清得越早的东西，清的时候赔得越多。

这才是这四行之间真正的取舍：不是「省字节」对「省计算」——那两件事在这张表上是同向的；是模型每一轮能看见多少历史对要重算多少。想让模型多记住一轮半，你得为此多算三倍半的 token。

摘要那一行给的是第三条路。它的平均在场轮数最低，只有三点八轮，但被丢掉的那些轮并没有彻底消失——它们变成了那个一百二十八个 token 的块，一直挂在头部后面。用这个块换回来的信息，代价是比丢一半那一行多算四百四十三个 token，以及多一次断点。

10. 读回来要多久

一条会话要活过进程重启，它的状态就得放在进程之外的某个地方——一个日志文件、一份快照、或者一张数据库表。这个东西叫会话存储（session store）。

11. 读回来的那一份，可能不是原来那一份

进程重启之后接着往下跑，代价在磁盘上吗？

先把上一节的数放进比例里。最长那一档、最慢那种读法，两点二毫秒；一轮模型调用七百三十八毫秒。恢复的钱不在磁盘上，差着三百多倍，怎么存都付得起。

12. 揭晓（三）：亲和保住的是会话私有那一段

把一台机器换成好几台，缓存就不再是一份了——每台副本各有各的一份，互相看不见。同一条会话这一轮落在甲、下一轮落在乙，乙那一侧对这条会话的历史一无所知。

躲开这件事的办法很直白：把同一条会话的每一轮都送回同一台副本。这个做法叫会话亲和（session affinity），也叫粘性会话（sticky session）。

八条会话轮流各推进一轮，每台副本的缓存都开得足够大，装得下一切——容量在这张表里不可能成为解释。

关键结论

命中率掉下来的时候要先问是哪一半掉了。头部那一半掉，说明副本太多、流量太散，每台都在重复付冷启动的钱；会话私有那一半掉，说明同一条会话被打散到了不同副本上。前者加机器只会更糟，后者要动的是分派规则。

任务 A（必做，约 80 分钟）· 把裁剪的两笔账同时记下来

第 1 步：先有一个会数块的缓存

今天所有结论都建立在「能对上几块」这一个数上，所以第一件事是把这个数算对。照 Day 16 那套做法：切成十六个 token 一块，只对装满的块算 hash，每一块的 hash 用父 hash 加本块 token 一起串出来。

def _chain(self, tokens):
    """把一串 token 切成整块，逐块串 hash：父 hash + 本块 token。"""
    hs, parent = [], b"\x00" * 32
    for i in range(0, len(tokens) - len(tokens) % BLOCK, BLOCK):
        h = hashlib.sha256(parent + bytes(str(tokens[i:i+BLOCK]), "utf-8")).digest()
        hs.append(h); parent = h
    return hs

def lookup(self, tokens):
    """从头数连续命中了几块，遇到第一个缺失就停——因果注意力只认前缀。"""
    n = 0
    for h in self._chain(tokens):
        if h not in self.order: break
        self.order.pop(h); self.order[h] = None   # 命中即刷新 LRU 位置
        n += 1
    return n

验收标准：造一串 token，查一次（应当零命中），插进去，再查一次（应当全部命中）；然后在这串 token 的开头插一个数再查，命中必须掉到零。最后一项是今天整页的地基，掉不到零说明 hash 没串起来。

常见坑：对没装满的那个尾块也算 hash。这样下一轮那个块被填满之后 hash 会变，你会看到一个莫名其妙的、每轮都差一块的命中率。

第 3 步：写出四种裁剪策略

四种做法的区别只在两行循环条件上——丢到刚好装得下，还是丢到目标水位以下。

def apply_policy(policy, head, kept, summary, window, keep_ratio, rng):
    """裁剪只在这里发生。返回 (新的 kept, 新的 summary, 这一轮动没动过前面)。"""
    def total(k, s): return len(head) + (len(s) if s else 0) + sum(len(u) + len(a) for u, a in k)
    if policy == "none" or total(kept, summary) <= window:
        return kept, summary, False
    if policy == "sliding":                       # 每次只丢最早的一轮，丢到刚好装得下
        while len(kept) > 1 and total(kept, summary) > window: kept = kept[1:]
        return kept, summary, True
    if policy == "chunk":                         # 一次丢到目标水位以下，丢完能撑好几轮
        while len(kept) > 1 and total(kept, summary) > window * keep_ratio: kept = kept[1:]
        return kept, summary, True
    if policy == "summary":                       # 丢掉的那些换成一个定长的摘要块
        dropped = 0
        while len(kept) > 1 and total(kept, summary) > window * keep_ratio:
            dropped += 1; kept = kept[1:]
        if dropped:
            summary = [rng.randrange(VOCAB) for _ in range(SUMMARY_TOKENS)]
        return kept, summary, True

那个 len(kept) > 1 不是装饰。窗口小到一定程度时，头部加上当前这一轮就已经超了，没有这个保护，循环会把当前轮也丢掉，然后你会得到一条空的上下文。

验收标准：把窗口开到大得装得下整条会话，四种策略跑出来的每一个数都必须完全相同。不相同说明某个策略在不该触发的时候动了手。

常见坑：裁完之后忘了重新拼上下文，还拿着裁之前那一份去查缓存。症状是命中率完全不掉，好得不像话。

  3. 今天四种策略都从最前面动手，所以断点全落在头部之后。设计第五种：保住头部和最近几轮，只挖掉中间那一段。断点位置会往后挪多少？命中率会好到什么程度？再回答：这么做会不会让消息配对出问题？
  4. 4.3 节那张表里写着今天没有引用计数——真实引擎里正在跑的请求，它的块是占住不能淘汰的。给模拟器加上这一层，然后回答：加上之后，第 12 节那张路由表里哪几行会变？
  5. 第 3 节那个近似计数按每四个字符算一个 token。找一个你能拿到的真分词器，对同一段中英混排的文本各数一遍，看这个四偏多少。然后回答：如果它系统性地少算，你的窗口预算会以什么方式出事？
  6. 第 12 节量的是命中率。把它换成「端到端的首 token 延迟」再看一遍：亲和那八成二和随机那五成四，折成时间之后差多少？这个差值和第 9 节那条斜率是什么关系？

板块 4工作现场

场景一 · 「加了截断之后，账单没降，首 token 反而变慢了」

抱怨里的那两件事其实是同一件事的两面，而且第 7 节那张表已经把它完整地演过一遍。

先问一个问题：这个截断是每轮都在动，还是攒够了才动一次。看代码最快的办法是找那个 while 的退出条件——是退到窗口以下就停，还是退到某个更低的水位。前者每一轮都会制造一个断点。

然后去要两个数：每轮发出的 token，和每轮实际 prefill 的 token。多数团队只有第一个。第二个通常要从推理服务那一侧取，vLLM 这类引擎会报前缀缓存的命中情况。两个数一起看，「发出去的少了、要算的多了」这句话就是一张图，不需要争论。

止血的做法是把节奏改掉：设一个触发水位和一个目标水位，超了才动，一次动到目标水位以下。长期的做法是把「这次裁剪让多少 token 从命中变成重算」记成一个指标——没有这个数，下一次有人提「要不要换个更大窗口的模型」的时候，还是只能靠感觉。

场景二 · 「重启之后前几轮特别慢，跑一会儿就好了」

「跑一会儿就好了」这半句是最强的线索：它说明慢的不是恢复本身，是恢复之后的头几轮。恢复本身是一次性的，而且按第 10 节那张表，就算是最长的会话、最慢的读法，也只有毫秒级。

要看的第一样东西是恢复出来的上下文和崩之前那一份逐字节比一遍。两个常见的差别来源：一是读回来的条数被某个 limit 限制住了；二是重新序列化的时候形状变了——键的顺序、空格、浮点数的打印格式，任何一处不同都够把前缀打断。

「跑一会儿就好了」也解释得通：断点之后重新算过一遍的那些块又进了缓存，从下一轮起就重新对得上了。所以这个现象每次重启复现一次，然后自己消失，很容易被当成偶发抖动放过去。

场景三 · 「上线截断之后，模型偶尔报工具调用格式错误」

先别怀疑模型。第 3 节那张表里，最常见的那种裁法——保留末端、单独保住系统消息——裁出来的第二条就是一个工具结果，而产生它的那次工具调用已经被裁掉了。模型收到一段自己没发出过的返回，很多接口会直接判非法。

要看的是裁剪之后那份消息列表的头几条，不是模型的输出。判据很简单：第一条（系统消息之后）是不是一条合法的起头，以及每一个工具结果的那次调用还在不在。

「偶尔」也说得通：只有当窗口边界恰好落在一轮的中间时才会出事，而每轮长短不一，所以它看起来是随机的。修法在库里就有一个参数，也可以自己在裁完之后做一次配对检查——后者更稳，因为消息该怎么配对由你用的模型接口定，不由裁剪的库定。

同事和面试官常问的

「上下文太长了怎么办？」——先把它拆成两笔：一笔是每轮都要重发的固定部分（系统提示词加工具注册表），一笔是按轮数长的历史。前者的修法是筛工具，后者才轮到裁剪。然后补一句关键的：裁剪不是免费的，它每次都会制造一个前缀断点，实测每轮削一点的那种写法比攒够了才削一次多算四倍半的 token。能说到这一句，说明你不是在背名词。

「滑动窗口和摘要压缩，你选哪个？」——先反问这条会话平均多长、窗口多大。真正的取舍不是这两个名字之间，是「模型每一轮能看见多少历史」和「要重算多少」之间。实测里每轮丢一轮多留一轮半的历史，代价是四倍半的重算。摘要是第三条路：在场的原始轮数最少，但被丢掉的东西以压缩形式还在。

「怎么知道我们的前缀命中率为什么掉了？」——把命中拆成共享头部和会话私有两半分别看。头部那一半掉，是副本太多、流量太散，每台都在重复付冷启动；私有那一半掉，是同一条会话被打散到不同副本，或者你自己在上下文前面动过刀。三种原因该动的东西完全不同，其中一种根本不在这台机器上。

「会话状态存哪儿？」——先说这不是性能问题：最长的会话最慢的读法也只有毫秒级，一轮模型调用是七百多毫秒。要紧的是读回来的那一份和存进去的那一份逐字节相同。然后点出那个坑：很多会话库的读接口带一个限制条数的参数，用了它，恢复就是一次没人察觉的截断，实测第一轮命中率从九成六掉到不足两成。

「同一个用户的请求要不要固定发到同一台机器？」——要，而且能给出价钱：四台副本上，亲和八成二，按负载随机五成四。但这个要求和负载均衡是冲突的——某台副本慢下来的时候，亲和说必须去那台，均衡说该躲开。所以真正的答案是「亲和是软的」，具体怎么软化是另一个题目。先保证的是分派那一层拿得到会话号，拿不到就什么都谈不了。

板块 5自检问题

1. 有人说：「我们把裁剪的目标水位从五成改成九成，这样留住的历史更多，模型效果更好。」用今天的数评估这个提议。

提议的前半句是对的，后半句省掉了代价，而这个代价正好落在被改的那个旋钮上。

目标水位定得越高，一次裁完之后离窗口上限越近，撑不了几轮又满了。水位调到九成，行为就在向「每轮削一点」那一端靠——第 7 节量到的正是这一端：断点从四次涨到十九次，要算的 token 从一万二涨到五万六，折成时间多五十三秒。

而且它连「省字节」这个安慰都没有：每轮削一点那一行发出去的 token 比丢一半那一行还多两成四，因为它永远贴着上限，一轮都没便宜过。

正确的说法是：水位这个旋钮的两端分别是「多留历史」和「少重算」，它是一个真取舍，该由产品那一侧定，而不是随手往上调。调之前先把两条曲线画出来（加分题一）。

错在哪：只报了这个旋钮买到的东西，没报它花掉的钱。

2. 「我们换成了窗口大四倍的模型，以后不用裁了，命中率会上去。」这句话哪一半对、哪一半有条件？

对的那一半有实测支撑。第 8 节最后一列四种策略的数字完全相同，因为窗口开到一万六千三百八十四之后这条会话一次都没触发裁剪，四种策略退化成同一件事，命中率回到不裁剪那一档的九成半。不裁就没有断点，这一点没有疑问。

有条件的那一半在「以后不用裁了」这个前提上。会话长度是一个分布，不是一个常数：窗口开大四倍，只是把顶破窗口的那条线往后推，长尾那些会话照样会顶破。而对顶破了的那部分，情况反而更糟——同一节量到，窗口从四千零九十六开到八千一百九十二，滑动窗口每一轮要重算的从五万六涨到八万九，因为每次断点之后要重算的量等于「窗口减头部」。

还有一笔账不在今天的页面上但躲不开：Day 15 算过，KV cache 的占用和上下文长度是成正比的。窗口开大四倍，同样一台机器能同时容纳的会话数就要往下掉。

正确的说法是：换大窗口之前先把裁法改对。裁法不改，窗口开大只是让每一次裁更贵。

3. 「重启之后第一轮慢得离谱，我们要把会话库换成更快的存储。」用今天的数评估。

这个提议要改的东西，在总账里几乎不存在。

第 10 节量的是最慢的一种读法、最长的一档会话：两点二毫秒。而一轮模型调用是七百三十八毫秒（Day 18 实测）。换成再快的存储，最多也就省掉这两点二毫秒里的一部分。

真正的嫌疑在第 11 节那张表：只取最近八条恢复，第一轮的命中率从九成六掉到不到两成，要算的 token 从四百多涨到四千多。这一段是实打实的计算，按第 9 节那条斜率折算是好几秒。

所以该做的第一件事是把恢复出来的那串 token 和崩之前那串逐字节比一遍。两个常见的差别来源：读回来的条数被 limit 限制住了；重新序列化的时候形状变了（键的顺序、空格、数字的打印格式）。

错在哪：看见「慢」就去找 IO，没有先问「慢的是哪一段」。恢复本身和恢复之后的第一轮是两件事，前者按毫秒计，后者按秒计。

4. 「我们从一台副本扩到两台，命中率反而从八成二掉到六成九。」怎么定位？下一步该做什么？

先把命中拆成两半分别看，这是第 12 节那张表教的读法。从一台到两台、按负载随机分派：头部那一半从九万零一百一十二掉到八万一千九百二十，会话私有那一半从十一万九千九百八十四掉到九万五千四百四十。两半都掉了，但掉的原因不同。

头部掉，是因为那份所有会话共享的前缀现在要在两台机器上各冷启动一次。这一笔是一次性的，会话越多越摊得开。

私有那一半掉，是因为同一条会话的相邻两轮落到了不同副本上，第二台对这条会话的历史一无所知。这一笔不是一次性的，每一轮都在付。

下一步不是加机器——同一张表里，四台掉到五成四，八台掉到不足四成，加得越多越糟。要动的是分派规则：让分派那一层拿得到会话号，把同一条会话固定送回同一台。表里亲和那四行不管几台副本都是八成二，说明这一步的收益不随规模衰减。

错在哪：把「扩容之后变慢」当成容量不够。缓存在这张表里是开到装得下一切的，容量在这里不可能是解释。

板块 10今日五句话

把这一页扣过去，用自己的话答下面五个问题，每题一两句。

1 · 一条 agent 会话的上下文由哪几块组成？哪一块是常数，哪一块按轮数长？把窗口翻一倍，能多撑的轮数大约怎么变？

2 · 「裁掉最早的一轮」这个动作，在缓存那一侧发生了什么？为什么内容一个字没改的那几轮也对不上了？

3 · 每轮削一点和攒满了削一次，在「发出多少、要算多少、留住多少历史」这三笔账上分别是什么答案？哪两笔是同向的，哪一笔才是真取舍？

4 · 把窗口开大一倍，滑动窗口这种裁法要算的 token 会怎么变？为什么？

5 · 进程崩了重启，恢复要判对不对，判据是什么？为什么「没报错」不够？

逐句自查

第 1 句如果只写「系统提示词加历史」就缺了一块。三块是头部（系统提示词加工具注册表，从头到尾不变）、已完成的轮次（单调涨，涨得最快）、这一轮新送进去的那一截（在一个区间里抖）。头部占比在实测那条会话上从七成半掉到不足一成。窗口翻倍能多撑的轮数也大约翻倍，因为第二块基本是线性涨的。

第 2 句如果答成「那几轮被删掉了所以对不上」就答反了——对不上的恰恰是没被删掉的那几轮。原因是位置：前面少了两轮，它们整体往前挪，块的切分边界跟着挪，每一块装的 token 组合变了，串出来的 hash 全不一样。实测那一行的命中块正好等于头部的块数。

第 3 句如果只答了「每轮削一点更省字节」就答错了方向。实测里每轮削一点发出去的反而多两成四，要算的多三点五倍——发出和要算这两笔是同向的，同时输。真取舍在第三笔：每轮削一点让模型平均多看见一轮半的历史，这一轮半就是那四倍半重算买到的全部东西。

第 4 句如果写成「窗口大了裁得少，所以要算的变少」就漏了一步推理。裁的次数确实少了，但每一次裁之后要重算的量等于「窗口减去头部」——窗口开大，单次代价跟着涨。实测这两个方向里后者赢：要算的从五万六涨到八万九。而攒满了才削一次那两种做法的走势相反，因为它们的断点次数掉得更快。

第 5 句如果答成「能读出来就行」就漏掉了今天最要紧的那件事。判据是读回来的那串 token 和崩之前那串逐字节相同。不同的话程序照样能跑、日志上什么都不会报，只是头部之后的整段要重算一遍——实测第一轮命中率从九成六掉到不足两成，而且后面每一轮都还在还这笔债。
