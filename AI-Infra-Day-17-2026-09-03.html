第 1 题（Day 16 · 前缀缓存）

两条请求共享一段 100 个 token 的开头，块大小是 16。前缀缓存最多能替这第二条省下多少个 token 的计算？剩下的那几个去哪了？

看答案

能省 96 个，也就是 6 整块。

100 除以 16 是 6 余 4。前 6 块每块都装满 16 个 token，两条请求的内容逐字节相同，算出来的 hash 也就相同，查表能对上。

剩下 4 个 token 落在第 6 块里。那一块要凑满 16 个才会被算 hash，而后面那 12 个 token 两条请求各写各的，凑出来的内容不一样，这一块的 hash 就不一样。于是这 4 个 token 只能重算。

这个零头在公共前缀不是块大小整数倍时一定存在，块开得越大零头越大。

今天要接的是同一条链的另一端：这次"查一下缓存里有没有"的动作，在代码里究竟站在哪一步——是在调度器决定这一步给谁分 token 之前，还是之后。

第 2 题（Day 14 · 服务化与冷启动）

沙箱执行超时，标准做法是先发 SIGTERM、等一个宽限期、再发 SIGKILL。实测下来这个宽限期几乎全是白等。为什么？而且孙子进程没人单独去杀，它是怎么跟着一起没的？

看答案

白等的原因是信号的规矩：一个进程只会对它自己装了处理函数的信号做出反应。用户提交的代码不会装 SIGTERM 的处理函数，所以这一下发过去等于没发。宽限期取多久，它就在那儿待多久，状态一点不变。

实测那条路径 520 毫秒里有 500 毫秒是宽限期，真正清空 cgroup 的是后面那一下 SIGKILL，用了不到 10 毫秒。

孙子进程跟着没了，靠的是进程号命名空间的一条内核规则：这个命名空间里的 1 号进程一旦终止，内核会把命名空间里剩下的所有进程都用 SIGKILL 收走。所以杀 1 号就够了，不用自己去追进程树——前提是这个沙箱确实有自己的进程号命名空间。

判断"杀干净了没有"，看的应该是 cgroup 里还剩几个任务，那是内核在数；容器状态是运行时自己记在文件里的东西。

第 3 题（Day 10 · 隔离谱系）

你想禁止沙箱里的代码打开文件，于是在 seccomp 名单里把 open 这个系统调用号禁掉了。跑一遍，程序照样把文件打开了。发生了什么？如果索性把能打开文件的号全禁掉，又会怎样？

看答案

名单挡的是号码，不是"打开文件"这件事。Linux 上打开文件有两个入口，老的 open 是 2 号，新的 openat 是 257 号，后者能干前者的一切。只禁 2 号，程序走 257 号照样进去。

两个号一起禁，程序连 main 都到不了：动态链接器要装 libc 这类共享库，而装共享库就得打开文件，它在启动阶段就死了。这就是写名单最难的地方——禁少了不管用，禁多了起不来。

还有一条更根本的限制：过滤器不能顺着指针去看内容，所以"只禁止打开 /etc/shadow"这种规则 seccomp 永远写不出来，它只能按号码一刀切。要按路径限制，得换一把锁。

板块 2 · 核心讲解

第一部分 · 为什么这份代码住在两个进程里

1. 你会怎么摆这份代码

如果让你从零写一个推理服务的骨架，你会把它摆成几个进程？

你是后端工程师，最自然的答案是一个。一个进程里跑 FastAPI，收到请求就丢进一个队列，另起一个协程转引擎循环，算完把 token 塞回各自的响应流。Day 9 那个玩具服务就是这么写的，一百多行，跑得挺好。

这个写法能撑到哪儿，Day 4 已经给过答案了。Python 里同一时刻只有一个线程能执行字节码，这条规矩叫全局解释器锁。HTTP 那一侧要做的事——解析请求头、分词、把生成的字拼成 JSON 再编码成字节——全是纯 Python 的活，全都要占着这把锁。而引擎那一侧每一步都要抢同一把锁去发起下一次计算。

并发一上来，这两拨活儿开始互相踩。用户多打一个字，引擎就晚一点点开始下一步；引擎步一密，HTTP 那边的响应就开始积压。

vLLM 的做法是把这两拨活儿放进两个操作系统进程，各自一把锁，互不干扰。今天这条路要走的，就是这两个进程之间的来回。

3. 两个进程，三个线程，和一句注释

第一部分开头说"一个进程装不下"，这话在源码里有一处非常直白的落点。引擎进程启动时会另起两个线程，注释写着它们为什么存在（vllm/v1/engine/core.py:1111-1114）：

# Background Threads and Queues for IO. These enable us to
# overlap ZMQ socket IO with GPU since they release the GIL,
# and to overlap some serialization/deserialization with the
# model forward pass.

翻成中文：这两个后台线程负责 socket 的收发，它们在等 socket 的时候会放开全局解释器锁，所以收发消息这件事可以和计算同时进行；顺带还能让打包解包和前向重叠起来。

Day 4 讲过这条规矩的两面：一个线程在纯 Python 代码里跑的时候占着锁，别人干等；而它一旦进了等待 IO 或者调 C 库的状态，锁就放开了，别人可以跑。socket 的收发正好属于后者。这两个线程的存在，是为了让 socket 上的等待和引擎的计算同时发生，而不是为了并行地算什么。

两个线程，加上跑忙循环的主线程，引擎进程里一共三个。线程之间不直接说话，靠两个普通队列交接：输入 socket 线程收到消息放进 input_queue，主线程从里面取；主线程算完把结果放进 output_queue，输出 socket 线程从里面取着发。这两个交接点在源码里各是一行（core.py:1453 和 core.py:1833）。

主线程那个循环本身只有十二行（core.py:1411-1422）：

def run_busy_loop(self):
    """Core busy loop of the EngineCore."""
    while self._handle_shutdown():
        # 1) Poll the input queue until there is work to do.
        self._process_input_queue()      # 先把队列里堆着的新请求全收进来
        self._maybe_publish_request_counts()
        # 2) Step the engine core and return the outputs.
        self._process_engine_step()      # 再走一个引擎步
        self._maybe_publish_request_counts()
    raise SystemExit

收信，走一步，回到开头。这个循环有个名字叫 忙循环（busy loop）。Day 9 里那个"引擎步"就是第二行做的事，它在这里只是一次函数调用。

第二部分 · 进门：文本怎么变成调度器里的一条记录

4. 文本在哪一行变成 token id

用户发来的是一串字。引擎那一侧只认整数。这个转换发生在前端进程，具体是 vllm/v1/engine/async_llm.py:435 这一行：

request = await self.input_processor.process_inputs_async(
    request_id, prompt, params, ...)

把文本切成 token 这件事是纯 Python 加 C 扩展的活，几十毫秒起步，而且它是同步的。如果直接在事件循环里做，这几十毫秒里整个前端一个请求都收不了。所以它没有直接调，调的是一个带 _async 后缀的版本。这个版本是这样造出来的（vllm/v1/engine/input_processor.py:73）：

# Raw-prompt preprocessing (tokenization and multimodal processing)
# is blocking, so async callers should run it on the renderer's
# thread pool to keep their event loop responsive.
self.process_inputs_async = make_async(
    self.process_inputs, executor=self.renderer._executor
)

而 make_async 里干活的就一行（vllm/utils/async_utils.py:43）：

return loop.run_in_executor(executor=executor, func=p_func)

这正是 Day 4 那个动作。当时那一天的结论是：事件循环里出现任何一段长时间占着解释器的纯计算，整个服务的响应就跟着停一下；解法是把它甩进线程池。分词就是这样一段。你在 Day 4 手写的那个修法，和这里是同一行代码。

做完这一步，一条请求就从"一段文字加一些参数"变成了"一串整数加一些参数"。后面它再也不会变回文字，直到出门那一刻。

5. 过河的那条消息里装着什么

转换完的请求要送到另一个进程去。交接点在 async_llm.py:501-504，两行，先后顺序有讲究：

# Register locally before the first await so concurrent tasks see this request.
self.output_processor.add_request(request, prompt, parent_req, index, queue)

# Add the EngineCoreRequest to EngineCore (separate process).
await self.engine_core.add_request_async(request)

先在本进程的输出处理器里登记，再把请求送过河。注释解释了为什么是这个顺序：登记这一步没有 await，中间不会切走；如果反过来先送过河，那么在 await 挂起的这段时间里，引擎可能已经把第一个 token 算出来送回来了，而前端这边还没有这条请求的登记，回来的东西无处安放。

Day 5 讲过挂起的协程：一个 await 就是一个可以被切走的点。这两行的顺序就是在数这些点。

送过河的这条消息叫 EngineCoreRequest，形状 2.2 节已经摆过。它经过的路是：前端把它 打包（serialize） 成 msgpack 字节 → 走 socket → 引擎进程的输入 socket 线程收到并 解包（deserialize） → 放进 input_queue → 主线程从队列里取出来，调 EngineCore.add_request（core.py:452），最后一行是把它交给调度器。

从这一刻起，这条请求在引擎里就是一条排队的记录了。

6. 这笔账，你先估一遍

这个过河的动作，一条请求进门时发生一次，之后每一个引擎步的结果回来时都要再发生一次。它到底要花多少钱，写下来再往下看。

预测 · 先写下来

问题一：同时在跑 32 条时，一步的结果那条回程消息是 677 字节。把它在两个进程之间送一个来回，中位数大约是多少？给个量级：几微秒、几十微秒、几百微秒，还是几毫秒。

问题二：把同时在跑的条数从 1 加到 128，消息从 24 字节涨到 2693 字节，涨了一百一十二倍。那个"一来一回"的时间大约会涨多少倍？

问题三：这台机器上一步 decode 是 125.9 毫秒。上面那个来回占一步的多少？写一个百分比或者千分比。

提示：2.4 节那张表已经把答案的一半摆出来了，但它只量了一种尺寸。问题二问的是这个数怎么随尺寸变。

关键结论

把一个 Python 服务拆成两个进程，代价不是"多了一次序列化"，而是"每次交接多一次固定的进程往返"。这笔固定开销跟消息大小几乎无关，跟交接的频率完全相关。

所以拆进程这个决定的正确问法不是"消息有多大"，而是"多久要交接一次"。vLLM 每个引擎步交接一次，这台机器上一步一百二十多毫秒，交接一百三十微秒，比例是千分之一，划得来。如果改成每个 token 都单独交接一次，账就完全不同了。

第三部分 · 一步之内，三方各交出什么

8. 请求的身份证：一个枚举，和一次比大小

一条请求在引擎眼里是什么？

是一个对象，上面挂着 token id 列表、算到第几个了、块表在哪儿，以及一个状态。状态这个东西定义在 vllm/v1/request.py:364，是一个整数枚举，十二个取值，顺序有意义：

序号状态它表示什么算不算结束
1WAITING在等待队列里，还没被调度过或者刚被踢回来否
2WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR要求模型必须按某种格式输出时，得先把格式编译成一份规则，它在等这个否
3WAITING_FOR_REMOTE_KVS在等别处的 KV 搬过来（Day 16 那条阶梯的上一级）否
4WAITING_FOR_STREAMING_REQ在等流式输入的下一段否
5RUNNING在跑否
6PREEMPTED被抢占了，进度清零等着重来（Day 9 讲的那个动作）否
7FINISHED_STOPPED正常停：吐出了 EOS，或者撞上停止条件是
8FINISHED_LENGTH_CAPPED到长度上限了是
9FINISHED_ABORTED被取消了是
10FINISHED_IGNOREDprompt 就超了上下文上限，压根没算是
11FINISHED_ERROR出错了是
12FINISHED_REPETITION检测到重复，主动掐掉是

最后那一列不是查表查出来的，是算出来的。判断一条请求有没有结束，源码里是一次比大小（request.py:387）：

@staticmethod
def is_finished(status: "RequestStatus") -> bool:
    return status > RequestStatus.PREEMPTED

PREEMPTED 的序号是 6，所以 7 到 12 全部算结束。枚举定义里还专门留了一行注释盯着这件事：Note: anything after PREEMPTED will be considered as a finished status——排在 PREEMPTED 后面的都算结束。这意味着往这个枚举里加取值必须看位置，加错了地方，一条还在跑的请求会被当成已经结束。

这个写法值得记一下，因为它是一类常见做法：把语义编进枚举的顺序里，换来的是判断变成一次整数比较。代价是这个顺序从此不能随便动，而编译器不会替你检查。

9. 查前缀这个动作站在哪

Day 16 留了一个问题：查最长命中前缀这件事，是在调度器决定这一步给谁分 token 之前，还是之后？

答案在 Scheduler.schedule 这 884 行里。它的顺序是固定的三段：

  • scheduler.py:558　# First, schedule the RUNNING requests.　先给正在跑的续上
  • scheduler.py:782　# Next, schedule the WAITING requests.　剩下的 token 预算才轮到等待队列
  • scheduler.py:1343　把这一步的决定装成一张单子交出去

查前缀在第二段里面，scheduler.py:845-853：

这段代码往下走两百多行，才到向内存要块那一步（scheduler.py:1085，调的是 Day 15 讲的 allocate_slots）。所以顺序是：先查缓存里有多少现成的，再按"还差多少"去要块。

这个位置说明三件事。

第一，查前缀发生在调度决定的中间，不是之前也不是之后。正在跑的那些请求已经先把 token 预算分掉了，等待队列的请求才轮到查缓存。所以缓存命中率高的请求并不会因此插队——它只是在轮到自己的时候少要一些块。

第二，那个 if request.num_computed_tokens == 0 说明查一次就够了。一条请求被分块预填充切成好几步慢慢算，只有第一步会查缓存，后面几步不会重查。

第三，命中的结果直接变成 allocate_slots 的一个入参，而不是走另一条路。这就是 Day 15 和 Day 16 那两天在代码里合流的地方：块表这个东西既是"内存怎么分"的产物，也是"哪一段不用算"的载体，同一个数据结构管两件事。

12. 两种停：一种在引擎里判，一种在前端判

上一节那个 check_stop 定义在 vllm/v1/core/sched/utils.py:94，它检查的东西很具体：

last_token_id = request.output_token_ids[-1]
if last_token_id == sampling_params.eos_token_id:       # 吐出了结束符
    request.status = RequestStatus.FINISHED_STOPPED
    return True

if last_token_id in (sampling_params.stop_token_ids or ()):   # 撞上指定的停止 token
    request.status = RequestStatus.FINISHED_STOPPED
    request.stop_reason = last_token_id
    return True

if (
    request.num_tokens >= max_model_len                  # 到上下文上限
    or request.num_output_tokens >= request.max_tokens   # 到这条请求自己的长度上限
):
    request.status = RequestStatus.FINISHED_LENGTH_CAPPED
    return True

三种情况，判据全是整数：某个 token id 等不等于结束符、在不在停止列表里、数量到没到上限。全部能在引擎进程里当场判完。

但用户还能提另一种要求。采样参数里有个 stop 字段，装的是一串文本，比如 ["\n\n", "答："]——看到这几个字就停。这个东西叫 停止串（stop string）。

引擎进程判不了它，因为引擎进程手上只有整数。而且这件事不是"把 token id 翻译一下"就能解决的：一个停止串可能横跨两个 token，也可能只占某个 token 的后半截，只有拼成文字之后才能找。

所以停止串的判定发生在前端。output_processor.py:695 拿到解码出来的文字之后顺手查一遍，命中就把这条请求标记成结束。然后紧接着一段（output_processor.py:735-738）：

self._finish_request(req_state)
if not engine_core_output.finished:
    # If req not finished in EngineCore, but Detokenizer
    # detected stop string, abort needed in EngineCore.
    reqs_to_abort.append(req_id)

翻译过来：引擎那边还不知道这条请求该停了，得专门发一条取消消息回去。这条消息由 async_llm.py:795 送出。

于是有了一个可以直接说给别人听的事实：token id 的停在引擎里判，字符串的停在前端判，后者比前者多花一个来回。在这个来回结束之前，引擎会照常再算至少一步——那一步的结果会被丢掉。

这不是设计缺陷，是"引擎不碰文字"这个决定的必然代价。要让引擎自己判停止串，就得把分词器搬进引擎进程，整套隔离也就没了。

13. 为什么不能每来一个 token 就整段重解

把 token id 变回文字，最直接的写法是什么？

把从头到现在所有的 token id 一起丢给分词器，让它解出完整的一段文字，然后减掉上一次已经吐出去的部分。正确，而且好写。

问题是每一步都要重解一遍越来越长的序列。第 4096 步要解 4096 个 token，前面 4095 个上一步刚解过。总的开销是长度的平方。

vLLM 的做法是只解一个窗口。它维护两个下标，一个叫 prefix_offset，一个叫 read_offset，每次只解 [prefix_offset, 末尾] 这一小段，再减掉 [prefix_offset, read_offset] 那一段解出来的文字，剩下的就是这一步新增的字。这个做法叫 增量解码（incremental detokenization），那两个下标是它的 解码窗口（prefix_offset / read_offset）。

两种写法在同一串 token 上各跑一遍，词表是按 utf-8 字节随机切出来的字节片词表。

输出多少个 token整段重解 ms只解窗口 ms倍数

长度每翻两番，整段重解的耗时翻四番多（1.9 → 30.7 → 476.4），窗口解法基本是线性（0.5 → 2.0 → 7.8）。到 4096 个 token 时差了六十一倍。一次长回答就在这个量级上。

那为什么不干脆"每个 token 各自解成一小段字，拼起来"？因为一个字可能被切在两个 token 中间。用 utf-8 演示最直观：一个汉字占三个字节，如果这三个字节分在三个 token 里，前两步解出来是这样。

那个 � 叫 替换符（replacement character，U+FFFD），是解码器遇到凑不成一个完整字符的字节时吐出来的占位符。源码里专门有一行盯着它（vllm/tokenizers/detokenizer_utils.py:260）：

if len(new_text) <= len(prefix_text) or new_text.endswith("�"):
    # utf-8 char at the end means it's a potential unfinished byte sequence
    # from byte fallback tokenization.
    return new_tokens, "", prefix_offset, read_offset

解出来的东西以替换符结尾，就返回空字符串，而且两个下标原样退回去——这一步什么都不吐，下一步连着这几个字节一起再试。窗口解法从不吐出一个还没凑齐的字。

这带来一个实测能看见的差别。上面那张表里，256 个 token 那一档两种写法解出来的文字并不一样：那串字节正好停在一个汉字的中间，整段重解在末尾吐了一个 �，窗口解法把它压住没吐。1024 和 4096 那两档正好停在字的边界上，两种写法结果完全相同。

所以流式接口上偶尔看到一个 �，多半不是模型出了问题，是某一层解码没做这个检查。

关键结论

"引擎只认整数，文字只存在于前端"这一条决定，一路决定了后面三件事：停止串必须在前端判并且要多发一条取消消息回去；解码必须做成增量的，否则开销是长度的平方；而增量解码又必须处理"字节还没凑齐"这个状态，于是有了那个替换符检查。

三件事看起来互不相干，其实是同一个决定的三个分支。

REPEAT_CODEC = 2000   # 打包/解包各重复多少次
RTT_ROUNDS   = 800    # 每种尺寸各走多少个来回
PROMPT_LEN   = 1024   # 一条新请求的 prompt 有多少 token
BATCHES      = [1, 8, 32, 128]
BLOCK_SIZE   = 16     # 取自 vllm/config/cache.py:80

def us(fn, n):
    """跑 n 次取单次平均微秒。先空跑 200 次热身，免得把首次开销算进去。"""
    for _ in range(200): fn()
    t0 = time.perf_counter()
    for _ in range(n): fn()
    return round((time.perf_counter() - t0) / n * 1e6, 2)

        m = s.recv()
        if m == b"BYE": s.send(b"BYE"); break

    ready = mp.Event()
    p = mp.Process(target=echo, args=(ADDR, ready), daemon=True); p.start(); ready.wait()

                  "p99_us": round(v[int(0.99 * len(v))], 1)}
    return out

第 4 步：把标尺放上去

没有标尺，微秒是个没有意义的数。这一段就是 Day 8 起一直用的那副权重，跑出"一步大概多久"。

"""P3 · 前向标尺　用法: OPENBLAS_NUM_THREADS=1 python3 p3_ruler.py"""
import statistics, time
import numpy as np

N, L = 4096, 8                       # 8 层 4096x4096 float32 = 512 MiB
W = [np.random.rand(N, N).astype(np.float32) for _ in range(L)]

def one_pass(S):
    X = np.random.rand(N, S).astype(np.float32)
    t0 = time.perf_counter()
    for w in W: w @ X                # 一次调用 = 把 512 MiB 权重完整读一遍
    return (time.perf_counter() - t0) * 1e3

for S, tag, reps in [(32, "一步 decode，批量 32", 12), (1024, "一次 prefill，1024 token", 5)]:
    one_pass(S)                      # 热身一次
    ms = sorted(one_pass(S) for _ in range(reps))
    print(f"{tag}: 中位数 {statistics.median(ms):.1f} ms  "
          f"最快 {ms[0]:.1f}  最慢 {ms[-1]:.1f}")

"""P4 · 解码账台　用法: python3 p4_detok.py"""
import random, time

TEXT = "推理服务把请求排进队列，调度器每一步决定谁上车。" * 400

def build_vocab(text):
    """把整段文字按 utf-8 字节切成 1~3 字节一片，做成 id -> bytes 的词表。
    这正是 byte-fallback 类分词器的形状，所以"字节没凑齐"是真会发生的。"""
    b = text.encode("utf-8")
    rnd, pieces, i = random.Random(7), [], 0
    while i < len(b):
        k = rnd.choice([1, 2, 3]); pieces.append(b[i:i + k]); i += k
    return {i: p for i, p in enumerate(pieces)}, list(range(len(pieces)))

VOCAB, IDS = build_vocab(TEXT)
def decode_all(ids): return b"".join(VOCAB[i] for i in ids).decode("utf-8", errors="replace")

def run_full(ids):
    """每来一个 token，把从头到现在的所有片重解一遍。"""
    text = ""
    for k in range(1, len(ids) + 1):
        text = decode_all(ids[:k])
    return text

def run_window(ids):
    """只解 [prefix_offset, 末尾] 这个窗口，减掉 prefix 那一段。
    照 vllm/tokenizers/detokenizer_utils.py:240-268 的形状写。"""
    out, prefix_offset, read_offset = "", 0, 0
    for k in range(1, len(ids) + 1):
        prefix_text = decode_all(ids[prefix_offset:read_offset])
        new_text    = decode_all(ids[prefix_offset:k])
        if len(new_text) <= len(prefix_text) or new_text.endswith("�"):
            continue                  # 字节还没凑齐：这一步不吐字，两个下标也不动
        out += new_text[len(prefix_text):]
        prefix_offset, read_offset = read_offset, k
    return out

for n in [256, 1024, 4096]:
    ids = IDS[:n]
    t0 = time.perf_counter(); a = run_full(ids);   t_full = (time.perf_counter() - t0) * 1e3
    t0 = time.perf_counter(); b = run_window(ids); t_win  = (time.perf_counter() - t0) * 1e3
    print(f"n={n:5d}  整段重解 {t_full:7.1f} ms  只解窗口 {t_win:6.1f} ms  "
          f"倍数 {t_full/t_win:5.1f}  两种写法结果相同: {a == b}")

板块 4 · 工作现场

场景一 · 「首 token 延迟的 P99 有毛刺，但 GPU 利用率很平」

指标上看不出问题，用户就是偶尔等两秒才出第一个字。GPU 曲线平滑，说明计算那一侧没有异常。

第 14 节那张表告诉你该去哪儿找：从请求进门到第一个 token 出去，中间有六段不在 GPU 上——HTTP 解析、分词、打包、过河、排队、以及回程的解码。前两段和最后一段住在前端进程，那个进程只有一个事件循环。

最常见的两个原因都在那一侧。一是有人往事件循环里塞了同步的活儿——比如加了一段日志要去查数据库，或者自己写的中间件里做了一次同步的模板渲染。第 4 节那个 run_in_executor 就是为了防这个，但只有 vLLM 自己的代码走了这条路，你加的没有。二是超长 prompt 的分词本身把线程池占满了。

排查顺序：先看这些毛刺发不发生在特定的 prompt 长度上；再在前端进程上挂一个采样式剖析器（Day 3 那把工具），看火焰图里有没有不该出现的同步调用。不要一上来就调 max_num_batched_tokens——那是引擎侧的旋钮，改它对前端一点用都没有。

场景二 · 「加了 stop 字符串之后，成本没降反升」

产品发现回答经常带一段多余的尾巴，于是给所有请求加上 stop 字符串。上线后账单没降。

第 12 节解释了一半：停止串在前端判，判出来之后要发一条取消消息回引擎，这中间引擎至少还会再算一步，那一步的结果被丢掉。这是固定的额外开销，输出越短占比越大。

但只靠这一条解释不了"没降"。另一半通常在别处：加 stop 之后每条请求确实短了，于是同一时刻能塞下更多请求，实际批量上去了，机器反而更忙。这时候该看的不是总成本，是每条请求的平均 token 数——如果这个数明显降了，改动是有效的，账单没降是因为吞吐上去了，那是好事。

能给出的建议是：能用 token 表达的停止条件就别用字符串。stop_token_ids 走的是引擎侧那条路，当场就停，没有这个来回。

场景三 · 「想在推理服务上加一个自己的功能，不知道该改哪儿」

这是最常见的一类活儿：加一个按租户的配额、加一段自定义的采样后处理、给每条请求打一段自定义的追踪记录。

第 14 节那张表就是决策表，问三个问题。这个功能需不需要看到文字？需要就只能放前端。它需不需要知道调度决定（这一步谁上车、块表怎么分）？需要就只能放引擎。它会不会引入阻塞调用？会就必须甩进线程池，否则整个前端跟着停。

举例：按租户限流不需要文字也不需要调度信息，放在最前面拦住就好，别往引擎里塞；而"某个租户的请求优先调度"必须进引擎，因为那是 schedule() 里的事——Day 9 讲过它有一个按优先级抢占的分支。

还有一条经验：任何要跨那条进程边界的新数据，都得先能被 msgpack 序列化。往 EngineCoreRequest 上挂一个复杂对象，第一个报错会出现在 socket 线程里，而不是你加代码的那一行。

同事和面试官常问的

  • 「vLLM 为什么要拆成两个进程？」——答"避免 GIL 争抢"只答了一半。完整的说法是：HTTP、分词、解码这些活儿全是纯 Python，和引擎循环抢同一把解释器锁；拆开之后各自一把锁。而拆开的代价是每个引擎步多一次进程往返，量下来是一步的千分之一，划得来。
  • 「一条请求进来到吐出第一个字，经过了哪些环节？」——按第 14 节那十六行讲，重点讲清楚两次跨进程和两次文字与整数之间的转换。能说出"引擎进程从头到尾不碰一个字符"就说明你真读过。
  • 「设置了 stop 字符串的请求怎么停下来的？」——前端解码出文字之后才能判，判出来发一条取消消息回引擎。追问"为什么不在引擎里判"，答：引擎手上只有整数，而且一个停止串可能横跨两个 token，不拼成文字找不到。
  • 「为什么解码要做成增量的？」——整段重解的开销是输出长度的平方，一次四千 token 的回答实测差六十倍。追问"那为什么不每个 token 各自解一小段拼起来"，答：一个字符可能被切在两个 token 中间，凑不齐的时候解出来是替换符，得压住不吐。
  • 「SchedulerOutput 里为什么要分新请求和老请求两个列表？」——老请求的数据已经在执行侧缓存着了，每步只发变化。实测差一百六十倍，而且这个倍数随并发上升。

板块 5 · 自检问题

1. 有人提议把分词也搬进引擎进程，理由是"少一次跨进程"。这个提议有什么问题？

先算它省下什么。分词发生在请求进门时，一条请求只发生一次。而跨进程这件事，进门发生一次、之后每个引擎步发生一次。搬走分词省掉的是那一次，占比极小。

再算它带来什么。分词是纯 Python 加 C 扩展的同步操作，几十毫秒起步。搬进引擎进程之后，它和引擎循环抢同一把解释器锁——每来一条新请求，正在生成的所有请求都要停几十毫秒。这正是第一部分开头那个"一个进程"的写法会出的毛病。

还有第三笔账：引擎进程从此要装分词器，也就要装模型的 tokenizer 文件、要处理不同模型的词表。今天这条路上"引擎只认整数"这条边界一破，第 12 节和第 13 节那两件事的位置全都要重新讨论。

更好的方向是反过来：分词已经在线程池里了，如果它还是瓶颈，加线程池的大小，或者把它挪到更前面的一层。

2. 你在 RequestStatus 枚举里加了一个新状态 WAITING_FOR_TOOL_RESULT，加在了末尾。上线后发现有些请求莫名其妙就结束了。为什么？

因为"结束了没有"这个判断是 status > RequestStatus.PREEMPTED，一次整数比较。PREEMPTED 的序号是 6，你加在末尾就是 13 号，比 6 大，所以被当成已经结束。

这个状态本意是"在等工具返回，还没结束"，应该加在 PREEMPTED 之前，和另外三个 WAITING_FOR_* 排在一起。枚举定义里那行注释就是在防这件事：排在 PREEMPTED 后面的都算结束。

这类 bug 的共同点是：语义编在顺序里，而顺序不受任何检查保护。加一个成员是一行改动，编译器和类型检查器都不会说话，直到运行时才出问题。

发现之后除了挪位置，值得顺手加一个测试：把枚举的每个成员和 is_finished 的期望值列成一张表比对，这样下次再有人加错，测试会说话。

3. 第 7 节量到"消息大一百一十二倍，来回时间几乎不变"。这个结论能不能推广成"进程间通信不用在意消息大小"？

不能。这个结论有一个明确的适用区间，就是被测的那个区间：24 字节到 2693 字节。

在这个区间里，一个来回的一百三十微秒基本花在固定的动作上——两次系统调用、一次进程唤醒、一次调度器把对方叫醒。搬两千多字节这件事在这些动作面前不值一提。

但第 10 节那张表里已经出现了 407 KB 的消息，比这个区间的上界大了一百五十倍。到那个尺度，拷贝和内存带宽就开始说话了。再往上，几 MB 的消息还会碰到 socket 缓冲区放不下、要分多次发的问题，那时候曲线的形状完全不同。

怎么判断自己在哪个区间：把消息尺寸扫一遍，画出来。曲线平的那一段是固定开销主导，开始往上斜的那一段是字节主导。拐点在哪台机器上都不一样。

4. 一个同事说："既然增量解码这么好，那把它也用在 prompt 上——用户提交的长 prompt 也可以边收边分词。"这个类比成立吗？

方向上有道理，但两件事的约束不一样，直接搬过去会出错。

增量解码之所以能成立，是因为输出 token 是一个一个产生的，而且顺序确定、只往后长。第 k 步的结果不会改变前 k−1 步已经吐出去的字（唯一的例外就是那个替换符，所以才要压住不吐）。

分词不满足这个条件。分词器是贪心地找最长匹配的，后面来的字符会改变前面的切分结果。举个例子：先看到 "in"，可能切成一个 token；再看到 "g"，"ing" 就变成另一个 token 了。边收边分词，前面切好的随时可能要推翻。

所以流式输入在 vLLM 里是另一套机制（第 8 节那个枚举里的 WAITING_FOR_STREAMING_REQ 就是给它的），它是按用户提交的分段来处理，不是按字符流增量切分。

这道题真正要练的是：看到"A 那边这么做很好"的时候，先问 A 成立的前提是什么，再看 B 满不满足。

板块 10 · 今日五句话

合上页面，用自己的话写

1. vLLM 为什么要把服务拆成两个操作系统进程？拆开的代价是什么，量级是多少？

2. 一条请求从进门到吐出第一个字，"文字"这个东西在哪两个位置出现过？中间那一段是什么？

3. 调度器交给执行器的那张单子，为什么要分成两个列表？省下了什么？

4. 一条请求设置了 stop 字符串，它比一条正常吐出 EOS 的请求多花了什么？

5. 增量解码在什么情况下会选择"这一步一个字都不吐"？为什么必须这样？

逐句自查标准

  • 第 1 句如果只写成"为了性能"就错了。要点名是解释器锁：HTTP、分词、解码这些纯 Python 的活儿和引擎循环抢同一把锁。代价要给数：每个引擎步多一次进程往返，这台机器上是一百三十微秒对一步一百二十多毫秒。
  • 第 2 句如果写成"进来是文字，出去是文字"，只说了一半。要点出这两个位置都在前端进程，中间十一步全在整数上进行——正是这条边界决定了后面停止串和解码的位置。
  • 第 3 句如果写成"为了省带宽"就太泛了。要点出老请求的数据已经在执行侧缓存着，每步只发变化；省下的主要是那份从头到尾不变的 prompt token 列表。有个数更好：实测差一百六十倍。
  • 第 4 句如果写成"多一次判断"就漏了关键。要点出多的是一整个来回：前端判出来之后要发一条取消消息回引擎，而在这条消息到达之前引擎至少还会再算一步，那一步白算。
  • 第 5 句如果只写"字节没凑齐"，还差半步。要补上判据和后果：解出来的文字以替换符结尾就不吐，而且两个下标原样退回，等下一步连着这几个字节一起再试。如果写成"下标照常前进"就错了——那样这几个字节就永远丢了。
