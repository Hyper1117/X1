Q1 · 1 天前（Day 10 · 隔离谱系）

启动开销那张表里有一行看起来很多余：unshare 一个命名空间都不开，只是白白多 exec 一次，中位数 2.44 毫秒。这一行是拿来排掉什么的？没有它，你会把「开 3 种命名空间比直接 exec 慢了 1.51 毫秒」这句话理解错在哪里？

展开答案

它排掉的竞争解释是：「慢下来的原因是命名空间本身贵。」

每往上加一层隔离，就多了一个包装程序，而多 exec 一个程序这件事本身就要花时间——跟它开不开命名空间没关系。那一行把这笔钱单独称了出来：1.21 毫秒到 2.44 毫秒，包装本身要 1.23 毫秒。

所以「3 种命名空间比直接 exec 慢 1.51 毫秒」这句话里，1.23 毫秒是包装的钱，只有 0.28 毫秒是命名空间的钱。把两笔混在一起，会得出「命名空间贵了五倍」的结论。

今天这一页有一张同样形状的表，而且需要同样的对照行，因为今天要往上叠的层数更多。

Q2 · 3 天前（Day 8 · prefill-decode 与四指标）

一个流式服务本来生成一个 token 就推一次，现在改成攒够 4 个推一次，别的一律不动。ITL 的 P50 会往哪个方向走、大约几倍？TPOT 呢？这两个数里有一个是假动作，另一个是真的退化，分别是哪个？

展开答案

ITL 的 P50 会涨到大约四倍：实测 76.3 毫秒变成 342.2 毫秒。原因是 ITL 量的从来就是「相邻两块之间」，而现在每一块里装了 4 个 token。

TPOT 分两种算法，差别就是整个陷阱。按收到几块算，80.4 毫秒变成 323.3 毫秒，看着慢了四倍；按分词器数出来的真实 token 数算，是 80.4 对 70.3 毫秒——反而快了一点，因为少做了四分之三的写和 flush。

所以 ITL 和按块算的 TPOT 都是假动作，服务一点没变慢，变的是分母。真的退化在 TTFT：570.6 毫秒变成 829.2 毫秒，因为第一块要等 4 个 token 都生成完才出发。

今天会有一次同样的分母陷阱：一个「起容器要多久」的数字，只要换一种数法就能差出好几倍。

Q3 · 7 天前（Day 4 · 事件循环与 GIL）

两段纯计算的代码，单次耗时几乎一样，都扔进同一个线程池外派。一段之后 /health 的 P99 掉回基准线，另一段几乎没改善。差别不在活有多重，那在哪？如果沙箱里跑的是模型生成的代码，这条判据还能用吗？

展开答案

差别在这段计算执行时放不放开 GIL。hashlib.sha256 在算的时候把 GIL 交出去，所以它在别的线程里跑，事件循环那个线程照样能推进：P99 从 217.0 毫秒掉到 5.2 毫秒，和什么都不干的基准（1.1 毫秒）是一个量级。json.dumps 全程握着 GIL，扔进线程池也只是换了个线程握着，P99 从 199.3 只降到 161.7 毫秒。

判据是「这段 C 实现的代码有没有在计算期间放开 GIL」，不是「活重不重」。

第二问的答案是不能用了，而且原因和 GIL 无关：模型生成的代码你事先读不到，没法查它调的每个库放不放 GIL。这正是沙箱存在的理由——判据从「我信得过这段代码的性质」换成「不管它是什么性质，它都出不去」。今天做的就是这个「出不去」。

当时给的解释是：挂载命名空间复制的是挂载点这张表，复制出来的那份内容和原来一模一样。换了一份完全相同的地图，看到的还是同一片地。

今天要做的就是把地图换掉。

这件事听起来是「再加一把锁」，其实不是。命名空间、配额、名单这三样是内核提供的机制，你只要开开关。而「一个自己的根」不是开关，是你得先准备出来的一堆文件。这是今天和昨天最大的体感差别。

2. 根文件系统：其实就是一个目录

你作为后端工程师，听到「容器有自己的文件系统」，第一反应可能是那里有个磁盘镜像文件，或者某种虚拟盘。都不是。

它就是宿主上的一个普通目录，里面按 /bin、/lib、/etc 这套布局摆好了程序要用的文件。等会儿有一个内核调用会把「根」这个位置指到这个目录上，从此这个目录里的 bin 在里面看就叫 /bin。这个准备好的目录，就叫根文件系统（rootfs）。

怎么造一个？把要跑的程序复制进去，再把它运行时要装载的共享库也复制进去。找共享库不用猜，ldd 会把清单列出来：

# ldd 列出这个二进制运行起来要装载哪些共享库，以及它们在宿主上的路径
$ ldd /bin/sh
	linux-vdso.so.1 (0x00007f7b47fdf000)
	libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f7b47c00000)
	/lib64/ld-linux-x86-64.so.2 (0x00007f7b47fe1000)

第一行的 linux-vdso.so.1 没有路径，因为它不是磁盘上的文件，是内核直接映射进每个进程的一小块代码，不用复制。剩下两行是真文件，照原路径复制过去就行。第三行那个 ld-linux 就是 Day 10 提过的动态链接器——程序启动时负责把这些库找出来装进内存的那一步。

把这件事写成脚本，就是今天的第一个程序：

#!/bin/bash
# mkrootfs.sh：把几个命令、它们依赖的共享库、以及 Python 的标准库复制进一个目录
ROOT=${1:-/root/lab/rootfs}
rm -rf "$ROOT"; mkdir -p "$ROOT"/{bin,lib,lib64,proc,sys,dev,tmp,oldroot,etc}
BINS="/bin/sh /bin/ls /bin/cat /bin/ps /bin/hostname /bin/id /bin/mount /bin/umount /bin/sleep /bin/true /usr/bin/python3.11"
for b in $BINS; do
  cp -aL "$b" "$ROOT/bin/"
  # 逐个共享库按原路径复制过去，路径必须一致，否则动态链接器找不到
  ldd "$b" 2>/dev/null | grep -o '/[^ ]*\.so[^ ]*' | while read -r so; do
    d="$ROOT$(dirname "$so")"; mkdir -p "$d"; cp -aL "$so" "$d/"
  done
done
ln -sf python3.11 "$ROOT/bin/python3"
# Python 起来之后要 import 一堆纯 Python 写的标准库，这些文件不在 ldd 的清单里
cp -a /usr/lib/python3.11 "$ROOT/usr/lib/"
# 标准库里还有一部分是编译成 .so 的扩展模块，它们各自又有自己的依赖
for so in "$ROOT"/usr/lib/python3.11/lib-dynload/*.so; do
  ldd "$so" 2>/dev/null | grep -o '/[^ ]*\.so[^ ]*' | while read -r dep; do
    d="$ROOT$(dirname "$dep")"; mkdir -p "$d"; cp -aL "$dep" "$d/"
  done
done

跑完之后应该看到一个 80 MB 上下、一千三百多个文件的目录。如果最后那个 lib-dynload 的循环漏掉了，症状很具体：/bin/sh 能跑，python3 起来之后 import ctypes 会报 libffi.so.8: cannot open shared object file——因为那个扩展模块的依赖不在 ldd python3 的清单里，它是模块自己的。

这一步很朴素，但它解释了后面一个数字为什么那么大。三把锁是内核里的开关，开一下就有；根文件系统是一千多个文件，得一个一个复制过去。第四部分会看到这两件事的价钱差了多少。

4. chroot：只改路径解析里的一个成分

换根这件事，Linux 上有个用了几十年的老办法叫 chroot。它的接口简单到只有一个参数：给它一个目录，从此这个进程解析绝对路径时，/ 就指向那个目录。

拿今天造好的根文件系统试一遍：

# chroot_test.py 的前半段。三个小函数把「读不到」和「读到了」都变成能打印的东西，
# 后面每个时刻都用同一组问题问一遍，才好逐行对照。
import os
def mounts():
    try: return sum(1 for _ in open("/proc/self/mounts"))   # 我眼里有几个挂载点
    except Exception as e: return type(e).__name__
def mark():
    try: return open("/hostmark.txt").read().strip()        # 宿主上那个暗号文件
    except Exception as e: return "读不到(" + type(e).__name__ + ")"
def cwd():
    try: return os.getcwd()
    except Exception as e: return type(e).__name__
print("宿主起点   条目数=%d 暗号=%s 挂载点=%s" % (len(os.listdir("/")), mark(), mounts()))
os.chroot("/root/lab/rootfs")      # 只换根，当前工作目录一动不动
print("chroot 后  条目数=%d 暗号=%s 挂载点=%s cwd=%s" % (len(os.listdir("/")), mark(), mounts(), cwd()))

前两格确实变了：26 个条目变成 10 个，昨天那个怎么都读得到的暗号，现在读不到了。Day 10 留下的那个洞，看起来堵上了。挂载点那一格读不到，是因为根文件系统里还没挂 /proc，那个文件不存在，这个不算异常。

奇怪的是最后一格。getcwd() 报了个「文件不存在」——问自己在哪儿，答不上来。

手册把原因写得很直白。man 2 chroot 的 NOTES 一开头就是：「This call does not change the current working directory, so that after the call '.' can be outside the tree rooted at '/'.」——这个调用不改变当前工作目录，所以调用之后，. 可以落在以 / 为根的那棵树之外。

同一页还有一句更重的：「it is not intended to be used for any kind of security purpose, neither to fully sandbox a process nor to restrict filesystem system calls.」——它不是为任何安全目的设计的，既不用来完整地沙箱化一个进程，也不用来限制文件系统相关的系统调用。

这句话在 Linux 手册里算是很少见的措辞。手册一般只描述行为，不劝你别用。它专门写了这么一段，说明这个误用普遍到值得写进文档。

手册接着给了三步，短到可以直接抄：「the superuser can escape from a 'chroot jail' by doing: mkdir foo; chroot foo; cd ..」。三个动作，全是普通命令。

环境一是上一节那个 chroot 之后的进程。环境二是今天要装配的那个容器，换根用的不是 chroot 而是 pivot_root，别的都一样。

两个「读不到」是不同意思，先分开。起点那一行环境一读不到挂载点条数，是因为根文件系统里没有挂 /proc，那个文件根本不存在；对照一下宿主上直接跑的基准——26 个条目、24 个挂载点——就知道那 24 个挂载点一个都没少，只是暂时读不到而已。

「走完之后」那四行是全部答案。26 正是宿主根目录的条目数，环境一原样走了回去，连暗号都又读到了；环境二四行一个没动。

为什么会这样，把两件事放在一起就清楚了。

第一件是 chroot 只做了一件事：改路径解析的起点。它没有动当前工作目录，所以调用之后，那个「当前目录」还指着宿主上的某个位置。cd .. 用的不是绝对路径解析，它是从当前目录往上找父目录——这条路根本不经过被改掉的那个起点。于是一路往上就走回了宿主的根。

第二件是挂载点那两个数：走完之后环境一眼里有 24 个挂载点，和宿主上直接跑时一模一样；环境二只有 2 个。chroot 从来不动挂载表，宿主上那 24 个挂载点在它的世界里始终都在，只是路径一时够不着；而换根之后的容器，挂载表里只剩自己的根和一个 /proc。它走不出去，不是因为够不着，是因为外面那些东西已经不在它的地图上了。

关键结论

chroot 换的是路径解析的起点，pivot_root 换的是挂载表里的根挂载。前者是一个能被绕过去的约定，后者是把外面那些挂载从这个进程的世界里摘掉。手册那句「不是为任何安全目的设计的」，说的就是这个区别。

板块 2 · 第二部分换根的正确做法

7. 挂载表是可以自己改的

先把上一部分那个「挂载点条数」说清楚，因为后面每一步都在动它。

你的进程解析一个路径时，内核要查一张表：哪个目录上盖着哪个文件系统。这张表就是 /proc/self/mounts 里的那些行，一行一个挂载点。宿主上是 24 行，容器里是 2 行。

Day 10 说挂载命名空间「复制的是这张表」。man 7 mount_namespaces 的原话是：「the mount list of the child's namespace is a copy of the mount list in the parent process's mount namespace」——子命名空间的挂载表是父进程那张表的一份拷贝。

拷贝的意义在于：从这一刻起，你在里面加一行、删一行，外面那张表不受影响。所以换根这件事的真正含义是——在自己那份拷贝上，把「根」这一行换成别的。

要换成什么？man 2 pivot_root 有一条硬要求：「new_root must be a path to a mount point, but can't be '/'」——新根必须是一个挂载点，而且不能是 / 本身。

可你手上的根文件系统只是个普通目录，不是挂载点。怎么把一个目录变成挂载点？

# 把一个目录挂到它自己身上。挂载点表里因此多出一行，源和目标是同一个位置
$ mount --bind /root/lab/rootfs /root/lab/rootfs

这个动作叫绑定挂载（bind mount）：把文件系统里已有的一棵子树，再挂到另一个位置上。两个位置看到的是同一份数据，改一边另一边立刻能看到。这里的用法是最省事的一种——源和目标写成同一个路径，唯一的效果就是让这个目录在挂载表里获得自己的一行。

绑定挂载在容器世界里到处都是。往容器里塞一个配置文件、把宿主的某个数据目录给容器用，用的都是它。今天只用它最退化的那种形态。

8. 换根四步

准备好之后，换根是四个动作。先看它们连在一起长什么样，再逐个说：

mount --make-rprivate /            # ① 把整棵挂载树的传播类型设成 private
mount --bind "$ROOT" "$ROOT"       # ② 让 rootfs 目录成为一个挂载点
cd "$ROOT"
pivot_root . oldroot               # ③ 旧根移到 ./oldroot，当前目录成为新的根挂载
cd /
/bin/mount -t proc proc /proc      # ④ 进程号那张表换了，/proc 也要重挂才对得上
/bin/umount -l /oldroot            # ⑤ 摘掉旧根，摘完就再也走不回去

说是四步写了五行，因为第 ③ 步的效果要靠第 ⑤ 步才完整。

pivot_root 自己做的事，手册一句话说完：「it moves the root mount to the directory put_old and makes new_root the new root mount」——把根挂载移到 put_old 这个目录下，并让 new_root 成为新的根挂载。注意它只是移动，没有丢弃。旧根这时候还挂在 /oldroot 上，里面就是完整的宿主文件系统。

所以第 ⑤ 步才是把门关上的那一下。umount -l 里的 -l 是惰性卸载（lazy unmount）：立刻把这个挂载点从表里摘掉，至于还有没有进程正在用它，等它们用完了内核自己收拾。这里用惰性版本是因为普通的 umount 会因为「设备正忙」失败——刚换过来，还有引用挂在上面。

第 ④ 步的理由写在 man 7 pid_namespaces 里，而且它说的正是今天这件事：「After creating a new PID namespace, it is useful for the child to change its root directory and mount a new procfs instance at /proc so that tools such as ps(1) work correctly.」——建了新的进程号命名空间之后，子进程最好换一下根目录，并在 /proc 上挂一份新的 procfs，这样 ps 之类的工具才能正常工作。procfs 就是 /proc 底下那个文件系统：它不占磁盘，内核把进程信息现编成文件的样子给你读。

Day 10 那个「加了 --pid 却没加 --mount-proc，/proc 里还是宿主那一堆」的坑，就是漏了这一步。

9. 挂载传播：一个容易漏的方向

你在容器里挂上去的东西，会不会漏到宿主上？

直觉上不会——都开了挂载命名空间了，表都是自己那份拷贝了，怎么会漏。

但挂载表的拷贝不是完全断开的。内核提供了一套机制，让一个挂载点上发生的挂载和卸载事件，能自动传到别的挂载点上去。这套机制叫挂载传播（mount propagation），每个挂载点有一个传播类型，决定事件怎么走。man 7 mount_namespaces 给了四种，今天要用的是前两种：

传播类型手册怎么说意思
MS_SHARED
共享挂载		「This mount shares events with members of a peer group. mount(2) and umount(2) events immediately under this mount will propagate to the other mounts that are members of the peer group.」它属于一个对等组（peer group），这个挂载点底下发生的挂载和卸载，会传给组里的其他成员
MS_PRIVATE
私有挂载		「This mount is private; it does not have a peer group. mount(2) and umount(2) events do not propagate into or out of this mount.」没有对等组，事件既不传进来也不传出去
MS_SLAVE
从属挂载		「events propagate into this mount from a (master) shared peer group. events under this mount do not propagate to any peer.」单向：外面的挂载能传进来，里面的传不出去
MS_UNBINDABLE「This is like a private mount, and in addition this mount can't be bind mounted.」私有，而且不许被绑定挂载

这四种里，共享是最需要留神的一种，而且它常常是默认状态。手册直接点名：「systemd(1) automatically remounts all mounts as MS_SHARED on system startup.」——systemd 在系统启动时把所有挂载重挂成共享。也就是说，你上岗后碰到的绝大多数生产机器，根挂载都是共享的。

共享到底会漏成什么样，做一次就知道。实验很小：先让 /tmp/prop 成为一个挂载点，把它的传播类型设成共享或私有，然后在挂载命名空间里往它底下挂一个 tmpfs（内存里的临时文件系统，用它只是因为随手挂一个最省事），最后回到宿主上看那个位置成没成挂载点。

# prop_test.sh 的主体，两种传播类型各跑一遍
mount --make-$mode /tmp/prop                 # $mode 取 shared 或 private
echo "传播类型 = $(findmnt -no PROPAGATION /tmp/prop)"   # findmnt 查挂载表，-no 只打指定那一列
# --propagation unchanged：让 unshare 别替你改传播类型，见下面那段
unshare --mount --propagation unchanged -- bash -c \
  'mount -t tmpfs none /tmp/prop/x; echo "  命名空间里看：$(findmnt -no TARGET /tmp/prop/x)"'
# 命名空间里的进程已经退出了，现在这条是宿主上的视角
findmnt -no TARGET /tmp/prop/x && echo "  宿主上看：也成了挂载点 → 漏出来了" \
                               || echo "  宿主上看：不是挂载点 → 没漏"

两次的输出：

── 父挂载设成 shared ──
传播类型 = shared
  命名空间里看：/tmp/prop/x
  宿主上看：也成了挂载点 → 漏出来了
── 父挂载设成 private ──
传播类型 = private
  命名空间里看：/tmp/prop/x
  宿主上看：不是挂载点 → 没漏

命名空间开了，挂载表复制了，东西照样漏了出去。这就是换根四步里第 ① 步 mount --make-rprivate / 存在的理由：进去之后第一件事，把整棵树的传播类型改成私有，切断这条通路。-r 是递归，意思是这棵树下面所有挂载点都改。

还有一件事值得说，因为它解释了为什么很多人从来没撞见过这个坑。上面那条命令里有个 --propagation unchanged，如果去掉它，两种情况都不会漏。原因在 man 1 unshare：「The default is to set the propagation to private.」而且它写明了从哪一版开始——「unshare since util-linux version 2.27 automatically sets propagation to private in a new mount namespace to make sure that the new namespace is really unshared.」

也就是说，命令行工具替你做了这一步。你要是直接调 unshare(2) 这个系统调用自己写容器，就没人替你做了。

传播类型还管着另一件事。刚才那条硬要求还有下半句，man 2 pivot_root 写着：「The propagation type of the parent mount of new_root and the parent mount of the current root directory must not be MS_SHARED.」——新根的父挂载和当前根目录的父挂载，传播类型都不能是共享。违反了会怎样，试一次：

$ unshare --mount --propagation unchanged -- bash -c '
    mount --make-shared /
    mount --bind /root/lab/rootfs /root/lab/rootfs
    cd /root/lab/rootfs; pivot_root . oldroot'
pivot_root: failed to change root from `.' to `oldroot': Invalid argument

这个报错很不友好——「参数无效」，而你的两个参数都完全正确。真正的原因在第三个地方：父挂载的传播类型。上岗后你多半会在别人的机器上撞见它一次，记住这个对应关系能省掉半小时。

关键结论

挂载命名空间给你的是一份拷贝，不是一堵墙。拷贝之间还连着挂载传播这条线，线的开关是每个挂载点的传播类型，而生产机器上的默认值往往是共享。所以进入命名空间后的第一个动作不是换根，是把传播类型改成私有——这一步既堵住了往外漏的路，也是 pivot_root 能不能成功的前提。

板块 2 · 第三部分装配

10. minibox 全文

零件齐了：一个根文件系统、三把锁、一套换根动作。拼起来是不到四十行 shell。三个开关分别控制装不装配额、换不换根、挂不挂名单，为的是后面每一列相对左边只多一样东西。

#!/bin/bash
# minibox：把配额、命名空间、换根、名单拼成一个能跑代码的最小容器。
# 每一层都能单独关掉，用来看「只多这一层」带来了什么。
#   CG=0/1  配额       PIVOT=0/1  换根      SEC=0/1  seccomp 名单
# 用法：minibox.sh <rootfs 目录> <要在里面跑的命令...>
set -e
ROOT=$1; shift
CG=${CG:-1}; PIVOT=${PIVOT:-1}; SEC=${SEC:-1}
CGROOT=/sys/fs/cgroup           # 这台机器上 cpu/memory/pids 挂在 cgroup v1 的各自目录下
NAME=minibox
LAB=$(cd "$(dirname "$0")" && pwd)

if [ "$CG" = 1 ]; then
  # 目录一删一建，计数器就归零，读到的是这一趟的净增量
  for c in cpu memory pids; do rmdir $CGROOT/$c/$NAME 2>/dev/null || true; mkdir -p $CGROOT/$c/$NAME; done
  echo 100000 > $CGROOT/cpu/$NAME/cpu.cfs_period_us          # 窗口：100000 微秒墙上时钟
  echo  50000 > $CGROOT/cpu/$NAME/cpu.cfs_quota_us           # 额度：每窗口 50000 微秒 CPU 时间
  echo 268435456 > $CGROOT/memory/$NAME/memory.limit_in_bytes # 256 MiB
  echo 64 > $CGROOT/pids/$NAME/pids.max                       # 最多 64 个进程
fi

# --fork 是必须的：进程号那张表要在下一个进程身上才生效
exec unshare --pid --fork --mount --uts --ipc --net -- \
  /bin/bash -c '
    set -e
    CG='"$CG"'; PIVOT='"$PIVOT"'; SEC='"$SEC"'; ROOT='"$ROOT"'; LAB='"$LAB"'
    if [ "$CG" = 1 ]; then
      for c in cpu memory pids; do echo $$ > /sys/fs/cgroup/$c/minibox/tasks; done
    fi
    hostname minibox
    if [ "$PIVOT" = 1 ]; then
      # 父挂载若是 shared，里面挂的东西会漏回宿主，而且 pivot_root 会直接拒绝
      mount --make-rprivate /
      # pivot_root 要求新根自己就是一个挂载点，所以把目录绑定挂载到它自己身上
      mount --bind "$ROOT" "$ROOT"
      cd "$ROOT"
      pivot_root . oldroot           # 旧根被移到 ./oldroot，当前目录成为新的根挂载
      cd /
      /bin/mount -t proc proc /proc  # 进程号换了，/proc 也得重新挂一次才对得上
      /bin/umount -l /oldroot        # 摘掉旧根，摘完就再也走不回去
      SECBIN=/bin/seccomp_run
    else
      mount -t proc proc /proc       # 不换根时也要重挂 /proc，否则看到的还是宿主那一堆
      SECBIN=$LAB/seccomp_run
    fi
    if [ "$SEC" = 1 ]; then exec "$SECBIN" 272 "$@"; else exec "$@"; fi
  ' -- "$@"

跑起来应该看到什么：./minibox.sh /root/lab/rootfs /bin/sh -c 'hostname; ls /' 打出 minibox 和十个条目。看到 pivot_root: Invalid argument，回去查第 9 节那个传播类型；看到 /usr/bin/mount: No such file or directory，是 bash 把 mount 的路径缓存了下来，而换根之后那个路径不存在了——这就是第 ④ ⑤ 两行为什么写成绝对路径 /bin/mount。

有三处顺序是不能调的，调了就出问题：

  • 入组写在 unshare 之后。写在前面也能工作，但那样外层脚本自己也进了这个组，它消耗的 CPU 会算在容器头上。
  • mount --make-rprivate 写在 mount --bind 之前。反过来的话，那个绑定挂载本身就是以共享的身份建出来的。
  • 重挂 /proc 写在 umount -l /oldroot 之前。反过来也能成，但那一瞬间 /proc 是旧根带过来的那一份，中间要是出错，你看到的是宿主的进程表。

最下面四行是今天仍然没变的，它们才是要带走的边界。前三行 Day 10 已经钉过一次：cgroup 限的是「你能用多少」，不改「机器有多大」。

剩下 /proc/self/cgroup 那一行是今天新冒出来的一个小口子。容器里读这个文件，读到的是 /minibox——宿主给这个 cgroup 起的名字，原样漏了进去。名字本身不值钱，但它泄露了宿主的组织方式：真实环境里这个路径常常长成 /kubepods/burstable/pod3f2a.../abcd...，里面带着调度层给这个容器安排的一串名字和它的编号。堵法是有的，而且今天的零件就够：入组之后再开一个 cgroup 命名空间，同一个文件就会读成 /。这是今天动手任务的加分题。

关键结论

14. 1 号进程不是普通进程

装配好之后有一件事变了，而且是在你没注意的地方变的。看第 11 节那张表的第一行：容器里能看见 1 个进程。那个进程的进程号是 1。

在 Linux 上，1 号进程有一套和别人不一样的规矩。man 7 pid_namespaces 写得很直接：「Only signals for which the 'init' process has established a signal handler can be sent to the 'init' process by other members of the PID namespace.」——只有那些 init 进程自己装了处理函数的信号，才能被命名空间里的其他成员发给它。而且从外面发也一样：「a process in an ancestor namespace can...send signals to the 'init' process of a child PID namespace only if the 'init' process has established a handler for that signal.」

这里的 SIGTERM 是「请你自己退出」那个信号：程序可以装一个处理函数接住它，善后完再退；Day 10 讲过的 SIGKILL 则是拦不住的那个。

翻译成后果：一个没装 SIGTERM 处理函数的程序，当它是容器里的 1 号进程时，你发 SIGTERM 给它，它不会死。

验一次。同一个 sleep，一次在宿主上直接跑（它是个普通进程），一次当 minibox 里的 1 号进程。两次都发 SIGTERM，等 0.6 秒，再用 kill -0 看它还在不在：

宿主上直接跑 sleep（不是 1 号进程）: SIGTERM 之后 → 已经退出
minibox 里当 1 号进程的 sleep      : SIGTERM 之后 → 还活着，只能用 SIGKILL

这就是「docker stop 为什么要等十秒才真的停下来」的机制根源：先发 SIGTERM，等一段宽限期，超时了再发 SIGKILL。你的镜像里如果 1 号进程是个不处理 SIGTERM 的程序，那十秒每次都得等满。

同一页手册还有一条要一起记住：「If the 'init' process of a PID namespace terminates, the kernel terminates all of the processes in the namespace via a SIGKILL signal.」——1 号进程一退出，内核用 SIGKILL 把这个命名空间里所有进程一起终结。对沙箱来说这是好消息：你只要能可靠地干掉 1 号进程，里面不管派生了多少子进程都会跟着走，不会有漏网的。

还有个相关的小陷阱藏在 man 1 unshare 里：「Note that when unshare is waiting for the child process, then it ignores SIGINT and SIGTERM and does not forward any signals to the child.」——unshare 等子进程的时候会忽略 SIGINT 和 SIGTERM，也不转发任何信号。所以在这套装配下，信号得直接发给容器里那个进程在宿主上的进程号，发给外层脚本没用。

15. 还开着的三个口子

装配完了，探针也打过了。剩下这三样是明后天的题目，今天先看清楚它们长什么样。

一 · 根文件系统是可写的，而且写穿到宿主

容器里往 /tmp 写一个文件，然后回宿主上看那个目录：

$ ./minibox.sh /root/lab/rootfs /bin/sh -c 'echo "容器里写的字" > /tmp/写进来的.txt'
$ cat /root/lab/rootfs/tmp/写进来的.txt
容器里写的字

原因在第 7 节：新根是宿主目录的一个绑定挂载，两边是同一份数据。所以容器里的代码能改这个目录里的任何东西——包括它自己的 /bin/sh。真跑不受信任的代码时，这一条是必须堵的。

二 · 机器有多大，它还是照实说

第 11 节最下面三行：/proc/cpuinfo 报 2 个 CPU，os.cpu_count() 返回 2，/proc/meminfo 报 8023 MB，而实际配额是半个核、256 MiB。这三个数从 A 列到 C 列一个字没变。

Day 10 已经把机制讲透了，今天只补一句今天才有的：换根之后 /proc 是重新挂的一份，但它挂的还是宿主内核的那个 procfs，报的还是整台机器。换根改的是「哪个目录是根」，不是「procfs 里写什么」。

三 · 内核还是同一个

Day 10 第四部分的结论今天原样成立，而且现在你有了一个具体的东西来指着说。你手上这个容器，里面的代码能发的系统调用，走的是和宿主上一切程序完全相同的那一份内核代码。三把锁加一个根，缩小的是「能做什么」，缩小不了「做的时候碰到的是谁的代码」。

关键结论

今天装出来的东西，把 Day 10 那张矩阵里「四列一模一样」的文件系统那几行改掉了，代价是启动时多花二十几毫秒——但真正的冷启动开销压根不在这里，它在准备那一千三百多个文件上，差了三十多倍。至于机器规格和共享内核这两条，装配一个也没动。

板块 4上岗关联

场景一 · 「我们的代码沙箱冷启动要一秒二」

产品说用户点一下「运行」，要等一秒多才看到输出。团队里有人提议「把 seccomp 关掉试试，那玩意儿肯定慢」。

你手上现在有一张能立刻反驳的表：整套隔离机制加起来是二十几毫秒，占不到那一秒二的百分之二。真正的钱在准备根文件系统和拉起语言运行时上。你该做的第一件事不是关锁，是把这一秒二按第 13 节那个方法拆开——每一层都做一个对照行，直到某一行明显比上一行贵。

拆完之后大概率会指向两件事：镜像/根文件系统的准备，和解释器的启动。这两件的解法分别是分层与池化预热，都是 Day 14 的内容。

场景二 · 「沙箱超时了但杀不掉」

你的 agent runtime 给每个工具调用设了 30 秒超时，超时就发 SIGTERM。线上发现有些沙箱超时之后又活了很久，直到某个兜底逻辑发 SIGKILL 才没。

第 14 节就是答案：容器里的 1 号进程只接受它自己装了处理函数的信号。用户提交的代码通常不会装 SIGTERM 的处理函数，所以 SIGTERM 对它是空的。

正确的做法有两层：一是终止路径上必须有 SIGKILL 兜底，而且宽限期要设成一个你能接受的值；二是让容器的 1 号进程是你自己写的一个小程序，它装好信号处理、把信号转给真正的用户代码、顺便回收派生出来的子进程。这个角色在容器生态里有个专门的名字，Day 13 读 runc 的时候会碰到它。

场景三 · 「同一段脚本，在我的机器上能起，到测试环境就报 Invalid argument」

典型的传播类型问题。你的开发机上根挂载可能是私有的，而测试环境跑着 systemd——手册那句「systemd 在系统启动时把所有挂载重挂成共享」正好解释了这个差异。

排查顺序：findmnt -no PROPAGATION / 看一眼，是 shared 就在换根前补上 mount --make-rprivate /。这条经验值钱的地方在于，报错信息（「参数无效」）完全没指向真正的原因。

问题答的要点
chroot 和容器差在哪？换的东西不一样：一个换路径解析的起点，一个换挂载表里的根挂载。前者不动挂载表，所以外面的东西还在它的世界里；而且它不动当前工作目录，从当前目录一路往上就能走回去。手册里明写着「不是为任何安全目的设计的」
为什么要 pivot_root 而不是 chroot？除了上一条，还因为 pivot_root 把旧根移到一个能被卸载的位置，卸载之后旧根就从这个进程的挂载表里彻底消失了。chroot 没有对应的动作
容器里的 1 号进程有什么特别的？两条：没装处理函数的信号发不进去；它一退出，内核用 SIGKILL 结束整个命名空间里的所有进程
起一个容器慢，先看哪儿？先按层拆，每层配一个只多包装不多机制的对照行。经验上隔离机制那部分是几十毫秒量级，文件准备和运行时启动是几百到上千毫秒量级
容器里 nproc 为什么报的是宿主的核数？它读的是「机器有多大」，cgroup 限的是「你能用多少」，两件事。要拿真实份额得去读配额文件，Day 10 那个 usable_cpus() 就是干这个的

板块 5自检问题

Q1 · 你在一台机器上写好了换根脚本，同事在他的机器上跑，pivot_root 报 Invalid argument。两个参数你们逐字对过，完全一样。接下来查什么？

查两台机器上根挂载的传播类型：findmnt -no PROPAGATION /。

手册的要求是「新根的父挂载和当前根目录的父挂载，传播类型都不能是 MS_SHARED」。这个条件不在你传的两个参数里，所以逐字对参数永远对不出问题——错误码指向的是「参数无效」，而真正无效的是环境。

为什么两台机器会不一样：跑 systemd 的系统在启动时把所有挂载重挂成了共享。所以「我的机器能跑」这件事本身不说明脚本对，只说明你那台机器的根挂载碰巧是私有的。

改法是在换根前加 mount --make-rprivate /。这一句同时解决两个问题：让 pivot_root 能过，以及切断容器里的挂载往宿主漏的那条路。

Q2 · 有人说：「我们已经开了挂载命名空间，容器里挂什么都影响不到宿主。」这句话在什么条件下是对的，什么条件下是错的？你怎么用两条命令验证？

对不对取决于挂载点的传播类型，不取决于有没有开命名空间。命名空间给的是挂载表的一份拷贝，而拷贝之间还连着挂载传播这条线。父挂载是私有的时候这句话对；是共享的时候，命名空间里的挂载会传出去。

验证两条命令：先 findmnt -no PROPAGATION / 看传播类型；再在命名空间里挂点东西，回宿主上用 findmnt 查那个位置在不在。

这里有个容易被绕过去的地方：用 unshare 命令行工具做实验，你多半复现不出漏的那种情况——它从 util-linux 2.27 起默认把传播设成私有。要看到真实行为得加 --propagation unchanged。所以「我试过没漏」这个证据，要先确认是谁替你把它堵上的。

Q3 · 你的沙箱冷启动 P99 是 1.4 秒。老板要求砍到 300 毫秒。按今天量到的比例，你会先动哪一块？为什么「把 seccomp 名单精简掉一半」这个提议不值得做？

先动准备根文件系统那一块。今天测到从零复制一份 80 MB / 1332 个文件的根，中位数是 1327 毫秒，而整套隔离机制加起来二十几毫秒。1.4 秒里绝大部分只可能在文件准备和运行时启动上。

方向是让每次启动不再复制文件：让多个容器共用同一份只读的底层文件，谁改了什么才单独存一份。这是 Day 14 的题目。

精简名单不值得做，有两个独立的理由。第一，量级不对：整个 seccomp 那一层只有三点几毫秒，全砍掉也够不到目标的零头。第二，Day 10 直接测过规则条数的影响——1 条、50 条、64 条三档的单次耗时范围互相重叠，看不出差别，贵的是「有没有过滤器」而不是「名单多长」。所以这个提议既解决不了问题，还会削弱防护。

Q4 · 容器里跑的代码把 /bin/sh 改了。你回宿主上一看，宿主的 /bin/sh 好好的。那被改的是什么？这件事危险在哪？

被改的是根文件系统那个目录里的 /bin/sh，也就是宿主上 rootfs/bin/sh 这个文件。它没影响宿主自己的 /bin/sh，因为那是两个不同的文件。

危险在于这个目录是被复用的。今天的绑定挂载是可读可写的，容器里的写直接落在宿主的那个目录上。下一个用同一个 rootfs 起来的容器，拿到的就是被改过的 /bin/sh。一段不受信任的代码通过这条路影响了后面所有的执行——它没有逃逸到宿主，但污染了执行环境。

顺带说，这也是为什么「跑完就把目录删了重建」这个笨办法是有效的，代价就是第 13 节那 1327 毫秒。明天讲的只读根加可写层，是同时要正确性和速度的做法。

句写成什么样就错了
第 1 句要说到两个不同的对象：一个换路径解析的起点，一个换挂载表里的根挂载。第二问如果写成「因为 chroot 权限不够」就错了，它成功了；正确的理由是它不动当前工作目录，而 cd .. 是从当前目录找父目录，这条路不经过被改掉的起点。补一句挂载点条数（24 对 2）能让答案更硬
第 2 句要点是 pivot_root 要求新根必须是一个挂载点，而你手上只有一个普通目录。如果只写「为了让它变成挂载点」，还差半句——为什么挂到自己身上就行：因为绑定挂载的效果就是在挂载表里加一行，源和目标写成同一个路径时，除了加这一行没有别的效果。不做它会看到 pivot_root: Invalid argument，和传播类型那个错撞成同一个错误码，这也是它值得记的原因
第 3 句两件事缺一不可：一是切断挂载往宿主漏的通路，二是满足 pivot_root 对父挂载传播类型的要求。只写第一件，会漏掉「为什么在别人机器上直接报错」；只写第二件，会漏掉真正的安全后果。如果你写成「因为命名空间不够」，那是把机制说反了——命名空间生效了，漏出去的路径是传播，不是命名空间失效
