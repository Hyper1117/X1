第 1 题（Day 23 · 把 CPU 摊到 span 上）

昨天那张表：32 条会话同时跑，把每个叶子 span 两端 time.process_time() 的差加起来，是这批会话真实 CPU 的 42.3 倍；并发降到 8 是 9.51 倍，降到 1 是 1.05 倍。

有人看完提议：那就把这个字段留在 trace 里，线上读出来除以当时的并发数，不就还原成每个 span 的真实 CPU 了吗。这个提议错在哪？

展开答案

先做一次除法。42.3 除以 32 是 1.32，9.51 除以 8 是 1.19，1.05 除以 1 是 1.05。三个商互不相等，而它们本该是同一个"还原系数"。所以这不是一个可以除掉的常数因子。

商为什么不等，昨天的机制那一段已经说清了：一个 chat span 期间，这个协程绝大部分时候挂在 await 上，事件循环正在跑别的会话的回调，那些回调烧掉的 CPU 全都落进了这个 span 的两次读数之间。落进来多少，取决于那一刻别的会话恰好在干什么——有的在解 JSON，有的只是在等。这个量和并发数有关，但不是正比。

更根本的一句昨天写在结论里：墙上时间可以按区间归因，因为一个时刻只有一段区间在往前走；CPU 不行，因为一个时刻只有一个协程在真正跑，而它是谁，两次时钟读数之间的差告诉不了你。除法救不了一个方法本身就不成立的口径。

今天接在这儿：昨天给出的替代路子是"不按 span 摊，按整个进程报，要定位就另开剖析器"。今天整页量容量，用的正是这条路。

第 2 题（Day 21 · 三种排法）

那张排队表里，单一 FIFO 队列时池子忙着的比例是 98.7%，全部做完是 2.230 秒；换成每租户硬配额之后，比例掉到 54.4%，全部做完涨到 4.044 秒。而换成轮转的那一行，"全部做完"和"忙着的比例"两列一个数都没动。

这两列之间是什么关系？为什么轮转动不了它们，硬配额能？

展开答案

那张表下面写着最后一列的算法：全部任务的服务时间之和（440 条 × 40 毫秒 = 17.60 秒），除以 8 个许可乘全部做完的秒数。

分子是固定的——一共有多少活儿，跟你怎么排队没关系。所以这两列其实是同一个数的两种写法：17.60 ÷（8 × 2.230）= 98.7%，17.60 ÷（8 × 4.044）= 54.4%。知道一列就能算出另一列。

轮转只改了"下一个空位给谁"，没改"一共有多少活儿"，也没让任何一个空位在有人排队的时候闲着。分母里那个秒数不动，比例自然也不动。硬配额不一样：乙丙手上握着许可却无事可做，甲有 400 条等着却只能用自己那份，将近一半的池子在空转。这个性质那天给了名字，叫工作保全——只要还有活儿等着就不让位置闲着，轮转有，硬配额没有。

今天接在这儿：今天要给运行时定一个并发上限。"这个上限该定多少"和"定完之后机器还剩多少利用率"，是同一件事的两面。

第 3 题（Day 17 · 过河的钱怎么收）

那天量到：vLLM 前端和引擎之间过一次河是 131.1 微秒；消息从 24 字节涨到 2693 字节（一百一十二倍），一个来回只从 129.2 微秒走到 133.9 微秒。结论是"过河的钱几乎全是固定开销，按次数收，不按字节收"。

现在把并发从一条提到一百多条，两个进程之间同时开着一百多条连接。这条结论里有一个前提今天会被打破——是哪个前提？

展开答案

被打破的前提是：一次交接的那笔固定开销，本身是个常数。

那天量的时候，两个进程之间的路只有一条。"固定开销"指的是两次系统调用、一次进程唤醒、一次调度——这几样和别人无关，所以它确实是常数，涨的只是次数。

一百多条连接同时开着的时候，一次交接不再只是"两个进程之间的一次往返"。发请求之前还得先在一堆连接里挑出该用哪一条，收完之后还得把它放回去；挑和放这两件事要看的是整个池子，而池子的大小随并发涨。

所以"按次数收"这一半今天仍然成立，"每次收多少是个常数"这一半今天不成立。今天整页算的就是这个不是常数的东西。

板块 2 · 第一部分 · 验收一个 agent 运行时，该打哪几个数

同一台机器、同一份代码，换一个判定标准，结论能差三倍。这一部分定的就是判定标准。

1. 照着压普通接口的那套，会给出一个错得离谱的数

交付日到了，"它能扛多少"这个数从哪儿来？

作为后端工程师，最顺手的一步大概是：抄起一个压测工具，对着运行时的 /run 接口以某个速率打，把 QPS 和 P99 画出来，找那条曲线拐弯的地方。这个做法在普通接口上是对的，在这里会给出一个错得很离谱的数。

三个地方对不上。

第一，QPS 在这儿几乎没有意义。一条会话要转六轮，每一轮等模型七百多毫秒、等工具两百多毫秒，一条会话五秒六。用"每秒完成几条会话"当横轴，一台机器上的数字会是个位数，而它随会话轮数变——同一台机器，会话从 6 轮变成 12 轮，这个数直接砍半，可机器的能力一点没变。真正稳定的横轴是"同时在跑几条"。

第二，压测工具自己会成为被测对象。Day 6 那条规矩在这台 2 核机器上格外要紧：一个在同一台机器上跑的压测器，要维护一百多条连接、解析一百多份响应，它烧的 CPU 会和被测服务抢核，于是你量到的塌点其实是压测器的塌点。今天的做法是把压测搬进被测进程自己身上，让它自己开一百多条会话——横轴变成"这个进程内部同时在跑几条"，压测器彻底退场。

第三，也是最要命的一条：P99 报警的时候已经晚了。这一条 Day 18 就量到过，今天会再撞一次。

2. 判定"它塌了"的那个指标

Day 18 那张并发扫描表里有一件事值得原样搬过来：128 条并发那一档，事件循环延迟均值已经到 22.62 毫秒、会话耗时是低并发时的 3.8 倍，而 CPU 占用是 81.8%——连一个核都没用满。那天写下的规矩是：判定并发上限用事件循环延迟，不用 CPU 使用率，也不用端到端延迟，后两个都比它晚。

这条规矩听起来像是"多打一个指标"，实际上它换掉的是判定的整个形状。CPU 使用率是一个有天花板的量，它涨到 100% 就不再动了，所以它没法告诉你"已经超了多少"。端到端延迟涨得晚，因为一次交接变贵之后，要经过好几轮才在会话总时长上攒够看得见的差。事件循环延迟不一样——这个词 Day 4 引入过：一个协程说"叫我睡 10 毫秒"，实际被叫醒时晚了多少。一旦回调开始排队，它当场就动。

今天把这条规矩落成一个具体的判据，好让四次扫描能横着比：拐点（knee point）取在事件循环延迟均值越过 10 毫秒的那两档之间。10 这个数不是拍的——探针的间隔是 10 毫秒，延迟均值达到一个探针间隔，意味着平均每次唤醒都要等过一整个周期，这是"回调队列已经排起来了"最朴素的一条界线。

外层已经在遍历整个池了，第 294 行那个 len([...]) 又把整个池遍历了一遍——它要数"现在有几条是空闲的"。这两层嵌起来，一次调用的代价就是池里连接数的平方。

更浪费的是这个内层扫描几乎总是白做。Python 的 and 是短路求值（short-circuit evaluation），从左往右算：只要 connection.is_idle() 为真，右边那个 len([...]) 就一定会被算出来，然后才拿去和阈值比。而这个阈值 max_keepalive_connections 在 httpcore 的默认配置下等于 sys.maxsize——比较结果永远是假。也就是说，一个数被完整地数出来，只为了参加一次注定不成立的比较。

9. 两条出路，各把墙挪了多远

瓶颈落在第三方库里，出路只有两条：改库，或者绕开。两条都值得量一次，因为它们付的代价完全不同。

第一条是上游修复（upstream fix）的本地预演：把那个内层扫描挡在一个 O(1) 的判断后面。逻辑一个字没变——池里连接总数都不超过阈值的时候，空闲的条数更不可能超过，所以那个 len([...]) 的结果一定是假，不用算：

elif (
    len(self._connections) > self._max_keepalive_connections   # ← 先问这一句，O(1)
    and connection.is_idle()
    and len([c for c in self._connections if c.is_idle()])
    > self._max_keepalive_connections
):

这种"运行时替换掉别人的函数"的做法叫猴子补丁（monkey patching）。它能立刻验证判断对不对，代价是把自己绑在了这个库的某个版本上——库一升级，被替换掉的那个函数可能已经换了样子，而你的补丁不会报错，只会静悄悄地失效或者更糟。把这一段变量提到循环外面的做法叫循环不变量外提（loop-invariant hoisting），是给上游提改动时最好写的一类。

第二条是绕行（workaround）：库一个字不改，把一个装了一百多条连接的池换成八个各装十几条的池，会话按序号分到某一个池上。这叫连接池分片（pool sharding）。既然那个函数的代价是池长的平方，把池长砍成八分之一，每次扫描就便宜六十多倍。

第 1 步：先有一个假模型

# svc_model.py —— 假模型服务
import asyncio, os
from fastapi import FastAPI, Request

TTFT = float(os.environ.get("TTFT_MS", "100")) / 1000.0   # 首 token 前等多久
ITL  = float(os.environ.get("ITL_MS", "5")) / 1000.0      # token 之间隔多久
NOUT = int(os.environ.get("N_OUT", "128"))                # 一轮吐几个 token

app = FastAPI()

第 2 步：把两把秤装进运行时

运行时那一侧要装的不是三个指标，是两把秤加一个探针。CPU 用进程 CPU 时钟量整个进程（Day 23 已经证明它不能按 span 摊），墙上时间用 perf_counter，事件循环延迟用一个 10 毫秒的探针。

# 事件循环延迟探针：说好睡 10 毫秒，实际晚了多少
class LagProbe:
    def __init__(self, interval=0.010):
        self.i = interval; self.samples = []; self.stop = False
    async def run(self):
        while not self.stop:
            a = time.perf_counter()
            await asyncio.sleep(self.i)
            self.samples.append((time.perf_counter() - a - self.i) * 1000)

def _install_counter():

        return r
    AsyncConnectionPool._assign_requests_to_connections = wrapped

验收标准：同一档下，开计数器和不开计数器的占核差别，要小于这一档三遍之间的浮动。差得多说明你的计数器太重了——最常见的原因是在里面做了字符串拼接或者写日志。

第 6 步：两条修法各量一次

一条是把那个内层扫描挡在 O(1) 判断后面（本页第 9 节那段），另一条是把一个池切成八个、会话按序号分派。各自单独扫一遍，再一起扫一遍，四条曲线用同一把尺判拐点。

验收标准：修好之后，"每次交接净耗"那一列从 16 条到 128 条应该几乎不动。如果它还在涨，说明还有第二个随并发变贵的动作没找出来，回第 4 步。

第 7 步：把并发上限填进准入控制

拿第 6 步扫出来的数，减去一档留余量，做成 Day 14 那个许可加队列上限。然后再扫一遍：这一次曲线应该在到达上限之后变平，而不是塌下去，代价是超出的请求当场被拒。

验收标准：把并发加到上限的两倍，事件循环延迟均值仍然在 1 毫秒量级，而被拒的请求数等于超出的那部分。延迟仍然爆掉，说明许可归还的时机写错了——它该在拿到结果那一刻归还，不是在整条会话收尾之后。

任务 B（约 30 分钟）· 用到你自己的服务上

找一个你手上任何一个 asyncio 写的、会去调别的服务的程序，哪怕它和 agent 毫无关系。做三件事：

  1. 给它加一个 10 毫秒的事件循环延迟探针，把均值和最大值打出来。这一步不改任何业务逻辑。
  2. 找出它的 HTTP 客户端是怎么建的，看看连接池上限是多少、有没有全局复用一个 client。如果它是每次请求新建一个 client，那连池都没有，每次都在重新握手；如果它是一个 client 配了很大的池，那就是本页量的这个形状。
  3. 用你手边最大的一档负载跑一遍，同时读两把秤：进程 CPU 占核比例，事件循环延迟均值。把这两个数和你现在监控面板上有的那些指标并排放，看哪个先动。

验收标准：你能说出一句"我们这个服务真正的容量判据应该是 X，因为 Y 比它晚"，并且 Y 是你自己量到的，不是抄这一页的。

板块 4 · 工作现场

场景一 · 「换了个更快的模型服务，我们的运行时反而告警了」

推理那一侧升级完，首 token 快了一半。产品很高兴，运行时这一侧开始报事件循环延迟。有人第一反应是"新版模型服务有问题"。

问题不在那边。Day 18 已经量过这件事：模型时序减半之后，每条会话的 CPU 一点没少（交接次数没变、字节数没变，运行时凭什么少干），可同样多的活儿被压进短一截的时间里，占核比例涨了 1.46 倍。今天这一页把它推到了更难受的地方——每次交接的价钱本身还随池子里的连接数涨，所以下游变快会同时推高两个乘数。

该做的事只有一件：重扫。设计文档第 3 条那句"模型服务换代之后要重扫"，写的就是这个场景。

场景二 · 「面板上一切正常，用户说慢」

CPU 使用率 40%，内存平稳，下游服务的 P99 正常，可用户报的会话耗时是平时的三倍。面板上找不到任何异常。

这是本页第 6 节那张表的样子。CPU 使用率是个有天花板的量，它在塌之前很久就不再有信息量了；下游 P99 正常是因为塌的是你这边，你甚至可能因为整体变慢而给下游发得更少。要在面板上看见这件事，得加一条事件循环延迟的曲线，它比 CPU 早两档报警。

还有一条更朴素的检查：把"每条请求消耗的 CPU"画成一条随并发变化的曲线。它如果是平的，容量可以外推；它如果在爬，说明有东西随并发变贵，那个东西迟早会把曲线拽下去。

场景三 · 「瓶颈在一个我们不维护的库里」

定位到了，问题在某个依赖的内部实现上。团队里通常会分成两派：一派要马上打补丁上线，一派要给上游提改动然后等。

本页第 9 节把这两条路的价钱都量出来了：猴子补丁立刻生效但把你绑在了这个版本上——库一升级，被替换掉的函数可能已经换了形状，而补丁不会报错，只会静悄悄失效。绕行（这里是分片）不碰库，升级安全，代价是多开的连接和多出来的一层分派规则，而且这层规则以后可能和别的分派规则打架。

实践里两条常常一起走：先绕行止血，同时把最小改动提给上游；上游合并、版本升上来之后再把绕行拆掉。这时候你需要一个能证明"拆掉之后没退化"的东西，而那个东西就是今天这套扫描。

同事和面试官会问的几句

  • 「你们这个服务能扛多少并发？」——正确的回答形状不是一个数字，是"判据是什么、上一次扫是什么时候、哪些条件变了要重扫"。直接给数字的人，八成给的是低并发外推出来的那个高估值。
  • 「CPU 才用了一半，为什么不再多放点进来？」——因为在异步服务里 CPU 使用率不是第一个撞墙的东西。给出你自己量到的那条"每次交接的开销随并发涨"的曲线。
  • 「这段阻塞代码要不要挪到线程池里？」——反问一句：这段阻塞的墙上时间是多少，其中真正烧 CPU 的是多少。两个数接近，挪出去只会更贵。
  • 「为什么不直接上剖析器？」——可以上，但要先用逐项关掉把自己的代码摘干净，而且要知道剖析器会改变被测对象，它的输出用来指路不用来算比例。

板块 5 · 自检问题

1. 有人说：「我们把并发上限从扫出来的 384 提到 500，反正 CPU 还没满。」用本页的数评估这个提议。

384 那一档的事件循环延迟均值是 9.07 毫秒，已经贴着判据线（10 毫秒）；512 那一档是 21.73 毫秒，会话 P50 从 7.8 秒跳到 14.5 秒。中间没有平缓过渡——第 6 节那个自己咬自己的圈决定了这条曲线在两档之间掉下去。

"CPU 还没满"这句话本身是错的判据。512 那一档 CPU 是 80.3%，384 那一档 69.4%，两者差了不到 11 个百分点，而会话耗时差了 86%。CPU 使用率在这段区间里几乎不带信息。

真正该说的是：384 已经是留了余量之后该往回退的位置，不是可以往上顶的位置。准入控制里填的数应该比它更小。

2. 「我们把连接池从 1 个切成 32 个，比 8 个更彻底。」这个提议错在哪儿，对在哪儿？

对的一半：累计的池长平方确实又降了二十倍（555264 → 27936），机制上没错。

错的一半：这二十倍买到的东西是零。第 9 节那张表里，8 个池到 32 个池，占核只从 26.0% 走到 22.3%，会话 P50 完全没动（5804 对 5808，在噪声里）。那个函数已经不是最大的一块了，继续砍它砍不出东西。

而代价是实打实的：32 个池意味着同一个下游最多同时挂着 32 份空闲连接，握手次数和文件描述符都要多；会话按序号分池这条规则也会和别的分派规则叠在一起。优化到收益耗尽点就该停，再往前走只剩代价。

3. 一个同事说：「第 8 节那张 cProfile 表显示 is_idle 被调了 53 万次，那我们直接按 53 万乘以每次的耗时，就能算出它值多少 CPU。」哪儿错了？

错在把一个被观察者效应污染过的数字当成了实测值。cProfile 给每次函数调用都记一笔账，被测进程因此变慢；变慢之后会话叠得更久，池里同时开着的连接更多，这个函数就被调得更多。53 万这个数本身是被剖析器抬高的。

本页里同一件事有两个口径可以对照：低开销计数器在 32 条并发下量到的累计池长平方是 706560，而 cProfile 那一档数出来的 is_idle 是 514608——两个数在同一个量级上对得住，说明计数器给的是可信的。但 64 条那一档，cProfile 数出来的是 938 万，计数器给的是 580 万，差了六成，因为并发越高剖析器的干扰越大。

正确的做法就是本页用的那个：剖析器只用来找出"该盯哪个函数"，找到之后换一把便宜的秤重新量，并且验证这把秤开不开对结果没影响。

4. 「既然每条会话只烧十一二毫秒 CPU，一个核一秒一千毫秒，那这台 2 核机器一秒能起一百多条会话。」这个算法哪一步开始不对？

第一步就把两个不同的量混在一起了。11 毫秒 CPU 是"一条会话从头到尾累计烧掉的"，而一条会话跨越 5.65 秒的墙上时间。要算容量，得先把它折成"一条会话平均占用一个核的百分之多少"：11.95 ÷ 5684 = 0.210%，然后一个核除以它，得 476 条同时在跑——注意这个数的单位是"条"，不是"条每秒"。

第二步的问题更隐蔽：这个外推只在"每条会话的 CPU 不随并发涨"的时候才成立。本页第 6 节那张表里它从 2.14 涨到 21.99，所以那时候的外推（Day 18 算出 405，实测墙 96~128）高估了四倍；第 10 节修完之后曲线拉平了，同样的外推给出 476，实测墙落在 384 到 512 之间，这才对得上。

所以这个算法的正确用法是当检验工具：外推值和实测差得远，说明曲线在爬，去找那个随并发变贵的东西。
