Q1 · 1 天前（Day 2 · 延迟的解剖学）

一个服务稳定地每秒进来 100 个请求，实测平均延迟是 200 毫秒。请问：任意一个瞬间，系统内部平均有多少个请求正在被处理？你用的是哪条关系式？
接着：如果运维为了"保护系统"，把最大并发数配置成了 10，会发生什么？

展开答案

用 Little's Law（利特尔法则）：L = λ × W。L 是系统里同时存在的请求数，λ 是到达速率，W 是每个请求在系统里待的总时间。

代进去：λ = 100 个/秒，W = 0.2 秒，所以 L = 100 × 0.2 = 20。也就是说，任意瞬间平均有 20 个请求同时在系统内部。

第二问要倒过来算。并发上限是 10，意味着 L 最多只能是 10。每个请求仍然需要 0.2 秒才能做完。那么这个系统每秒最多能处理 L ÷ W = 10 ÷ 0.2 = 50 个请求。

但外面每秒来 100 个。进得比出得快一倍。多出来的请求只能在并发上限外面排队，队列会一直变长，不会自己稳定下来。表现出来就是：延迟从 200ms 开始往上飘，飘到几秒、几十秒，永远不收敛。如果队列长度有上限，那么队满之后就开始直接拒绝请求。

这里的关键认识是：并发上限不是一个安全阀，它是一个吞吐量上限。你设的并发数除以单个请求的耗时，就是这台机器的吞吐天花板，跟你希望它是多少没关系。

Q2 · 2 天前（Day 1 · 全景与基线）

你在周报里写「服务平均延迟 30 毫秒」，你的 leader 说这个数没有意义，要看 P99。P99 = 200ms 这句话，逐字翻译成中文是什么意思？为什么平均值会掩盖问题？如果一个 agent 任务要串行调用这个服务 15 次，情况会更好还是更坏？

展开答案

P99 的逐字翻译：把这段时间内所有请求的延迟，从小到大排成一队，站在 99% 那个位置上的请求，它的延迟是 200 毫秒。换句话说，每 100 个请求里，有 1 个比 200 毫秒还慢。

平均值为什么掩盖问题，举个具体的数：99 个请求各花 10ms，1 个请求花了 2000ms。平均延迟 = (99×10 + 2000) ÷ 100 = 29.9ms。周报上写「平均 30ms」，看起来非常健康。但确实有一个用户干等了 2 秒。平均值把这个人平摊没了。

第三问是反直觉的地方，结论是更坏。单次调用踩到慢请求的概率是 1%，也就是不踩到的概率是 99%。串行调用 15 次，一次都不踩到的概率是 0.9915 ≈ 86%。反过来，至少踩到一次慢请求的概率 ≈ 14%。

也就是说，一个 P99 看起来还行的底层服务，被 agent 串 15 次之后，大约每 7 个 agent 任务就有 1 个会明显变慢。调用链越长，尾部延迟被放大得越厉害。这正是后面阶段三做 agent runtime 时会反复回到的问题。

核心讲解

1. 今天这一节要回答的问题

服务慢了，你怎么知道它慢在哪一行代码上？

昨天 Day 2 把一次请求的延迟拆成了两大块：一块是排队等着，一块是真正在被处理。今天要往"真正在被处理"这一块里面继续钻。请求进了函数以后，那几十毫秒到底花在哪儿了？

你作为后端工程师，第一反应大概是：加日志、打时间戳。像这样：

t0 = time.time()
result = do_something(req)
log.info("do_something 耗时 %.1fms", (time.time()-t0)*1000)

这个办法能用，但它有四个问题，而且每一个都很致命。

第一，你得先猜对位置。你在 do_something 外面埋了时间戳，可真正慢的是它内部调用的第 7 层的某个函数。你测出来"这里花了 80ms"，然后呢？你还得往里面再埋一层，再跑一次，再看。慢的地方越深，你要来回猜的次数越多。

第二，你得改代码然后重新部署。线上服务半夜出问题，你不可能改一行代码、发一次版、等它复现。

第三，埋得越细，测量本身越贵。time.time() 这个调用本身要花掉几十到几百纳秒。如果你在一个每秒被调用一百万次的函数里埋点，光是测量就吃掉了可观的 CPU。测量行为改变了被测量的对象。

第四，你只能看见你想到要看的地方。如果时间花在了一个你压根没想到的地方——比如某个库在偷偷做正则编译、比如 JSON 序列化——你永远埋不到那儿。

所以我们需要一个完全不同的思路。

2. 剖析器：换一种问法

这一节回答：有没有一种办法，不改代码、不用猜，就能知道时间花在哪？

剖析器（profiler）就是干这件事的工具。名字听着抽象，它做的事其实很朴素：它不去测"某个函数花了多久"，它去问"随便挑一个时刻，程序此刻在干什么"。

换个日常场景你就明白了。假设你想搞清楚一个工厂工人一天八小时都花在哪些事情上。

笨办法：给他每一个动作都掐秒表，拧螺丝按一次表，搬箱子按一次表。累死，而且他被你盯着，动作都变形了。这就是上面说的埋点计时。

聪明办法：每隔一分钟，你远远地给他拍一张照。一天下来你有 480 张照片。数一数：210 张照片里他在拧螺丝，96 张在搬箱子，48 张在等零件送过来。那你就知道了，他大约 44% 的时间在拧螺丝。你从头到尾没打扰过他，也没提前假设他在干什么。

这个"每隔一段时间拍一张照"的做法，就叫采样（sampling）。每秒拍多少张，叫采样频率（sampling rate），单位是赫兹（Hz）。99 Hz 就是每秒采 99 次，大约每 10 毫秒一次。

为什么剖析器分成两类，以及为什么生产环境只敢用一类

剖析器有两个流派。

一类叫插桩式剖析器（instrumenting profiler）。它在每个函数的进入和退出处都插一段计时代码。Python 自带的 cProfile 就是这一类。它给你的数字非常精确——每个函数被调用了几次、总共花了多久，一清二楚。代价是每次函数调用都变贵了。对于函数调用密集的 Python 代码，程序整体可能慢上一倍到几倍。

另一类叫采样式剖析器（sampling profiler），就是上面说的"拍照"。py-spy、perf 都属于这一类。

下面这张表把两者放在一起对比，重点是对比它们的开销和能否用在线上——因为这两点决定了你上岗以后实际会用哪一个。

对比项插桩式（如 cProfile）采样式（如 py-spy）
怎么工作每次函数进出都记一笔账每隔几毫秒看一眼程序在哪
开销来自程序自身的函数调用次数只跟采样频率有关
典型开销程序慢 2～10 倍1% 以下
要改代码吗要，得包一层跑不用，可以挂到已经跑着的进程上
结果性质精确计数统计估计，样本少了不可信
能用在线上吗不能能

这张表你重点看「开销来自」这一行，它是两者最本质的差别。插桩式的开销跟着程序的忙碌程度走：程序调用的函数越多，账记得越多，越拖慢。采样式的开销是你自己定死的：不管程序在跑什么，每秒就采 99 次，一次采样的成本是固定的。

这条差别直接决定了结论：线上服务只能用采样式。因为你不能接受一个诊断工具把线上服务拖慢一倍。而插桩式的价值在本地——当你已经锁定了一小段代码，想知道里面某个函数到底被调用了 10 次还是 10 万次的时候，它给的精确计数是采样式给不了的。

采样式的两个性质，你得记住

性质一：结果是统计意义上的，样本太少就不能信。

算笔账。以 99 Hz 采样 30 秒，你会拿到大约 3000 个样本。假设某个函数真实占用了 1% 的 CPU 时间，那它大约会出现在 30 个样本里——这个数还算能看。但如果一个函数只占 0.1%，它大约只出现 3 次，这跟随机噪声没法区分了。

所以有个实用的判断标准：火焰图上占比小于 1% 的东西，不要花时间去分析它。它可能是真的，也可能是采样抖出来的。要看清更细的东西，你得采更久或者采更密。

性质二：采样频率常见值是 99 而不是 100，这不是笔误。

假设你的程序里有个后台任务每 10 毫秒醒来一次。你用 100 Hz 采样，也是每 10 毫秒一次。两个周期一样长，采样点就可能每次都恰好落在那个任务醒着的瞬间（或者恰好每次都错过它）。结果就是这个任务的占比被严重高估或者严重低估。这种两个周期性行为对齐的情况叫锁步。选 99 这种质数，就是让采样周期跟程序里任何常见的周期都对不齐。

3. 调用栈和火焰图：几千个样本怎么看

这一节回答：采了 3000 个样本，是一堆散乱的函数名，怎么变成一张能看懂的图？

先补一个细节。剖析器每次"拍照"，拿到的不是一个函数名，而是整条调用栈（call stack）——这个词你写后端时应该已经见过，就是报错时打印出来的那一长串。也就是从程序入口一路调下来的完整链条，比如：

main → handle_request → tokenize → normalize_text → re.sub

这很重要。因为知道"20% 的时间在 re.sub 里"用处有限——正则替换可能被十几个地方调用。但知道"20% 的时间在 main → handle_request → tokenize → normalize_text → re.sub 这条路径上"，你就知道该去改哪里了。

现在你有 3000 条这样的栈。火焰图（flame graph）就是把它们合并显示的一种画法。合并规则很简单：前缀相同的栈，画成同一个方块。3000 条栈里有 2800 条都以 main → handle_request 开头，那 handle_request 就画成一个占总宽度 93% 的方块。

读火焰图的三条规则

规则一：横轴不是时间轴。

这是新手最容易搞错的一点，值得单独强调。火焰图上从左到右的顺序，通常就是按函数名的字母序排的，没有任何时间含义。左边的方块不是先执行的，右边的不是后执行的。

横轴上唯一有意义的是宽度。一个方块占总宽度的百分之几，就代表它出现在了百分之几的样本里，也就是大约占了百分之几的时间。

规则二：纵轴是调用深度，下面的调用上面的。

最底下那一层是程序入口，往上一层是它调用的函数，再往上是更深的调用。所以一根很高的"火苗"只是意味着调用链很深，本身不代表有问题。深层调用在现代软件里很常见。

规则三：先看图顶部的宽平台。

这是最实用的一条。在最顶端的那一层方块，代表的是采样那一刻真正在 CPU 上执行的那个函数，它没有再调用别人。这部分时间叫自身耗时（self time）——函数自己烧掉的时间，不含它调用的子函数。

所以你的目光要落在顶部又宽又平的那些块上。宽，说明占的时间多；在顶部，说明时间是它自己烧掉的，不是它的下游烧的。这两条同时满足的地方，就是你该动手优化的地方。

反过来说一个常见的误读：看到一个很宽的方块就以为找到瓶颈了。如果这个宽方块在图的中间层，它上面还叠着好几层，那它只是"路过"——时间是它的子函数花掉的，改它本身没有任何意义。

4. 揭晓：一半的时间凭空消失了

我用一个自己写的最小采样器跑了这个负载（原理和 py-spy 默认行为一致，30 行代码，等下动手环节你会亲手跑一遍）。默认参数下，结果是这样的：

=== 只统计"正在 CPU 上跑"的样本（py-spy 默认行为）===
  99.4%   318 个样本   cpu_burn
   0.6%     2 个样本   io_wait

那一半的等待时间，在火焰图上几乎完全不存在。不是被低估了，是压根没出现。图上会显示 cpu_heavy 占了 99% 以上，看起来这个程序是个纯计算密集型程序。

可你明明知道，它有一半时间在干等。

为什么会这样

因为采样器在拍照之前，还多做了一步：它先看一眼这个线程当前是什么状态，如果这个线程不在 CPU 上跑，它就直接跳过，这张照片不拍。

Linux 给每个线程都记录了一个状态字母，放在 /proc/<pid>/task/<tid>/stat 这个文件里。你关心两个值：

状态含义这个线程此刻在……
RRunning / Runnable正在 CPU 上执行，或者已经准备好了正排队等 CPU
SSleeping在等某件事发生：等定时器、等网络包、等锁、等磁盘

这张表看第三列。我们的脚本在 time.sleep(0.05) 期间，线程状态是 S。采样器看到 S 就跳过了。所以那 10 秒钟的等待，一个样本都没留下。

这个默认行为不是 bug，是有意为之。因为大多数时候你打开剖析器，问的问题是"我的 CPU 被谁吃了"，这时候把干等的线程混进来只会稀释信号——想象一个有 200 个连接的服务器，其中 195 个连接在闲着等新请求，如果全算进去，火焰图上 97% 都是"在等待"，你什么都看不出来。

现在给这个现象一个名字

只统计"线程真的在 CPU 上跑"的那部分时间做剖析，这种做法叫 on-CPU 分析。

研究"线程为什么不在 CPU 上、它在等谁、等了多久"，这个方向叫 off-CPU 分析。

这两个词是今天最重要的收获。它们对应两个完全不同的问题：

on-CPU 分析off-CPU 分析
回答的问题CPU 忙的时候，在忙什么？时间没在 CPU 上的时候，卡在等什么？
什么时候用CPU 跑满了，想知道被谁吃了CPU 没跑满，但服务就是慢
能抓到的问题低效算法、序列化开销、正则、无谓的拷贝锁竞争、磁盘 IO、等下游服务、线程池排队
工具py-spy（默认）、perf recordpy-spy --idle、strace、off-CPU 火焰图

这张表最该看的是「什么时候用」这一行。它给了你一条现场可用的判断路径：先看机器的 CPU 使用率。跑满了，用 on-CPU 分析。没跑满但服务慢，那你要找的东西在 on-CPU 火焰图上根本不会出现，别在那儿盯着浪费时间，得换 off-CPU 的思路。

顺带说一句，这条判断路径能直接接上昨天 Day 2 讲的「利用率与 P99 的非线性关系」：CPU 才 40% 但 P99 已经很难看，这种情况在真实服务里非常常见，而它的原因几乎从来不在 on-CPU 火焰图上。

把等待也算进来是什么样

py-spy 提供了 --idle 这个开关，意思是"闲着的线程也一起统计"。同一个负载，打开之后：

=== 统计全部样本（相当于 py-spy --idle）===
  54.8%   387 个样本   io_wait
  45.2%   319 个样本   cpu_burn

现在是 55% / 45%，跟真实的一半一半基本对上了。剩下的几个百分点的偏差来自采样本身的抖动，以及采样线程自己要抢 CPU 造成的轻微干扰。

关键结论

on-CPU 火焰图回答的是"CPU 忙的时候在忙什么"，不是"时间花在哪"。这是两个不同的问题。一个服务如果大部分时间在等，你拿 on-CPU 火焰图去看，会得到一个完全正确但完全没用的答案。
所以每次打开一张火焰图，先问自己一句：这张图里的 100% 指的是墙上时钟走过的时间，还是 CPU 忙碌的时间？

顺便说，这个坑对你四周后的岗位特别要命。AI 推理服务、agent runtime、sandbox 服务，这三样东西的共同点就是大量时间花在等待上：等模型返回、等工具调用完成、等容器起来。默认的 on-CPU 火焰图对这类服务的诊断能力非常有限。

5. 三个工具，各管一段

这一节回答：py-spy、perf、strace 这三个名字，分别该在什么时候拿出来用？

下面这张表在对比这三个工具各自能看见什么、以及各自的盲区在哪。之所以要这样对比，是因为新手最容易犯的错是拿一个工具死磕到底——比如 py-spy 上什么都没看出来，就以为服务没问题了。实际上你只是用错了工具。

工具能看见看不见一句话用法
py-spyPython 函数级的调用栈默认看不见等待的时间；看不见 C 扩展内部（除非加 --native）Python 服务慢了，第一个掏出来的工具
perf整台机器：内核、C/C++ 库、CPU 硬件计数器看不懂 Python 的函数名，只能看到解释器的 C 函数怀疑问题在 Python 之下（库、内核、硬件）时用
strace进程发出的每一个系统调用，以及每个调用花了多久用户态的计算完全看不见；开销大，不能用在高流量线上进程卡住了，想知道它到底在等谁

这张表重点看「看不见」这一列，因为它决定了什么时候你该换工具。三者的盲区正好互补：py-spy 看得懂 Python 但看不到底层；perf 看得到底层但读不懂 Python；strace 两个都不管，专门回答"在等谁"。

实际工作里的顺序几乎总是：先 py-spy（成本最低，信息最直接）。py-spy 显示热点在某个 C 扩展或者根本没热点，再上 perf。如果进程完全卡死不动了，直接 strace。

perf stat：一条命令看机器视角

perf 的完整用法很大，今天只给你一个最小的、马上能用的入口：perf stat。它不采栈，只统计一段时间内的一些计数器。

# 跑这个脚本，同时统计几个计数器
perf stat -e task-clock,context-switches,page-faults,cycles,instructions python3 workload.py

输出里你只需要看懂这几个字段：

字段意思你该从中看出什么
task-clock进程真正占用 CPU 的毫秒数把它除以总运行时间。我们这个脚本跑 20 秒，task-clock 大约 10 秒，比值 0.5 —— 一眼看出有一半时间没在用 CPU
context-switches被操作系统换下 CPU 的次数数值异常大，说明线程在频繁地睡下、醒来，通常意味着锁竞争或者线程开太多
instructions / cycles相除得到 IPC（每周期执行几条指令）IPC 低于 1，通常说明 CPU 大量时间在等内存。这个话题 Day 7 讲内存与 NUMA 时会展开

这张表你先只掌握第一行就够了。task-clock 除以墙上时钟时间，这一个比值就能立刻告诉你，该走 on-CPU 路线还是 off-CPU 路线。这是本节最实用的一句话。

perf record 采栈、生成 native 火焰图这部分，今天不讲，留到你把 py-spy 用顺手之后。

strace：只学一个用法

场景：一个进程完全没反应了，CPU 也是 0，你想知道它卡在哪。

# -p 挂到已经在跑的进程上；-T 显示每个系统调用花了多久
# -f 跟踪它创建的所有子线程
sudo strace -f -T -p 12345

你会看到一行行系统调用。如果屏幕上停在这么一行不动了：

futex(0x7f8a2c000b60, FUTEX_WAIT_PRIVATE, 2, NULL

没有右括号和返回值，说明这个调用还没返回——进程正卡在这里。futex 是 Linux 实现锁的底层机制，卡在这里通常意味着在等一把锁。如果卡在 recvfrom 或 read，那是在等网络或者磁盘。

今天 strace 就到这里，够你应付"进程卡死"这一种情况了。

动手任务

两个任务，预计一共 2 小时。任务 A 是必做，任务 B 是把今天的方法用到真实服务上。

任务 A · 亲手复现 on-CPU 盲区（约 1 小时）

第 1 步：装工具并解决权限

py-spy 要读另一个进程的内存，这需要操作系统授权。Linux 上默认只允许读自己的子进程，所以直接挂到一个已经在跑的进程上通常会失败。

# 安装。py-spy 是个 Rust 写的独立程序，装在哪个 Python 环境里都行
pip install py-spy

# 检查当前的 ptrace 权限策略。1 = 只能看自己的子进程（默认），0 = 同用户的进程都能看
cat /proc/sys/kernel/yama/ptrace_scope

# 如果上面输出是 1，用下面任一种方式解决：
# 方式一（推荐，临时）：每次用 sudo 跑 py-spy
# 方式二（省事，重启后失效）：放开策略
sudo sysctl -w kernel.yama.ptrace_scope=0

如果你在 Docker 容器里做这个实验，容器默认禁用了 ptrace，需要在启动时加上 --cap-add=SYS_PTRACE。这一点后面阶段四做 sandbox 的时候还会遇到，那时候你会从另一个角度重新理解它：正因为 ptrace 能读别的进程的内存，它才是沙箱必须封掉的能力之一。

第 2 步：准备负载脚本

这个脚本就是前面预测环节用的那个。它故意做成"一半算、一半等"，因为这是最能暴露 on-CPU 盲区的形状。

# workload.py
import time, hashlib

def cpu_heavy(seconds: float):
    """纯计算：不停做哈希，全程占着 CPU 不放。"""
    end = time.perf_counter() + seconds
    # 用 perf_counter 而不是 time.time()，因为它单调递增，
    # 不会被系统时钟调整影响，测时间必须用它
    data = b"x" * 4096
    while time.perf_counter() < end:
        # 反复哈希，制造真实的 CPU 负载。乘 128 是为了让每轮的活儿大一点，
        # 免得循环里 perf_counter 的调用本身占了大头
        data = hashlib.sha256(data).digest() * 128

def waiting_for_someone_else(seconds: float):
    """纯等待：用 sleep 模拟等数据库 / 等下游 HTTP / 等磁盘。
    关键在于这段时间进程完全不消耗 CPU。"""
    time.sleep(seconds)

def handle_one_request():
    cpu_heavy(0.05)                 # 50ms 真算
    waiting_for_someone_else(0.05)  # 50ms 干等

if __name__ == "__main__":
    t0 = time.perf_counter()
    for _ in range(200):  # 200 轮 ≈ 20 秒，够采样器攒够样本
        handle_one_request()
    print(f"总耗时 {time.perf_counter()-t0:.1f}s")

先单独跑一遍确认它正常：python3 workload.py。你应该看到 总耗时 20.0s。如果明显超过 20 秒，说明你的机器上 cpu_heavy 里的循环开销偏大，把 * 128 调小一点。

第 3 步：三条命令，看三种视角

# 【视角一】实时看：像 top 一样滚动显示哪个函数最费 CPU
# 先在一个终端跑 python3 workload.py，另开一个终端执行下面这条
sudo py-spy top --pid $(pgrep -f workload.py)

# 【视角二】默认录制：生成 on-CPU 火焰图
# -o 指定输出文件，-d 20 表示采样 20 秒
sudo py-spy record -o oncpu.svg -d 20 --pid $(pgrep -f workload.py)

# 【视角三】把等待也算进来：加 --idle
sudo py-spy record -o all.svg -d 20 --idle --pid $(pgrep -f workload.py)

录完之后，用浏览器打开这两个 .svg 文件（火焰图是可交互的，点方块可以放大）。

验收标准：

  • oncpu.svg 里，cpu_heavy 应该占到 95% 以上，waiting_for_someone_else 几乎看不见。
  • all.svg 里，两者应该大致各占一半（45%～55% 都算正常）。
  • 你能指着 oncpu.svg，说出为什么那一半等待时间不见了。

常见坑：

  • Permission denied 或 Failed to open process：ptrace 权限问题，回到第 1 步。
  • pgrep 返回空：脚本已经跑完了。把 range(200) 改大，或者先启动脚本再执行 py-spy。
  • 火焰图上全是 <module> 之类看不懂的名字：说明采样时程序还在启动阶段，等它进入主循环再采。
  • 两张图看起来一模一样：确认 --idle 真的加上了，并且拼写正确。

第 4 步（选做，但很值）：自己写一个 30 行的采样器

用别人的工具是一回事，知道它怎么实现的是另一回事。下面这个脚本把采样器的原理完整展示了一遍：一个线程干活，另一个线程定期偷看它的调用栈和线程状态。这就是 py-spy 的核心逻辑，只是 py-spy 用 Rust 从进程外面做，能挂到别的进程上。

文件分三块：worker 是被观察的负载；thread_state 负责读线程状态；主循环负责采样和统计。

# mini_sampler.py
import sys, threading, time, collections
sys.setswitchinterval(0.0002)  # 调小 GIL 切换间隔，否则采样线程抢不到 CPU，
                               # 会严重低估计算阶段的样本数（GIL 是 Day 4 的主题）

def cpu_burn(seconds):
    end = time.perf_counter() + seconds
    while time.perf_counter() < end: pass

def io_wait(seconds):
    time.sleep(seconds)

def worker():
    for _ in range(20):
        cpu_burn(0.1); io_wait(0.1)   # 真实比例：一半一半

def thread_state(tid):
    # Linux 把线程状态放在 /proc 里。第二个字段是进程名，可能含空格和括号，
    # 所以从最后一个 ')' 之后开始切，这是读 /proc/stat 的标准做法
    with open(f"/proc/self/task/{tid}/stat", "rb") as f:
        rest = f.read().decode()
    return rest[rest.rindex(")") + 2:].split()[0]

t = threading.Thread(target=worker); t.start()
on_cpu, all_s = collections.Counter(), collections.Counter()
while t.is_alive():
    # sys._current_frames() 返回所有线程当前的栈帧，这就是"拍照"
    f = sys._current_frames().get(t.ident)
    if f is not None:
        name = f.f_code.co_name          # 只取栈顶函数名，够说明问题了
        all_s[name] += 1
        if thread_state(t.native_id) == "R":   # R = 正在 CPU 上跑
            on_cpu[name] += 1                  # 只有 R 状态才计入 on-CPU
    time.sleep(0.005)                          # 200 Hz
t.join()

for title, c in [("on-CPU 视角", on_cpu), ("全部样本", all_s)]:
    total = sum(c.values())
    print(f"\n=== {title}（{total} 个样本）===")
    for k, v in c.most_common(): print(f"{100*v/total:6.1f}%  {k}")

跑 python3 mini_sampler.py，你应该看到类似这样的输出：on-CPU 视角下 cpu_burn 接近 100%（我实测是 320 个样本全部落在它身上），全部样本视角下两者各占一半上下（我实测 54.6% / 45.4%）。如果两个视角的结果差不多，检查 thread_state 是不是一直返回同一个字母——多半是 native_id 取错了线程。

# 1. 从火焰图上抄下热点函数名和它所在的文件路径（火焰图方块上会显示）

自检问题

1. 采样式剖析器的开销"跟程序的快慢无关"，这句话为什么成立？

先看开销从哪来。采样式剖析器每秒固定采 N 次，每次做的事是一样的：暂停一下目标线程、读出它的调用栈、记一笔、放开。这一套动作的成本是个常数，跟目标程序此刻在跑什么、跑得多快，一点关系都没有。

所以总开销 ≈ 采样频率 × 单次采样成本。你把采样频率定成 99 Hz，那不管目标程序每秒调用 100 次函数还是 1 亿次函数，剖析器都只干 99 次活。

对比一下插桩式就清楚了。插桩式的开销 = 函数调用次数 × 每次记账的成本。函数调用次数是程序自己决定的，你控制不了。一个调用密集的程序，插桩式的开销就爆炸。

这条性质的实际意义是：采样式剖析器的开销是你能预算的。你可以在上线前说"我开 99 Hz 采样，开销大约 0.5%"，并且这个数在任何负载下都成立。这就是它敢用在生产环境的根本原因。

2. 你拿到一张火焰图，最底下一层是 main，占 100% 的宽度。有人说"看，瓶颈在 main 函数"。他错在哪？

他把"经过"当成了"消耗"。

火焰图上一个方块的宽度，代表这条调用路径出现在多少比例的样本里，不代表这个函数自己烧了多少 CPU。main 占 100%，只是因为每一个样本的调用栈都从 main 开始——它当然要出现在所有样本里。

要看一个函数自己烧了多少时间，得看它没有被其他方块盖住的那部分宽度，也就是它露在最顶上的部分。这部分叫自身耗时（self time）。main 上面几乎肯定叠满了别的方块，它自己露出来的部分接近于零，所以它的自身耗时接近零。

正确的看法是：忽略底层的宽方块，把目光移到图的顶部，找那些又宽又平的块。那才是 CPU 真正在执行的代码。

3. 一个 FastAPI 服务，CPU 使用率只有 25%，但 P99 高达 2 秒。你先用 py-spy 默认参数录了一张火焰图，图上最宽的是 epoll_wait 之类的等待函数，看不出什么。接下来该怎么办？

先做一个判断：CPU 只有 25%，说明这台机器四分之三的时间是闲的。请求慢，但慢在不需要 CPU 的地方。这直接指向 off-CPU 方向。

所以 on-CPU 火焰图看不出东西，这本身就是一条重要信息，不是"工具没用"。它排除掉了"算法太慢"这一整类可能。

接下来至少有三条路可以走，从便宜到贵：

  1. 加 --idle 重新录一张。这样等待中的栈也会出现，你能看到线程具体阻塞在哪个 Python 函数上——是在等下游 HTTP，还是在等数据库，还是在等一把锁。
  2. 用 perf stat 算 task-clock ÷ 墙钟时间。确认"确实大部分时间没在用 CPU"这个判断，而不是被 CPU 使用率这个指标误导（比如服务是多进程的，你只看了一个）。
  3. strace 挂上去，加 -T 看每个系统调用的耗时。找那些动辄几百毫秒才返回的调用，看它们是 recvfrom（等网络）、futex（等锁）还是 read（等磁盘）。

还有一种情况要特别留意，因为它在 FastAPI 里极其常见：某个 async 函数里调用了一个同步阻塞的库，把事件循环整个卡住了。这时候 CPU 使用率很低，所有请求一起变慢。这个具体形态是明天 Day 4 的主要内容。

4. 为什么剖析器要采集整条调用栈，而不是只记录"当前在哪个函数"？只记函数名不是更省事吗？

省事，但很多时候没法用。

举个具体例子。你只记函数名，得到的结果是「json.dumps 占 18%」。这个信息你拿去干什么？json.dumps 在整个服务里可能被十几个地方调用——请求日志里调一次、返回响应时调一次、往消息队列里发事件时调一次。你不知道该优化哪一处，甚至不知道该不该优化（有些是必要的）。

有了调用栈就不一样了。你看到「handle_request → log_request → json.dumps 占 15%」，剩下 3% 分散在别处。结论立刻就清楚了：绝大部分开销来自记日志，而日志是可以改成异步的，或者干脆降低日志级别。

还有第二个理由：调用栈自带上下文，让你能看懂陌生的代码库。你在别人的项目里看到一个没见过的函数占了 30%，只有函数名的话你还得去 grep 半天。有了完整的栈，从上到下读一遍，这条路径是干什么的基本就清楚了。这也是任务 B 里那个"从热点反查源码"方法能成立的前提。

采样式剖析器sampling profiler靠定期采样工作的剖析器，开销固定且很低，能用在生产环境，如 py-spy、perf
插桩式剖析器instrumenting profiler在每个函数进出处插计时代码，数字精确但开销大，如 cProfile，只适合本地用
火焰图flame graph把几千条调用栈按公共前缀合并画出来的图；宽度是时间占比，横轴不是时间轴
自身耗时self time一个函数自己烧掉的时间，不含它调用的子函数；在火焰图上就是它露在顶部的那部分宽度
on-CPU 分析on-CPU analysis只统计线程真正在 CPU 上执行的时间，回答"CPU 忙的时候在忙什么"
off-CPU 分析off-CPU analysis研究线程为什么不在 CPU 上、在等什么，回答"CPU 没满但为什么慢"

今日五句话 · 费曼式复述

合上这一页，不看笔记

想象你要把今天这块讲给一个刚入职的同事听。他会写 Python，但从来没做过性能分析。用五句话讲给他听，每句话都要是完整的中文句子，不能只写关键词。

第 1 句——剖析器和"加日志打时间戳"最根本的区别是什么？

第 2 句——采样为什么开销这么低，低到能开在生产环境上？

第 3 句——看火焰图时，眼睛应该先落在图上的什么位置，为什么是那里？

第 4 句——on-CPU 火焰图有一个大盲区，它是什么，为什么会有这个盲区？

第 5 句——现场看到一个慢服务，你用什么线索决定走 on-CPU 还是 off-CPU 路线？

自查标准

  • 第 1 句写不出来 → 回去重读「2. 剖析器：换一种问法」，特别是工厂工人那个例子。
  • 第 2 句里如果没提到"开销只跟采样频率有关，跟程序在跑什么无关"，就还没抓住重点。
  • 第 3 句如果写成了"看最宽的方块"，不完整——必须同时说到"顶部"。少了这个词就会把 main 当成瓶颈。
  • 第 4 句如果只说了"看不到等待时间"，但说不出为什么看不到（线程状态是 S 就跳过不采），说明只记住了结论没记住机制。这种记忆过两周就没了。
  • 第 5 句是今天最实用的一条。标准答案很短：看 CPU 用满没有，或者算 task-clock ÷ 墙钟时间。如果你写了一长段，说明还没提炼出来。
