Q1 · 1 天前（Day 4 · 事件循环被阻塞）

一个异步接口里有一句 await call_model()，你在它前后打了时间戳，监控上报"调用模型耗时 P99 = 300ms"。下游团队拿出他们的监控说"我们只有 80ms"。
两边都没说谎。多出来的 220 毫秒去哪了？你要做哪一个实验来确认？

展开答案

那 220 毫秒很可能根本没离开你的进程。

await 做的是"发出请求，然后交还控制权"。下游 80 毫秒就把响应送回来了，操作系统也早把数据放好了，但要把你的协程重新唤醒，得等事件循环轮到它。而这时候事件循环正忙着给别的请求跑同步代码——比如序列化一个大 JSON。那段代码不交还控制权，你的协程只能排队。

你测到的"调用耗时"里，混进了别人的计算时间。

确认实验（做任何一个都行）：

  • 降负载对照。把 rps 降到平时的四分之一再测同一个指标。下游不会因为你发得少就变快，所以这个数字如果大幅下降，凶手一定在本地。
  • 装事件循环延迟哨兵。看它的累计滞后，量级对得上就实锤了。

→ 今天你会亲手量到这个现象：一句写死 40 毫秒的等待，在高负载下测出 94 毫秒。而且你会发现，这件事火焰图完全看不出来。

Q2 · 3 天前（Day 2 · 利用率与排队的非线性）

一个单线程服务，每个请求占用 33 毫秒 CPU，每秒进来 25 个请求。

  1. 利用率是多少？
  2. 如果把单请求 CPU 优化到 20 毫秒（省 39%），利用率变多少？
  3. 排队等待时间大约变成原来的几分之一？先猜一个，再算。
展开答案

一：ρ = 25 × 0.033 = 0.825。　二：ρ = 25 × 0.020 = 0.50。

三：排队等待大致正比于 ρ / (1 − ρ)。

优化前 0.825 ÷ 0.175 = 4.71；优化后 0.50 ÷ 0.50 = 1.00；比值 ≈ 0.21

排队降到原来的 21%，砍掉约八成。而你只把 CPU 省了 39%。放大来自分母：1 − ρ 是"还剩多少余量"，它从 0.175 涨到 0.50，涨了近 3 倍，整个比值就塌了。

→ 今天最后一节会把这个算式和实测摆在一起对照，你会看到同一个改动在两种负载下省出来的绝对毫秒数差十六倍。

2. 先看看被剖析的是什么

这一节回答：这个网关每个请求都干了些什么。

真实的推理服务前面都有一层 Python 写的网关。它不做模型计算，但每个请求都要过它。它的活儿是固定的四步：

步骤在干什么在算还是在等
① 收请求读 HTTP、解析算（很少）
② 分词把一段长上下文切成 token算
③ 调模型把 token 发给推理引擎，等它返回等
④ 序列化把整轮响应转成 JSON 发回去算

这张表重点看第三列。两步在算、一步在等——这个"算一半等一半"的形状，正是所有 AI 服务网关的共性，也是今天全部麻烦的来源。

为了让它像真的：上下文用了 36000 个词（一个跑了很多轮的 agent 会话就是这个量级），响应带 650 条 choice 和 logprobs。

第 ③ 步有个特殊安排：它不是真的去调下游，而是一句 await asyncio.sleep(0.040)。这样你手里就有了一个绝对准确的参照物——它必须是 40 毫秒，测出来的任何偏差都只能来自别的东西。第 6 节靠它抓到了一个很难发现的问题。

至于每一步各花多久——先别急着知道。今天有一半的内容就是在回答"怎么把它量出来"，提前告诉你就没意思了。

5. 为什么：挂起的协程不在任何线程的栈上

这一节回答：time.sleep() 和 await asyncio.sleep() 到底差在哪？

这两件事看起来都是"等 40 毫秒"，机制完全不同。

time.sleep(0.04)：线程真的睡过去了。调用栈原封不动地留在那个线程上：

worker → handle_request → time.sleep      ← 栈还在，只是线程状态从 R 变成了 S

采样器去抓这个线程的栈，能抓到完整的一条。默认会因为状态是 S 而跳过，--idle 就是告诉它"睡着的也采"。Day 3 的救兵之所以管用，是因为栈一直都在，只差一个开关。

await asyncio.sleep(0.04)：协程被挂起了。控制权交还给事件循环，那个协程的栈帧被摘下来存进 Task 对象。这一刻线程正在跑的是事件循环自己：

run_forever → _run_once → select          ← 线程当前的栈，业务函数一个都没有

而采样器用的 sys._current_frames()（py-spy 读进程内存也是同理）拿到的是"每个线程当前的栈"。挂起的协程（suspended coroutine）不属于任何线程，所以它不在结果里。

--idle 管的是"线程在睡要不要统计"，而这里的问题是"栈根本不在"。两个开关管的不是同一件事。

这个说法可以直接验。让一个协程停在 await 上，然后从两个角度去找它：

async def handle_request():
    await asyncio.sleep(0.30)          # 协程在这里被挂起

async def inspector():
    await asyncio.sleep(0.10)          # 等它进入 await 之后再看

    # 角度一：线程当前的栈里，有没有 handle_request？
    fr = sys._current_frames().get(threading.get_ident())

    # 角度二：问 asyncio 自己，它知不知道这个任务在哪？
    for t in asyncio.all_tasks():
        if t.get_coro().__qualname__.startswith("handle_request"):
            stack = t.get_stack()      # Task 对象里存着它挂起处的帧

跑出来是这样：

线程当前栈: <module> → run → run → run_until_complete → run_forever → _run_once → _run → main → inspector
里面有 handle_request 吗: False

all_tasks 找到了，它停在: ['handle_request']

线程栈上全是事件循环的机器零件，一个业务函数都没有。而 asyncio.all_tasks() 一找一个准。

关键结论

在 asyncio 服务上，"谁在等什么"这个问题，两种火焰图都答不了。因为等待中的协程根本不在线程栈上。

对应的正确工具是 asyncio.all_tasks() 加 task.get_stack()——它遍历的是任务，不是线程。线上排查时把它挂在一个调试接口或信号处理器上，需要时 dump 一次，就能看到此刻所有挂起的协程各自停在哪一行。
（py-spy dump 对 asyncio 服务也是同样的局限：它看得见线程，看不见挂起的任务。）

这一条对你四周后的岗位几乎每天都要用：推理网关、agent runtime、sandbox 调度服务，全是 asyncio 写的，全是"大部分时间在等"。指望火焰图告诉你它们在等谁，方向从一开始就错了。

6. 那就自己打点：把一次请求摊成三段

这一节回答：既然剖析器答不了，用什么答？

答案朴素得有点让人失望：在四步流水线的每一步前后各记一个时间戳。

这种做法叫 阶段计时（span timing），是分布式追踪（OpenTelemetry）的最小内核，阶段三给 agent runtime 加可观测性时你会正式用到它。

t0 = time.perf_counter()
TOKENIZE(CONTEXT)                            # ② 分词（在算）
t1 = time.perf_counter()
await asyncio.sleep(0.040)                   # ③ 调模型（在等）
t2 = time.perf_counter()
n = len(json.dumps(RESPONSE))                # ④ 序列化（在算）
t3 = time.perf_counter()
# 四个时间戳，三段耗时。这三段是火焰图给不了的：
# 它能告诉你"CPU 花在 tokenize 上"，但给不出"这个请求的 tokenize 花了多少毫秒"
STAGES.append({"tok": (t1-t0)*1000, "model": (t2-t1)*1000, "ser": (t3-t2)*1000})

量出来终于有了能动手的东西。这张表重点看 model 那一列，因为它是写死的 40 毫秒——任何偏差都不可能来自它自己。

压测点② 分词③ 调模型④ 序列化③ 比 40ms 多出
8 rps16.65 ms42.17 ms8.16 ms+2.2 ms
35 rps16.70 ms94.33 ms7.84 ms+54.3 ms

两件事一起浮出来了。

第一，时间的分配终于清楚了：分词 16.7、等模型 40、序列化 8.2，加起来约 67 毫秒——正好等于低负载下测到的 P50 总延迟（67.7 毫秒）。其中"在算"的部分是 25 毫秒；每秒进来 8 个请求，就是每秒 0.20 秒的 CPU，也就是两成利用率。第 3 节那个 22.2%，说的就是这件事。

第二，那句写死 40 毫秒的等待，在高负载下测出了 94.33 毫秒。多出来的 54 毫秒，比这句 await 自己声称的还多。

第二点正是温故 Q1 那道题的实验室版本。asyncio.sleep(0.040) 登记了一个 40 毫秒后的闹钟，闹钟准时响了，但这时候事件循环正忙着给别的请求做分词和序列化——那是同步代码，不交还控制权。你的协程只能排在后面。

所以"调模型耗时"这个指标里混着别人的计算时间。如果第 ③ 步真的是调下游，你会在监控上看到"下游耗时 94 毫秒"，然后花一整天去查下游——而问题在你自己这一层。

识破它的第一个办法就是对照低负载：同样一份代码，8 rps 下只多出 2.2 毫秒。下游不会因为你 rps 高就自己变慢，所以撑大的部分一定来自本地。第二个办法是装 Day 4 那个事件循环延迟哨兵。

7. 三段加起来 67 毫秒，可高负载下 P99 是 637 毫秒

这一节回答：剩下那五百多毫秒藏在哪？

阶段计时是从"处理函数第一行"开始记的。可请求到达服务器之后、处理函数被调用之前，还有一段时间：连接躺在队列里，等事件循环轮到它。

换个日常场景就明白了。你去餐厅吃饭，从进门到吃完九十分钟。这里面有两段完全不同的时间：门口等位，和坐下之后。等位太久说明店太小或客人太多；坐下之后太久说明后厨慢。你不分开量，就分不清该扩店还是该换厨子。

请求也一样。从"客户端打算发出"到"服务端真正开始处理"，这段叫 排队延迟（queueing delay）；从开始处理到处理完，叫 服务时间（service time）。

怎么量？让服务端自己报。把处理函数首尾的时间差随响应带回去，客户端一减就得到排队：

排队延迟 = (客户端从"计划发出"起算的总延迟) − (服务端自报的服务时间)

这个办法的好处是两个时间戳都取自服务端自己的时钟，不需要两边对表。跨机器压测时这一点尤其重要。

拆开之后，P99 就不再是一个笼统的数字了。三轮重复，报范围：

压测点P99 总延迟其中：排队其中：服务排队占比
8 rps103 ~ 110 ms11 ~ 37 ms66 ~ 100 ms约 10 ~ 35%
35 rps592 ~ 852 ms391 ~ 496 ms200 ~ 355 ms约 60 ~ 70%

这张表重点看"其中：排队"这一列。35 rps 下它占了 P99 的三分之二——而这一段，on-CPU 火焰图看不见、wall-clock 火焰图看不见、连阶段计时也看不见，因为那时候处理函数还没被调用。

排队是怎么来的：有效容量

为什么 8 rps 下排队只有几十毫秒，35 rps 下就涨到四百多？

算一下这个服务能扛多少。第 ② 和 ④ 步是"在算"，它们占着事件循环：16.7 + 8.2 ≈ 25 毫秒。第 ③ 步是"在等"，用的是 await，不占事件循环。

所以这个单进程服务每秒最多处理 1 ÷ 0.025 ≈ 40 个请求。这个数叫 有效容量（effective capacity）。注意它只由"在算"的部分决定——那 40 毫秒的等待完全不影响容量，这正是异步服务值得存在的理由。

有了容量就能算利用率：8 rps 是 0.20，35 rps 是 0.86。而第 3 节用/proc 直接量到的是 22.2% 和 84.2%——两条完全独立的路子，结果差不到三个百分点。（量到的略高一点，因为读 HTTP 头、写响应这些活儿没被算进那三段里。）

温故 Q2 那个算式说排队正比于 ρ/(1−ρ)。按实测利用率代进去：0.22 时是 0.28，0.84 时是 5.25，差十九倍。实测排队的中位数从 32 毫秒涨到 436 毫秒，差十四倍。量级对得上。ρ 越靠近 1，这个式子越陡，也越不准——所以它是用来判断方向和量级的，不是用来报小数点后两位的。

关键结论

这也解释了一个很常见的线上事故：测试环境用 5 rps 压，一切正常；上线 200 rps，P99 炸了。不是测得不够久，是测试环境的利用率太低，排队根本没产生，而线上问题九成来自排队。
所以压测的目标不是"跑通"，是把利用率打到接近生产的水平。顺序应该是：先量容量 → 算利用率 → 再定压测点。

现在这笔账终于合上了

把 35 rps 下一次中位请求的 190 毫秒摊开，是这么四段（P99 那一条的区别只有一处：第 ① 段涨到四百多毫秒，其余三段基本不变）：

这一段大约多久谁看得见它
① 排队等着被接待~71 ms只有「总延迟 − 服务时间」
② 分词（在算）~17 mson-CPU 火焰图 ✓　阶段计时 ✓
③ 等模型（含被撑大的部分）~94 ms只有阶段计时（两张火焰图都看不见）
④ 序列化（在算）~8 mson-CPU 火焰图 ✓　阶段计时 ✓

这张表重点看最后一列，它就是今天整套方法的地图：三种手段各管一段，缺一段你就会诊断错方向。而新手最容易做的事，恰恰是只用其中最花哨的那一种。

8. 读火焰图还有一个坑：一个步骤会被拆成好几帧

这一节回答：为什么栈顶排行榜会低估一个函数的真实占比？

第 3 节那张表把分词和序列化的帧合成了一行"计算步骤合计"，当时留了一句"为什么要合，第 8 节讲"。原因就是这一节：如果不合，排行榜会给你一个错的答案。

分词函数最后一行是这个：

return [hash(t) % 50000 for t in toks]   # 一个列表推导式

Python 把列表推导式编译成一个独立的代码对象，名字就叫 <listcomp>。采样器抓到栈顶时看到的是它，不是 tokenize_slow。

这件事有多严重，用一个只有两个函数的小实验就能量清楚：反复交替跑分词和序列化，一边用 perf_counter 记下各自的真实耗时，一边用同一个采样器统计栈顶。真实答案是已知的，正好用来给排行榜打分。（脚本就是把网关那份代码里的采样器和 tokenize_slow 抄出来、去掉网络部分，二十行。）

for _ in range(120):
    a = time.perf_counter(); tok(CONTEXT);      b = time.perf_counter()
    json.dumps(RESPONSE);                       d = time.perf_counter()
    T["tok"] += b - a;  T["ser"] += d - b       # 真实耗时，作为标准答案

跑出来：

真实耗时: tok 1.87s  ser 0.91s  -> 67.1% / 32.9%
采样份额: tok 34.4%   iterencode 31.6%   <listcomp> 31.3%   <module> 2.5%

真实比例是 2 : 1，分词是序列化的两倍。可栈顶排行榜的第一名是 tok 34.4%，第二名 iterencode 31.6%——看起来两者半斤八两。你照着这张榜去做决策，很可能先去优化序列化。

把 <listcomp> 认回它的父函数，34.4% + 31.3% = 65.7%，对 31.6%，正好是 2 : 1。采样器一直是准的，错的是"按栈顶函数名排行"这个读法。

这正是 Day 3 强调"必须采集整条调用栈、而不是只记栈顶函数名"的实战理由。有了完整的栈，<listcomp> 会挂在 handle → tokenize_slow → <listcomp> 这条路径下，火焰图上它就画在 tokenize_slow 方块的正上方，一眼看得出是一伙的。排行榜没有这个信息，火焰图有——这就是为什么要看图，不要只看榜。

同类的还有生成器表达式（<genexpr>）、被装饰器包了一层的函数（栈顶显示成 wrapper）、C 扩展内部的函数（iterencode 其实就是 json.dumps）。读排行榜之前，先把属于同一个逻辑步骤的帧合并起来。

9. 该改哪儿：收益取决于你在利用率曲线的哪一段

这一节回答：热点找到了，改它能换来多少？

按第 6 节的阶段计时，分词 16.7 毫秒、序列化 8.2 毫秒，分词占单请求 CPU 的三分之二——它就是那个热点。而且它只是个纯 Python 的逐字符循环，换成内建 split() 语义完全一样：实测从 16.4 毫秒降到 4.7 毫秒，单请求 CPU 从 25 降到 13.5 毫秒。

那 P99 会改善多少？这个问题没有唯一答案。同一个改动，两种负载各测三轮：

压测点慢分词 P99快分词 P99改善
8 rps（利用率 0.22）103 ~ 110 ms69 ~ 75 ms约 31%
35 rps（利用率 0.84）592 ~ 852 ms94 ~ 100 ms约 84%

这张表重点看最后一列：同一份代码、同一个改动，低负载下改善三成，高负载下改善八成半。换成绝对值差得更狠——一个省了约 33 毫秒，一个省了约 537 毫秒，十六倍。

为什么？因为你省下的 12 毫秒计算，真正换来的是排队的塌陷。单请求 CPU 从 25 降到 13.5 毫秒，容量就从 40 涨到 74 rps，35 rps 下的利用率从 0.84 掉到 0.47（实测 46.5%）。ρ/(1−ρ) 从 5.25 降到 0.89，模型说排队该降到原来的 17% 左右；实测中位数从 436 毫秒降到 26 毫秒，是 6%——比模型预计的还狠一些，方向和量级都对上了。

所以"预期收益"这个数，脱离负载就没有意义。一份只写"优化分词可提升性能"的报告，等于什么都没说。

10. 交付物：top 3 瓶颈假设表

这一节回答：今天做完，交出去的东西该长什么样？

剖析的产出不是"我找到瓶颈了"，而是一张 瓶颈假设表（bottleneck hypothesis table）。

第 1 步：网关服务（含迷你剖析器）

这个文件分四块：第一块造真实尺寸的请求和响应，给出快慢两版分词；第二块是采样剖析器，同时统计 on-CPU 和 wall-clock；第三块是四步流水线加阶段计时；第四块启动时自报两步耗时。分词版本用环境变量切，这样两次实验跑的是同一份代码，只差一个开关。

# d5_gateway.py
import asyncio, json, time, random, os, sys, threading, collections, resource

MODE = os.environ.get("TOKENIZER", "slow")      # slow / fast，用环境变量切换

# ---- 第一块：造真实尺寸的请求与响应 ----
random.seed(0)                                  # 固定种子，保证你我的数据量一致
WORDS = [f"tok{i}" for i in range(3000)]
CONTEXT = " ".join(random.choice(WORDS) for _ in range(36000))
RESPONSE = {"id": "cmpl-1", "choices": [
    {"text": "y"*40, "logprobs": [random.random() for _ in range(24)]} for _ in range(650)]}

def tokenize_slow(text):          # 逐字符扫描的纯 Python 循环。真实代码库里很常见，
    toks, cur = [], []            # 因为一开始上下文只有几百个词，没人觉得它是问题
    for ch in text:
        if ch == " ":
            if cur: toks.append("".join(cur)); cur = []
        else: cur.append(ch)
    if cur: toks.append("".join(cur))
    return [hash(t) % 50000 for t in toks]      # ← 这个列表推导式在火焰图上会单独成一帧

def tokenize_fast(text):          # 完全相同的语义，交给内建 split
    return [hash(t) % 50000 for t in text.split()]

TOKENIZE = tokenize_slow if MODE == "slow" else tokenize_fast

# ---- 第二块：采样剖析器，两种视角一起统计 ----
MAIN_TID  = threading.get_ident()        # Python 层线程 id，用来抓栈
MAIN_NTID = threading.get_native_id()    # 操作系统线程 id，用来读 /proc
oncpu, wall = collections.Counter(), collections.Counter()
SAMPLING = [False]

def thread_state(ntid):
    # Linux 把线程状态放在 /proc 里。第二个字段是进程名，可能含空格和括号，
    # 所以从最后一个 ')' 之后开始切。R = 在 CPU 上跑，S = 在等。
    with open(f"/proc/self/task/{ntid}/stat", "rb") as f:
        rest = f.read().decode()
    return rest[rest.rindex(")") + 2:].split()[0]

def fold(frame):                         # 把整条调用栈拼成 "a;b;c"
    names = []                           # 必须采整条栈，不能只记栈顶 —— 见第 8 节
    while frame is not None and len(names) < 24:
        names.append(frame.f_code.co_name); frame = frame.f_back
    return ";".join(reversed(names))

def sampler():
    while True:
        time.sleep(0.002)                                  # 约 500 Hz
        if not SAMPLING[0]: continue
        fr = sys._current_frames().get(MAIN_TID)           # 给主线程拍一张快照
        if fr is None: continue
        st = fold(fr)
        wall[st] += 1                                      # 无条件计数 = wall-clock 视角
        try:
            if thread_state(MAIN_NTID) == "R":             # 只有 R 才计入 on-CPU 视角
                oncpu[st] += 1
        except OSError:
            pass
threading.Thread(target=sampler, daemon=True).start()

# ---- 第三块：四步流水线 + 阶段计时 ----
T_START = time.perf_counter()
STAGES = []
async def handle(reader, writer):
    try:
        line = await reader.readline()
        if not line: writer.close(); return
        while True:                             # 把 HTTP 头读干净，否则下次读会串
            h = await reader.readline()
            if h in (b"\r\n", b"\n", b""): break
        path = line.split()[1].decode()

        if path == "/cpu":                      # 第 3 节那个判据：进程 CPU 时间 ÷ 墙上时间
            ru = resource.getrusage(resource.RUSAGE_SELF)
            body = json.dumps({"cpu_s": round(ru.ru_utime + ru.ru_stime, 3),
                               "wall_s": round(time.perf_counter() - T_START, 3)}).encode()
        elif path == "/stats":
            def top(c, k=5):
                tot = sum(c.values()) or 1
                return [{"pct": round(100*v/tot, 1), "frame": s.split(";")[-1]}
                        for s, v in c.most_common(k)]
            n = max(1, len(STAGES))
            body = json.dumps({"mode": MODE, "requests": len(STAGES),
                "stage_ms": {k: round(sum(x[k] for x in STAGES)/n, 2) for k in ("tok","model","ser")},
                "oncpu_top": top(oncpu), "wall_top": top(wall)}).encode()
        elif path == "/ctl/on":
            SAMPLING[0] = True; STAGES.clear(); oncpu.clear(); wall.clear(); body = b'{"on":true}'
        elif path == "/ctl/off":
            SAMPLING[0] = False; body = b'{"on":false}'
        else:
            t0 = time.perf_counter()
            TOKENIZE(CONTEXT)                    # ② 分词（在算）
            t1 = time.perf_counter()
            await asyncio.sleep(0.040)           # ③ 调模型（在等）。写死 40ms，
                                                 #    这样任何偏差都只能来自别处 —— 第 6 节靠它
            t2 = time.perf_counter()
            n = len(json.dumps(RESPONSE))        # ④ 序列化（在算）
            t3 = time.perf_counter()
            STAGES.append({"tok": (t1-t0)*1000, "model": (t2-t1)*1000, "ser": (t3-t2)*1000})
            # svc_ms 随响应回传。客户端用"总延迟 − svc_ms"就得到排队延迟，
            # 两个时间戳都取自服务端自己的时钟，两边不用对表
            body = json.dumps({"n": n, "svc_ms": round((t3-t0)*1000, 2)}).encode()

        writer.write(b"HTTP/1.1 200 OK\r\nContent-Length: %d\r\nConnection: close\r\n\r\n"%len(body)+body)
        await writer.drain()
    except Exception: pass
    finally:
        try: writer.close()
        except: pass

# ---- 第四块：启动，先自报两步的实测耗时 ----
async def main():
    # 这两个数是后面一切推算的基础（有效容量 = 1 / 它们之和），
    # 而它们取决于当天这台机器，所以每次启动现场量，别写死
    for f, arg, name in ((TOKENIZE, CONTEXT, f"tokenize({MODE})"),
                         (json.dumps, RESPONSE, "serialize")):
        for _ in range(3): f(arg)
        xs = []
        for _ in range(5):
            t = time.perf_counter(); f(arg); xs.append((time.perf_counter()-t)*1000)
        xs.sort(); print(f"  {name:20s}: {xs[len(xs)//2]:.1f} ms", flush=True)
    srv = await asyncio.start_server(handle, "127.0.0.1", 8861, backlog=512)
    print(f"gateway up (TOKENIZER={MODE})", flush=True)
    async with srv: await srv.serve_forever()

asyncio.run(main())

# d5_load.py
import asyncio, time, sys, random, json

async def one(path, t_due, res):
    now = time.perf_counter()
    if t_due > now: await asyncio.sleep(t_due - now)
    try:
        r, w = await asyncio.open_connection("127.0.0.1", 8861)
        w.write(f"GET {path} HTTP/1.1\r\nHost: x\r\nConnection: close\r\n\r\n".encode())
        await w.drain(); data = await r.read(); w.close()
        total = (time.perf_counter() - t_due) * 1000       # 从"计划发出"起算，不是从"连上"起算。
                                                           # 为什么必须这样，明天 Day 6 讲
        svc = json.loads(data.split(b"\r\n\r\n",1)[1])["svc_ms"]
        res.append((total, svc))                           # 两个数一起存，才拆得出排队
    except Exception: pass

async def run(rps, secs):
    rnd = random.Random(99); res = []; t0 = time.perf_counter()
    ts, t = [], 0.0
    for _ in range(int(rps*secs)):
        t += rnd.expovariate(rps)                          # 指数间隔 = 随机到达。
        ts.append(t0 + t)                                  # 均匀节拍几乎测不出排队
    await asyncio.gather(*[asyncio.create_task(one("/v1/completions", x, res)) for x in ts])
    res.sort(key=lambda x: x[0])
    def p(q): return res[min(len(res)-1, int(len(res)*q))]
    t50, s50 = p(.50); t99, s99 = p(.99)
    print(json.dumps({"rps": rps, "n": len(res),
        "p50_total": round(t50,1), "p99_total": round(t99,1),
        "p99_svc": round(s99,1), "p99_queue": round(t99-s99,1)}))

if __name__ == "__main__":
    asyncio.run(run(float(sys.argv[1]), float(sys.argv[2])))

# probe_stack.py
import asyncio, sys, threading

async def handle_request():
    await asyncio.sleep(0.30)              # 协程在这里被挂起

async def inspector():
    await asyncio.sleep(0.10)              # 等它进入 await 之后再看
    fr = sys._current_frames().get(threading.get_ident())
    names = []
    while fr is not None:                  # 把线程当前的栈整条拿下来
        names.append(fr.f_code.co_name); fr = fr.f_back
    print("线程当前栈:", " → ".join(reversed(names)))
    print("里面有 handle_request 吗:", any("handle_request" in n for n in names))

    for t in asyncio.all_tasks():          # 换个角度：问 asyncio 自己
        if t.get_coro().__qualname__.startswith("handle_request"):
            print("all_tasks 找到了，它停在:", [f.f_code.co_name for f in t.get_stack()])

async def main():
    t = asyncio.create_task(handle_request())
    await inspector()
    await t
asyncio.run(main())

你应该看到：线程当前栈里全是 run_forever → _run_once → select 这类事件循环零件，handle_request 不在其中；而 all_tasks 一找一个准。如果线程栈里能看到 handle_request，检查你是不是把 await asyncio.sleep 写成了 time.sleep——那样协程没被挂起，栈当然还在。

任务 B · 用到你自己的服务上，产出一张假设表（约 1.5 小时）

把 Day 1 那个最小服务（或任何一个你手上的 FastAPI 服务）跑起来，按这个顺序走。顺序很重要，每一步都在为下一步排除可能性。

  1. 先量 CPU 利用率。一条命令的事，但它决定你该主看哪张图。
  2. 先拆两段，还不要开剖析器。在处理函数首尾打时间戳，把服务时间回传，算出排队占比。三分钟，但它决定了后面所有工作的方向。
  3. 如果排队占了大头，问题是容量不够。这时候才去开剖析器找 CPU 热点，因为砍 CPU 就是在涨容量。
  4. 如果排队很小但延迟还是高，问题在服务时间内部。看阶段计时哪一段最长。如果最长的是"等"的那一段，别去翻火焰图——第 4、5 节讲了原因。
  5. 用 asyncio.all_tasks() dump 一次挂起的任务，看它们停在哪些行。
  6. 装上 Day 4 的事件循环延迟哨兵。如果读数很大，那你阶段计时里"等待"那一段的数字全都不可信——里面混着别人的计算。
  7. 产出假设表，五栏一栏都不能少，尤其是预期收益和它的负载条件。

验收标准：你能拿着这张表跟人说清三件事——为什么先改这条而不是那条；改完预期能拿到多少；以及在什么流量下这个预期才成立。

加分题

上岗关联

场景一：线上告警，一个 asyncio 写的推理网关 P99 涨了三倍。你 ssh 上去，第一反应如果是 py-spy record，那你大概率会盯着一张 90% 都是 select 的图发呆半小时。今天这套顺序能省下这半小时：先看 CPU 利用率、先拆排队和服务，图是最后才开的。

场景二：误诊下游。监控上"调用推理引擎耗时 P99 = 300ms"，你去找推理团队，对方说"我们这边只有 80ms"。两边都没说谎——多出来的是你自己的事件循环在忙别人的活。今天第 6 节那张表就是这个场景的实验室版本，判据是：同样的代码在低负载下还多不多。

场景三：压测环境测不出来的问题。团队用 5 rps 压，一切正常；上线 200 rps，P99 炸了。原因就是第 7 节：测试环境的利用率太低，排队根本没出现，而线上问题九成来自排队。

面试常问：

  • "你怎么给一个陌生服务做性能分析？"——说顺序：看 CPU 利用率、拆排队与服务、定压测点、再开剖析器、最后产出假设表。能说出顺序和每步的理由，比会用十个工具更值钱。
  • "py-spy 对 asyncio 服务有什么局限？"——它看得见线程，看不见挂起的任务。要回答"谁在等什么"，得用 asyncio.all_tasks() 或者自己打点。
  • "压测应该压到多少 rps？"——压到接近生产的利用率。用低于生产的负载压测，等于换了一个系统在测。

自检问题

1. 一个服务 CPU 利用率只有 30%，但 P99 很高。火焰图和 off-CPU 分析，哪个更可能告诉你原因？为什么？

off-CPU 分析。

关键在采样剖析器的工作方式：它只在线程正在 CPU 上跑的那些瞬间才能抓到栈。CPU 利用率 30% 意味着，线程有 70% 的时间根本不在 CPU 上——它在等锁、等网络回包、等磁盘、等被调度器选中。

所以火焰图能告诉你的，只是那 30% 的时间是怎么花的。它画得再漂亮，覆盖的也只是三成的故事。而"P99 高、CPU 却闲"这个组合本身就在指向剩下那 70%。

反过来，如果 CPU 已经跑到 95% 而 P99 很高，那火焰图就是主力工具，因为时间确实都花在执行上了。

选哪张图，先看 CPU 利用率。今天这个服务在低负载下实测 22.2%，所以第一张 on-CPU 图必然解释不了它的延迟。

2. Day 3 那个实验里，加上 --idle 之后等待时间立刻从 0.6% 变成 54.8%。今天同样统计等待，那 40 毫秒还是 0%。两个实验差在哪一个具体的机制上？

差在栈还在不在。

Day 3 用的是 time.sleep()。这是让线程睡过去，调用栈原封不动地留在那个线程上，只是状态从 R 变成 S。采样器默认看到 S 就跳过，--idle 就是告诉它"睡着的也采"。栈一直都在，所以一采就有。

今天用的是 await asyncio.sleep()。这是让协程挂起：控制权交还给事件循环，协程的栈帧被摘下来存进 Task 对象，线程转头去跑事件循环自己的代码。这一刻线程的栈是 run_forever → _run_once → select，业务函数一个都没有。

而采样器（sys._current_frames()，py-spy 读进程内存也一样）拿的是"每个线程当前的栈"。被挂起的协程不属于任何线程，所以它不在结果里。

--idle 解决的是"线程在睡要不要统计"，这里的问题是"栈根本不在"。两个开关管的不是同一件事。

正确工具是 asyncio.all_tasks() 加 task.get_stack()，因为它遍历的是任务而不是线程。任务 A 第 4 步可以亲手验一遍。

3. 你按今天的方法拆完某服务，发现排队只占 P99 的 5%，服务时间占 95%，而服务时间里 90% 是"在等下游"。这时候该做什么？不该做什么？

不该做的：不要去优化 CPU 热点。

排队只占 5%，说明容量非常充裕、利用率很低。这时候就算把 CPU 砍掉一半，利用率从比如 0.15 降到 0.08，ρ/(1−ρ) 从 0.18 降到 0.09，绝对值本来就小到可以忽略。

更关键的是上限：服务时间里 90% 是等待，也就是 on-CPU 部分只占整体不到 10%。就算你把所有计算优化到零，P99 也只能改善不到 10%。这是上限，不是估计。

该做的：去查"在等谁"。而且今天学到了，在 asyncio 服务上这件事不能靠火焰图：

  • 先用 asyncio.all_tasks() dump 一次，看挂起的任务停在哪些行。这一步直接给出"等的是哪个调用"。
  • 再用阶段计时确认每一段各占多久。
  • 然后必须做一件事：装 Day 4 的事件循环延迟哨兵，或者降负载对照一次。因为你测到的"等待"里可能混着自己的事件循环没来得及唤醒的时间——今天第 6 节那多出来的 54 毫秒就是这么来的。先排除这一项，再去找下游。
4. 假设表里"预期收益"那一栏，为什么必须带上负载条件？举一个不带会出事的具体例子。

因为同一个改动的收益可以相差三倍以上，而差别不在代码里，在流量里。

今天的实测：把分词从 16.4 毫秒优化到 4.7 毫秒——8 rps（利用率 0.22）下 P99 改善约 31%；35 rps（利用率 0.84）下改善约 84%。

会出什么事：假设团队在测试环境用 8 rps 评估，看到"只能改善 31%"，判定"收益一般，排到下个季度"。而生产跑在 0.84 的利用率上，这个改动实际值 84%——换成绝对值是每条尾请求省掉半秒。不带负载条件的收益估计，会让你把最该做的事排到最后。

反过来也会出事：在高负载下测出 78%，写进报告说"这个优化能提升 78%"，然后团队扩容之后利用率降到 0.3，实际只拿到 20%，你的估计就成了空头支票。

正确写法是把条件写进去：「利用率 < 0.5 时约 22%，利用率 > 0.8 时约 78%」。多写十个字，这一栏才有意义。
