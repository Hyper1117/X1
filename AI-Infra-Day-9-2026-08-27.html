第 1 题（Day 8）
一个推理服务报出来 TPOT 平均 45 毫秒，看着很健康。用户抱怨"打字打到一半会卡一下"。这两件事怎么同时成立？你会去查什么？

看答案

TPOT 是一次除法算出来的平均值：端到端延迟减去 TTFT，再除以 token 数减一。一条回答里所有的停顿都被摊平进这个数。

而用户感受到的是每一次停顿。一条两百个 token 的回答有一百九十九个间隔，其中五个被拖到八百毫秒，其余都是二十几毫秒——平均下来仍然是四十几毫秒，但那五次停顿用户全都经历过。

要查的是 ITL 的高百分位，不是 TPOT。ITL 是那一串间隔本身，是分布，能看 P99。再往下一步，把服务端每一步的起止时刻记下来，看那些大间隔里夹着什么。昨天的答案是：夹着别人的 prefill。

今天要做的事情就是把那个"别人的 prefill"从中间拿掉。

第 2 题（Day 6）
你用开环压测器测出 P99 是 380 毫秒。同事说这个数不能信，因为压测器自己可能没按时把请求发出去。怎么用一个数字堵住他的嘴？

看答案

记录每条请求的"计划发出时刻"和"实际发出时刻"的差，报出它的 P99。这个差有个名字叫发送迟滞。

用法只有一条：拿它和你测的延迟比量级。

如果发送迟滞是几毫秒，而你测的是几百毫秒，差一个数量级以上，那这份数据站得住。如果两者同一量级，你测的就是压测器不是服务，得换机器发压或者降速率。

Day 6 那次的发送迟滞 P99 落在个位数到几十毫秒，而结论涉及的差异是几百毫秒，所以结论成立。

今天所有实验都在同一台两核机器上跑，压测器和服务各占一个进程，这个警惕一天都不能松。

第 3 题（Day 2）
一台服务器的利用率从 50% 提到 90%，忙碌程度只涨了不到一倍。平均排队时间会变成原来的几倍？给出量级和它背后的形状。

看答案

九倍。不是一倍。

形状是 ρ / (1 − ρ)。分母是剩下的空闲比例，空闲越接近零，整个值越往上冲。代进去：利用率一半时是 1，利用率九成时是 9。

原因在于请求到达是随机的，不是掐着点来的。利用率越高，"闲下来把队伍清空"的窗口越少；积压一旦形成就散不掉。

这就是线上服务把水位定在六七成的理由——那三成不是浪费，是买延迟的稳定。

今天的实验全部跑在九成五以上的利用率上，所以你会看到一些非常夸张的等待时间。那不是服务坏了，是这条曲线的右端本来就长这样。

放行那段代码只有九行，两种策略的差别全在这里：

def admit():
    """把排队的请求放进 prefilling。两种调度策略只差这个函数。"""
    if SCHED == "static":
        # 上一批没跑完，一条新的都不接
        if running or prefilling: return
        room = MAX_SEQS
    else:
        # 有空位就补，不管别人跑到哪儿了
        room = MAX_SEQS - len(running) - len(prefilling)
    while room > 0 and pending:
        prefilling.append(pending.pop(0)); room -= 1

第一部分 · 谁在等谁两种放行策略，以及一个会让你猜错的对照

1. 你现在会怎么写这个调度器

这一节回答：把请求攒成一批，最自然的写法是什么？它错在哪？

你是后端工程师，要给这个引擎写放行逻辑。最自然的写法大概是：攒够一批，一起处理，处理完再攒下一批。

这个写法在别的地方是对的。批量写数据库、批量发消息、批量调外部接口，都是这么干的，而且效果很好。它的前提是：一批里每个元素的处理时间差不多。

生成式推理不满足这个前提。一条请求要吐多少个 token，事先不知道，而且差异极大——有人问"今天几号"，有人让模型写一篇文章。第一条八个 token 就结束，第二条要八百个。

把这两条放进同一批，会发生什么，上面那张表已经演过了：短的先跑完，槽位空出来，但下一条请求进不来，因为这一批还没结束。空着的槽位就一直空到最长那条跑完为止。

这种"攒一批、跑到全部结束、再攒下一批"的做法，就叫 静态批处理（static batching）。

与之相对的另一种做法是：不等整批结束，谁跑完谁下车，空出来的位子立刻让下一个排队的上来。这叫 连续批处理（continuous batching），有时也叫 in-flight batching。

顺便把一个昨天一直在用、但没正式命名的东西补上。引擎循环转一圈，做一次矩阵乘法，给这一批里每条序列各推进一个 token——这一圈叫一个 引擎步（engine step / iteration）。上面那张表里的每一行就是一步。连续批处理的另一个名字 iteration-level scheduling，说的就是"以引擎步为粒度重新决定谁上车"。

2. 先别急着下结论

到这里，标准答案已经呼之欲出：连续批处理更好，因为它不浪费槽位。

这个结论是对的，但只对了一半，而漏掉的那一半恰恰是上岗后会咬你的部分。所以先做个实验。

两台服务器，除了 SCHED 全部一样：批量上限 8、prompt 8 个 token、每秒 2 条请求、跑 60 秒、一共 137 条。压测器用固定种子，两边拿到的到达时刻表和输出长度完全一致。

然后再分两组跑：一组所有请求的输出长度都是 24 个 token；另一组从 4 到 44 之间随机取，平均下来还是 24。两组的 token 总量几乎一样。

这个第二组不是为了"更真实"才加的。它是对照组：如果连续批处理的好处来自"批处理"这件事本身，那它在定长那组也应该赢。如果它只在变长那组赢，那好处的来源就是别的东西。

关键结论

连续批处理的收益，全部来自"不同请求的输出长度不一样"这一件事。长度一致时它只有代价没有收益，实测反而更慢。

所以这不是一个"新方法比旧方法好"的故事。真实负载里输出长度差异极大，所以它几乎总是赢——但赢的原因不是"批处理"，而是"补位"。搞混这两件事，下一节那个坑就躲不掉。

对照组的价值也在这里。如果只跑变长那一组，看到连续批处理赢了 26%，你会得出"连续批处理更快"这个结论，而且它在那次实验里完全成立。定长那一组一跑，才知道这句话缺了前提。

账已经分成两半：decode 那半连续批处理赢，prefill 那半它输。既然输的那半是"每放行一条就多读一遍权重"，下一个问题自然就是——能不能不多读这一遍？

第二部分 · 把插队的账消掉prefill 挡住 decode，怎么修才是真的修好

5. 昨天那条尾巴，现在有名字了

这一节回答：prefill 插在两次 decode 中间，为什么削短它没用？

Day 8 量到过一件事：ITL 分布的整条尾巴，逐个点名都能归到 prefill 头上。一条请求正在一个字一个字往外吐，突然有人发来新请求，引擎跑去做 prefill，这条请求的下一个字就得多等一整遍权重读取。

最自然的修法是：把长 prompt 切成小块，一步只算一块。每次插队变短，尾巴自然就矮了。

这个做法叫 分块预填充（chunked prefill）。它是对的，但单独用会出事。

把上一部分的账搬过来就知道为什么了。一次 prefill 的成本主要不是"算了多少个 prompt token"，而是"把权重完整读了一遍"。把 128 个 token 的 prompt 切成 4 块，插队时长确实降到四分之一——但插队次数变成 4 次，权重被读了 4 遍。

总账是变差的。

所以还得配一件事：把这一块 prompt 和正在生成的那些 token 挤进同一次矩阵乘法。这样一步之内既推进了 prefill 也推进了 decode，而权重只读一遍。这种一次同时装着两种活的批，叫 混合批（mixed batch）。

代码上就是把两次调用合成一次，列数相加：

if MIXED and pre_S and dec_B:
    # 合批：prompt token 和 decode token 挤进同一次矩阵乘法，权重只读一遍
    matmuls(pre_S + dec_B)
else:
    # 不合批：各算各的，权重被读两遍
    if pre_S: matmuls(pre_S)
    if dec_B: matmuls(dec_B)

运行之后看服务端日志里步的类型：合批那组绝大多数是 M 开头的混合步；不合批那组是 P 和 D 交替。如果开了 MIXED=1 却几乎看不到 M，说明 prefill 和 decode 没有在同一步撞上，多半是负载太低。

关键结论

这也解释了 vLLM 文档里那句话的两个方向：一步里算的 prompt token 少一点，ITL 更好；多一点，TTFT 更好。这个取舍就是上面这三行的连续版本。

8. vLLM 的调度器里根本没有"阶段"这回事

到这里可以去看真实实现了。vLLM 的调度器主函数开头有一段注释，把整套设计一句话说完了。vllm/v1/core/sched/scheduler.py 第 501 到 511 行：

「There's no "decoding phase" nor "prefill phase" in the scheduler. Each request just has the num_computed_tokens and num_tokens_with_spec. At each step, the scheduler tries to assign tokens to the requests so that each request's num_computed_tokens can catch up its num_tokens_with_spec.」
——调度器里没有"解码阶段"，也没有"预填充阶段"。每条请求只有两个数：已经算完了多少 token、总共需要多少 token。每一步，调度器把 token 配额分给各条请求，让前一个数追上后一个数。

这句话值得停一下。Day 8 花了整整一天把 prefill 和 decode 分成两个阶段讲，而真实实现里这两个词在调度器中不存在。

两者不矛盾。prefill 和 decode 是描述"矩阵形状"的词，那一层的区别是真的。而在调度这一层，一条请求还差多少 token 没算，是 prefill 差的还是 decode 差的，没有区别——都是"欠着几个 token"。把它统一成一个数之后，分块预填充、混合批、prefix caching、投机解码全都变成同一套代码的特例。

紧接着的两行标出了顺序：第 547 行 First, schedule the RUNNING requests，第 771 行 Next, schedule the WAITING requests。先给正在生成的续上，剩下的配额才给新来的。这和昨天那个装置正好相反——昨天是先 prefill 再 decode，所以尾巴全长在别人的字间。vLLM 选了另一边。

第三部分 · 调度器手里的旋钮两个参数、一次抢占，以及源码里的实际写法

9. 第一个旋钮：同时最多几条

这一节回答：把并发上限调大，什么时候有用，什么时候只是数字变大？

上面所有实验里那个"批量上限 8"，在 vLLM 里是一个配置项。vllm/config/scheduler.py 第 63 行起：

把它从 1 扫到 16，其余全部锁死：连续批处理、不切不合批、prompt 8 个 token、输出固定 24、每秒 1 条、跑 40 秒、49 条请求。

10. 第二个旋钮：一步最多算几个 token

光有"最多几条序列"是不够的。八条序列可能是八条正在吐字的（一步八个 token），也可能里面混着一条 prompt 有八千个 token 的新请求（一步八千多个 token）。这两种情况一步的耗时差着几十倍。

所以还需要第二个上限，管的是 token 总数。同一个文件第 49 行：

max_num_batched_tokens: int = Field(default=DEFAULT_MAX_NUM_BATCHED_TOKENS, ge=1)
"""Maximum number of tokens that can be processed in a single iteration."""
DEFAULT_MAX_NUM_BATCHED_TOKENS: ClassVar[int] = 2048

这个数叫 max_num_batched_tokens。它就是第 8 节那句注释里的"token 配额"——每一步调度器手上有这么多 token 可以分，分完为止。这个配额本身有个名字，叫 token 预算（token budget）。

分块预填充就是这个预算的自然结果，不是一个额外的功能。预算 2048，来了一条 prompt 八千 token 的请求，一步分给它 2048 个，剩下的下一步再说——它自动就被切开了。同一个文件第 75 行也印证了这一点：enable_chunked_prefill: bool = True，默认开着。

两个旋钮的分工可以这样记：max_num_seqs 限的是"几个人上车"，max_num_batched_tokens 限的是"这一车总共装多少货"。任何一个先到上限，这一步就不再往里加了。

第 6 节那三行实测，就是调小这个预算的效果：预算越小，一步里能塞的 prompt token 越少，插队越短，ITL 越好，但一条 prompt 要更多步才算完，TTFT 越差。

11. 内存不够的时候，牺牲谁

前面所有讨论都假设"想放几条就放几条"。真实系统里放不下——每条正在生成的序列都要占一块显存存中间结果，放太多就爆了。

爆了怎么办？调度器得从正在跑的里面拉一条下来，把它的内存让出去。这个动作叫 抢占（preemption）。

vLLM 拉哪一条，源码里写得很直白。scheduler.py 第 702 行，非优先级模式下：

preempted_req = self.running.pop()

running 是按到达顺序排的，pop() 取的是最后一个。被牺牲的是最新来的那条。

这不是随手写的。最新那条已经算出来的 token 最少，把它拉下来，扔掉的工作量最小。反过来牺牲最老那条，等于把一条已经吐了几百个字的请求推倒重来。

推倒重来不是比喻。第 1365 行那个函数干的事情是：

self._free_request_blocks(request)          # 把它占的内存块全部释放
request.status = RequestStatus.PREEMPTED
request.num_computed_tokens = 0             # 已算完的 token 数清零，从头再来

释放内存块，然后把"已经算完多少 token"清零，扔回等待队列。它之前算的东西一点没留下，回来之后整个 prompt 要重新算一遍。这种处理方式叫 重算（recompute）。

另一条路是把中间结果搬到 CPU 内存里存着，回来再搬回去，叫 swap。vLLM 文档写着「In vLLM V1, the default preemption mode is RECOMPUTE rather than SWAP, as recomputation has lower overhead in the V1 architecture」——V1 默认选重算，因为在新架构下重算的开销更低。这两条路的取舍要等 Day 15 把内存账算清楚才谈得下去。

还有一种模式：如果配了优先级策略，牺牲的就不是最新那条，而是优先级最低的那条。第 668 行：

preempted_req = max(self.running, key=lambda r: (r.priority, r.arrival_time))

按"优先级，然后到达时间"取最大——优先级数值越大越低级，同优先级里取最晚到的。这就是给不同租户分级之后，调度器实际执行的动作。

关键结论

调度器只有三件事可做：这一步让谁上车、给每个人分多少 token 配额、装不下时踢谁下去。今天这三部分正好一样一件。

三件事都没有"最优解"，只有把压力从一个指标推到另一个指标。补位提高吞吐但增加 prefill 次数；切碎改善 ITL 但恶化 TTFT；抢占保住了内存但让某条请求白算一遍。

"""Day 9 的推理服务：和 Day 8 同一套骨架，只是把调度器做成可换的。
用法: OPENBLAS_NUM_THREADS=1 python3 server.py <端口>
环境变量:
  SCHED     = continuous | static   何时接纳新请求
  MAX_SEQS  = 整数                  decode 批量上限（同时最多几条在生成）
  CHUNK     = 0 或正整数            一步最多算几个 prompt token；0 = 一口气算完
  MIXED     = 0 | 1                 1 = prefill 和 decode 合成同一次矩阵乘法
  STEPLOG   = 文件名                记录每一次引擎步
"""
import asyncio, json, os, sys, time
import numpy as np

N, L = 4096, 8                      # 8 层 4096x4096 float32 权重，合计 512 MiB
W = [np.random.rand(N, N).astype(np.float32) for _ in range(L)]
SCHED    = os.environ.get("SCHED", "continuous")
MAX_SEQS = int(os.environ.get("MAX_SEQS", "1000"))
CHUNK    = int(os.environ.get("CHUNK", "0"))
MIXED    = os.environ.get("MIXED", "0") == "1"
STEPLOG  = open(os.environ.get("STEPLOG", "/dev/null"), "w")

class Seq:
    __slots__ = ("q", "todo", "left", "admitted")
    def __init__(self, prompt_len, out_len):
        self.q = asyncio.Queue()
        self.todo = prompt_len       # prompt 里还剩几个 token 没算
        self.left = out_len          # 还要吐几个 token
        self.admitted = False

pending, prefilling, running = [], [], []   # 排队等着 / 正在做 prefill / 正在吐 token

def matmuls(S):
    """S 列输入过一遍全部权重。一次调用 = 把 512 MiB 权重完整读一遍。"""
    X = np.random.rand(N, S).astype(np.float32)
    for w in W: w @ X
    return S

def admit():
    """把 pending 里的请求放进 prefilling。两种调度策略只差这个函数。"""
    if SCHED == "static":
        # 上一批没跑完，一条新的都不接
        if running or prefilling: return
        room = MAX_SEQS
    else:
        room = MAX_SEQS - len(running) - len(prefilling)
    while room > 0 and pending:
        prefilling.append(pending.pop(0)); room -= 1

async def engine():
    while True:
        admit()
        if not prefilling and not running:
            await asyncio.sleep(0.001); continue

        # --- 这一步要算多少 prompt token ---
        budget = CHUNK if CHUNK > 0 else 10**9
        pre_S, ready = 0, []
        for s in prefilling:
            if budget <= 0: break
            take = min(s.todo, budget)
            s.todo -= take; pre_S += take; budget -= take
            if s.todo == 0: ready.append(s)

        dec_B = len(running)
        if MIXED and pre_S and dec_B:
            # 合批：prompt token 和 decode token 挤进同一次矩阵乘法，权重只读一遍
            a = time.perf_counter(); matmuls(pre_S + dec_B); b = time.perf_counter()
            STEPLOG.write(f"M {a:.6f} {b:.6f} {pre_S} {dec_B}\n")
        else:
            # 不合批：各算各的，权重被读两遍
            if pre_S:
                a = time.perf_counter(); matmuls(pre_S); b = time.perf_counter()
                STEPLOG.write(f"P {a:.6f} {b:.6f} {pre_S} 0\n")
            if dec_B:
                a = time.perf_counter(); matmuls(dec_B); b = time.perf_counter()
                STEPLOG.write(f"D {a:.6f} {b:.6f} 0 {dec_B}\n")

        # --- 把这一步产出的 token 发出去 ---
        done = []
        for s in running:
            s.q.put_nowait("x"); s.left -= 1
            if s.left <= 0: s.q.put_nowait(None); done.append(s)
        for s in done: running.remove(s)
        for s in ready:                      # prompt 算完的，第一个 token 现在出来
            prefilling.remove(s)
            s.q.put_nowait("x"); s.left -= 1
            if s.left > 0: running.append(s)
            else: s.q.put_nowait(None)

        STEPLOG.flush()
        await asyncio.sleep(0)

async def handle(reader, writer):
    try:
        head = await reader.readuntil(b"\r\n\r\n")
    except Exception:
        writer.close(); return
    n = 0
    for line in head.split(b"\r\n"):
        if line.lower().startswith(b"content-length:"): n = int(line.split(b":")[1])
    req = json.loads(await reader.readexactly(n) if n else b"{}")
    s = Seq(int(req.get("prompt_len", 8)), int(req.get("max_tokens", 24)))
    writer.write(b"HTTP/1.1 200 OK\r\nContent-Type: text/event-stream\r\n"
                 b"Transfer-Encoding: chunked\r\n\r\n")
    await writer.drain()
    pending.append(s)
    while True:
        if await s.q.get() is None: break
        payload = b'data: {"t":"x"}\n\n'
        writer.write(b"%x\r\n" % len(payload) + payload + b"\r\n")
        await writer.drain()
    writer.write(b"0\r\n\r\n")
    try:
        await writer.drain(); writer.close()
    except Exception: pass

async def main():
    asyncio.create_task(engine())
    srv = await asyncio.start_server(handle, "127.0.0.1", int(sys.argv[1]))
    print(f"listening {sys.argv[1]} SCHED={SCHED} MAX_SEQS={MAX_SEQS} "
          f"CHUNK={CHUNK} MIXED={int(MIXED)}", flush=True)
    async with srv: await srv.serve_forever()

asyncio.run(main())

"""开环压测器：按泊松到达发请求，逐 token 记录时间戳。
用法: python3 loadgen.py <port> <rps> <秒数> <prompt_len> <max_tokens> [标签]
     max_tokens 可以是一个整数（每条都一样），也可以写成 u:4:44
     表示每条从 4 到 44 之间均匀随机取一个（种子固定，各组拿到同一串长度）
输出一行 JSON，含每条请求的 ttft / itl 列表 / 端到端延迟。
"""
import asyncio, json, random, sys, time

async def one(port, plan_t, prompt_len, max_tokens, out):
    now = time.perf_counter()
    if plan_t > now: await asyncio.sleep(plan_t - now)
    body = json.dumps({"prompt_len": prompt_len, "max_tokens": max_tokens}).encode()
    try:
        r, w = await asyncio.open_connection("127.0.0.1", port)
    except Exception:
        return
    w.write(b"POST /gen HTTP/1.1\r\nHost: x\r\nContent-Length: %d\r\n\r\n" % len(body) + body)
    await w.drain()
    await r.readuntil(b"\r\n\r\n")
    ts, ntok = [], 0
    while True:
        line = await r.readline()                 # chunk 长度行
        if not line or line.strip() == b"0": break
        payload = await r.readexactly(int(line.strip(), 16) + 2)
        ts.append(time.perf_counter())
        ntok += payload.count(b"x")               # 这一个 chunk 里真的装了几个 token
        if b"data:" not in payload: break
    w.close()
    if not ts: return
    # 延迟一律从"计划发出时刻"起算，不是从真正 write 的时刻起算
    out.append({"ttft": ts[0] - plan_t,
                "itl": [ts[i] - ts[i-1] for i in range(1, len(ts))],
                "e2e": ts[-1] - plan_t, "n": len(ts), "ntok": ntok, "plan": plan_t})

async def main():
    port, rps, dur = int(sys.argv[1]), float(sys.argv[2]), float(sys.argv[3])
    plen, mspec = int(sys.argv[4]), sys.argv[5]
    tag = sys.argv[6] if len(sys.argv) > 6 else ""
    rnd = random.Random(1234)
    t0 = time.perf_counter() + 0.5
    plan, t = [], t0
    while t - t0 < dur:
        plan.append(t)
        t += rnd.expovariate(rps)                 # 泊松到达：间隔随机，不跟服务周期锁相
    lrnd = random.Random(99)                      # 输出长度用另一个固定种子，各组完全一致
    if mspec.startswith("u:"):
        lo, hi = int(mspec.split(":")[1]), int(mspec.split(":")[2])
        lens = [lrnd.randint(lo, hi) for _ in plan]
    else:
        lens = [int(mspec)] * len(plan)
    out, tasks = [], []
    for pt, mtok in zip(plan, lens):
        tasks.append(asyncio.create_task(one(port, pt, plen, mtok, out)))
    await asyncio.gather(*tasks)
    print(json.dumps({"tag": tag, "rps": rps, "dur": dur, "plen": plen,
                      "mtok": mspec, "lens": lens, "sent": len(plan), "reqs": out}))

验收标准

  • 定长那两组的差距明显小于变长那两组。如果两组差距一样大，说明你的输出长度分布方差不够，把范围拉开再试。
  • 你能从服务端日志里数出 decode 步的批量分布，并指出 static 那边有多少步的批量小于上限的一半。
  • 吞吐曲线在某个 MAX_SEQS 之后走平，而且你能说出走平的原因是负载够不着这个上限，不是硬件到顶了——证据是那一档的实际批量平均值明显小于上限。

常见坑

  • 两个进程抢两个核。压测器和服务各占一个，这台机器就满了。看到 ITL 中位数随速率涨得比 decode 步耗时快很多，先怀疑这一条，用发送迟滞验证。
  • static 那组跑不完。它的有效吞吐比 continuous 低，同样的速率可能压垮它，队列越排越长。发现 timeout 被触发就把速率降到 1.5 以下。
  • 拿设定的 dur 当分母算吞吐。过载时请求会在窗口结束后很久才完成，用设定时长做分母会把吞吐算高。要用"最后一条完成时刻减第一条计划发出时刻"。

上岗关联

场景一：吞吐上不去，但 GPU 利用率看着不低

先别看 GPU，先看实际批量的分布。如果分布左偏、大量步只服务一两条序列，问题在调度不在算力。

接下来分两种情况。同时排队的请求本来就少，那是流量问题或者路由问题，加机器没用。有请求在排队但批量还是上不去，那就是放行逻辑的问题——检查 max_num_seqs 是不是设小了，或者内存不够导致一直在抢占。抢占次数 vLLM 会打日志，也有 Prometheus 指标。

场景二：产品要求"首字必须一秒内出来"，同时要求吞吐翻倍

这两个要求指向相反的旋钮，得让他们排优先级。

能给出的是一张取舍表而不是一个方案：调大 max_num_seqs 换吞吐，代价是每个人的字变慢；调小 max_num_batched_tokens 换 ITL，代价是长 prompt 的首字更慢。第 6 节和第 9 节那两张表就是这两条取舍的形状。

顺带一提，如果长 prompt 是主要负载，还有第三条路：把 prefill 和 decode 拆到不同实例上。那是 Day 8 延伸材料里那篇文档讲的事，代价是要多一套机器。

场景三：线上偶发某条请求"卡住很久然后突然全出来"

这个形状是抢占。请求被踢回队列、进度清零、重新排队重算，用户端看到的就是长时间没动静，然后一次性追上来。

排查顺序：先看抢占计数有没有同步上涨，再看是不是在内存吃紧的时段发生的。解法通常是限制并发或者给 KV cache 更多空间，而不是去优化模型。

同事和面试官常问的

  • 「continuous batching 为什么比 static 快？」——只答"不浪费槽位"是对的但不完整。加一句"收益全部来自输出长度的方差，长度一致时它反而略慢，因为每放行一条就多一次 prefill"，就说明你真做过对照。
  • 「chunked prefill 是干什么的？」——它把长 prompt 切开，让它不至于一次堵住所有人的字。追问"那为什么不切得越碎越好"，答：切碎必须配合把 prompt 和 decode 放进同一步，否则权重被读的次数成倍增加，总账是亏的。
  • 「max_num_seqs 调大有什么坏处？」——每步要带的序列多了，一步就慢，所有人的 TPOT 一起变差。而且调大不等于用得上，实际批量才是要看的数。
  • 「内存不够时 vLLM 踢谁？」——默认踢最新那条，因为它已算的 token 最少、重算最便宜；配了优先级就踢优先级最低的。踢下去之后进度清零，整个 prompt 要重算。

自检问题

1. 一个服务从 static 换成 continuous batching，上线后吞吐只涨了 3%。老板问是不是白改了。你怎么查？

先查输出长度的分布，这是决定收益上限的那个量。

如果这个服务的输出长度高度集中（比如都是固定格式的短回答，都在 20 到 30 个 token），那 3% 就是它应得的收益，改动没做错，只是这个场景本来就没多少可捞的。第 3 节那两组定长实验里，continuous 甚至还小输了一点。

如果输出长度差异很大，那 3% 说明补位没有真的发生，要往下查两件事。一是实际批量的分布：如果仍然大量步只服务一两条，说明放行逻辑没生效或者被别的上限卡住了。二是 prefill 步数：如果它涨得非常多，那 decode 侧省下来的时间被 prefill 侧吃掉了——这正是第 4 节那张账本上的形态，解法是把 prompt 和 decode 合进同一步。

怎么区分这两件事：数一下引擎步里 prefill 占了多少。占比很低就是第一种，占比很高就是第二种。

2. 你把 max_num_batched_tokens 从 8192 调到 2048，ITL 的 P99 明显改善，但用户投诉变多了。可能发生了什么？

最可能的是 TTFT 变差，而这个服务的用户对首字更敏感。

这个参数管的是一步能算多少 token。调小之后，一条长 prompt 要分更多步才算完，第一个字自然出得更晚。第 6 节那张表里，切碎之后 TTFT 从 11.6 秒涨到 25.8 秒，就是这个方向的极端版本。

还有第二种可能，跟第一种会同时发生：预算调小之后，每一步能容纳的 prompt token 变少，同样的流量需要更多引擎步，总吞吐下降，于是队列变长，所有人的等待都变长。这时候 ITL 好看是因为每一步都变短了，但端到端时长反而更差。

区分方法：看端到端延迟。如果 ITL 改善而端到端变差，就是第二种；如果端到端没变而只有 TTFT 变差，就是纯粹的取舍生效了，那就要回去和业务确认到底哪个指标更重要。

3. 有人提议：既然抢占要把进度清零重算，那干脆永远不抢占，请求太多就直接拒绝。这个方案有什么问题？

方向上不算错，很多系统确实这么做，这叫准入控制。但它把一个可以延后的成本换成了一个不可逆的失败。

先说清楚这个提议的名字：在请求进门时就判断"扛不扛得住"，扛不住直接拒绝，这叫准入控制（admission control）。

抢占的代价是某条请求白算一遍，用户感受到的是变慢；直接拒绝的代价是这条请求没有了，用户感受到的是报错。对大多数场景，慢比失败好接受。

还有一个更实际的问题：拒绝的判断得在请求进来时做，而那时你不知道它要生成多少 token。一条请求会占多少内存，取决于它最终吐多长，这个数事先不知道。所以"够不够"这个判断只能一边跑一边做——这正是抢占存在的原因。

合理的做法是两者都要：用准入控制挡住明显扛不住的流量，用抢占处理跑起来之后才发现的超额。它们管的是不同时刻的同一个问题。

4. 第 9 节里 max_num_seqs 从 1 调到 2，吞吐没涨而 TPOT 翻倍。如果换成一台真实的 GPU 服务器，这个坑还在吗？

形状还在，位置不在同一个地方。

这个坑的成因是 Day 7 讲的那件事：批量为 1 时走"矩阵乘向量"的代码路径，批量大于等于 2 时走"矩阵乘矩阵"，后者为了让内层循环命中缓存要先把权重重排一遍，于是权重被过了两遍。批量很小的时候，这笔重排费摊不回来。

GPU 上的具体实现不同，但同一类现象存在：小批量时算力严重空转，一步的耗时基本由"把权重读一遍"决定，加几列几乎不要钱也几乎不赚钱。真正的分界线在这台硬件的算力除以带宽那个数上——Day 7 算过，这台机器上是个位数，一块 H100 上是几百。

所以结论不是"2 是个坏数字"，而是"在拐点左边加批量，收益接近零"。要判断自己那台机器的拐点在哪，就把 Day 7 那两把尺子量一遍。

合上这一页，用自己的话回答。每题一到三句，写完对照后面的自查标准。

5. 内存不够时 vLLM 踢掉哪条请求？为什么是那一条？被踢掉的那条损失了什么？

逐句自查标准

第 1 句　如果只写"批处理效率低"，等于没说。要说出具体场景：一批八条，七条二十个 token 就结束，一条要四十四个；后面二十几步里槽位空着一半，但新请求进不来。还要补一句为什么空槽位是纯浪费——一步的耗时主要由读一遍权重决定，批量掉下去省不了时间，只是少吐了 token。

第 2 句　"不浪费槽位"只答了一半。必须说出"什么情况下没好处"：输出长度一致时。而且要知道那时它还略亏，因为一条一条放行意味着一条一条 prefill。能说出"没好处的情况"，才说明你知道好处从哪来。

第 3 句　如果写成"切碎增加了开销"，太笼统。要具体到：一次前向的成本主要是把权重完整读一遍，跟这一步算几个 token 关系不大。切成四块就是读四遍。所以省下的插队时间被多读的权重吃掉了。

第 4 句　两个都要说清楚管的是什么维度：一个限序列条数，一个限 token 总数。调大 max_num_seqs 换吞吐、牺牲 TPOT；调小 max_num_batched_tokens 换 ITL、牺牲 TTFT。如果你写的是"调大性能更好"，那是漏掉了牺牲的那一边。另外要补一句上限不等于实际值。

第 5 句　默认踢最新到达的那条。理由要说出来：它已经算完的 token 最少，重算最便宜。损失的是全部进度——内存块释放、已算 token 数清零、回到队列后整个 prompt 重来。如果答"踢最不重要的"，那是优先级模式，要说明这是配置出来的另一种策略。
