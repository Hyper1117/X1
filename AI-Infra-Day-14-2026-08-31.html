Q1 · 1 天前（Day 13 · runc、containerd 与 OCI 分层）

昨天读到 exec fifo：runc init 把命名空间、根、配额都装好之后，卡在这个命名管道的写端等着，runc start 打开读端才放行 execve。

现在你要做一个"提前建好一批沙箱放着等请求"的池子。按这个机制，池里的沙箱应该停在哪个状态？为什么这个状态是唯一可选的那个——停在 running 不行吗，停在还没 create 不行吗？

展开答案

停在 created。

推理分两头。停在还没 create 等于什么都没提前做，池子是空的，省不下任何东西。停在 running 则意味着 execve 已经发生了——容器里那个进程已经在跑 config.json 里写死的那条命令。可是请求还没来，你还不知道要跑什么代码，这个进程只能跑一个"什么也不干"的占位程序。

而 created 这个状态恰好卡在中间：命名空间建好了、rootfs 挂好了、cgroup 装好了、能力砍好了，唯独 execve 还没发生。规范给这个状态的定义就是"环境已就绪但用户程序还没执行"。它是唯一一个"活儿全干完了，但还没定死要跑什么"的时刻。

接今天：今天会量出停在 created 到底替你省下多少，答案会比你按昨天那张表推的要少。

Q2 · 3 天前（Day 11 · 手搓最小容器）

Day 11 那个实验：同一个 sleep 二进制，在宿主上直接跑，发 SIGTERM 它就退了；在容器里当 1 号进程跑，发 SIGTERM 它还活着。

二进制没变、信号没变，差别到底在内核的哪一条规则上？再往下一步：一个沙箱服务给每次执行设了超时，超时先发 SIGTERM、等一个宽限期、再发 SIGKILL。对"用户随手提交的一段代码"来说，这个宽限期通常在做什么？

展开答案

差别在进程号命名空间给 1 号进程开的特例：命名空间里的其他成员发信号给 1 号进程，只有 1 号进程自己装了处理函数的那些信号才送得到；从祖先命名空间往里发也受同一条限制。SIGKILL 不在此列，它拦不住。

在宿主上跑的 sleep 是个普通进程，SIGTERM 的默认动作是终止，于是它退了。当它是容器里的 1 号进程时，它没装 SIGTERM 处理函数，这个信号就被内核直接丢掉了——不是它"接住了不理"，是根本没送到。

所以对用户随手提交的代码，宽限期几乎总是在纯粹地空等：那段代码不会装信号处理函数，SIGTERM 对它是一个空动作，宽限期到点之后才轮到真正管用的 SIGKILL。

接今天：今天会把这个空等的钱量出来，还会回答一个 Day 11 没碰的问题——用户代码要是还派生了一个孙子进程，SIGKILL 打在 1 号进程身上，孙子会怎样。

Q3 · 7 天前（Day 7 · 内存层级与缺页）

Day 7 那组对照：扫过 1 GB 的匿名内存，第一遍四百多毫秒，第二遍三十几毫秒。加上 MAP_POPULATE 之后，262 144 次缺页原封不动地搬到了 mmap 那一步，第一遍立刻掉到和第二遍同一个量级。

今天的主角是"提前把沙箱建好放着"。请说出它和 MAP_POPULATE 在结构上是同一个动作的哪几点，以及它们各自把成本搬到了哪里去。

展开答案

三点是同一个形状。

一，总工作量一点没少。MAP_POPULATE 没有让那 262 144 次缺页消失，它只是让它们在别的时刻发生；提前建好的沙箱也一样，命名空间、挂载、cgroup 该建的一样要建。

二，搬走的是"谁来等"。缺页的四百毫秒本来落在第一遍扫描那个调用者头上，搬走之后落在 mmap 调用上；建沙箱的开销本来落在第一个请求头上，搬走之后落在服务空闲的时候。

三，代价都是提前占住资源。MAP_POPULATE 让你在真正用之前就吃掉了 1 GB 物理内存；预先建好的沙箱同样在没人用的时候就占着内存和进程号。

接今天：今天这一页有三条优化路线，它们全都是这个形状——把同一笔钱挪到请求路径之外。区别只在于挪走的那一段有多大。

3. 这条路上每一个动作都是阻塞的

你作为后端工程师，写这个服务的第一版大概长这样：一个 POST /run，里面调 subprocess.run 把 runc 跑起来，等它返回，把结果发回去。逻辑上没有任何问题。

问题在于这个函数里没有一个动作是能让出去的。挂 tmpfs、挂 overlay、runc create、runc start、从管子上读输出、runc delete、卸载——全是同步系统调用。Day 4 的结论在这里原样成立：写在 async def 里的同步调用，会把整个事件循环按住，此刻所有别的请求都停在原地。

Day 4 给过的解法是把这类活儿甩给线程池。今天的服务里每一处阻塞动作都走了这条路：

# 错的：整个事件循环停在这一行上
@app.post("/run")
async def run(req):
    out = cold_run(req.code)          # 里面全是同步的 mount / runc / read
    return out

# 对的：甩给线程池，事件循环立刻回去伺候别的请求
@app.post("/run")
async def run(req):
    out = await asyncio.to_thread(cold_run, req.code)
    return out

跑起来看什么：两个版本在只有一条请求的时候完全一样快，差别只在并发的时候才出现。想亲眼看到差别，把第一版跑起来，一边发一条会跑三秒的代码，一边发一条一毫秒就完事的代码——后者会等满三秒。这也是验证你自己有没有写错的最快办法。

这里说的"甩给线程池"，就是 Day 4 那个 run_in_executor。asyncio.to_thread 是它的现代写法，底层是同一件事。

4. 闸门：许可、队列、拒绝

事件循环不卡了，新问题立刻来：请求来多少，服务就起多少个沙箱。一百条请求同时到，就是一百个容器在两个核上抢。

需要一个数：同时最多允许几个沙箱在跑。这个数叫 并发上限（concurrency limit），实现它的东西是一个计数器，谁要跑先拿一张 许可（semaphore），跑完还回去。拿不到的就等着。

光有上限还不够。等着的那些请求排成一条队，队伍要是没有长度限制，晚来的请求会一直排到客户端自己超时——它们占着连接、占着内存，最后没有一个人拿到结果。所以队列也要有上限，超了直接回一个"现在满了"。这个动作叫 准入控制（admission control），而"上游发太快时，用拒绝或者变慢把压力顶回去"这件事整体叫 背压（backpressure）。

三样东西的代码合起来只有几行：

if state["waiting"] >= QMAX:        # 队列满了：不排无限长的队，当场回 429
    return Response(status_code=429)
state["waiting"] += 1
try:
    async with state["sem"]:        # 许可：同时在跑的沙箱不超过 MAXC 个
        return await run_in_sandbox(req.code)
finally:
    state["waiting"] -= 1

剩下的问题是 MAXC 取几。

把上限扫一遍

先说压测器怎么发请求。它不等上一条回来就发下一条，这是 Day 1 那个开环压测；相邻两条之间隔多久，取自一个平均值等于 1/λ 的指数分布随机数——也就是说间隔忽长忽短，长期平均下来每秒 λ 条。这种发法叫泊松到达（Poisson arrivals）。用它而不用"每 28.6 毫秒准时发一条"，是因为 Day 6 那个锁相：等间隔的压力很容易和被测系统里某个周期性的节拍对上，量出来的数会失真。

参数这样定：用重的那段用户代码（单次 34 毫秒 CPU），λ 固定在 35 次/秒，预热池给到 8 个（恒大于任何一档的 MAXC，保证池不会空），只改 MAXC 一个旋钮，别的全锁死。压测器压 3 秒不计数，再计 20 秒。

这里要说清楚为什么加上限反而更慢。这台机器只有 2 个核，用户代码是纯 CPU 的。允许 4 个沙箱同时跑，并不会让这两个核多出算力来，只会让四份活儿在同样两个核上轮流切换——总吞吐一点没涨（三行的请求数几乎一样），但每一份活儿的完成时间都被拉长了。等于把排队从服务门口挪进了操作系统的调度器里，而挪进去之后你就管不着它了。

关键结论

并发上限不是"越大越安全"的旋钮。它的合理取值由两件事夹出来：下界是"到达率乘以服务时间"，低于它队伍会发散；上界是这台机器真正能并行干活的资源数，超过它只会把排队藏进调度器。这台机器上这两个数分别是 35 × 0.034 ≈ 1.2 和 2，取 2 正好。

8. 路线一 · 预热池：把建沙箱挪到没人看的时候

甲那条路的做法有个名字：预热池（warm pool）。服务空闲的时候先建好一批沙箱停在 created，请求来了从池里取一个，用完扔掉，再补一个新的进去。

这个"预热"和 Day 6 那个"预热"是两回事。Day 6 说的是量任何东西之前先跑几轮不计数，把缓存之类一次性的开销先付掉，那是测量方法；这里说的是提前把资源建好放着，那是服务设计。同一个词，两件事。

池子不是免费的，代价有三笔，都能量出来。

第一笔：补一个进池子要多久

量"从零建一个沙箱到它可以接活"这一段，实测 P50 是 103.35 毫秒。这个数决定了池子的补充速度：一个后台补充协程，一秒最多补 9 个进去。

它同时给出了池大小的下界。Day 2 的利特尔法则在这里可以直接用：池里需要常备的数量，等于"到达率 × 一个沙箱从被取走到被补回来的时间"。到达率 35 次/秒、补一个 0.103 秒，就是 3.6 个——池子小于 4 个，稳定状态下就会经常见底。

第二笔：占着的内存

同时开四个预热沙箱，每个的 cgroup 记账在 7.76 到 8.04 MiB 之间，四个合起来 31.74 MiB；同一时刻整机的 MemAvailable（内核给出的"还能拿来用"的内存估计）下降了 27.38 MiB。两个数量级一致，可以按"每个预热沙箱八兆内存"来估。

八兆很便宜，但要注意这是一个只装了标准库的镜像。换成一个预先 import torch 的沙箱，这个数会完全不同——那时候池子多大就不再是延迟问题，而是内存问题。

第三笔：池空了怎么办

这一笔最容易被忽略。池子见底的时候，请求有两条路：等一个新的补进来，或者当场走冷路径。前者让这条请求多等一百毫秒，后者让它多等三十毫秒——但无论哪条，这条请求的耗时都和池子里有货时完全不同。

把两条路的数摆出来就知道差多少。命中池子的请求走的是表 B 第二行那 53 毫秒；当场走冷路径的走的是第一行那 85 毫秒；选择等一个新的补进来，最坏要多等一整个补充周期，也就是第 8 节开头那 103 毫秒。三个数互相之间差一到两倍。

于是延迟分布不再是一个包，而是分成了几坨。Day 6 讲过这个形状，它叫双峰分布。它的麻烦之处在于，平均值会落在两坨中间那个根本没有请求的位置上，看平均值等于什么都没看。这种服务只能看百分位。

10. 路线三 · 预导入之后 fork

第三条路动的是最大的那两段。做法是：容器里常驻一个进程，它一起来就把那一组库全部导入好，然后停在那儿等活；来一个任务就 fork 一个孩子，孩子直接带着已经导入好的模块去执行。这种"预先把重活干完、之后靠 fork 复制"的进程有个名字，叫 受精卵进程（zygote），也叫 fork 服务器（fork server）。

它便宜在哪，可以直接接上 Day 12 那个词。fork 出来的孩子和父亲共享同一批内存页，只有被写的那些页才会真的复制一份——这就是 Day 12 讲 overlay 上层时用的写时复制，同一个机制换了个场合。父进程已经导入好的那些模块，孩子一个字节都不用重新算，也不用重新解析一遍。

核心循环只有十几行：

# 开工之前先把重活干完：这一段只在容器起来时执行一次
import json, re, base64, urllib.request, http.client, datetime, statistics, hashlib

while True:
    with open('/app/rt/req') as f:       # 阻塞在命名管道上，等宿主写进一行
        line = f.readline()
    task = json.loads(line)
    pid = os.fork()                      # 全天最便宜的一步
    if pid == 0:                         # 孩子：带着已经导入好的模块直接干活
        g = {}
        exec(task['code'], g)
        with open('/app/rt/resp', 'w') as o:
            o.write(json.dumps({"ret": g.get('RESULT')}) + "\n")
        os._exit(0)                      # 用 _exit，不跑父进程注册的退出钩子
    os.waitpid(pid, 0)                   # 收尸，否则进程号表会被僵尸占满

跑起来应该看到：每次调用一点几毫秒返回，而且这个数不随调用次数变化。要是你看到它一次比一次慢，先去 ps 里数一下僵尸进程——十有八九是 waitpid 那行漏了，Day 13 讲过这个坑。

代价也很实在，有两条。

一，隔离的粒度变粗了。冷路径上，每个任务有自己的容器、自己的进程号表、自己的一次性可写层；用 zygote 之后，同一个容器里连续跑的多个任务共享同一个内核视图和同一个可写层。孩子进程之间靠的是普通的进程边界，不是容器边界。跑互不信任的用户代码时，这个差别是致命的——通常的做法是一个 zygote 只服务一个用户会话，会话结束整个容器扔掉。

二，它只对"重活能预先干完"的场景有效。父进程导入的是哪几个库，是你在容器起来的时候就写死的。用户代码要是 import 了一个你没预导入的东西，那部分开销原样回来。

12. 超时：宽限期在多数情况下是白等

温故第二题已经把机制说了：容器里的 1 号进程只接收它自己装了处理函数的信号。用户提交的代码不会装。所以这个宽限期对它们来说是纯粹的空等。

第一，宽限期整个是浪费。五百毫秒过去，容器状态没变，cgroup 里还是两个任务。真正起作用的是后面那一下 SIGKILL，它用不到十毫秒就清空了。整条终止路径 520 毫秒里，有 500 毫秒是白等的。

第二，孙子进程跟着死了，而且没人单独去杀它。心跳文件停在 SIGKILL 之前，说明它是被同一下带走的。机制是进程号命名空间的一条规则：这个命名空间的 1 号进程一旦终止，内核会把命名空间里剩下的所有进程全部用 SIGKILL 收走。这一条对沙箱很重要——它意味着你不需要自己去追用户代码派生出来的进程树，杀 1 号就够了，前提是这个沙箱确实有自己的进程号命名空间。

第三，"杀干净了没有"这件事，判据不该是容器状态，该是 cgroup 里还剩几个任务。状态是 runc 记在自己那份状态文件里的东西，而 cgroup 的任务列表是内核在数。今天这个探针读的就是后者。

那宽限期还要不要？要，但要分开对待。你自己写的那个 1 号进程（如果你按 Day 13 说的放了一个进去）应该装 SIGTERM 处理函数，让它有机会把结果刷出去、把日志写完；而对用户代码，宽限期应该取一个很小的值，因为等下去几乎不会有收益。把这两件事用同一个数配置，是常见的错法。

沙箱停了之后还要拆。表 A 里 runc delete 那一行是 5.46 毫秒，看起来无关紧要。但那一行量的是一种特定情况，换一种就完全不同了：

第一行和第二行是同一个容器、同一个状态，唯一差别是命令后面多了一个 -f。多出来的是 101 毫秒，而且四种情况里但凡走到 100 毫秒这一档的，抖动都极小——min 和 max 只差不到 3 毫秒。这种"贵得非常整齐"的形状通常意味着底下有一个固定的等待，而不是有活要干。

翻源码，八行就找到了。runc v1.3.5 的 delete.go 第 16 到 25 行：

func killContainer(container *libcontainer.Container) error {
	_ = container.Signal(unix.SIGKILL)
	for i := 0; i < 100; i++ {
		time.Sleep(100 * time.Millisecond)
		if err := container.Signal(unix.Signal(0)); err != nil {
			return container.Destroy()
		}
	}
	return errors.New("container init still running")
}

把这段逐行读：先发一发 SIGKILL，然后进循环。循环体的第一句是 Sleep(100ms)，第二句才去探测进程还在不在。也就是说，哪怕进程在 SIGKILL 之后一微秒就没了，这个函数也一定会睡满第一个 100 毫秒才发现。101 毫秒这个数就是这么来的。

接着看这个函数在什么时候被调用。同一个文件第 73 到 87 行：

if force {
	return killContainer(container)
}
s, err := container.Status()
...
switch s {
case libcontainer.Stopped:
	return container.Destroy()
case libcontainer.Created:
	return killContainer(container)
default:
	return fmt.Errorf("cannot delete container %s that is not stopped: %s", id, s)
}

两条路通向那 100 毫秒。带 -f 是一条，无条件走 killContainer；不带 -f 但容器状态是 Created 是另一条。只有"状态是 Stopped 且不带 -f"这一种组合，才走 Destroy() 直接拆，也就是表 E 第一行那 5.76 毫秒。

源码里第 68 到 72 行的注释解释了 -f 为什么对已经停掉的容器也要这么干：容器万一没有自己的进程号命名空间，它的 cgroup 里可能还留着别的进程，所以要无差别地补一刀。这个设计对通用场景是对的，只是对"每秒要拆几十个沙箱"的服务来说代价太高。

第三行的含义对预热池是直接的坏消息：池里那些 create 好但一直没被用掉的沙箱，你要关服务、要缩池、要换镜像，每拆一个都是 107 毫秒。池子有 32 个，光是拆就是三秒半。

14. 把回收挪出请求路径

把前两节的数加起来看一次最糟的执行：用户代码死循环，超时 SIGTERM 空等 500 毫秒，SIGKILL 7 毫秒，runc delete -f 107 毫秒，拆 overlay 7 毫秒。终止和回收合起来 621 毫秒——在"这次执行被允许跑多久"之外，又多出来大半秒。

如果这 621 毫秒发生在请求路径上，它就直接写进这条请求的延迟里；更糟的是，如果许可是在回收完成之后才归还的，那么这 621 毫秒里所有排队的请求都在跟着等。

这就引出了这一部分唯一的设计原则：把不需要用户等的事情，从请求路径（request path）上挪走。具体到这里是三件事——

  1. 许可在"结果已经拿到"的那一刻就归还，不等回收。
  2. 回收交给一个后台任务去做，请求这一侧只把沙箱标记成待拆。这种做法叫异步回收。
  3. 补池子也归后台。请求路径上只有"取一个"，没有"造一个"。

做完这三件事之后，那 621 毫秒还在，机器还是要付它。变化的只是谁在等：不再是某一条倒霉的请求，而是后台那条协程。这一点要说清楚，免得把"挪走"当成"消失"——如果后台的回收速度长期跟不上请求速度，池子会持续见底，冷路径会持续被走到，账最后还是要还。

关键结论

今天这一页从头到尾只做了一件事：把一次执行拆成一串互不重叠的段，然后逐段问"这一段能不能不在请求路径上发生"。预热池挪走了建容器那两段（表 B 上量到 32.2 毫秒），zygote 又挪走了解释器启动与库导入那两段（表 A 上合计 46.17 毫秒），异步回收挪走了终止与拆卸那 621 毫秒。一段都没有消失，全部还在机器上，只是换了个时刻发生。

两个任务，约两小时。任务 A 是把今天这套东西搭出来并量一遍，任务 B 把它接到你自己手上的东西上。

任务 A · 从一条命令做到一个能压测的服务（约 1.4 小时）

第 1 步：造一个装得下解释器的镜像目录

Day 11 那个 mkrootfs.sh 里只放了 sh 和 ls。这次要放下 python3、它的标准库目录、以及 ldd 列出来的那几个动态库。

验收标准：chroot 你的镜像目录 /usr/bin/python3 -c "import json,re,urllib.request; print('ok')" 能打出 ok。

常见坑：报 No module named 'encodings'，说明标准库目录没复制全或者位置不对——CPython 是按编译时写死的相对路径找标准库的，/usr/lib/python3.11 这个层级不能改。

第 2 步：把冷路径跑通，并且把十一段都量出来

照第 2 节那张走一遍的表，自己实现一遍：挂 tmpfs、挂 overlay、写 config.json、runc create、写任务、runc start、读输出、runc delete、卸载。

关键是让容器里的进程自己打三个 CLOCK_MONOTONIC 时刻出来，否则你只能量到一个总数，拆不开。

验收标准：把各段加起来，和端到端那个数的差不超过 1 毫秒。差得多说明有一段没被算进去。

常见坑：runc create 挂住不返回。原因是你用管子接了它的标准错误——容器进程会继承这个管子，而它此刻正卡在 exec fifo 上不退出，于是永远读不到 EOF。把标准错误接到临时文件上就好了。这个坑今天这套代码踩过一次。

第 3 步：包成 HTTP，加上许可和队列

用 FastAPI 加 uvicorn。每一个阻塞动作都要用 asyncio.to_thread 甩出去。

验收标准：一边发一条会跑 3 秒的代码，一边发一条 1 毫秒的代码，后者必须立刻返回。做不到就说明还有同步调用留在事件循环上。

常见坑：许可用 threading.Semaphore 而不是 asyncio.Semaphore。前者会把事件循环整个按住，症状和上面那条一模一样，但更难查，因为代码里看不到明显的同步调用。

第 4 步：加一个 zygote 池，把两条路的数放在一起

照第 10 节那个循环写。宿主一侧和容器一侧用两个命名管道通信，管道建在 overlay 的上层里，两边都看得见。

验收标准：连续调用一百次，耗时不应该有上升趋势。有上升就去数僵尸进程。

常见坑：命名管道的读写两侧同时只能有一对。多个请求并发打同一个 zygote 容器时，两条响应会串在一起。今天这套代码是靠"一个容器同一时刻只服务一个请求"绕过去的——用完还回池子之前，别人拿不到它。

第 5 步：把并发上限扫一遍

写一个开环压测器（独立进程），到达率固定，把 MAXC 从 1 扫到 8，画出 P50 和 P99。

验收标准：你应该能在自己的机器上找到那个拐点，并且它应该和你的核数有关。找不到拐点，多半是用户代码太轻，服务时间被 HTTP 开销淹没了——把它调重到几十毫秒再试。

板块 4 · 工作现场

场景一 · 「沙箱冷启动 P99 一秒四，砍到 300 毫秒」

Day 11 里这个场景出现过一次，当时你只能说"钱不在锁上"。今天你有完整的一套动作。

第一步不是优化，是拆账。按第 2 节那十一行在你自己的系统上做一遍，要求各段加起来等于端到端。这一步做完，方向基本就定了。

如果大头在容器创建，预热池能砍掉它，但要先算三个数：补一个进池子要多久、池子要多大（到达率乘以补充时间）、每个占多少内存。

如果大头在语言运行时启动和依赖导入——按今天这个镜像的比例，这是最可能的情况——那预热池只能帮你砍掉三成八，真正的解法是预导入之后 fork，代价是隔离粒度变粗，需要用"一个会话一个容器"来补。

如果大头在镜像准备，先分清是"镜像不在本地"还是"镜像在本地但页缓存是冷的"。这两件事的解法完全不同，前者是懒加载，后者是让镜像别被挤出内存。

场景二 · 「压力一上来延迟就崩，但 CPU 只有六成」

典型症状是 P50 还行、P99 高得离谱，而机器看起来没满。

先查并发上限设成了多少。如果它明显大于核数，你看到的就是第 4 节那张表：吞吐一点没涨，每份活儿都被拉长。CPU 六成而延迟崩，通常还意味着有一部分时间花在了不占 CPU 的地方——比如等回收、等池子补货。

再查许可是什么时候归还的。如果归还发生在回收之后，那么每一次回收的 100 多毫秒都在挡着后面的队伍。这一条在代码里通常是一个位置很不起眼的 finally。

场景三 · 「超时了，但是沙箱没死透」

Day 11 已经解释了 SIGTERM 为什么无效。今天补两条可操作的。

一是判据要换。别用"容器状态变了没有"判断死没死，用 cgroup 里还剩几个任务。前者是 runc 记的账，后者是内核在数。

二是别自己去追进程树。只要这个沙箱有自己的进程号命名空间，杀掉 1 号进程，内核会把里面剩下的全收走——今天量到的是不到十毫秒清空。反过来说，如果你发现杀了 1 号还有残留，那要怀疑的是这个沙箱压根没有自己的进程号命名空间。

同事和面试官常问的

  • 「你们的沙箱冷启动多少？」——这个问题问得不完整，回答的时候要先把口径说清楚：算不算镜像准备、算不算语言运行时启动、算不算回收。同一套系统这三个口径能差三倍。
  • 「为什么不直接用 docker run？」——因为它每次要走一遍高层运行时那一整套（Day 13 那张分层图），而你需要的只是最底下那一层的 create 和 start，还需要能把 create 提前。
  • 「预热池要开多大？」——到达率乘以"一个沙箱从被取走到被补回来"的时间，这是下界；上界是内存。两个数都要当场给得出来源。
  • 「fork 出来的沙箱安全吗？」——分场景。同一个用户的连续任务之间可以接受，不同用户之间不行，因为孩子进程之间只有普通的进程边界。

板块 5 · 自检问题

Q1 · 你把并发上限从 2 调到 8，吞吐一点没涨，P99 从 190 毫秒涨到 217 毫秒。有人说"那把它调回 2 就行了"。这个结论对不对？在什么情况下调大是对的？

结论在今天这个负载下对，但它不是一条普遍规则。

今天的用户代码是纯 CPU 的，两个核就是两份并行能力的上限，允许更多沙箱同时跑只会让它们互相切换。换成一个大部分时间在等网络的用户代码，情况完全反过来：一个沙箱在等回包的时候不占 CPU，这时候并发上限设成 2 就会让机器大量空闲。

所以正确的说法是：并发上限的上界是"这台机器上真正被这类任务占满的那种资源"的数量。任务是 CPU 密集的，上界就是核数；任务是等待密集的，上界要大得多，真正的约束会变成内存或者别的东西。这正是 Day 4 那对 CPU 密集与 IO 密集的区分，换了个场合再出现一次。

Q2 · 表 B 里，甲（提前 create）省下 32.2 毫秒，丙（预导入之后 fork）省下 83.9 毫秒。那么把两者叠起来，是不是能省 116 毫秒？

不能，而且这个问题本身有个陷阱：总共才 85.39 毫秒，省不出 116。

原因是这两条路砍的段有重叠。丙那条路里，容器是常驻的，所以"挂 overlay 加 runc create"这两段本来就已经不在请求路径上了——甲省的那 32.2 毫秒，丙已经顺带省了。丙那 1.47 毫秒里剩下的东西只有：写一次管道、fork 一次、执行、写回一次。

这类"能不能叠加"的问题，判断方法是回到表 A 那张分段表，看两条路各自划掉的是哪几行。划掉的行有交集，收益就不能相加。

Q3 · 你的预热池有 32 个沙箱，需要滚动更新镜像，于是要把它们全拆了重建。你估计"拆一个几毫秒，32 个不到一秒"。实际上会是多久？为什么？

大约三秒半，是估计的三倍多。

池里的沙箱停在 created 状态，而 runc delete 对这个状态走的不是直接销毁那条路。源码 delete.go 那个 switch 里，只有 Stopped 才走 Destroy()，Created 走的是 killContainer；而 killContainer 的循环体第一句就是睡 100 毫秒。所以每拆一个至少 107 毫秒，32 个就是 3.4 秒。

"几毫秒"那个估计来自表 A 里 runc delete 那一行，但那一行量的是已经退出的容器。同一条命令，容器状态不同，代价差近二十倍——这是今天最值得记住的一个反直觉点。

Q4 · 有人提议：既然宽限期对用户代码是白等，干脆超时直接发 SIGKILL，省下这 500 毫秒。这个提议哪里对、哪里不对？

对的部分：针对用户提交的代码，宽限期确实几乎不产生收益，缩到很小甚至零是合理的。

不对的部分是"直接"这个词把两个不同的进程混成了一个。如果你按 Day 13 的建议，在容器里放了一个自己写的 1 号进程（它装了信号处理、负责转发信号和收养孤儿），那么 SIGTERM 对它是有效的，它需要那一点时间把已经产生的输出刷出去、把退出码报上去。直接 SIGKILL 会让这些丢掉。

正确的形状是两层：外层给你自己那个 1 号进程一个很短的宽限期（几十毫秒量级，够它刷一次缓冲），内层由它自己决定要不要给用户代码宽限。用同一个数配置这两层，要么白等，要么丢数据。

板块 10 · 今日五句话

合上页面，用自己的话回答下面五个问题，每题一两句。

五句话
  1. 一次冷启动里最大的那一段是什么？它比第二大的那一段大多少？
  2. 预热池把沙箱停在哪个状态？为什么不能停在别的状态？
  3. 常驻容器加 runc exec，为什么比"提前 create 然后 start"还慢？
  4. 并发上限的下界和上界分别由什么决定？在今天这台机器上这两个数是多少？
  5. 同一条 runc delete，什么时候要 5 毫秒、什么时候要 107 毫秒？

逐句自查

  • 第 1 句如果写成"runc create"就错了。分段表里 create 是 25.65 毫秒，导入库是 31.89 毫秒，后者更大。这一句要答对的关键是记住"解释器和它的库"整体（14.28 加 31.89 共 46.17 毫秒）才是真正的大头，而它和容器完全没关系。
  • 第 2 句如果只写了"created"而说不出理由，只算答对一半。理由必须包含两头：running 意味着 execve 已经发生、跑什么已经定死；还没 create 意味着什么都没提前做。
  • 第 3 句如果写成"exec 要多走一层网络/多一次进程通信"就错了，两条路都不走网络。正确的答案是 exec 要现拉起 runc 二进制、现建一个新进程去加入命名空间并重装一遍 cgroup、能力、过滤器；而 start 面对的进程这些活儿在 create 的时候就干完了。
  • 第 4 句如果只答了"等于核数"就漏了一半。下界是到达率乘服务时间（今天是 35 × 0.034 ≈ 1.2），低于它队伍发散；上界才是核数 2。两个数缺一不可，而且换成等待密集的任务，上界会完全不同。
  • 第 5 句如果答成"加了 -f 就慢"就漏了第三行。-f 是其中一条路，容器状态是 Created 是另一条；只有"Stopped 且不带 -f"这一种组合才是 5 毫秒。
