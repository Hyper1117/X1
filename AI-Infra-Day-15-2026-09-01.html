第 1 题 · 来自 Day 14

你的预热池里停着 32 个沙箱，状态都是 created。现在要换镜像，把它们全部拆掉重建。你按分段表里 runc delete 那一行的 5 毫秒估算，认为 32 个一秒之内搞定。实际会是多久？为什么？

看答案

三秒半左右，是你估计的二十倍。

分段表里那 5 毫秒量的是已经退出（Stopped）的容器。同一条命令，容器状态不同，代价差近二十倍：Stopped 那一档中位 5.76 毫秒，其余三档全部落在 107 毫秒上。

机制在 runc 的 delete.go 里：只有「Stopped 且不带 -f」才直接走销毁；Created 状态走的是杀进程那条路，而那个循环体的第一句就是睡 100 毫秒，第二句才去看进程还在不在。哪怕进程一微秒就没了，也得睡满第一个 100 毫秒。

识别信号也值得记住：那一档四种情况的最小值和最大值只差不到 3 毫秒。贵得这么整齐，通常说明底下压着一个固定的等待，而不是真有活要干。

接今天：今天也有一笔钱是「提前占住资源，换请求路径上不花时间」。区别是昨天占住的是几十毫秒和几 MiB，今天占住的是几十 GB，而且占住之后立刻会碰到一个新问题——怎么分。

第 2 题 · 来自 Day 12

容器往下层一个 12 MB 的文件里改了 1 个字节，上层目录多出多少字节？如果它只是把这个文件从头读到尾呢？另外：那次实测里上层实占 12322396 字节，而 tmpfs 报的已用是 12324864，差的 2468 字节是什么？

看答案

改 1 个字节，上层多出 12322396 字节——整个文件的完整副本。机制是写时复制：内核在写之前先把这个文件从下层整份搬到上层，副本多大只跟原文件多大有关，跟你改了几个字节没关系。

只读不写，上层是 0 字节。这正是同一份下层能被大量容器共用、互不影响的原因。

那 2468 字节：文件系统按整页分配，一页 4096 字节。12324864 除以 4096 正好是 3009，而 12322396 除以 4096 是 3008.4——3008 页装不下，只能给 3009 页，最后那一页有 2468 字节是空着的。

接今天：这最后一页空着的部分今天有名字，而且它会从 2468 字节放大到几十 GB 里的一大块。今天整页都在处理它和它的孪生兄弟。

第 3 题 · 来自 Day 8

那张引擎步统计表里，发压速率从每秒 0.5 条加到 3.0 条，prefill 步的耗时中位数一直卡在 83 毫秒左右纹丝不动，decode 步却从 31.7 涨到 101.6 毫秒。两种步用的是同一份权重、同一个函数。为什么一个不动、一个涨三倍？

看答案

因为一次前向的成本主要是「把 512 MiB 权重完整读一遍」，这一步顺带算了几列，对总时间影响不大。

prefill 恒定不是因为 prompt 短，是因为同时到达的几条请求的 prompt 会被拼进同一次矩阵乘法。列数从 8 变成 24，对一次要读 512 MiB 的乘法来说几乎不额外收费。

decode 会涨，是因为同时在生成的请求数从 1 涨到 9，列数确实多了。Day 8 那张单次前向表里，一列到八列的总耗时本来就要涨两倍多，量级对得上。

于是那两个指标涨的是两样不同的东西：首 token 延迟涨的八点九倍全是排队，每输出 token 耗时涨的两倍多全是批量。

接今天：那一页的装置里明确写着「注意力和 KV cache 完全没有，所以今天所有绝对时间都是下限」。今天把这一项补上——你会看到在长上下文、大批量下，它不是小数点后的修正，它能超过权重那一项。

板块 2 · 核心讲解

第一部分 · 这几十 GB 到底是什么

1. 模型每吐一个字，真的要把前面说过的话重读一遍吗

如果生成第 501 个字要用到前面 500 个字的中间结果，那这些中间结果是每次现算，还是存着？

Day 8 留了一句没展开的话：生成第 t+1 个 token 要用到前面 t 个 token 的中间结果。今天先把「中间结果」这四个字换成具体的东西。

模型每读进一个 token，会给它算出两样东西。一样是「我是什么」，供后面的 token 拿来匹配；另一样是「匹配上了之后你能从我这里拿走什么」。你可以先当成图书馆卡片：一张卡片上有书名（用来找），也有书的内容摘要（找到之后要读的）。

生成下一个 token 的时候，模型拿当前这个 token 的一个向量，去跟前面每一个 token 的「书名」比一遍，比出一组权重，再按这组权重把前面每一个 token 的「摘要」加权加起来。这就是它「回头看」的全部动作。类比到此为止，机制的细节今天不需要，你只要接受一件事：这个动作需要前面每一个 token 的那两样东西，一个都不能少。

这两样东西模型不会凭空知道，是把 token 过一遍网络算出来的。所以只有两条路。

一条是每一步都现算：生成第 t+1 个 token 时，把前面 t 个 token 重新过一遍网络，把它们的那两样东西再算一次，用完扔掉。另一条是第一次算出来就留着，后面每一步只算新来的那一个。

先不看时间，只数次数。第一条路生成 T 个 token，要算的 token 次数是 1 + 2 + … + T，也就是 T×(T+1)/2 次；第二条路是 T 次。T 取 500，两个数是 125250 和 500，相差 250 倍。

把这两样东西存下来、后面每一步直接取用，这个做法就叫 KV cache（键值缓存）。那两样东西分别叫 键（key） 和 值（value），名字就是从这儿来的——「书名」是键，「摘要」是值。

今天整页处理的都是它。而它带来的第一个问题，从名字里就能看出来：缓存要占地方。

2. 今天的实验台

今天没有服务、没有压测器，也没有 GPU。六个互不通信的小程序，各自量一件事。先把它们摆出来，后面每张表都能对回到其中一个。

2.1 一次测量里到底有什么

P2 那个分配器里，一条「请求」就是三个整数，没有文字、没有分词器：

意思是：这条请求进来时已经有 231 个 token 要一次算完，之后要一个一个生成 88 个。分配器只关心这两个长度，因为内存占用只跟长度有关，跟内容无关。跑一次就是一条命令：

3. 存下来到底省了多少

上一节数的是次数，250 倍。次数不等于时间——Day 7 和 Day 8 都反复撞到同一件事：一次前向的成本主要由「把权重完整读一遍」决定，多喂几列几乎不额外收费。所以省下来的时间会比省下来的次数少。少多少，跑一次就知道。

关键结论

KV cache 不是让计算变快的技巧，它是一笔交换：把「每一步重算前面所有 token」换成「一直占着内存」。今天剩下的四分之三，全都在处理这笔交换的另一头。

4. 一个 token 值多少字节

现在逐项算。一条序列里的每一个 token，在每一层里都留下一个键和一个值。

一个键有多大？它是按「头」分开存的。模型把 hidden 那 4096 维切成若干个头各自算，本页的设定是 32 个 查询头（query head），每个头 每头维度（head_dim） 是 128 维。但键和值不必跟查询头一样多：让几个查询头共用一份键值，能直接把这块内存除以那个倍数，这个做法叫 分组查询注意力（GQA, grouped-query attention）。本页设的是 8 个 键值头（KV head），也就是四个查询头共用一份。

于是一层里、一个 token 的键，占的是「键值头个数 × 每头维度 × 每个数几个字节」。值一样大。再乘层数，就是这个 token 的全部：

每 token 字节数 = 2 × 层数 × 键值头个数 × 每头维度 × 每个数的字节数
              = 2 ×  8  ×      8      ×    128    ×      4
              = 65536 字节 = 64 KiB

开头那个 2 是键和值各一份。代进本页的设定，一个 token 是 64 KiB。顺带留意中间那一步：一层里一个 token 的键正好是 4096 字节，和 Day 7 那个操作系统内存页一样大。这是巧合，别把两种「页」当成一回事——第二部分会专门说清楚它们的关系。

第二部分 · 放不下的，从来不是内存

5. 一条请求刚进来，你怎么知道该给它留多少

这条请求最后会长到多长？在它跑完之前，谁也不知道。

你是后端工程师，手上有一个 512 MiB 的池子，请求一条一条进来。最自然的写法是：请求进来时算出它最多可能要多少，一次性划一块连续的空间给它，跑完再还回来。

「最多可能要多少」是一个已知量，就是上下文长度上限，本页设的是 2048 个 token。所以每条请求进来就占住 2048 × 64 KiB = 128 MiB。

这个写法在别的地方是对的。给一个固定大小的缓冲区、给一个已知长度的数组，一次划够是最省事也最快的做法。但这里有个前提不成立：你不知道这条请求最后会长到多长。这不是实现问题，是任务本身的性质——模型什么时候停下来，要等它真的吐出停止符才知道。Day 9 的自检题里已经出现过这句话，当时用它解释「为什么只做准入控制不够、必须有抢占」。今天它换了个身份，变成内存浪费的来源。

回到 2.3 节那条轨迹。那条请求最后只长到 140 个 token，可它一进来就占住了 2048 个位子。占住 2048、用掉 140，利用率 6.8%。剩下 93.2% 的内存被划走了，谁也不能用，但里面什么都没有。这一条特别短，整批 120 条请求平均下来是多少，第 8 节会给。

这种「已经划给某个人、但他实际没用上」的浪费，叫 内部碎片（internal fragmentation）。「内部」的意思是浪费发生在已分配的那一块里面。Day 12 那 2468 字节就是它最小的一个样本：文件系统按整页分配，最后一页只用了一小截，剩下的空着但已经算你头上了。今天这个数从 2468 字节放大到 120 MiB。

整块预留这个做法，浪费的比例不取决于你的代码写得好不好，只取决于「请求实际长度」和「长度上限」这两个数差多远。而这两个数天然差得很远：上限要按最长的那条设，实际长度大部分请求都短得多。

6. 那就别一次划够，让它慢慢长

下一个自然的改法：进来时只按 prompt 长度划一小块，不够了再往后要一截。这正是动态数组的做法，你写过很多次。

问题是「往后要一截」这个动作有个隐含条件：紧挨着你这块的后面得是空的。而在你后面很可能已经坐了别人。这时只有两条路：搬家，把整段复制到别处一块够大的空地上；或者搬不动，就得把某条请求整个踢下去腾地方。把已分配的东西挪到一起、腾出大片连续空间的动作叫 紧凑（compaction），它不便宜——搬一条 2048 token 的序列，是 128 MiB 的复制。

更麻烦的是另一种情况：池子里明明还剩很多空闲字节，但它们碎成了几十个小段，每一段都不够装下一条请求要的那么长。总量够，连续的段不够。

这种「空闲的总量足够、但没有一段连续的空间够大」的浪费，叫 外部碎片（external fragmentation）。「外部」的意思是浪费发生在已分配的块之间。

这两种碎片是一对：你为了消灭内部碎片而按需分配，就会制造外部碎片；你为了消灭外部碎片而一次划够，就会制造内部碎片。第 8 节把这一对放在同一批请求上跑一遍，看代价各是多少。

7. 这道题操作系统在七十年前解过一次

Day 7 讲过页表和地址翻译缓存，讲过大页省的是翻译的钱。但那一天从「内存是按块管理的」直接开始，跳过了一个问题：为什么要按块管理？

答案就是上面这两种碎片。早期的系统给进程分配的是一整段连续的物理内存，于是进程反复启动和退出之后，物理内存被切得七零八落，明明还剩几百兆，却没有一段连续的够装下一个新进程。分页的做法是：把地址空间切成固定大小的块（x86 上是 4096 字节），进程要几块给几块，这些块在物理内存里爱在哪就在哪，不要求连着；进程看到的连续，是页表翻译出来的假象。

代价是多了一层间接：每次访问都要先查一次表，才知道这一页真正在哪。Day 7 的地址翻译缓存就是为了让这一层查表尽量便宜。

把这套办法照搬到 KV cache 上，就是今天的主角。内存池切成固定大小的 块（block），每一块装固定个数 token 的键和值；一条序列要多少块给多少块，块之间不要求连续；每条序列配一张 块表（block table），记着它的第几块在池子里的哪个位置。计算的时候按块表去取。这个做法叫 分页注意力（PagedAttention）。

vLLM 里这几件事都能在源码里指着看。一块装几个 token 是个常量，默认 16：

# vllm/config/cache.py:79
DEFAULT_BLOCK_SIZE: ClassVar[int] = 16

一块占多少字节，是第 4 节那个公式去掉层数、加上块大小的样子。num_heads 就是键值头个数（第 405 行），num_states 在最常见的情况下就是块大小（第 180 行）：

# vllm/v1/kv_cache_interface.py:412
return (self.head_size + self.head_size_v) * get_dtype_size(self.dtype)

# vllm/v1/kv_cache_interface.py:415-416
def unpadded_page_size_bytes(self) -> int:
    return self.num_heads * self.num_states * self.state_content_size_bytes

把这两行连起来读：一块的字节数 = 键值头个数 × 块大小 × (键的维度 + 值的维度) × 每个数的字节数。这和你在第 4 节手算的那一行是同一个式子，只是把「每 token」换成了「每块」，并且把键和值写成了相加而不是乘 2。

而「这台机器能开多少块」，就是一道除法，源码里也是一行：

# vllm/v1/core/kv_cache_utils.py:1440
num_blocks = available_memory // bytes_per_block

分子那个「可用内存」是怎么来的，是第 14 节的旋钮。分母你现在会算了。

最后说清楚两种「页」的区别，免得后面混。操作系统的页是硬件的事：页表由内核填，翻译由 CPU 里的专门电路做，一页固定 4096 字节。KV cache 的块是纯软件的事：块表就是一个普通数组，取块由代码自己做，一块装多少个 token 由你配。两者只是借用了同一个想法，没有任何机制上的关系。第 4 节那个「一层一个 token 的键正好 4096 字节」纯属数字上的巧合。

vLLM 的设计文档里给出了这些块在内存里的排布方式，K 和 V 是两个独立的张量：

# docs/design/paged_attention.md
const scalar_t* __restrict__ k_cache,   // [num_blocks, num_kv_heads, head_size/x, block_size, x]
const scalar_t* __restrict__ v_cache,   // [num_blocks, num_kv_heads, head_size, block_size]

最外面那一维是块号——池子就是一个大数组，块表里存的就是这一维的下标。这也说明第 3 部分要量的东西是什么：按块号跳着取，比顺着取要贵多少。

关键结论

推理服务喊「内存不够」的时候，缺的经常不是字节，是连续的字节。

分块把「连续」这个要求去掉，代价是多一层间接寻址和每条序列最后一块的零头。这两笔代价具体多大，就是下一部分要称的东西。

为什么和 Day 7 那个二十六倍差这么多？因为跳的粒度完全不同。Day 7 每次只跳去读 64 字节的一个缓存行，跳一次只赚 64 字节，全靠地址翻译和预取器；这里每跳一次要连着读 64 KiB，等于一千个缓存行连着走，硬件预取器有的是时间跟上，那一次跳的成本被摊到一千次读里。块表之所以便宜，不是因为间接寻址便宜，是因为块本来就够大。

11. 那块大小到底该定多少

读那一侧从 4 KiB 往上就是平的，等于没有约束。所以块大小的取值由另外两笔钱决定，一头拉一个方向。

第四部分 · 装不下的时候，搬走还是重算

12. 现在这两条路可以放到同一杆秤上

Day 9 讲过抢占：内存不够时把一条正在跑的请求拉下来，vLLM 拉的是最新到达的那条。当时留了一句「被拉下来之后有两条路——把它的 KV 扔掉、回来重算，或者搬到 CPU 内存里存着、回来再搬回去；这两条路的取舍要等把内存账算清楚才谈得下去」。现在算清楚了。

两条路各自要付的东西，形状完全不同。搬走付的是字节：一条上下文 S 个 token 的序列，KV 是 S × 每 token 字节数，出去一趟回来一趟，要搬两遍。重算付的是运算：把这条序列的 prompt 重新做一次 prefill。

短序列那几行比 196 高一些，原因也在式子里：那个式子把重算写成「运算量 ÷ 算力」，前提是 prefill 已经落到算力那一边。S 只有 128 的时候它还没完全落进去，这台机器在那个形状上只跑到 86 GFLOP/s，到 S 等于 2048 时是 119。也就是说短序列的重算单位成本更高，于是搬显得更划算。这是 Day 7 那条屋顶线在今天最后一次露面。

式子右边四项，两项是机器的属性（算力、搬运速率），两项是模型的属性（每 token 的 KV 字节数、参数量）。没有一项跟负载有关。所以这是一个可以在部署之前一次算清楚的问题，不需要压测。

但这台机器上的 0.0051 不能搬到 GPU 上去。GPU 的算力比这里的 CPU 高三四个数量级，而「搬运速率」在那边是 PCIe 而不是内存条。式子不变，两个分子分母的数全变了。vLLM 的文档里写着它的选择：

# docs/configuration/optimization.md
In vLLM V1, the default preemption mode is `RECOMPUTE` rather than `SWAP`,
as recomputation has lower overhead in the V1 architecture.

拿你手上那张卡的算力和 PCIe 速率代进去，是今天加分题里的一道。

13. 一步 decode 到底要读多少字节

还有一笔账，是 Day 8 欠下的。那天的装置表里写着「注意力和 KV cache 完全没有，所以今天所有绝对时间都是下限，真服务只会更慢」。慢多少，现在能算了。

一步 decode 要读两样东西。权重是所有请求共用的，读一遍，这一项是常数，本页骨架是 512 MiB。KV 是每条请求各自的，每条要把自己全部上下文读一遍，这一项等于「批量 × 上下文长度 × 每 token 字节数」。

板块 4 · 工作现场

场景一：并发上不去，抢占计数一直在涨

监控上同时在跑的序列数一直卡在个位数，队列里却排着人，抢占计数每分钟涨几十。有人提议加机器。

先分清是哪一种「不够」。算一次账：可用内存除以每 token 字节数，等于能装多少 token；再除以当前的平均上下文长度，等于理论上能同时跑几条。如果这个数远大于实际并发，那内存是够的，问题在别处——先查 max_num_seqs 是不是设小了，再查 block_size 是不是被调大过。如果这个数本来就等于实际并发，那是真的不够，加机器或者提高 gpu_memory_utilization 才有意义。

另外记住那个 43 倍：抢占真正的代价不是抢占次数，是被抢占的请求白算掉的 token 数。这两个数差着两个数量级，报给上游看的应该是后者。

场景二：产品问「这台机器能同时服务多少人」

这个问题没有唯一答案，但有唯一的算法。你要问回去的是两个数：平均上下文多长，以及并发的定义是「同时连着」还是「同时在生成」。

然后把链条走一遍：显存总量 → 减去权重 → 乘以给 KV 的比例 → 除以每 token 字节数 → 除以平均上下文长度。每一步都写下来，因为产品下次会问「那我们把上下文从 8K 提到 32K 呢」，那时你只要改一个数。

顺便准备好一句话解释为什么答案不是一个固定数字：同样一台机器，用户平均聊两轮和平均聊二十轮，答案差一个数量级。

场景三：评审会上要把上下文上限从 4K 提到 32K

这是一个几乎每个做推理服务的团队都会开的会。你要在会上说清楚代价，而且代价不止一条。

第一条是容量：每条请求的内存上限乘以八，同一台机器能同时服务的人数除以八。第二条是速度，也就是第 13 节那张表：上下文长了之后，一步 decode 里 KV 那一项会超过权重，批量再怎么凑也摊不薄它。第三条是抢占：上下文一长，装不下的概率上升，而被踢掉的请求要白算的东西也更多。

能减轻的办法也有：把上下文上限和「保证的并发数」绑在一起对外承诺；给长上下文单独一组机器，别和短请求混在一起抢同一个池子。后面这一条属于 Day 26 的题目。

同事和面试官常问的

「PagedAttention 到底解决了什么问题？」只答「减少内存碎片」是复读文档。要说清楚是哪一种碎片：整块预留造成的是内部碎片，按需连续增长造成的是外部碎片，分页把「连续」这个要求去掉，两种一起解决。而且要能说出代价在哪——多一层间接寻址，以及每条序列最后一块的零头。

「block_size 该设多大？」只答「用默认值」不算错但没内容。往大了开省簿记、省块表宽度，但每条序列平均浪费半块；往小了开省内存，但块对象和取块动作成倍增加。两边各有一段平台，默认值落在交界处。补一句：读的那一侧几乎不构成约束，因为一块的字节数早就远大于一个缓存行。

「被抢占的请求，为什么不换出去而要重算？」先给式子：搬运时间比重算时间等于「每 token 的 KV 字节数 × 算力」比「参数量 × 搬运速率」，跟序列多长无关。再说这个比值在 GPU 上和在 CPU 上是两个方向，因为分子里的算力和分母里的搬运速率在两种硬件上差得完全不成比例。最后才提 vLLM V1 的默认值是重算。

「我们的服务内存够，为什么还老抢占？」这是场景一那道题的面试版。够不够要看的不是剩余字节数，是「有没有一段合适的空间」以及「峰值时刻的并发乘以平均上下文」。还要问一句抢占发生在什么时段——如果集中在某几分钟，那多半是长请求扎堆而不是容量不足。

板块 5 · 自检问题

1. 有人把 KV cache 的数据类型从 float16 换成 float32，说「精度高一点更稳」。除了内存翻倍，还有什么后果？

一步 decode 要读的字节数里，KV 那一项翻倍。第 13 节那张表说明这一项在大批量长上下文下能占到八九成，所以这个改动接近于把 decode 的时间翻倍。

还有第二重后果：能装的 token 数减半，于是同样的负载下抢占次数上升，而每次抢占又要白算一整个 prompt。第 8 节那张表里，利用率从 98.4% 掉到 78.8% 时抢占次数涨了二十六倍——不是线性关系，是接近临界点之后的加速。

错在哪：把「内存翻倍」当成唯一代价。内存这条线上的每一个改动，都会同时出现在容量、速度和抢占三个地方。

2. 一个同事说：「块表要跳着取内存，所以 PagedAttention 一定比连续存放慢，只是慢得值。」这句话对吗？

结论方向对，量级完全不对，而且原因说反了。

跳着取确实比顺着取慢，但慢多少取决于每次跳完之后连着读多少字节。第 10 节的对照里，一段 64 字节时多花 3.6 毫秒，一段 64 KiB 时差值是负零点零零九——落在噪声里。而真实的块大小对应的正是几十 KiB 这个量级。

所以正确的说法是：这一层间接在真实的块大小上量不出来，不是「慢得值」，是「几乎不慢」。原因不是间接寻址本身便宜，是块本来就够大，一次跳的成本被摊到上千个缓存行上。

顺带一提，如果他拿「随机撒开」和「numpy 整段拷贝」去比，会得出块表贵一倍多的结论——那是两个不同函数的开销差，不是内存的差。

3. 服务上线后你发现，同样的负载，白天抢占次数是夜里的十倍。但两个时段的请求数几乎一样。可能是什么原因？你会先看哪个数？

请求数一样不代表内存压力一样。内存占用取决于「并发 × 上下文长度」，而不是请求数。

最可能的原因是白天的对话轮次更多、上下文更长。先看的应该是上下文长度的分布，尤其是高百分位——平均值会把这件事平均掉。一条 8K 的请求顶得上十六条 512 的。

第二个要看的是并发的时间分布：如果白天请求扎堆在几个尖峰上，瞬时并发会远高于按平均算出来的数，而抢占是由瞬时决定的。这一点 Day 2 那个排队公式已经给过形状——利用率靠近 1 的时候，一点点波动会被放大很多倍。

错在哪：拿请求数当内存压力的代理。它们之间隔着两个乘数。

4. 你把 block_size 从 16 改成 1，理由是「利用率能到 100%」。这个改动在什么情况下真的划算，什么情况下会翻车？

利用率确实会到 100%，第 11 节那张表的第一行就是。省下来的是「每条序列平均半块」，块大小 16 时这是 8 个 token。

代价在另外两列。块的个数变成 16 倍，本页那个分配器的耗时从 10.9 毫秒涨到 27.7 毫秒；块表从每条 128 个条目变成 2048 个。前者是 CPU 上的开销，会直接吃掉调度线程的时间；后者会让每一步要传给计算那一侧的索引表变大十六倍。

什么时候划算：序列极短、条数极多，浪费的那半块占比很大的场景。什么时候翻车：序列长、并发高，此时省下的那点零头微不足道，而多出来的簿记开销落在每一步上。

还有一件事明天会变得重要：块同时也是跨请求前缀复用的匹配单位，块越小，能对上的粒度越细，要做的匹配判断也越多。这一笔在本页的分配器里根本不存在，因为今天每条序列各存各的。

合上这一页，用自己的话回答

1. 一条 2048 个 token 的请求，它的 KV cache 占多少字节？把式子里每一项是什么说清楚。

2. 「整块预留」和「按需连续增长」各自浪费在哪里？这两种浪费为什么不能同时消灭？

3. 块表带来的间接寻址，在真实的块大小上要多花多少时间？为什么是这个量级？

4. 决定「被踢掉的请求该搬走还是重算」的是哪四个量？为什么序列多长不在其中？

5. 一步 decode 要读的字节里，哪一项是所有请求分摊的、哪一项不是？这对批量该开多大意味着什么？

逐句自查标准

  • 第 1 句如果只写出一个数字，等于没答。要点在那个式子有五项，而且能说出为什么开头有个 2（键和值各一份），以及为什么是键值头个数而不是查询头个数。
  • 第 2 句如果写成「一个浪费多一个浪费少」，太笼统。正确的说法是它们是同一个约束的两面：只要坚持「一条序列的内存必须连续」，你就只能在划太多和找不到连续空间之间选一个。分页把这个约束本身去掉了。
  • 第 3 句如果写成「跳着取当然更慢」，只答对了方向。今天的测量是：一段 64 KiB 时差值落在噪声里。原因必须说到「一次跳完之后连着读多少字节」，只说「块表有开销」不算。
  • 第 4 句如果漏掉「算力」或「搬运速率」中的任何一个，这个式子就不成立了——它恰恰是靠这两个机器属性的比值翻方向的。至于为什么没有序列长度：两边都正比于它，相除时约掉了。
  • 第 5 句如果只写「权重是常数」，只说了一半。关键在后半句：每多凑一个用户就多一份 KV 要读，凑人能摊薄权重、摊不薄 KV，所以长上下文下批量的收益会自己封顶。

板块 11 · 明日预告

今天从头到尾有一个假设没被质疑过：每条序列的 KV 是它自己的，跟别人无关。所以三种分配方式比的都是「怎么给一个人分地方」。
